# Эксперимент: Web Push → нативный GChat

Пользователь согласовал минимальный технический эксперимент 2026-11-07: проверить запуск нативного приложения после нажатия веб-пуша, без APNs-ключей, с кнопкой перехода при блокировке автоматического открытия. Это согласование только эксперимента; [D008](../../docs/architecture/decisions/D008-capacitor-bridge.md) остаётся draft.

## Поведение и границы

- Эксперимент включается только отдельной Web-сборкой с `VITE_GCHAT_IOS_LAUNCH_SPIKE=true`. Обычная сборка сохраняет существующую обработку уведомлений.
- В экспериментальной сборке нажатие уведомления о звонке открывает страницу `/calls?native_launch_spike=1` (в серверном размещении — с префиксом `/apps/client`). Уведомления диалогов сохраняют свой переход.
- Для локальной тестовой PWA обработчик нажатия сначала сохраняет в отдельном CacheStorage одноразовую отметку времени без payload звонка. Если iOS открывает стартовый экран вместо запрошенной страницы, тестовый экран считывает и удаляет отметку при запуске/возвращении и переходит на фиксированную страницу запуска native. Отметка действительна 30 секунд; без неё открытие тестовой PWA не запускает native. После `openWindow` worker также посылает фиксированный сигнал открывшейся странице; тестовый экран принимает его только от своего service worker и всё равно проверяет сохранённую отметку. Ошибка CacheStorage не мешает исходной попытке `openWindow`. Это восстановление не доказывает, что iOS всегда вызывает `notificationclick`.
- Страница один раз пытается открыть фиксированную ссылку `gchat-launch-spike://open`; кнопка «Открыть GChat» повторяет переход по явному действию пользователя. Кнопка «Остаться в Web» возвращает обычный клиент. Результат открытия не выводится из таймера или события visibility: его подтверждает только нативный экран.
- Debug-приложение регистрирует тестовую URL-схему и показывает подтверждение получения точной ссылки при холодном и повторном запуске. Release не обрабатывает экспериментальную команду. Ссылка не передаёт сервер, сессию, токены или идентификатор звонка и не выполняет авторизацию, смену сервера или принятие вызова.
- Доставка использует существующие PWA-подписку, Web Push и backend. Нужны установленная на домашний экран PWA на iOS 16.4+, разрешение уведомлений, сеть и HTTPS-стенд. APNs credentials, Universal Links и изменения backend не входят в эксперимент.
- По последующему поручению пользователя локальный вариант эксперимента использует отдельную тестовую PWA на Mac: локальное уведомление через `showNotification` и настоящий Web Push с задержкой 10 секунд. Используется тот же собранный экспериментальный service worker и та же страница перехода. Backend GChat, рабочие аккаунты и существующие подписки не нужны. Тестовый HTTPS-сервер хранит единственную подписку и отдельную временную VAPID-пару только в памяти, отправляет только фиксированное тестовое уведомление на разрешённый Apple endpoint и очищает состояние при остановке. Это не меняет правило стабильной VAPID-пары рабочих окружений.
- Эксперимент не реализует WebRTC и не доказывает доставку native-входящего, работу звонка в фоне или возможность ответить после истечения серверного срока. Переход не переносит браузерную сессию в native.

## Критерии приёмки

На физическом iPhone проверить настоящий Web Push при закрытой PWA и на заблокированном экране. После нажатия записать: открылась ли PWA, запустился ли GChat автоматически, потребовалась ли кнопка или системное подтверждение, появилось ли нативное подтверждение. Повторить с незапущенным и уже запущенным GChat; отдельно проверить отсутствие установленного приложения и переход «Остаться в Web». Не считать локальное уведомление или Simulator проверкой настоящей доставки.

Успешная сборка, тесты worker и открытие схемы из Simulator подтверждают только свои участки цепочки. Гарантия одного нажатия определяется результатом физической проверки, а не наличием обработчика URL.

## Запуск

### Локальная проверка

Собрать экспериментальную серверную Web-сборку командой ниже, затем запустить `node applications/ios/experiments/web-push-launch/server.mjs`. Сервер требует `GCHAT_SPIKE_HOST` (LAN IPv4 Mac), `GCHAT_SPIKE_CERT_FILE` (серверный сертификат), `GCHAT_SPIKE_KEY_FILE` (его приватный ключ) и `GCHAT_SPIKE_CA_CERT_FILE` (корневой сертификат), слушает только выбранный LAN-адрес: HTTPS на порту 8444 и выдачу единственного публичного корневого сертификата по HTTP на 8445 (`/gchat-launch-test.cer`). Приватные ключи остаются на Mac.

Корень используется только как CA, сервер получает отдельный подписанный им сертификат: RSA 2048+ / SHA-256+, `basicConstraints=critical,CA:FALSE`, `keyUsage=digitalSignature,keyEncipherment`, `extendedKeyUsage=serverAuth` и LAN-адрес в SAN. Сервер проверяет назначение, IP, подпись CA и сроки перед запуском. Нельзя использовать корневой сертификат вместо серверного: исходный тестовый корень не содержит обязательного серверного EKU. Требования — в [документации Apple](https://support.apple.com/en-ie/103769). iPhone должен доверять корню. Обход TLS-проверки не допускается. При необходимости пользователь самостоятельно устанавливает свой тестовый корневой сертификат и включает доверие по [инструкции Apple](https://support.apple.com/ru-ru/102390).

Открыть напечатанный HTTPS-адрес на iPhone, добавить страницу на экран «Домой» и запустить оттуда. Разрешение уведомлений запрашивается кнопкой. «Показать уведомление» проверяет отображение и `notificationclick`, но не сетевую доставку. «Отправить Web Push через 10 секунд» создаёт отдельную тестовую подписку и планирует одну реальную отправку: до доставки можно свернуть PWA или заблокировать экран. Ответ push-провайдера не подтверждает доставку на iPhone. Подписка не выводится в интерфейс или логи. Установка тестовой PWA не меняет PWA `gcall.online`; после проверки сервер останавливается и тестовую PWA можно удалить.

При отказе тестовая страница показывает этап и безопасное имя ошибки, без исходного сообщения исключения. Регистрация worker имеет ограниченное время ожидания; статус меняется до начала асинхронной операции. Диагностика не содержит endpoint подписки, ключей или данных аккаунта.

Для проверки обработки нажатия локальный сервер дописывает к выдаваемому worker независимые наблюдатели `install`, `activate`, `push` и `notificationclick`. Они отправляют только имя события на тот же LAN-origin; сервер хранит ограниченный список отметок времени в памяти и возвращает его в `/spike/status`. Тестовая страница аналогично сообщает `page-ready`, `page-visible` и `intent-found`. События не содержат payload, URL клиента или подписки. Наблюдатели не меняют алгоритм навигации, не активируют worker самостоятельно и не попадают в обычную сборку.

После изменения экспериментального worker нажать «Обновить тест»: кнопка дожидается установки новой версии и явно активирует её штатной командой GCHAT_ACTIVATE, затем перезагружает только тестовую страницу. Локальный fixture не обслуживает реальные звонки; обычная PWA сохраняет принятый механизм защищённого обновления.

```sh
GCHAT_SPIKE_HOST="${GCHAT_IOS_LAN_IP:?Set Mac LAN IPv4}" \
GCHAT_SPIKE_CERT_FILE="${GCHAT_IOS_TLS_CERT:?Set PEM certificate path}" \
GCHAT_SPIKE_KEY_FILE="${GCHAT_IOS_TLS_KEY:?Set PEM private key path}" \
GCHAT_SPIKE_CA_CERT_FILE="${GCHAT_IOS_TLS_CA:?Set PEM root certificate path}" \
node applications/ios/experiments/web-push-launch/server.mjs
```

### Проверка с backend GChat

Из корня репозитория:

```sh
VITE_GCHAT_IOS_LAUNCH_SPIKE=true pnpm --filter @gchat/web build:server
```

Разместить сборку на отдельном HTTPS-стенде по [инструкции Web](../web/README.md#сборка-для-серверного-web). После обновления PWA убедиться, что новый worker активирован штатной кнопкой обновления. Выполнить вход и включить Web Push в PWA; для настоящего уведомления позвонить этому пользователю из другого тестового аккаунта. Сначала отдельно проверить страницу `/apps/client/calls?native_launch_spike=1` и кнопку открытия.

Debug-сборка и установка на телефон — по [README iOS](README.md#установка-на-физический-iphone). При Personal Team без Push Notifications entitlement создать отдельный пустой plist и передать его в `CODE_SIGN_ENTITLEMENTS`: эксперимент не использует нативные уведомления. Пустое значение build setting недостаточно: Xcode может продолжить требовать Push Notifications. Не менять Team или bundle identifier в репозитории.

```sh
plutil -create xml1 /tmp/gchat-launch-spike-no-push.entitlements
# К xcodebuild из README добавить:
# CODE_SIGN_ENTITLEMENTS=/tmp/gchat-launch-spike-no-push.entitlements
```

## Результаты

Проверка 2026-11-07:

- Debug-сборка с пустым entitlements plist успешно подписана Personal Team и установлена поверх существующего тестового приложения на физическом iPhone 14.
- Холодный запуск через `devicectl --payload-url gchat-launch-spike://open` выполнен; пользователь подтвердил зелёное сообщение «Ссылка получена: холодный запуск». Это проверка доставки URL в native, а не перехода из уведомления или Safari.
- В Safari на Mac проверены отображение страницы и переход «Остаться в Web» к обычному клиенту. При отсутствии обработчика схемы Safari показывает системное сообщение о недействительном адресе; после закрытия сообщения запасная кнопка остаётся доступна. Это не проверка поведения iPhone.
- Обычная Web-сборка, экспериментальная серверная сборка, проверки TypeScript, Web lint, тесты worker и документация проходят. В iOS-сборке остаётся существующее предупреждение Sendable в GChatPlugin; в Web-сборке — предупреждение размера bundle.
- Экспериментальная Web-сборка не опубликована на `gcall.online`; локальная тестовая PWA запущена на LAN Mac. Через HTTPS с проверкой сертификата подтверждены выдача страницы, manifest, service worker с включённым экспериментом и страницы перехода; запросы с чужим Origin и endpoint вне Apple отклоняются. Публичный корневой сертификат скачивается отдельно от приватного ключа.
- Пользователь установил тестовую PWA и включил доверие корню. Начальный сертификат сервера совпадал с CA и не содержал serverAuth EKU; это исправлено отдельным серверным сертификатом с тем же установленным корнем, IP SAN и serverAuth. Цепочка проверена OpenSSL и `security verify-cert` с SSL-политикой Apple и явным корнем.
- После включения доверия провайдер принял настоящую тестовую отправку (HTTP 201); пользователь сообщил, что уведомление открывает стартовый экран тестовой PWA. Явная ссылка «Открыть GChat без уведомления» запускает native по подтверждению пользователя.
- После обновления теста локальное уведомление прошло обработчик `notificationclick`: сервер записал последовательность `install`, `activate`, `page-ready`, `notificationclick`. Затем пользователь подтвердил: «сейчас все работает». Это успешный результат текущего сценария уведомления и перехода на данном iPhone; число дополнительных нажатий и системных подтверждений отдельно не зафиксировано. Предложенная дополнительная замена `openWindow` навигацией существующей страницы не выполнялась: пользователь подтвердил успех текущей версии.
- Полная повторная цепочка с настоящим Web Push после успешного обновления, отдельные прогоны cold start / lock screen, отсутствие установленного приложения и другие версии iOS ещё требуют приёмки. Текущий эксперимент не реализует звонковый движок.

Локального HTTPS-стенда достаточно для эксперимента без изменения рабочего сервера. Успех текущего сценария не является гарантией запуска одним нажатием во всех состояниях iOS. Экспериментальный флаг сборки меняет переход звонковых уведомлений для всех установок PWA, получивших эту сборку.

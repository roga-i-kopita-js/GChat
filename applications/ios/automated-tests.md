# План автоматизированных проверок GChat iOS

Все проверки, не требующие ручной оценки поведения физического iPhone, автоматизируются. Этот документ описывает целевое покрытие: Xcode-проект, native test target и native-плагин ещё предстоит создать. Web unit-тесты адаптера bridge реализованы в [runtime.test.ts](../web/src/shared/native/runtime.test.ts); они не закрывают проверки настоящего Capacitor в Simulator. Simulator не используется как ручной этап приёмки. Ручные проверки физического устройства вынесены в [отдельный план](manual-tests.md).

Контракты и архитектурные критерии — в [D008](../../docs/architecture/decisions/D008-capacitor-bridge.md); существующий системный стенд и запуск реализованных E2E — в [E2E README](../../tests/e2e/README.md). Новые Simulator/native-наборы пока не подключены к командам репозитория; их выполнение нельзя объявлять успешным по результатам существующих browser/protocol-тестов.

## Уровни автоматизации

| Уровень                                    | Покрытие                                                                                                                                                                                                                                     |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit и интеграционные native-тесты         | Session manager, сериализация refresh/logout, ошибки защищённого хранилища, отбрасывание запоздавших ответов. Время и отказы управляются fixture.                                                                                            |
| Web unit/browser-тесты                     | Обработчик route, память HTTP-транспорта, очистка кешей, защита от результатов прошлого цикла, отсутствие секретов в URL/history/storage.                                                                                                    |
| UI и интеграционные тесты в iOS Simulator  | Реальный WKWebView/Capacitor bridge, локальное стартовое приложение, загрузка серверного Web, навигация, ввод формы, повтор после ошибки и перезапуск WebView/процесса. Конкретный runner и команды подключаются при создании Xcode-проекта. |
| Backend/protocol E2E и тесты развёртывания | CORS/Origin, header-based WSS, server-side state, неизвестный результат создания, конкурентные вызовы, HTML/assets и rollback. Используется выделенный тестовый стенд.                                                                       |

Проверки разных уровней дополняют друг друга: mock bridge не заменяет Simulator-проверку реального bridge; протокольный `active` не заменяет ручную слышимость на iPhone. Существующие backend/browser-тесты переиспользуются там, где уже проверяют нужное правило, без дублирования одинаковых проверок.

## Подготовка и результат

Зафиксировать native/Web/backend/bridge версии и Simulator runtime. Нужны тестовые аккаунты A/B с правом звонить, C для смены пользователя, HTTPS-стенд с разрешённым и запрещённым origins, управляемые transport/storage fixtures. В тестах автоматически восстанавливать предусловия, управлять временем и отказами, проверять побочные эффекты и очищать данные после выполнения. Секреты, сырые HTTP/WS-сообщения, токены и SDP/ICE не сохраняются в артефактах.

Для каждого ID и варианта фиксировать `not_run`, `pass`, `fail` или `blocked`, версии окружения и ссылку на безопасный отчёт runner. Пропущенный, отключённый или ещё не реализованный тест не является `pass`. Ниже приведены действия тестового сценария и необходимые assertions; они выполняются автоматически, а не оператором в Simulator.

## A: авторизация и восстановление WebView

| ID  | Среда           | Шаги                                                                                                                                                                                         | Ожидаемый результат                                                                                                                                                                                                                                             |
| --- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A01 | Simulator/стенд | На login ввести неверный пароль, затем правильный.                                                                                                                                           | Ошибка показана в форме. HTTP login выполняет native; после надёжного сохранения сессии он вызывает `route` с access token. Web сам загружает данные. Refresh token в Web не поступает.                                                                         |
| A02 | Simulator/стенд | Завершить процесс после успешного входа и запустить снова с сохранённой сессией. Повторить после истечения access token.                                                                     | Адрес и сессия восстанавливаются; при необходимости native выполняет refresh. Повторный ввод пароля не нужен. WSS/device binding восстанавливаются без WebView.                                                                                                 |
| A03 | Simulator/стенд | Просрочить access token и одновременно инициировать несколько HTTP-запросов Web и reconnect native WSS.                                                                                      | Native координирует одну общую операцию refresh; нет конкурентной ротации старого refresh token. Истёкшая HTTP-операция повторяется не более одного раза по Auth-политике. Обычный refresh не очищает кеши UI.                                                  |
| A04 | Simulator/стенд | Через fixture дать backend зафиксировать ротацию, потерять ответ и повторить запрос в пределах окна результата. Затем повторить отдельный прогон с запуском приложения после истечения окна. | В первом прогоне native использует прежние token/request_id и восстанавливает пару. Во втором допустим новый вход после подтверждённого `SESSION_INVALID`; нет слепой ротации со случайным новым ID.                                                            |
| A05 | Simulator/стенд | Разорвать сеть во время refresh; отдельно вернуть временный отказ и rate limit. Повтор соблюдает прежний request_id и Retry-After. Пользователь видит ожидание/ошибку с повтором, а не ложный успешный вход или logout.                                                                               |
| A06 | Simulator/стенд | Выполнить logout из Web, затем в отдельном прогоне из native UI. Войти пользователем C.                                                                                                      | Оба инициатора используют native HTTP logout. После подтверждения закрываются WSS/аудио, удаляется сессия, приходит `loggedOut()`. Адрес сохраняется в query login. После нового входа нет данных A в UI/кешах.                                                 |
| A07 | Simulator/стенд | Потерять ответ logout или получить временный отказ; затем повторить операцию.                                                                                                                | До подтверждения нет ложного успешного выхода и удаления сессии. Повтор возможен; подтверждённый выход и повторное событие очистки обрабатываются безопасно.                                                                                                    |
| A08 | Simulator/стенд | Задержать ответ refresh, выполнить logout и затем доставить старый ответ. | A09 | Simulator/стенд | Приостановить WebView; выйти из native и войти другим пользователем. Возобновить WebView. | A10 | Simulator/стенд | Во время восстановления native-сессии вызвать `webReady`; отдельно имитировать ошибку чтения Keychain и ошибку записи после login.                                                           | До готовности не отображаются старые данные. ## C10: неизвестный результат и конкуренция команд звонка

Сценарий выполняется автоматически через native/protocol test harness на стенде; физический iPhone и ручные действия не требуются. Проверка реального аудио остаётся в ручном плане.

| ID  | Среда                 | Действия теста                                                                                                   | Ожидаемый результат                                                                                                                                                           |
| --- | --------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C10 | Native/protocol стенд | Через fixture потерять ответ `call.create`; отдельно создать встречные вызовы и позвонить занятому пользователю. | Нет автоматического повтора `call.create` и дубликатов; native сверяет текущее состояние. Конкурентные исходы, занятость и освобождение участников соответствуют DirectCalls. |

Сборка libwebrtc/XCFramework, checksum и воспроизводимость сборки проверяются средствами сборочной автоматизации по D008. Симулированные события CallKit/PushKit проверяют логику обработчика, но не засчитываются как физическая аудио- или APNs-приёмка.

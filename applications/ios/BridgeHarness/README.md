# GChat Bridge Harness

Тестовое iOS-приложение для первого этапа [API device](../../../docs/web/device-api.md#профиль-native-http-первой-версии): нативный HTTP v1 и существующие команды [устройства](../../../docs/web/device-bridge.md). Используется тот же Capacitor/Swift-плагин, который собирается в основной GChat. Сборка имеет отдельный bundle identifier `com.gchat.bridgeharness`, собственные UserDefaults/Keychain и имя `GChat Bridge`.

## Границы

HTTP, включая тесты отказов, доступен без аккаунта. Для разрешений, аудиотестов и файлов требуется native-сессия: при необходимости сервер удаляет внешний префикс `/api` и проксирует API и единственный native WSS в **изолированный тестовый backend** на loopback Mac. Нет фиктивной авторизации, аккаунтов или второго звонкового клиента. Не подключайте рабочий backend: вход и выход являются настоящими Auth-операциями. Пароли/токены/файловое содержимое/пути не выводятся в результаты. CSP запрещает Fetch WebView; вызовы идут через Capacitor в URLSession.

Это внутренний диагностический Web-экран, не реализация публичной фабрики `createDevice` и не миграция основного Web. Реализованы HTTP-профиль и navigationVersion: 1 с диагностическим Data router; CameraSession/запись/PiP ещё не объявляются доступными. Нативные storage.getRoot/storage.getUsage доступны через диспетчер; публичный Web-фасад StorageService ещё не подключён. Системные команды проверяют существующую реализацию. Harness не запрашивает APNs entitlement и допускает Personal Team; доставку push эта сборка не проверяет. Основная GChat сохраняет свои APNs entitlements. Звук, системные prompts и bookmarks требуют физической приёмки; Simulator и fixtures её не заменяют.

## Запуск

Используйте Node из корневого `.nvmrc` и установленный полный Xcode. Подготовьте HTTPS-сертификат и ключ по [правилам стенда iOS](../README.md#https-стенд-для-simulator-и-iphone): валидный сертификат serverAuth с SAN имени/IP Mac, подписанный вашим тестовым CA. Для iPhone имя/IP должны быть доступны с телефона; localhost относится к телефону. Приватный ключ не передаётся на устройство и не сохраняется в репозитории.

```sh
export GCHAT_BRIDGE_CERT_FILE=/absolute/path/server.pem
export GCHAT_BRIDGE_KEY_FILE=/absolute/path/server-key.pem
# По умолчанию сервер доступен только на Mac:
export GCHAT_BRIDGE_HOST=127.0.0.1
export GCHAT_BRIDGE_PORT=8446
# Необязательно: изолированный backend для реального login и системных команд.
# export GCHAT_BRIDGE_BACKEND=http://127.0.0.1:3000
pnpm --filter @gchat/ios bridge:build
pnpm --filter @gchat/ios bridge:serve
```

В другом терминале:

```sh
pnpm --filter @gchat/ios build:bridge
xcrun simctl bootstatus booted -b
xcrun simctl keychain booted add-root-cert /absolute/path/test-ca.pem
xcrun simctl install booted applications/ios/BridgeHarness/DerivedData/Build/Products/Debug-iphonesimulator/App.app
xcrun simctl launch booted com.gchat.bridgeharness
```

Сначала запустите выбранный Simulator через Xcode. В стартовой форме приложения введите `https://127.0.0.1:8446` (либо origin с выбранным именем/IP и портом). Сервер отдаёт диагностический экран на `/apps/client`, сохраняя обычные проверки origin/main frame/cycle. Основной Web собирать не требуется. Не запускайте `cap sync/copy`.

Для iPhone используйте [команды установки](../README.md#установка-на-физический-iphone), добавив `GCHAT_DISPLAY_NAME='GChat Bridge'`, `CODE_SIGN_ENTITLEMENTS=../BridgeHarness/BridgeHarness.entitlements`, отдельный уникальный `PRODUCT_BUNDLE_IDENTIFIER` вашего Team и новый `-derivedDataPath`. На Mac задайте `GCHAT_BRIDGE_HOST` доступным LAN-адресом и откройте только тестовый стенд. CA должен быть установлен с полным доверием на iPhone. После проверки остановите сервер и удалите ненужный тестовый CA.

## Приёмка первого этапа

1. Стартовый экран открывается без backend; capabilities содержит httpVersion: 1.
2. «Проверить HTTP и ограничения»: все строки passed: true — бинарное тело, 204, HTTP 422 без подмены успешным статусом, фильтрация Set-Cookie, запрет редиректа, 8 МиБ, чужого origin, Cookie и Auth endpoint, несовместимая версия.
3. «Проверить отмену и старый цикл»: отмена до регистрации, активного URLSessionTask и запрос старого цикла возвращают CANCELLED. Новые запросы после отмены работают.
4. С тестовым backend вход выполняется через native Auth; запросы разрешений доступны после входа. После выхода команды возвращают UNAUTHENTICATED. Без backend HTTP-тесты работают, login не обещает успех.
5. Чтение состояния не вызывает prompts. Разрешение запрашивается отдельным нажатием. Аудиотест запускается отдельно, останавливается командой и при смене цикла. Проверьте звук на физическом iPhone.
6. Выбор файла показывает только тип, размер и сохранность доступа. После перезапуска доступ виден в списке; реальные bookmarks/provider проверяются на устройстве. Тест не меняет и не удаляет выбранные файлы.

Автоматически: `pnpm --filter @gchat/ios test`, `pnpm --filter @gchat/ios build:bridge`, `pnpm docs:check`. NativeHTTPTests используют URLProtocol fixtures для HTTP-статусов, binary, лимитов, ошибок сети/timeout, подстановки токена и отмен. Эти проверки не подтверждают сетевую доступность TLS на iPhone или работу камеры/PiP.

Для автоматического HTTP smoke используйте отдельную установку без сохранённой native-сессии. Без системных prompts запустите стенд с `GCHAT_BRIDGE_AUTORUN=1`. После открытия страницы harness выполняет HTTP/отмены/пересинхронизацию цикла и отказы без сессии, затем передаёт через тот же native HTTP только итоговые счётчики на локальный fixture endpoint. В терминале стенда ожидается `Bridge HTTP smoke: 21/21 passed`. Для отдельного тестового Simulator можно задать сервер при запуске без ручного ввода: `xcrun simctl launch <SIMULATOR_UDID> com.gchat.bridgeharness --bridge-server https://localhost:8446`. Аргумент поддерживается только Debug-сборкой с bundle identifier com.gchat.bridgeharness либо com.gchat.bridgeharness.dev.<суффикс> и сохраняет origin обычным механизмом выбора сервера.

Debug-harness сохраняет только фиксированные этапы bridge, нормализованные коды ошибок и числовой код NSURLErrorDomain в `Library/Caches/gchat-bridge-diagnostics.txt` (последние 60 строк). Данные запросов, идентификаторы, токены и пути выбранных файлов туда не записываются. Файл можно прочитать через `xcrun devicectl device copy from --device <UDID> --domain-type appDataContainer --domain-identifier <BUNDLE_ID> --source Library/Caches/gchat-bridge-diagnostics.txt --destination /tmp/gchat-bridge-diagnostics.txt`. При подключении к LAN iOS может запросить разрешение локальной сети; без него сквозной прогон на LAN не подтверждается.

## Физическая проверка HTTP

2026-11-08 (Asia/Nicosia): автоматическая HTTP-матрица без native-сессии пройдена на iPhone 14 / iOS 26.6.2, приложение `com.gchat.bridgeharness.dev.72g952phm3`. Проверялись HTTP-ответы и бинарное тело, bodyless HEAD/304, лимит ответа, запрет редиректов, проверка аргументов/origin/Auth, отмены, активный дубль requestId, смена цикла и отказ защищённых команд без сессии.

До включения доступа «Локальная сеть» WebView загружал тестовую страницу, а URLSession возвращал NSURLErrorDomain -1009. После разрешения доступа на iPhone сквозной прогон завершился успешно. Эта проверка не подтверждает реальную авторизацию, звук, файловые providers/bookmarks, камеру/PiP или доставку push.

## Ручное наблюдение с Mac

По прямому запросу пользователя согласован режим: пользователь нажимает кнопки на iPhone, проверяющий получает результаты на Mac. Требования готовы к реализации в диагностическом harness; публичный production bridge не расширяется.

- Отправляются начало/завершение действия, безопасный код ошибки, длительность, нормализованные состояния разрешений, терминальное состояние аудиотеста, настройки уведомлений, число файловых доступов и тип/размер/сохранность выбранного файла.
- Данные передаются тем же native HTTP в изолированный HTTPS-стенд; он проверяет разрешённые поля/значения и сохраняет ограниченный журнал. Пароли, токены, имена/пути/содержимое файлов, bookmarks, координаты, аудио и имена аксессуаров не передаются.
- Состояние перечитывается после действий/foreground и по device.changes.wait; постоянный опрос системных API не добавляется. Смена цикла отменяет старое наблюдение.
- На iPhone показываются понятный статус действия и доставки диагностики. Тестовые реквизиты из E2E fixture могут быть предзаполнены, но вход и системные prompts выполняются только по нажатию пользователя.
- Слышимость подтверждается отдельными кнопками пользователя; успешное завершение аудиотеста не считается доказательством слышимости. Отмена, отказ и отсутствие сессии сохраняются как фактические результаты.
- Приёмка: нажатия и ошибки видны проверяющему без чтения JSON пользователем; завершение аудиотеста видно после его старта; повторный foreground не создаёт второго наблюдателя; неверные поля и чувствительные значения отвергаются до записи. Невозможность доставки видна на iPhone и не отменяет уже выполненную системную операцию.

Для наблюдения задайте `GCHAT_BRIDGE_EVENTS_FILE=/tmp/gchat-bridge-manual-events.jsonl` при запуске сервера с `GCHAT_BRIDGE_BACKEND=http://127.0.0.1:3300` и без `GCHAT_BRIDGE_AUTORUN`. Журнал содержит JSONL; при достижении 1 МиБ предыдущий файл переносится в `.previous`. Команда `pnpm --filter @gchat/ios test:bridge` проверяет допустимые метрики и отказ записи секретов/лишних полей. На iPhone тестовые реквизиты предзаполнены; нажимать «Войти в тестовый аккаунт» нужно только на изолированном стенде.

## Автоматическая файловая матрица NativeCore

[DeviceFilesMatrixTests](../NativeCore/Tests/GChatCoreTests/DeviceFilesMatrixTests.swift) выполняются через обычный `pnpm --filter @gchat/ios test` без участия пользователя. Каждый тест создаёт собственную временную область и UserDefaults suite, затем удаляет только свои данные. Проверяются пустые и многочастные бинарные файлы, чтение за EOF, копирование/переименование/перемещение с сохранением ссылок, запрет перезаписи и перемещения в поддерево, рекурсивное удаление и инвалидирование ссылок, WRONG_TYPE, утрата доступа, конфликт курсора, BUSY и отмена staged write при reset. Найденный отказ directory.list по ссылке на файл исправлен на контрактный WRONG_TYPE и проверяется регрессией.

Это проверки NativeCore на файловой системе macOS: они не подтверждают поведение сторонних iOS document providers, ошибки реальной квоты или частичное выполнение облачным provider. Подтверждённый физический объём файловых проверок описан в ручном прогоне выше.

## Внутренние области Data / Temporary / Cache

Реализован нативный блок [StorageService](../../../docs/web/device-api.md#storageservice): корни возвращаются как FileRef, содержимое обслуживают существующие файловые команды. Постоянные ссылки Data/Cache восстанавливаются без picker; внутренние области исключены из списка предоставленных внешних доступов. Корни защищены от move/rename/remove, внешние access-команды к ним не применяются. Temporary очищается при сбросе Web-цикла; после сбоя очищаются только области без живого владельца, подтверждённого OS advisory lock. Usage возвращает логический размер обычных файлов области и null для неизвестной отдельной квоты.

На экране добавлена кнопка «Проверить Data / Temporary / Cache». Сценарий создаёт только собственные UUID-каталоги fixture внутри приложения, пишет/читает бинарные данные, проверяет usage, сбрасывает Web-цикл и проверяет исчезновение Temporary и сохранность Data. Один маркер Data остаётся для проверки следующего запуска; предыдущий удаляется только после сверки с собственным fixture в Data. Чужие выбранные файлы не изменяются. Результаты приходят в тот же журнал безопасных метрик.

Для автоматического прогона запустите HTTPS-стенд с `GCHAT_BRIDGE_STORAGE_AUTORUN=1`, подключённым изолированным backend и без HTTP autorun. Сценарий использует существующую native-сессию; при её отсутствии входит синтетическим E2E-аккаунтом. Повторный запуск приложения проверяет сохранённый Data-маркер. NativeCore XCTest проверяют восстановление ссылок, защиту корней, sandbox, usage, временные владельцы и очистку после сбоя. Fixture на macOS не заменяет интеграционный прогон WKWebView/Swift и iOS-файловую систему.

Проверка Storage в Simulator (2026-11-08, Asia/Nicosia): через реальный WKWebView → Swift диспетчер прошли получение трёх корней, запись/чтение, usage, очистка Temporary при смене цикла и сохранность Data/внешнего реестра. Повторный запуск процесса подтвердил чтение Data по прежнему ID. Это подтверждение Simulator; физический прогон Storage учитывается отдельно от ранее выполненных ручных проверок внешних файлов.


## Автоматическая проверка навигации

Перед запуском стенда выполните `pnpm --filter @gchat/ios bridge:build`: собирается диагностический модуль на существующем Web toolchain. Запустите HTTPS-стенд с `GCHAT_BRIDGE_NAVIGATION_AUTORUN=1` без других autorun-флагов. Кнопка «Проверить навигацию» запускает Web-сценарии повторно. В Debug-сборке только bundle GChat Bridge после navigationReady автоматически получает нативные тестовые переходы; обычное приложение их не выполняет.

Harness использует один настоящий React Router Data router с basename `/apps/client`, маршрутами-fixture и принятым App-нормализатором URL. Проверяются команды Swift → WKWebView → router → Swift, replace и повтор requestId, обычный переход, redirect, ошибка loader, вытеснение, отказ/подтверждение blocker, revalidate без сброса revision и отменённый до старта signal. В журнал передаются только фиксированные имена проверок, outcome и boolean; URL, токены и содержимое маршрутов не логируются.

Прогон Simulator 2026-11-08 подтвердил перечисленные сценарии через настоящий WKWebView/Swift bridge. Основные экраны также переведены на Data router; их маршрутная регрессия проверяется отдельно от fixture-прогона. Контакты/admin перенесены в loaders/actions и Query удалён; публичная композиция device и оставшиеся критерии data-flow ещё не завершены.


## Fetch-адаптер и основной Web

Navigation autorun сначала выполняет навигационную матрицу, затем Fetch-профиль через тот же native HTTP: настоящий Response/clone, бинарное тело, HEAD/204/304, HTTP 422, запрет redirect/чужого origin, лимит ответа, отмена и последующий запрос. Метрики Fetch содержат только фиксированный fetchCheck и passed. Navigation и Storage autorun допускаются вместе: Storage выполняется после Fetch.

Для проверки собранного основного Web сначала выполните `pnpm --filter @gchat/web build:server`, затем задайте `GCHAT_BRIDGE_CLIENT_ROOT` абсолютным путём к `applications/web/dist` и подключите изолированный backend. HTML/статические assets берутся из сборки, API/WSS сохраняют тестовый proxy. Autorun в этом режиме не применяется к основным экранам. Не смешивайте основной Web и диагностический экран при трактовке результатов.

Физический прогон 2026-11-08: на установленном iPhone автоматически прошли Navigation, Fetch и Storage; повторный запуск подтвердил восстановление Data по прежнему FileRef. В начале без сессии Observe вернул ожидаемый UNAUTHENTICATED; после входа синтетическим аккаунтом Storage прошёл. Это не подтверждает camera capture/PiP, call engine, реальный файловый provider или системные аудиопрерывания. В Simulator отдельно открыта серверная сборка основного Web: восстановлена native-сессия, выполнены native-переходы и SDK загрузил группы/контакты через URLSession. На iPhone подтверждён запуск основной сборки Web и нативные переходы; отображение/данные этого экрана отдельно не засчитываются по одному логу запуска.

# GChat Audio Test

Отдельный Swift/CallKit harness по [принятому первому этапу](../../../docs/ios/native-calls.md). Это технический аудиостенд, а не замена основного приложения. Собственный bundle identifier и Keychain отделяют его сессию от оболочки GChat. APNs/PushKit не подключены.

## Сборка SDK и harness

Сначала собрать и упаковать официальный SDK по [WebRTC README](../WebRTC/README.md). Распакованный `WebRTC.xcframework` должен находиться в игнорируемом `applications/ios/WebRTC/Artifacts/`. Можно создать там символьную ссылку на результат своей сборки. Pin и checksum закреплены в build-lock.json; бинарник не добавляется в git.

Из корня репозитория:

```sh
xcodebuild -project applications/ios/CallHarness/CallHarness.xcodeproj \
  -scheme GChatCallHarness -configuration Debug -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath /tmp/gchat-call-harness-sim CODE_SIGN_IDENTITY=- build

xcodebuild -project applications/ios/CallHarness/CallHarness.xcodeproj \
  -scheme GChatCallHarness -configuration Debug \
  -destination "id=${GCHAT_IOS_DEVICE_ID:?Set iPhone UDID}" \
  -derivedDataPath /tmp/gchat-call-harness-device \
  DEVELOPMENT_TEAM="${GCHAT_IOS_TEAM_ID:?Set Signing Team}" \
  PRODUCT_BUNDLE_IDENTIFIER="${GCHAT_IOS_HARNESS_BUNDLE_ID:?Set unique harness bundle ID}" \
  -allowProvisioningUpdates -allowProvisioningDeviceRegistration build
```

Проект собирает только arm64, как и принятый SDK. Устанавливать `App.app` основного приложения вместо `GChatCallHarness.app` не нужно; инструкция devicectl и настройки подписи — в [README iOS](../README.md#установка-на-физический-iphone). Harness не запрашивает Push Notifications entitlement и может подписываться Personal Team.

## Запуск и проверка

Подготовка изолированного backend/Web peer/LAN TURN — в [E2E README](../../../tests/e2e/README.md#локальный-ios-аудиостенд). Нельзя указывать рабочий сервер с пользовательскими данными. На iPhone ввести HTTPS-origin тестового proxy и тестовый аккаунт, нажать «Войти и разрешить микрофон». Без разрешения микрофона вызов не начинается. Сервер и native-сессия привязаны друг к другу; для смены сервера сначала выполнить подтверждённый logout.

Второй участник открывает Web peer на Mac и входит другим тестовым пользователем той же группы. Для исходящего из harness в техническое поле вводится UUID этого тестового пользователя из изолированной БД; это не продуктовый интерфейс контактов. Для входящего Web peer звонит аккаунту harness через обычные контакты.

Ответ/завершение доступны через CallKit и кнопки harness; mute управляет нативным аудио. При подключённом аудио строка «Аудиоустройство» показывает фактический выход; кнопка справа открывает системный выбор устройства вместо прежнего переключателя громкой связи. Состав списка и доступность гарнитур требуют физической проверки по [контракту выбора устройства](../../../docs/ios/audio-devices.md). Имена аксессуаров показываются только в UI, в диагностику не попадают. Используется TURN-only. Поле «Медиа: connected» учитывает соединение WebRTC и активированную CallKit аудиосессию; успешная авторизация или WSS online не означают наличие звука.

При подключённом аудио доступен системный ползунок «Громкость разговора». Для проверки измените его положение, затем нажмите боковые кнопки громкости iPhone и проверьте синхронизацию. Повторите для обоих встроенных динамиков и с заблокированным экраном; [поведение и критерии приёмки](../../../docs/ios/call-volume.md) описаны отдельно. После установки пользователь сообщил, что управление громкостью работает отлично. Отдельные результаты для обоих маршрутов и проверки скрытия ползунка после завершения не детализированы; полный набор критериев не считается автоматически пройденным.

Кнопка «Скопировать диагностику» вверху экрана собирает снимок состояния и показывает подтверждение. При проблеме нажать её сразу после теста и вставить текст в чат разработчика. Состав снимка ограничен [контрактом диагностики](../../../docs/ios/native-calls.md#протокольное-поведение); пароли, токены и содержимое сигнализации не копируются.

Тот же снимок автоматически перезаписывается в `Library/Application Support/GChatCallHarness/diagnostics.txt`. Разработчик может прочитать только этот файл с подключённого устройства через `xcrun devicectl device copy from` с `--domain-type appDataContainer` и bundle identifier harness. Снимок содержит активность приложения, число/время WSS-сообщений и число сбросов CallKit. Он не отправляется на backend.

В `UIBackgroundModes` нужны `audio` и `voip`. При проверке на физическом iPhone отсутствие `voip` приводило к сбросу провайдера при входящем, несмотря на успешные `call.updated` и `call.current: ringing`; с обоими режимами контроллер сохраняет входящий без сброса. Эта настройка не подключает APNs/PushKit. После `providerDidReset` harness освобождает объекты CallKit, корректно завершает свой текущий звонок и восстанавливает наблюдение через существующий WSS; следующий звонок создаёт новый провайдер.

Для приёмки оба участника должны подтвердить слышимость. Затем проверить фон, lock screen, Bluetooth, обычное телефонное прерывание и восстановление сети по [ручным сценариям](../manual-tests.md). Сборка Simulator и тестовые media fixtures слышимость не подтверждают. Матрица iOS 16.x / актуальная iOS остаётся обязательной для полного Gate 1.

SDK и оба адаптера не подключены к основной Capacitor-оболочке; её `nativeCalls` остаётся false. Production URL-схема и управление звонком через Web bridge этим harness не добавляются.

## Текущая проверка

Актуальные баги, уточнённые симптомы и точки продолжения отдельных сессий — в [реестре аудиобагов](../../../docs/ios/audio-bugs.md). Записи ниже сохраняют хронологию проверок; последующие уточнения в реестре имеют приоритет при определении текущего статуса.

После первоначального положительного отзыва о регуляторе громкости пользователь уточнил дефект: в наушнике фактическая громкость не меняется ни от ползунка, ни от боковых кнопок iPhone. Снимок call_id `71fd497c-89f6-4cae-a544-27e7e290dfe9` показывает active/connected, Bluetooth-выход и outputVolume 0.6. Значение outputVolume не доказывает слышимого изменения. Критерий регулировки на этом маршруте считается fail; требуются сравнение с разговорным динамиком в том же звонке и уточнение модели гарнитуры. Системный регулятор не заменяется программным усилением WebRTC без согласования изменения контракта.

Модель гарнитуры уточнена: Samsung Galaxy Buds3. Пользователь также сообщил, что на динамике iPhone голос не меняется, хотя индикатор громкости телефона меняется. Следующий снимок того же звонка всё ещё содержит BluetoothHFP и outputVolume 0.6; переход на встроенный выход в нём не зафиксирован. Поэтому отличие регулировки в foreground harness от аппаратных кнопок на системном экране активного звонка ещё требуется проверить. Нерабочая фактическая регулировка противоречит принятому контракту громкости и остаётся незакрытым дефектом; движение ползунка не считается приёмкой.

Пользователь подтвердил, что на заблокированном системном экране активного звонка боковые кнопки изменяют слышимую громкость. Затем уточнил: громкость меняется через боковые клавиши, но ползунок не двигается. Актуальный подтверждённый дефект — отсутствие синхронизации ползунка с регулировкой разговора, а не общий отказ аппаратных кнопок. Предыдущие сообщения об отсутствии эффекта не считаются доказательством неисправности аппаратной регулировки после этого уточнения. [Предложенный контроль без MPVolumeView](../../../docs/ios/call-volume-isolation.md) снят, код контрольной сборки не создавался. Требование синхронизации из контракта громкости остаётся невыполненным.

При повторных звонках Web → iOS обнаружен дефект Web-пира: если карточка предыдущего завершённого звонка оставалась в состоянии клиента, обработка нового call_id повторно освобождала медиа и останавливала только что полученный для новой попытки микрофон. SDP-offer не отправлялся; это согласуется с последними попытками без negotiation на сервере. Очистка уже завершённого звонка исправлена в Web-клиенте, добавлена регрессия двух последовательных звонков с обоими порядками ответа/события создания. Физический повтор после исправления ещё требуется; дефект системной кнопки CallKit этим не закрывается.

XCFramework собран из закреплённого официального commit и включает обе arm64-секции и лицензии. Harness успешно собирается для Simulator и подписывается/устанавливается на физический iPhone 14. Пользователь подтвердил `WSS: online` после native-авторизации. Проверены HTTPS readiness, header-based WSS, device.register, native.bridge_policy и call.current через LAN proxy; тестовые TURN-пакеты проходят между relay allocations с корректным Docker NAT mapping. Это проверки соответствующих участков, а не двустороннего голоса.

2026-11-08 (Asia/Nicosia), iPhone 14 / iOS 26.6.2, harness 0.1.0 (1): пользователь подтвердил звонок и двустороннюю слышимость в Web → iOS с Safari на изолированном стенде. Сервер зафиксировал `active` с 00:10:05.974 до обычного `hangup` в 00:10:24.321; call_id `ef7aa754-6f80-4b49-a782-a2835fb2ba41`. Native использует relay-only. Это частичная физическая проверка; выбранная ICE-пара, обратное направление, фон/блокировка, маршруты, прерывания и восстановление сети требуют отдельной проверки. Матрица Gate 1 не закрыта.

Следующая попытка C04 в той же среде не прошла: пользователь сообщил об остановке звука/разговора при сворачивании и блокировке. Call_id `d2bb7edf-d40d-41f5-b15a-27c60b951fca`: `active` в 00:14:40.524, `hangup` в 00:14:47.084. Снимок iPhone зафиксировал background, завершённый звонок, ноль сбросов CallKit и отсутствие ошибки. Причина пользовательского/системного действия завершения ещё уточняется; фоновое аудио не считается принятым. Нужно отдельно проверить уход на «Домой» и блокировку с учётом действия боковой кнопки iOS.

При продолжении C04 пользователь отдельно подтвердил сохранение двустороннего звука после ухода на «Домой». Нажатие боковой кнопки завершило звонок, приложение осталось открытым. После включения системной настройки Prevent Lock to End Call пользователь сообщил об успешном продолжении звонка при заблокированном экране, затем подтвердил успешное выполнение проверки: 40 секунд с выключенным экраном, слышимость в обе стороны и завершение через системный экран вызова. Наблюдение согласуется с системным завершением боковой кнопкой в предыдущих попытках; текущая диагностика не сохраняет источник `CXEndCallAction`. Ручная аудио/UI-часть C04 подтверждена пользователем на доступном iPhone 14 / iOS 26.6.2. Сверка native-пингов этого прогона ещё не выполнена; полная матрица Gate 1 не закрыта.

Пользователь также подтвердил mute на iPhone: при выключении микрофона голос iPhone → Web исчезает, звук Web → iPhone сохраняется; после включения микрофона голос возвращается без переподключения. Остальные аудиомаршруты этим результатом не подтверждены.

Проверка громкой связи не прошла: пользователь сообщил, что переключение не работает и звук чрезмерно громкий у уха. Обнаружен отдельный дефект UI: флаг громкой связи менялся локально по нажатию и не отражал системные изменения маршрута. Исправление читает фактический `currentRoute`, обновляется по `routeChangeNotification` и показывает тип выхода без названий/идентификаторов аксессуаров; кнопка доступна только при подключённом аудио. Причина громкости и физическое переключение динамиков требуют повторной проверки на устройстве.

При повторе пользователь сообщил, что переключение и синхронизация по-прежнему не работают. Снимок для call_id `a6810030-16d6-406d-89e8-97a98ad7e071` содержит `active`, фактический громкий динамик и совпадающий флаг UI; он не содержит доказательства выполнения команды переключения. Добавлена отложенная проверка фактического выхода после команды: успешный вызов API сам по себе не считается переключением. Безопасная диагностика маршрутизации содержит последнюю команду и её результат, счётчики команд/смен маршрута, последнюю системную причину, category/mode/options и системную громкость. Имена и идентификаторы аксессуаров не записываются. Физическая проверка громкой связи остаётся fail до повторного подтверждения; первопричина ещё не установлена.

В диагностическом повторе для call_id `25df8f84-cbe7-4528-bf0d-1ae65c371d9a` после двух последовательных нажатий в harness зафиксированы команда #1 → фактический громкий динамик и команда #2 → фактический разговорный динамик. В обоих снимках флаг UI соответствует `currentRoute`, аудио остаётся connected, звонок active; category playAndRecord, mode voiceChat, options 4, volume 0.15. Это подтверждает применение команд на уровне аудиосессии в данном повторе. Физическое изменение слышимости и синхронизация с кнопкой системного экрана ещё не подтверждены.

После серии переключений на системном экране пользователь сообщил о странном поведении и задержке примерно на третьей попытке. В следующем снимке того же звонка счётчик смен маршрута вырос с 4 до 9, выход — громкий динамик, UI-флаг соответствует выходу, звонок active, аудио connected, сбросов CallKit нет. Число команд harness осталось 2: эти последующие переключения зарегистрированы как системные изменения. Итоговый снимок не измеряет задержки/краткие провалы аудио и не доказывает исправность серии переключений. Проверка C03 остаётся fail; характер задержки ещё уточняется.

Пользователь уточнил симптом: кнопка не меняется либо мигает и возвращается в предыдущее состояние. В качестве исправления порядка подготовки аудио полная WebRTC-конфигурация без активации перенесена до регистрации входящего/запроса исходящего CallKit; повторный setCategory в обработчиках ответа/старта удалён. Правило жизненного цикла — в [контракте Native Calls](../../../docs/ios/native-calls.md#владение-и-границы). Связь этого изменения с физическим симптомом требует проверки в новом звонке; C03 не считается пройденным по результату сборки.

Повтор после переноса подготовки аудио не дал улучшения. Пользователь уточнил, что нажимал кнопку на заблокированном системном экране iPhone. Для call_id `56e1d4f8-abae-492a-89a5-ab53a5060ad5` счётчик команд harness равен 0, то есть симптом воспроизводится без команд его кнопки. Последний снимок сделан уже после завершения и не содержит момента отката. Добавлен ограниченный буфер локальных аудиособытий по [контракту диагностики](../../../docs/ios/native-calls.md#протокольное-поведение), чтобы сопоставить системную смену маршрута с работой WebRTC и CallKit. Первопричина остаётся неустановленной; следующий повтор выполняется на заблокированном экране.

В повторе с буфером аудиособытий, call_id `6bf427a7-f5a1-48d0-a666-2469c9a35474`, после сообщения пользователя «откат» зафиксирован единственный переход Receiver → Speaker с причиной override. Обратного перехода в буфере нет; после переключения также нет повторной подготовки, активации или остановки WebRTC. Звонок остаётся active, медиа connected, команд harness 0. Таким образом, этот повтор подтверждает расхождение состояния системной кнопки с фактическим громким выходом; немедленный возврат маршрута со стороны WebRTC записью не подтверждён. Первопричина рассинхронизации системного UI остаётся неустановленной.

CallKit не обязан показывать системный интерфейс поверх активного приложения: по [пояснению Apple DTS](https://developer.apple.com/forums/thread/844750), в foreground интерфейс предоставляет само приложение. В harness используется кнопка «Ответить через CallKit»; для диагностики отдельно записываются completion `reportNewIncomingCall` и наличие звонка в `CXCallObserver`. Успешная регистрация системного звонка не подменяет подтверждение видимого интерфейса или звука пользователем.

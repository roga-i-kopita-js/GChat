# GChat Web

Распределение ответственности между маршрутизатором, runtime, страницами, оболочкой и UI kit описано в [архитектурном паттерне](../../docs/web/architecture-pattern.md).

Полноценный браузерный клиент: вход, группы и собеседники, входящие и исходящие голосовые звонки, микрофон, восстановление и выход. Для администраторов доступен раздел управления аккаунтами: поиск, создание, смена пароля, отключение и включение; правила и ограничения — в [веб-контракте](../../docs/web/README.md#администрирование). [Контракт клиента](../../docs/web/README.md) и [карта документации](../../docs/README.md).

Диалоги 1х1 описаны отдельно: [клиентский контракт](../../docs/web/dialogs.md) описывает экраны, отправку, историю и прочтение, [bootstrap](../../docs/web/bootstrap.md) — общий runtime и хранение. Оба клиентских документа приняты пользователем; реализованы маршруты, лента virtua, текст/стикеры, черновики и локальная синхронизация. Browser использует IndexedDB, iOS — SQLite через GChat bridge с постоянным fallback. Проверки ошибок, реального iPhone и push учитываются отдельно в контрактах.

## Настройки устройства

Раздел «Настройки → Основные» находится в `src/features/settings` и использует типизированные сервисы device из `src/shared/device`; универсальный командный bridge остаётся приватным. Браузерные и нативные операции выбираются внутри bridge; настройки не создают второй звонковый клиент. Требования к экранам — в [Settings](../../docs/web/settings.md), команды и ограничения — в [Device bridge](../../docs/web/device-bridge.md).

## Навигация и исходники

Прямые ссылки, история браузера и перезагрузка поддерживаются одним React Router Data router; основное дерево находится в `src/app/routes.tsx`, владелец — NavigationHost. Device создаётся через createDevice один раз в main.tsx; его DeviceProvider монтирует router. Он передаётся в типизированный контекст React Router через getContext. Loaders/actions читают context.get(deviceContext); App/форма входа получают device из loaderData. Общая sessionMiddleware защищает основную ветку и resource-маршруты, а пользователя обработчики получают через context.get(userContext). Контакты и admin-список/карточка загружаются loaders, административные изменения выполняет action, подсказки групп — fetcher. TanStack Query и QueryClientProvider удалены. Диалоги подписываются на live-модели своего runtime, без второго кеша истории. Таблица маршрутов, параметры URL и правила доступа описаны в [веб-контракте](../../docs/web/README.md#маршрутизация-и-структура-исходников), мотивация — в [D007](../../docs/architecture/decisions/D007-web-routing.md).

Исходники разделены на `src/app` (маршруты и оболочка), `src/features/auth`, `src/features/calls`, `src/features/administration` и `src/shared` (API-транспорт и UI). Жизненный цикл звонка находится выше страниц. Изменяя навигацию, проверяйте прямой URL, возврат после входа, «Назад»/«Вперёд», обновление страницы, административный доступ и сохранение звонка между разделами.

## Разработка с настроенным backend

Из корня репозитория, с версиями Node/pnpm из `.nvmrc` и `package.json`:

```sh
pnpm install
pnpm --filter @gchat/web dev
```

Команды `dev`, `build`, `typecheck` и `test` сначала автоматически собирают workspace-зависимость [backend-api](../../docs/packages/backend-api.md) из сохранённых исходников. Экспорт OpenAPI и инфраструктура backend для сборки SDK не нужны. При изменении HTTP-контракта обновляйте SDK по инструкции пакета.

Vite принимает `http://127.0.0.1:5173` и проксирует `/api` и `/ws` на backend `http://127.0.0.1:3000`. Другой backend задаётся переменной процесса `GCHAT_BACKEND_URL` при запуске Vite. Прокси сохраняет браузерный Origin. В backend нужно явно включить origin страницы в `SIGNALING_BROWSER_ORIGINS`.

### Локальный dev для телефона и PWA

Адрес локального dev-стенда GChat: **[https://192.168.178.22:8449](https://192.168.178.22:8449)**. Телефон и компьютер разработки должны находиться в одной локальной сети. Это адрес GChat для ручной проверки на устройстве; корневой legacy Mattermost/Jitsi к этому стенду не относится.

На этом адресе HTTPS-сервер отдаёт результат `pnpm --filter @gchat/web build` и проксирует `/api` и `/ws` на локальный backend `http://127.0.0.1:3302`. Origin `https://192.168.178.22:8449` должен присутствовать в `SIGNALING_BROWSER_ORIGINS` backend. Стенд использует локальные тестовые данные GChat; Web Push и APNs выключены. Перед ручной проверкой PWA обновите размещённую сборку; обычный Vite dev-сервер не включает service worker. В уже установленной PWA примените доступное обновление вне звонка. Живую раздачу `dist/` не следует очищать во время сборки: сначала соберите полный комплект в отдельный каталог, разместите все его статические файлы, затем замените HTML и в последнюю очередь `sw.js`. Предыдущие хешированные файлы оставьте доступными для открытых окон и уже начавшейся установки worker; неполная публикация штатно отклоняется service worker.

Для микрофона, Web Locks и PWA сертификат HTTPS должен быть действующим, включать IP `192.168.178.22` и быть доверенным на проверяемом устройстве. Адрес относится к текущей LAN-конфигурации компьютера; после смены IP нужно согласованно обновить URL, сертификат и разрешённый origin backend. Проверка готовности API через тот же origin: `GET https://192.168.178.22:8449/api/ready`.

### Размещение сборки

Для рабочего окружения соберите `pnpm --filter @gchat/web build`, разместите `dist/` на HTTPS-origin и настройте reverse proxy: `/api/*` передаётся в backend без префикса `/api`, `/ws` — с upgrade и исходным Origin. Остальные клиентские пути, включая прямое открытие вложенной карточки, получают `index.html` (SPA fallback). Нельзя перенаправлять эти запросы на `/` с потерей пути и query. Backend отдельно настраивается по своему README; TURN должен быть доступен клиентским устройствам.

## Сборка для серверного Web

```sh
pnpm --filter @gchat/web build:server
```

Сборка поддерживает браузерный и встроенный режимы одного Web-клиента. HTML и файлы `dist/static/` подготовлены для `/apps/client` и `/apps/static/`; React Router использует `/apps/client` как basename. Публичные файлы `dist/` вне `static/` доступны под `/apps/` (например, `/apps/icons/`). Backend раздаёт эту сборку при заданном `GCHAT_WEB_ROOT`, включая SPA fallback под `/apps/client`; комплект и проверки описаны в [развёртывании](../../docs/operations/deployment.md). Это не закрывает проверку production remote loading в Capacitor по D008. Обычный `build` сохраняет корневые пути текущего браузерного развёртывания.

Создана [iOS-оболочка](../ios/README.md) с Capacitor-плагином `GChat`, выбором встроенного режима до выполнения JS и нативной сессией. Основная оболочка подключает нативный движок по [контракту iOS](../../docs/ios/native-app.md), сообщает `nativeCalls: true` и `webCallControls: true`; PWA и iOS используют [общий экран звонка](../../docs/design/call-screen.md). [Форматы запросов, событий и правила сессии](../../docs/web/README.md#встроенный-web-и-capacitor-bridge) — в контракте клиента. Для проверки обработки отсутствующего плагина в dev: `VITE_GCHAT_RUNTIME=native pnpm --filter @gchat/web dev`, затем `/apps/client/login`; ожидается явная ошибка bridge. Такой запуск не проверяет настоящий Capacitor или iOS.

## Изолированный стенд и проверки

Системные E2E находятся в общем модуле [@gchat/e2e](../../tests/e2e/README.md), который проверяет взаимодействие приложений и инфраструктуры. Набор `web` запускает настоящий клиент через браузер; набор `protocol` проверяет общий механизм независимыми участниками. Подготовка стенда, покрытие и запуск описаны в README модуля.

Проверки самого веб-приложения:

```sh
pnpm --filter @gchat/web typecheck
pnpm --filter @gchat/web build
pnpm --filter @gchat/web test
```

После подготовки общего стенда все системные E2E запускаются из корня:

```sh
pnpm test:e2e
```

Для отдельного набора веб-клиента: `pnpm --filter @gchat/e2e test --project web`. Backend и клиент запускаются автоматически тестовым модулем; локальных E2E-сценариев и Playwright-конфига у приложения нет.

Для ручной проверки отдельно запустите backend стенда и веб-клиент:

```sh
pnpm --filter @gchat/e2e backend
# В другом терминале:
GCHAT_BACKEND_URL=http://127.0.0.1:3300 pnpm --filter @gchat/web dev
```

Откройте `http://127.0.0.1:5173` в двух независимых профилях браузера и войдите разными тестовыми пользователями из README стенда. Вкладки одного профиля используют одну сессию. Перед автоматическим E2E-прогоном остановите вручную запущенные серверы на тех же портах.

## Форматирование и линтинг

Как и backend, веб-клиент использует Prettier и Oxlint из корня workspace с общими `.prettierrc.json` и `.oxlintrc.json`. Отдельные версии инструментов и копии правил в приложении не создаются. Команды ниже выполняются из корня и проверяют только веб-приложение:

```sh
pnpm --filter @gchat/web lint
pnpm --filter @gchat/web lint:fix
```

`lint` запускает Oxlint без допустимых предупреждений, затем Prettier в режиме проверки. `lint:fix` выполняет Prettier → Oxlint с исправлениями → Prettier. Форматирование включает TypeScript/TSX, CSS, HTML, JSON, YAML и Markdown. Генерируемые `dist/`, `.local/`, `test-results/`, `playwright-report/` и зависимости исключены через `.gitignore` приложения и корневой `.prettierignore`.

Инструменты можно запускать отдельно:

```sh
pnpm --filter @gchat/web format
pnpm --filter @gchat/web format:check
pnpm --filter @gchat/web style:check
pnpm --filter @gchat/web style:fix
```

Общие правила сохраняются: сортировка импортов, пустые строки между смысловыми блоками, явные возвращаемые типы самостоятельных TypeScript-функций и вывод типов inline-callback по [общему правилу](../../docs/development.md#стиль-javascript-и-typescript); `any` и утверждения типов разрешены только в тестах. Корневой lint-staged также обрабатывает staged-файлы веб-клиента. Команды линтинга не заменяют typecheck и тесты.

## Сессия и ограничения

Один браузерный профиль использует сохранённую сессию и device binding. Токены и незавершённый запрос refresh находятся в localStorage; они доступны скриптам того же origin. Не подключайте сторонние скрипты к клиентскому origin. Web Locks сериализует ротацию и выбирает одну вкладку-владельца WSS/микрофона; BroadcastChannel передаёт остальным безопасное состояние UI. Выход из профиля действует на все его вкладки.

После перезагрузки браузер может потребовать явное включение звука. Для работы вне localhost требуется HTTPS. Оповещения доступны в открытом клиенте. PWA, Web Push и кеширование фронта реализованы по [контракту](../../docs/web/README.md#pwa-web-push-и-кеширование); доставка при закрытой странице требует отдельной приёмки с настоящим провайдером. iOS-интеграция проверяется отдельно. Клиент рассчитан на браузеры с Web Locks, BroadcastChannel и WebRTC; текущие автоматические проверки выполняются в Chromium.

## Ленивые и вложенные маршруты

Таблица URL остаётся статической; UI разделов и обработчики данных загружаются через object-form `route.lazy` с отдельными динамическими импортами. Оболочка и владельцы сессии/звонков сохраняются при переходах. Диалоги используют список-layout с Outlet для index/переписки; admin — список с Outlet для карточки, настройки — явное дерево index/general/секций. Каждый экран настроек имеет свой ленивый модуль: корень не импортирует «Основные», список «Основные» не импортирует реализации секций. Общие строки и наблюдение за устройством переиспользуются без импорта страниц. Страницы не разбирают pathname для выбора секции настроек. Статические границы ошибок доступны и при отказе импорта модуля; useNavigation показывает состояние перехода. Список диалогов и переписка используют разные route.lazy-модули; Composer и отображение сообщений подключаются с перепиской. В звонках карточка собеседника, карточка вызова и диагностика используют отдельные условные lazy-модули; глобальный входящий контейнер не импортирует CallCard статически и сохраняет базовые кнопки при загрузке/ошибке. Полные правила и критерии — в [потоке данных](../../docs/web/data-flow.md#ленивые-модули-и-вложенные-маршруты).

## HTTP и внутреннее хранилище device

createApi использует Fetch browser либо Fetch-совместимый NativeHttpTransport, выбранный на время документа. NativeRuntime проверяет httpVersion/navigationVersion и отменяет старый сетевой контекст при пересинхронизации/смене сессии. Native не использует Fetch WebView, не передаёт Web-токен в native HTTP envelope и не добавляет повторов бизнес-операций. Полный контракт — в [API device](../../docs/web/device-api.md#профиль-native-http-первой-версии).

device.storage предоставляет getRoot/getUsage через приватный командный диспетчер; React получает сервис через DeviceProvider. В browser три области OPFS и постоянный реестр внутренних ссылок исключены из внешних grants. Временные владельцы защищены Web Locks; живая вкладка не очищается при старте другой. Общая фабрика createDevice подключена в main.tsx; оставшиеся ограничения native Call lifetime/PiP и приёмки перечислены в контракте Device API.

## Регрессия после удаления Query

Основной набор device/маршрутов — `pnpm --filter @gchat/e2e test:device`. Для реальных диалогов/браузерных звонков на подготовленном изолированном E2E-стенде используется `pnpm --filter @gchat/e2e exec playwright test --config router.config.ts`; конфиг может переиспользовать только тестовые backend/Web. `GCHAT_ROUTER_WEB_PORT` выбирает порт Web, который должен быть разрешён backend в SIGNALING_BROWSER_ORIGINS. Перед E2E завершите сборки SDK/Web, чтобы HMR не менял модули во время сценария.

## История звонков и контакты

Раздел «Звонки» показывает серверную историю с фильтрами, сведениями и подтверждением повтора; контакты открываются из «Диалогов». Поведение, данные, маршруты и критерии приёмки определяет [принятый контракт экрана](../../docs/design/calls-history.md). Начальная загрузка идёт через loaders, страницы и обновления принадлежат одному runtime на device/session scope. Отдельного браузерного транспорта или локального постоянного хранилища истории нет.

Для работы требуется backend с миграцией `0008_call_history`; порядок применения — в [контракте API](../../docs/backend/modules/direct-calls/history-api.md). Unit-проверки истории находятся рядом с фичей, браузерные проверки — в `tests/e2e/tests/device/call-history.e2e.ts` и входят в `test:device`. Проверки используют демонстрационные данные и не подтверждают реальное аудио на iPhone.

## Дизайн-система

Все экраны используют [принятое оформление «Северное сияние»](../../docs/design/winter-theme-task.md). Разработчик конфигурирует палитру, градиенты, типографику, геометрию, аватары, количество и движение декора через `src/shared/ui/tokens.css`. Значения по умолчанию соответствуют готовой HTML-вёрстке с уточнениями из контракта оформления; локальные CSS-цвета не подменяют токены. Пользовательского переключателя тем нет.

`WinterWeather` находится вне маршрутов и не перезапускается при навигации. Переходы используют постоянный React `ViewTransition` вокруг `Outlet` по руководству React Router и переходы по [контракту зимнего оформления](../../docs/design/winter-theme-task.md#визуальное-поведение-переходов--согласовано): горизонтальный сдвиг на телефоне и fade от 801 CSS px на desktop. При уменьшенном движении анимации отключаются, без API навигация работает сразу. UI-проверки находятся в `tests/e2e/tests/device/call-history.e2e.ts` общего E2E-пакета; снимки не подтверждают ручную приёмку iPhone/WebView.

## Редактирование сообщений

Свои сохранённые текстовые сообщения можно изменить через меню сообщения. Стрелка ↑ в пустом поле ввода открывает последнее загруженное своё текстовое сообщение; Escape возвращает обычный черновик. Поведение и технические правила — в [контракте редактирования](../../docs/backend/modules/dialogs/message-editing.md). Для работы нужны backend с миграцией `0009_message_editing` и SDK с версиями сообщений. Новая Web переводит кеш в schema v2; новая iOS-оболочка поддерживает bridge v2, старая использует постоянный fallback в IndexedDB с переносом черновиков/outbox.

При обновлении учитывайте согласованный порядок выпуска: старый backend не читает новые записи шифрования v2. Проверки версии сообщения, конфликтов, потерянного ответа и офлайн-синхронизации включены в `tests/e2e/tests/web/dialogs.e2e.ts`; unit-проверки кеша и native fallback находятся в `src/shared/dialogs/`.

# GChat Web

Полноценный браузерный клиент: вход, группы и собеседники, входящие и исходящие голосовые звонки, микрофон, восстановление и выход. Для администраторов доступен раздел управления аккаунтами: поиск, создание, смена пароля, отключение и включение; правила и ограничения — в [веб-контракте](../../docs/web/README.md#администрирование). [Контракт клиента](../../docs/web/README.md) и [карта документации](../../docs/README.md).

## Навигация и исходники

Прямые ссылки, история браузера и перезагрузка поддерживаются React Router. Таблица маршрутов, параметры URL и правила доступа описаны в [веб-контракте](../../docs/web/README.md#маршрутизация-и-структура-исходников), мотивация — в [D007](../../docs/architecture/decisions/D007-web-routing.md).

Исходники разделены на `src/app` (маршруты и оболочка), `src/features/auth`, `src/features/calls`, `src/features/administration` и `src/shared` (API-транспорт и UI). Жизненный цикл звонка находится выше страниц. Изменяя навигацию, проверяйте прямой URL, возврат после входа, «Назад»/«Вперёд», обновление страницы, административный доступ и сохранение звонка между разделами.

## Разработка с настроенным backend

Из корня репозитория, с версиями Node/pnpm из `.nvmrc` и `package.json`:

```sh
pnpm install
pnpm --filter @gchat/web dev
```

Команды `dev`, `build`, `typecheck` и `test` сначала автоматически собирают workspace-зависимость [backend-api](../../docs/packages/backend-api.md) из сохранённых исходников. Экспорт OpenAPI и инфраструктура backend для сборки SDK не нужны. При изменении HTTP-контракта обновляйте SDK по инструкции пакета.

Vite принимает `http://127.0.0.1:5173` и проксирует `/api` и `/ws` на backend `http://127.0.0.1:3000`. Другой backend задаётся переменной процесса `GCHAT_BACKEND_URL` при запуске Vite. Прокси сохраняет браузерный Origin. В backend нужно явно включить origin страницы в `SIGNALING_BROWSER_ORIGINS`.

Для рабочего окружения соберите `pnpm --filter @gchat/web build`, разместите `dist/` на HTTPS-origin и настройте reverse proxy: `/api/*` передаётся в backend без префикса `/api`, `/ws` — с upgrade и исходным Origin. Остальные клиентские пути, включая прямое открытие вложенной карточки, получают `index.html` (SPA fallback). Нельзя перенаправлять эти запросы на `/` с потерей пути и query. Backend отдельно настраивается по своему README; TURN должен быть доступен клиентским устройствам.

## Сборка для серверного Web

```sh
pnpm --filter @gchat/web build:server
```

Сборка поддерживает браузерный и встроенный режимы одного Web-клиента. HTML и файлы `dist/static/` подготовлены для `/apps/client` и `/apps/static/`; React Router использует `/apps/client` как basename. Публичные файлы `dist/` вне `static/` доступны под `/apps/` (например, `/apps/icons/`). Backend раздаёт эту сборку при заданном `GCHAT_WEB_ROOT`, включая SPA fallback под `/apps/client`; комплект и проверки описаны в [развёртывании](../../docs/operations/deployment.md). Это не закрывает проверку production remote loading в Capacitor по D008. Обычный `build` сохраняет корневые пути текущего браузерного развёртывания.

Создана [iOS-оболочка](../ios/README.md) с Capacitor-плагином `GChat`, выбором встроенного режима до выполнения JS и нативной сессией. Звонковый движок ещё отсутствует; оболочка возвращает `nativeCalls: false`. [Форматы запросов, событий и правила сессии](../../docs/web/README.md#встроенный-web-и-capacitor-bridge) — в контракте клиента. Для проверки обработки отсутствующего плагина в dev: `VITE_GCHAT_RUNTIME=native pnpm --filter @gchat/web dev`, затем `/apps/client/login`; ожидается явная ошибка bridge. Такой запуск не проверяет настоящий Capacitor или iOS.

## Изолированный стенд и проверки

Системные E2E находятся в общем модуле [@gchat/e2e](../../tests/e2e/README.md), который проверяет взаимодействие приложений и инфраструктуры. Набор `web` запускает настоящий клиент через браузер; набор `protocol` проверяет общий механизм независимыми участниками. Подготовка стенда, покрытие и запуск описаны в README модуля.

Проверки самого веб-приложения:

```sh
pnpm --filter @gchat/web typecheck
pnpm --filter @gchat/web build
pnpm --filter @gchat/web test
```

После подготовки общего стенда все системные E2E запускаются из корня:

```sh
pnpm test:e2e
```

Для отдельного набора веб-клиента: `pnpm --filter @gchat/e2e test --project web`. Backend и клиент запускаются автоматически тестовым модулем; локальных E2E-сценариев и Playwright-конфига у приложения нет.

Для ручной проверки отдельно запустите backend стенда и веб-клиент:

```sh
pnpm --filter @gchat/e2e backend
# В другом терминале:
GCHAT_BACKEND_URL=http://127.0.0.1:3300 pnpm --filter @gchat/web dev
```

Откройте `http://127.0.0.1:5173` в двух независимых профилях браузера и войдите разными тестовыми пользователями из README стенда. Вкладки одного профиля используют одну сессию. Перед автоматическим E2E-прогоном остановите вручную запущенные серверы на тех же портах.

## Форматирование и линтинг

Как и backend, веб-клиент использует Prettier и Oxlint из корня workspace с общими `.prettierrc.json` и `.oxlintrc.json`. Отдельные версии инструментов и копии правил в приложении не создаются. Команды ниже выполняются из корня и проверяют только веб-приложение:

```sh
pnpm --filter @gchat/web lint
pnpm --filter @gchat/web lint:fix
```

`lint` запускает Oxlint без допустимых предупреждений, затем Prettier в режиме проверки. `lint:fix` выполняет Prettier → Oxlint с исправлениями → Prettier. Форматирование включает TypeScript/TSX, CSS, HTML, JSON, YAML и Markdown. Генерируемые `dist/`, `.local/`, `test-results/`, `playwright-report/` и зависимости исключены через `.gitignore` приложения и корневой `.prettierignore`.

Инструменты можно запускать отдельно:

```sh
pnpm --filter @gchat/web format
pnpm --filter @gchat/web format:check
pnpm --filter @gchat/web style:check
pnpm --filter @gchat/web style:fix
```

Общие правила сохраняются: сортировка импортов, пустые строки между смысловыми блоками, явные возвращаемые типы TypeScript-функций; `any` и утверждения типов разрешены только в тестах. Корневой lint-staged также обрабатывает staged-файлы веб-клиента. Команды линтинга не заменяют typecheck и тесты.

## Сессия и ограничения

Один браузерный профиль использует сохранённую сессию и device binding. Токены и незавершённый запрос refresh находятся в localStorage; они доступны скриптам того же origin. Не подключайте сторонние скрипты к клиентскому origin. Web Locks сериализует ротацию и выбирает одну вкладку-владельца WSS/микрофона; BroadcastChannel передаёт остальным безопасное состояние UI. Выход из профиля действует на все его вкладки.

После перезагрузки браузер может потребовать явное включение звука. Для работы вне localhost требуется HTTPS. Оповещения доступны в открытом клиенте; Web Push, PWA, фоновый/закрытый браузер и iOS-интеграция требуют отдельных решений и проверок. Клиент рассчитан на браузеры с Web Locks, BroadcastChannel и WebRTC; текущие автоматические проверки выполняются в Chromium.

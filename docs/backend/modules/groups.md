# Groups

## Назначение и границы

Groups владеет группами и членством пользователей. Группы отображаются пользователю в приложении; навигация и устройство интерфейса находятся за рамками backend-контракта. Участники общей группы имеют взаимное разрешение по членству на звонки один на один. Групповые звонки не предусмотрены.

Группами и составом участников управляет только администратор. Текущий этап реализует схему хранения и внутреннюю проверку общего членства. Выдача данных клиенту реализована. Получение/создание нормализованной группы, административные выборки и назначение членства при создании аккаунта реализованы через GroupsService. Исходные требования — в [требованиях продукта](../../product/requirements.md).

## Публичный API

Пользовательские HTTP-маршруты реализованы в GroupsController и описаны ниже. Административными маршрутами владеет Backoffice; `GET /contacts` не вводится.

GroupsModule экспортирует GroupsService:

```ts
hasCommonGroup(firstUserId: string, secondUserId: string): Promise<boolean>
```

Метод принимает идентификаторы пользователей в формате UUID. Возвращает true, если у двух разных пользователей есть хотя бы одна общая группа; иначе false. Для одинаковых идентификаторов возвращает false без запроса к БД. Неизвестный корректный UUID не имеет членства и даёт false.

Проверяется только членство. Метод не подтверждает активность аккаунтов, действительность сессий или возможность создать звонок с учётом занятости. Эти проверки остаются обязанностью потребителей и владельцев соответствующих данных. Результат описывает состояние на момент SQL-запроса, не резервирует право на будущую операцию и не блокирует изменение членства.

### Транзакционная проверка для DirectCalls — реализовано

`lockCommonGroup(tx, firstUserId, secondUserId): Promise<boolean>` использует переданную транзакцию PostgreSQL. Выбирает одну общую группу и удерживает `FOR SHARE` на строке группы и двух строках членства до завершения транзакции потребителя. Выбор детерминирован по UUID группы и пользователей. Удаление выбранной группы/членства ждёт эти блокировки; если удаление завершилось раньше, метод использует оставшуюся общую группу либо возвращает false. Он не проверяет аккаунты, сессии и занятость.

Метод реализован отдельно от `hasCommonGroup`; последний сохраняет семантику обычного чтения. [Порядок создания звонка и потери членства](direct-calls/README.md#потеря-общего-членства--согласовано) принадлежит DirectCalls.

### Выдача клиенту — реализовано

Клиент получает данные двумя отдельными авторизованными запросами:

- Список моих групп: только группы, в которых состоит текущий пользователь.
- Список участников выбранной группы: доступен только текущему участнику этой группы. Знание UUID чужой группы не даёт права читать её участников.

Отключённые аккаунты исключаются из ответа со списком участников на backend. HTTP-маршруты и DTO реализованы в GroupsController и описаны ниже.

#### HTTP API для клиентов

Маршруты используются полноценным [веб-клиентом](../../web/README.md) и доступны другим авторизованным клиентам. Проверка пользователя принадлежит Auth.

| Запрос | HTTP 200 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `GET /groups` | `{groups: [{id: UUID, name: string}]}` — группы авторизованного пользователя. |
| `GET /groups/:group_id/members` | `{members: [{id: UUID, display_name: string}]}` — активные аккаунты участников доступной пользователю группы. |

Оба запроса используют действующий HTTP Auth; user_id текущего пользователя определяется по сессии, не принимается в query или body. Список участников включает текущего пользователя, если его аккаунт активен; клиент не предлагает звонок самому себе. Изображения профилей этими DTO не вводятся: при отсутствии аватара клиент отображает инициалы имени.

Пустой список групп — успешный ответ, а не ошибка. Неизвестная группа и группа без текущего членства пользователя возвращают одинаковый `404 NOT_FOUND`; чужой UUID не раскрывает её состав. Проверка членства и чтение участников должны использовать согласованный снимок. Некорректный UUID даёт `400 VALIDATION_ERROR`, ошибки Auth — его базовые 401, отказ зависимости — `503 SERVICE_UNAVAILABLE`. Ответы пользовательских списков не должны попадать в общий публичный кеш.

Группы сортируются PostgreSQL по name/id, участники — по display_name/id, с collation используемой БД. Возвращаются полные списки без пагинации. Веб-клиент повторяет чтение при фокусе и раз в минуту; отдельные события изменения групп не вводятся. Эти запросы не предоставляют права изменять группы и не заменяют проверку доступа DirectCalls при создании звонка.

### Создание через CLI — реализовано

Правила ниже определяют назначение группы при создании аккаунта. По новым [бизнес-требованиям бэк-офиса](../../product/backoffice.md) при создании обычного пользователя через административный API группа обязательна; при создании администратора через CLI — необязательна. Без группы администратор имеет доступ к БО, но не получает собеседников для звонков. CLI не управляет существующими аккаунтами; его параметры принадлежат Auth. Для формы создания аккаунта согласован административный поиск групп `GET /admin/groups?q=...`, независимо от членства администратора; HTTP-контракт принадлежит [Backoffice](backoffice.md#чтение). Подсказки не создают группы. Отдельное управление группами этими требованиями не вводится.

При создании аккаунта в БО или через CLI администратора группа задаётся названием; правила ниже применяются, если она указана. Если такая группа существует, новый пользователь добавляется в неё; если отсутствует — группа создаётся и пользователь добавляется в созданную группу. Перед поиском и сохранением название очищается от пробелов по краям и приводится к нижнему регистру; пустое после нормализации название отклоняется. Группы сопоставляются по нормализованному названию: `Family`, `family` и `FAMILY` обозначают одну группу. Нормализованное название должно быть уникальным, в том числе при конкурентном создании пользователей. Отдельные команды создания и переименования групп, добавления и удаления участников в текущий объём не входят. Правила создания аккаунта и CLI только для создания администраторов принадлежат [Auth](auth.md#cli).

## Правила и инварианты

- Звонки возможны только один на один; вызов всей группы отсутствует.
- Для разрешения по членству достаточно одной общей группы. Без общей группы начать звонок нельзя.
- Пользователь может состоять в нескольких группах; несколько общих групп не меняют результат проверки.
- Пользовательские данные группы пока ограничены текстовым названием. Описание и аватар не требуются.
- Обычный пользователь не получает административных прав из членства.
- При выдаче участников клиенту отключённые аккаунты (`disabled_at IS NOT NULL`) исключаются из ответа на backend. Их членство сохраняется; текущий внутренний `hasCommonGroup` по-прежнему проверяет только членство. Выдача участников реализована.

### Хранение

Схема — [groups.schema.ts](../../../applications/backend/src/groups/groups.schema.ts). Группы и членство принадлежат Groups, аккаунты — Auth. Отдельная таблица направленных разрешений не создаётся.

- `gchat_groups`: UUID `id` с генерацией в БД, обязательное текстовое `name`.
- `gchat_group_members`: `group_id`, `user_id`; составной первичный ключ запрещает повторное членство.
- Внешние ключи исключают ссылки на несуществующие группы и аккаунты. Удаление группы или аккаунта каскадно удаляет соответствующее членство; удаление группы не удаляет аккаунты.
- Индекс по `user_id` поддерживает поиск членства пользователя.

Схема требует непустого нормализованного названия и его уникальности; ограничения добавлены миграцией `0004_backoffice.sql`. Существующие ненормализованные или повторяющиеся названия не объединяются автоматически: такая миграция завершится ошибкой без изменения данных. Пустая группа (без участников) допустима.

## Зависимости и регистрация

GroupsModule — обычный NestJS-модуль без `@Global()`, `forRoot()` и `forFeature()`. Импортирует DatabaseModule, регистрирует GroupsRepository и GroupsService, экспортирует только GroupsService. Репозиторий получает DatabaseService и глобальный ErrorService через DI.

Потребители импортируют GroupsModule непосредственно. GroupsModule импортируется DirectCallsModule; публичный GroupsController использует AuthGuard. Подключение схемы к генератору миграций не зависит от импортов NestJS.

## Ошибки и частичное выполнение

Проверка выполняет один запрос чтения без кеширования и побочных эффектов. Отказ PostgreSQL не превращается в false: ожидаемые ошибки соединения, ресурсов и таймаутов преобразуются через ErrorService в SERVICE_UNAVAILABLE. Неожиданные ошибки передаются выше без подмены результата. Общий формат — в [Error](errors.md).

Создание аккаунта и его членства атомарно в PostgreSQL по [Auth](auth.md#cli) и Backoffice; неизвестный результат COMMIT не разрешает слепой повтор. Миграция применяется стандартным [мигратором](../operations/migrations.md), а не при запуске HTTP-сервера.

## Конфигурация

Собственных переменных нет. Подключение PostgreSQL и бюджеты запросов принадлежат [Database](database.md).

## Критерии приёмки и проверки

- Создание пользователя через БО либо администратора через CLI при заданной группе использует нормализованное название группы (пробелы по краям удалены, нижний регистр); пустое название отклоняется. Существующая группа переиспользуется, отсутствующая создаётся; конкурентное создание не порождает дубликаты групп. Реализация использует UNIQUE и INSERT ON CONFLICT в переданной транзакции.
- Общее членство даёт true в обоих направлениях, отсутствие общего членства — false.
- Сам себе пользователь позвонить не может: проверка возвращает false.
- После удаления одного общего членства доступ сохраняется, если осталась другая общая группа. После удаления последнего — следующая проверка возвращает false.
- Дубликаты членства и ссылки на несуществующие записи запрещены БД.
- Удаление группы удаляет членство, сохраняя аккаунты.
- Отказ БД не выдаётся за отсутствие разрешения.
- Список моих групп содержит только группы текущего пользователя; список участников выбранной группы доступен только её участнику. Эти запросы реализованы.
- Ответ со списком участников не содержит отключённых аккаунтов; фильтрация выполняется на backend без удаления членства. Этот критерий реализован.

Unit-тесты расположены рядом с модулем; административные выборки и конкурентное создание проверяются также в `test/backoffice.integration.spec.ts`. `test/groups.integration.spec.ts` включается только через GROUPS_INTEGRATION_DATABASE_URL, создаёт отдельную временную БД, применяет миграции повторно и удаляет БД после проверки. Тестовому пользователю нужны права создания и удаления БД. Без явного URL интеграционные тесты пропускаются. Команды проверок — в [README backend](../../../applications/backend/README.md#сборка-и-проверки).

## Открытые решения

- При необходимости больших групп отдельно спроектировать пагинацию; текущий API возвращает полные списки. Нагрузочная проверка больших списков не выполнена.
- Проверка членства при конкурентном создании звонка реализована через `lockCommonGroup`; её реализация относится к интеграции с [DirectCalls](direct-calls/README.md#потеря-общего-членства--согласовано), не к текущему методу чтения.

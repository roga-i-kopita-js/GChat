# Error

## Назначение и границы

ErrorModule стандартизирует выброс исключений из сервисов и их обработку на глобальном уровне. Он предоставляет базовый класс исключения `AppError` и внедряемую фабрику `ErrorService`. Сервис получает фабрику через конструктор и выбрасывает созданное исключение через `throw this.error.rateLimited({...payload})`. Глобальный HTTP-фильтр перехватывает исключение и формирует статус, заголовки и тело ответа в общем формате.

Бизнес-модуль определяет условие отказа, публичный код и безопасное сообщение. Контроллеры не дублируют обработку через `try/catch` для формирования ответа.

В объём входят базовый класс ошибки, внедряемая фабрика ErrorService, глобальный фильтр исключений, согласованное оформление ошибок валидации и стандартных ошибок HTTP. Входные DTO валидируются встроенным NestJS `ValidationPipe` с `class-validator`. ErrorModule оформляет результат валидации, а бизнес-проверки остаются в сервисах.

Логирование выполняется через [LoggerModule](logger.md); HTTP-фильтр пишет безопасные события 5xx. Идентификатор запроса для корреляции не вводится. Поле `request_id` в запросе `/auth/refresh` остаётся ключом идемпотентности Auth и не связано с корреляцией логов.

## Публичный API

### Использование в сервисах

#### Базовый класс и использование в сервисах

`AppError` наследует `Error` и содержит HTTP-статус, публичный код и безопасное сообщение; для валидации — описания полей. Для ограничения частоты поддерживается значение `retryAfterSeconds`, которое фильтр преобразует в `Retry-After`. Внутренняя причина может храниться отдельно и не сериализуется в ответ.

Согласованный интерфейс использования:

```ts
@Injectable()
export class AuthService {
  constructor(private readonly error: ErrorService) {}

  checkLimit(retryAfterSeconds: number) {
    throw this.error.rateLimited({
      message: 'Слишком много попыток. Попробуйте позже.',
      retryAfterSeconds,
    });
  }
}
```

Методы внедряемого `ErrorService` возвращают новый экземпляр `AppError`, а не выбрасывают его самостоятельно. `rateLimited(payload)` фиксирует HTTP 429 и код `RATE_LIMITED`; payload содержит безопасное сообщение и параметры ошибки. Фиксированные статус и код не переопределяются через payload. Внутренняя причина и служебные параметры не копируются в JSON-ответ автоматически. Фабрики `invalidCredentials`, `accessTokenExpired`, `accessTokenInvalid`, `sessionInvalid`, `forbidden`, `notFound`, `serviceUnavailable` и `internal` принимают необязательные `message` и `cause`. `validation` дополнительно принимает `fields`; `rateLimited` требует целое неотрицательное `retryAfterSeconds`. Для новых публичных кодов предусмотрен `create({ status, code, message, ... })`.

ErrorModule не зависит от Auth или других бизнес-модулей и не содержит их условий отказа. Сервис не формирует HTTP-ответ и не обращается к объекту response.



### Формат HTTP-ответа

HTTP-статус передаётся статусом ответа. Тело:

```json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Не удалось войти. Проверьте логин и пароль."
  }
}
```

`code` — стабильный машинный код в UPPER_SNAKE_CASE. Клиент принимает решения по HTTP-статусу и коду, а не по тексту. `message` — безопасное пояснение; его формулировка не является машинным контрактом. Локализованные тексты интерфейса может формировать клиент.

Для `VALIDATION_ERROR` используется дополнительный массив `fields`, если ошибка относится к конкретным полям:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте введённые данные.",
    "fields": [
      { "field": "login", "code": "INVALID_FORMAT" }
    ]
  }
}
```

Ошибки всего тела, включая некорректный JSON, возвращаются без `fields`. Значения входных данных в ответ не включаются. Имена полей берутся из известного контракта запроса. Общего поля для произвольных внутренних подробностей нет.

### Коды и HTTP-статусы

| HTTP | Код | Назначение |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | Некорректное тело или параметры запроса |
| 401 | `INVALID_CREDENTIALS` | Отказ входа по правилам Auth |
| 401 | `ACCESS_TOKEN_EXPIRED` | Истёк срок access token |
| 401 | `ACCESS_TOKEN_INVALID` | Access token отсутствует или недействителен |
| 401 | `SESSION_INVALID` | Сессия или refresh token недействительны по правилам Auth |
| 403 | `FORBIDDEN` | Нет права выполнить действие |
| 404 | `NOT_FOUND` | Маршрут или разрешённый к раскрытию ресурс не найден |
| 429 | `RATE_LIMITED` | Превышен лимит; заголовок `Retry-After` содержит число секунд |
| 500 | `INTERNAL_ERROR` | Неожиданная внутренняя ошибка |
| 503 | `SERVICE_UNAVAILABLE` | Временная недоступность зависимости или блокировки |

Коды Auth сохраняют смысл, определённый в [спецификации Auth](auth.md). Бизнес-модули могут добавлять коды с документированными HTTP-статусами. Наличие ресурса и существование аккаунта не раскрываются там, где это запрещено правилами модуля.

## Правила и инварианты

### Валидация DTO

Глобальный `ValidationPipe` проверяет DTO через декораторы `class-validator`. Его `exceptionFactory` преобразует ошибки проверки в `AppError` со статусом 400, кодом `VALIDATION_ERROR` и списком полей. Далее ответ формирует тот же глобальный фильтр. Сам фильтр повторно данные не валидирует. Включены `transform: true`, `whitelist: true` и `forbidNonWhitelisted: true`; неявное преобразование примитивов не включается. Неизвестные свойства отклоняются, их имена и значения не возвращаются. Для вложенных DTO нужны декораторы `@ValidateNested()` и `@Type()` из class-transformer. Пути вложенных полей разделяются точкой, например `profile.login` или `contacts.0.login`.

Элементы `fields` содержат `field` и `code`. Сообщения декораторов class-validator не публикуются, значения и DTO не включаются в ответ.

| Ограничение class-validator | Код поля |
| --- | --- |
| `isDefined`, `isNotEmpty` | `REQUIRED` |
| `minLength` | `TOO_SHORT` |
| `maxLength` | `TOO_LONG` |
| `isLength` | `INVALID_LENGTH` |
| Остальные ограничения | `INVALID_FORMAT` |

Одинаковые коды одного поля не дублируются. Неизвестные свойства приводят к `VALIDATION_ERROR` без раскрытия их имён; если ошибок известных полей нет, `fields` отсутствует.

Стандартные HTTP-исключения Nest со статусами 400, 401, 403, 404, 429, 500 и 503 получают соответствующий код из таблицы раздела 3 и безопасное стандартное сообщение. Остальные HTTP-статусы сохраняются с кодом `HTTP_ERROR`. Исходные сообщения и тела исключений не копируются. Для 429 с известной задержкой сервис использует `rateLimited`, чтобы вернуть `Retry-After`.

## Зависимости и регистрация

ErrorModule объявляется глобальным через `@Global()` и импортируется один раз в AppModule. Повторный импорт в бизнес-модулях не требуется. `ErrorService` объявляется через `@Injectable()`, регистрируется в `providers` и экспортируется из ErrorModule. Бизнес-сервисы получают его через конструктор: `constructor(private readonly error: ErrorService) {}`. `AppError` остаётся классом исключения и не регистрируется как провайдер.

Глобальный фильтр зависит от LoggerService, зарегистрированного через LoggerModule.forRoot() в корневом модуле.

## Ошибки и частичное выполнение

### Глобальный фильтр

Глобальный HTTP-фильтр регистрируется один раз внутри ErrorModule через `APP_FILTER`. Правила обработки:

1. Известная публичная ошибка приложения преобразуется в согласованный формат.
2. Ошибки валидации и разбора JSON преобразуются в 400 `VALIDATION_ERROR`.
3. Стандартные HTTP-исключения Nest преобразуются в общий формат по явно заданному соответствию. Произвольное тело исключения не копируется. Для статусов без специального кода применяется `HTTP_ERROR` с безопасным стандартным сообщением и исходным HTTP-статусом.
4. Неизвестное исключение возвращает 500 `INTERNAL_ERROR` с нейтральным сообщением.

Драйверные ошибки PostgreSQL и Redis не превращаются автоматически в 503 по тексту исключения. Модуль-потребитель распознаёт ожидаемый отказ зависимости и преобразует его в публичную ошибку. Неожиданная ошибка остаётся 500.

Аналогично Auth преобразует `LockError` в 503 по своему контракту. Внутренние `LOCK_*` и `mayHaveExecuted` не публикуются автоматически. Ответ 503 не обещает, что изменений не было, и не разрешает слепой повтор операции; правила повтора определяет её контракт.

В HTTP-ответ не попадают stack trace, SQL, URL подключений, секреты, токены, входное тело или исходные сообщения драйверов. Ответы Auth с ошибками получают `Cache-Control: no-store`.

### Healthcheck, CLI и WebSocket

`GET /health` и `GET /ready` сохраняют текущий контракт. В частности, 503 readiness возвращает `status`, `service` и `checks`, без оболочки `error`. Исключение реализуется явно для healthcheck, а не общим разрешением возвращать произвольные тела исключений.

HTTP-фильтр не обрабатывает CLI и WebSocket. CLI показывает безопасный результат и завершается с ненулевым кодом при ошибке; общий формат машинного вывода CLI здесь не вводится. Формат ошибок WebSocket-команд и коды закрытия определяются отдельно при описании Signaling с использованием тех же публичных кодов там, где совпадает смысл.

## Конфигурация

Отдельных переменных окружения нет. ValidationPipe и APP_FILTER регистрируются в ErrorModule. Формат логирования задаётся [Logger](logger.md).

## Критерии приёмки и проверки

- Публичные ошибки Auth возвращают согласованные статусы и коды.
- ErrorModule регистрируется глобально один раз; бизнес-модули не импортируют его повторно.
- ErrorService доступен через внедрение в конструктор без повторного импорта ErrorModule.
- Фабрика `this.error.rateLimited(payload)` возвращает новый `AppError` с HTTP 429 и кодом `RATE_LIMITED`; исключение выбрасывает вызывающий сервис через `throw`.
- `AppError`, выброшенный непосредственно из сервиса, обрабатывается глобально без ручного преобразования в контроллере.
- Ошибки DTO из NestJS `ValidationPipe` с `class-validator` проходят через тот же формат ответа.
- Некорректный JSON и ошибки входных полей получают общий формат 400.
- Неизвестный маршрут возвращает 404 в общем формате.
- Неожиданное исключение возвращает безопасный 500 без внутренних подробностей.
- Ожидаемые ошибки зависимостей преобразуются потребителем в 503; ошибки программирования не маскируются под сбой зависимости.
- 429 сохраняет `Retry-After`, ошибки Auth — `Cache-Control: no-store`.
- Тела и статусы healthcheck сохраняются, включая отказ одной или обеих зависимостей.
- HTTP-фильтр не изменяет обработку CLI и WebSocket.

`test/error.e2e.spec.ts` проверяет глобальное внедрение в отдельный модуль-потребитель, выброс из сервиса, заголовки, фабрики, скрытие внутренних причин, вложенную валидацию, неизвестные свойства, некорректный JSON и 404. Существующие HTTP-тесты проверяют сохранение контракта healthcheck.

## Открытые решения

Формат ошибок WebSocket и правила завершения CLI определяются при реализации соответствующих потребителей. Публичные коды новых бизнес-модулей добавляются вместе с их контрактами.

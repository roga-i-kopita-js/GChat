# Backoffice

## Назначение и границы

Проект технического решения для [бизнес-требований бэк-офиса](../../product/backoffice.md). Статус: согласовано, готово к реализации. Административные маршруты, роли и описанные внутренние методы пока отсутствуют. Правила хранения, паролей и сессий находятся в Auth; правила групп и членства — в Groups. Согласованный будущий контракт не означает наличия реализации.

Бэк-офис реализуется обычным `BackofficeModule` внутри существующего NestJS backend. Отдельный сервис, база, система аккаунтов и авторизация не вводятся. Раздел существующего веб-клиента обращается к административному HTTP API с Bearer access token GChat. CLI оставляется только для создания новых аккаунтов с ролью `admin`, включая первого администратора. Создание обычных пользователей, смена их паролей, отключение и включение через CLI не предусматриваются. Реализация веб-интерфейса в этот технический объём не входит; контракт узкого CLI определяется в Auth.

Модуль предоставляет административные сценарии и собирает ответы. Auth сохраняет владение аккаунтами, ролями, паролями и сессиями; Groups — группами и членством. Административная роль не меняет права обычных маршрутов групп и звонков.

В объём входят чтение аккаунтов, создание с назначением одной группы, смена пароля, отключение и включение. Изменение имени/логина, удаление, самостоятельное управление группами, аудит, массовые операции и устойчивый журнал выполнения не добавляются.

### Основание и текущее состояние

- В [Auth](auth.md#cli) приняты валидация, генерация данных входа и последовательности административных операций; их реализации пока нет. В `AuthSessions` есть операции одной сессии, но нет массового отзыва.
- `AuthService.authenticate` проверяет актуальный аккаунт и сессию. Роли нет ни в схеме аккаунта, ни в `AuthIdentity`, ни в JWT.
- Groups уже выдаёт группы пользователя и участников. Эти маршруты ограничены членством и не подходят для административного обзора. Административные выборки добавляются отдельно по правилам владельца.
- Уникальность нормализованного имени группы принята в Groups, но пока отсутствует в схеме. Её миграция необходима для создания аккаунта через API.

## Публичный API

### Общие правила

Префикс — `/admin`. Все маршруты защищены последовательно `AuthGuard` и `AdminGuard`. Клиент не передаёт роль исполнителя, его UUID или ID сессии в теле. Личность берётся из проверенной сессии. UUID в пути обозначает целевой аккаунт.

DTO и Swagger оформляются по [соглашениям backend](../conventions.md). Неизвестные поля отклоняются; `null` не заменяет отсутствующее необязательное поле. Все ответы, включая ошибки, получают `Cache-Control: no-store`. Секреты не передаются в URL.

### Чтение

Согласован маршрут карточки `GET /admin/users/:user_id` с ответом 200 `{user: AdminUser}`. Доступ разрешён только действующему администратору. Для неизвестного корректного UUID возвращается `404 NOT_FOUND` после проверки доступа, для некорректного UUID — `400 VALIDATION_ERROR`. Обычный пользователь не получает сведения о существовании целевого аккаунта.

| Запрос | Результат HTTP 200 |
| --- | --- |
| `GET /admin/users?q=...&status=all&limit=25&offset=0` | `{users: AdminUser[], total: number}` |
| `GET /admin/users/:user_id` | `{user: AdminUser}` |
| `GET /admin/groups?q=...&limit=20&offset=0` | `{groups: [{id, name}], total: number}` — подсказки при создании |

Согласованный `AdminUser`: `{id, login, display_name, role, status, disabled_at, groups: [{id, name}], created_at, updated_at}`. Время — строка ISO 8601 в UTC, `disabled_at` допускает `null`. `status` вычисляется backend из того же значения `disabled_at`: `active`, если оно равно `null`, иначе `disabled`. Отдельная колонка статуса в БД не создаётся; клиент не задаёт статус в теле запроса. Значения `all` в ответе нет — оно используется только в фильтре. Вычисляемый статус возвращается в списке, карточке и ответах после изменений. Пароль, хеш и данные сессий отсутствуют. Список включает аккаунты вне групп администратора и отключённые аккаунты. Все группы аккаунта возвращаются в каждой строке; отсутствие групп — `[]`.

Параметры списка аккаунтов:

- `q`: необязательная строка до 80 символов после trim; пустая строка не ограничивает результат. Согласован поиск по подстроке без учёта регистра по имени или логину: `андр` находит `Андрей`. `%` и `_` трактуются буквально.
- `status`: `all | active | disabled`, по умолчанию `all`. Активность определяется только `disabled_at IS NULL`.
- Согласованный `limit`: целое от 1 до 100, по умолчанию 25 для аккаунтов; `offset`: неотрицательное целое, по умолчанию 0. Числовые query-параметры преобразуются явно и валидируются.
- Согласована сортировка по возрастанию: аккаунты — `display_name ASC, id ASC`, группы — `name ASC, id ASC`, с collation БД. ID задаёт однозначный порядок при одинаковых именах или названиях; это относится и к группам внутри `AdminUser`, и к подсказкам групп. `total` считается после фильтрации, до пагинации.

Список и `total`, включая группы строк, читаются в одном согласованном снимке PostgreSQL. Пагинация применяется к аккаунтам до объединения с членством, иначе несколько групп исказят страницу. Между запросами страницы состав может измениться; стабильный снимок на время просмотра не обещается. Пустая страница — 200 с пустым массивом.

Согласован `GET /admin/groups` для подсказок существующих групп при вводе названия. Если введено новое название, форма предупреждает о создании группы вместе с аккаунтом. Для подсказок групп согласован `limit` от 1 до 100, по умолчанию 20; `offset` по умолчанию 0. Ограничения `q` и `offset` те же, что для аккаунтов; поиск выполняется по названию группы. Неверный `limit`, включая 0 и значения больше 100, даёт `400 VALIDATION_ERROR`, без молчаливого обрезания до границ. Подсказки не создают группу; окончательное решение о переиспользовании принимается при создании аккаунта по правилам Groups. Если подсказка не найдена, это не гарантирует отсутствие конкурентно созданной группы.

### Изменения

Маршруты изменяющих операций согласованы: каждое действие выполняется отдельным POST-запросом. Общий маршрут редактирования аккаунта не вводится. Согласован единый формат успешного ответа `{user: AdminUser}` для всех четырёх операций; пароль, хеш и данные сессий в него не входят.

| Запрос | Тело | Успех |
| --- | --- | --- |
| `POST /admin/users` | `{display_name, group_name, login?, password}` | 201: `{user: AdminUser}` |
| `POST /admin/users/:user_id/password` | `{password}` | 200: `{user: AdminUser}` |
| `POST /admin/users/:user_id/disable` | `{}` | 200: `{user: AdminUser}` |
| `POST /admin/users/:user_id/enable` | `{}` | 200: `{user: AdminUser}` |

Ответ `user` описывает состояние аккаунта в транзакции успешно выполненной операции. DTO собирается в согласованном снимке этой транзакции и отправляется только после подтверждённого COMMIT. Это позволяет обновить карточку без отдельного запроса чтения. Последующие конкурентные операции могут изменить аккаунт; ответ не резервирует его состояние. При смене собственного пароля ответ успешной операции возвращается после отзыва сессий, а следующие защищённые запросы требуют нового входа.

Отсутствие `login` включает серверную генерацию по [Auth](auth.md#cli). `password` обязателен: браузер генерирует его криптографически стойким генератором либо администратор задаёт его вручную. Отсутствующий или пустой пароль отклоняется; сервер пароль не генерирует. Валидация имени, логина и пароля остаётся в Auth, названия группы — в Groups. Проверка выполняется до первого изменения. Явный занятый логин даёт 409 `LOGIN_TAKEN`; при коллизии сгенерированного логина генерация повторяется с ограниченным числом попыток, исчерпание — 503.

Пароль не включается в тело ответа ни при создании аккаунта, ни при смене пароля. Повторного GET для получения пароля нет. Браузер хранит отправленное значение только в памяти и показывает его для копирования после подтверждённого успеха. При закрытии окна результата значение очищается; повторно получить его с backend нельзя. При ошибке или неизвестном результате нельзя показывать пароль как подтверждённо установленный. Правила генерации и хранения значения на клиенте относятся к веб-контракту; правила валидации и хеширования — к Auth.

Согласовано: повторный disable уже отключённого аккаунта повторяет очистку оставшихся сессий и результатов ротации, сохраняет исходный `disabled_at` и возвращает 200 с `{user}` после подтверждённого COMMIT. Повторный enable активного аккаунта возвращает 200 с `{user}` без отзыва новых сессий. Состояние «уже включён/отключён» не является ошибкой. Повтор проходит обычные проверки сессии и прав исполнителя; запрет самоотключения сохраняется. Повтор создания или смены пароля является новой операцией. Заголовок идемпотентности и сохранение ответа для повторной выдачи не вводятся. После неизвестного результата автоматический повтор запрещён.

## Правила и инварианты

### Роли и проверка доступа

Роль хранится в аккаунте по [контракту Auth](auth.md#аккаунт). БО создаёт обычный аккаунт `user`, CLI — администратора `admin`; поле роли в запросе создания через API не принимается.

Auth добавляет `role` в JWT при login и новой ротации refresh, а также в `AuthIdentity`. Согласовано: подписанный JWT доступен для чтения владельцу; «непубличная» роль означает отсутствие в обычных данных о других пользователях. Роль видна в собственном JWT и административных DTO, но не добавляется в DTO участников групп.

Согласовано: `AdminGuard` использует актуальную роль аккаунта, прочитанную Auth из PostgreSQL при проверке запроса, а не claim предъявленного JWT. Auth передаёт эту роль в проверенной личности `AuthIdentity`; отдельное чтение аккаунта только ради роли не требуется. Claim в JWT используется клиентом для отображения раздела, но сам по себе не разрешает административные операции. Роль задаётся при создании аккаунта; повышение и понижение существующих аккаунтов в текущий объём не входят.

Проект ещё не вышел в production. Перенос существующих аккаунтов, совместимость с JWT прежнего формата и поэтапное развёртывание старой и новой версий в объём этого решения не входят.

### Создание администраторов — только CLI

CLI backend выполняет только создание нового аккаунта с ролью `admin`, включая первого администратора. Назначение/снятие роли существующего аккаунта, смена пароля, отключение и включение через CLI не предусматриваются. Создание обычных пользователей выполняется через бэк-офис.

CLI запускается оператором с доступом к окружению backend и использует внутренние сервисы Auth. Действующая административная HTTP-сессия не требуется. CLI не запускается при старте сервера и не читает список администраторов из `.env`. Пароль вводится скрыто, без аргумента командной строки; правила валидации и хеширования остаются в Auth. Параметры согласованы в [Auth](auth.md#cli): обязательные явно заданные имя и логин, скрытый интерактивный ввод пароля, необязательное название группы; роль всегда `admin`. Без группы администратор может работать в БО, но не получает собеседников для звонков.

HTTP-операции смены роли и создания администратора не вводятся. Администратор может отключить другого администратора через бэк-офис; его роль и членство сохраняются, сессии отзываются по правилам Auth. Самоотключение запрещено: backend сравнивает UUID цели с UUID исполнителя из проверенной сессии и возвращает 403 `FORBIDDEN` до любых изменений при совпадении. Скрытие кнопки в интерфейсе не заменяет эту проверку.

При встречных отключениях администраторов побеждает операция, первой получившая общую блокировку административного доступа в PostgreSQL и успешно зафиксировавшая отключение. Ожидающая операция повторно проверяет актуальные активность и роль исполнителя, а также действительность его сессии, после получения блокировки и до изменений. Если исполнителя уже отключили, операция отклоняется по правилам Auth. Проверки только в HTTP guard недостаточно. Если первая операция не зафиксировала отключение, следующая может продолжить после повторных проверок.

Другой действующий администратор может повторно включить отключённого администратора через `POST /admin/users/:user_id/enable`. Включение и отзыв старых сессий с результатами ротации выполняются одной транзакцией PostgreSQL; при её откате аккаунт остаётся отключённым. Роль, пароль и членство сохраняются. После успеха требуется новый вход с текущим паролем, старые сессии не восстанавливаются.

Администратор может сменить через БО пароль себе или другому администратору через `POST /admin/users/:user_id/password`. Все сессии целевого аккаунта отзываются, при смене собственного пароля требуется новый вход. Отключённый до операции аккаунт остаётся отключённым.

Если административный доступ потерян, оператор может создать нового администратора через CLI. Изменение пароля или включение прежнего аккаунта не являются функциями CLI.

### Создание аккаунта и группы

Создание выполняется одной транзакцией PostgreSQL: аккаунт, получение/создание нормализованной группы, членство. Хеширование пароля выполняется до транзакции через AuthCrypto с общим лимитом операций Argon2. Redis при создании не используется, сессия новому пользователю не выдаётся.

Auth и Groups принимают переданную транзакцию через внутренние методы. Backoffice координирует её, не выполняя собственные INSERT/UPDATE в чужие таблицы. Группа создаётся через уникальное ограничение и обработку конфликта, а не через незащищённое «проверить, затем вставить». Конфликт группы не отменяет создание пользователя: используется существующая группа.

Схема должна обеспечивать непустое нормализованное имя группы и его уникальность. Перенос и объединение старых групп не проектируются. Изменения схемы выполняются штатным [мигратором](../operations/migrations.md); уже применённые миграции не редактируются.

### Смена пароля, отключение и включение

Применяются [транзакционные правила Auth](auth.md#последовательности-административных-операций). Сессии и результаты ротации переносятся в PostgreSQL. Backoffice не реализует второй алгоритм отзыва. Смена пароля, отключение и включение атомарны с отзывом сессий; успех возвращается только после подтверждённого COMMIT. Смена пароля сохраняет `disabled_at` без временного отключения аккаунта.

WS-билеты и ограничение их выдачи также переносятся в PostgreSQL по контракту Auth. Билет не даёт доступ после удаления связанной сессии. Поведение сигнализации и активного аудио остаётся в Auth и DirectCalls.

### Конкурентность — согласованное направление

[Auth](auth.md#конкурентные-операции) координирует login, refresh и отзыв блокировками строк аккаунтов и сессий внутри PostgreSQL-транзакций. Длительные блокировки на выделенных соединениях между PostgreSQL и Redis и `auth_version` не вводятся. Последний результат ротации хранится в строке сессии по контракту Auth. Очистка принадлежит Auth: согласован `@nestjs/schedule` с запуском раз в минуту и Redlock для координации процессов и ограниченными SQL-пачками; Целевая SQL-схема двух таблиц определена в Auth; реализация пока отсутствует.

Встречные отключения администраторов сериализуются общей транзакционной advisory-блокировкой PostgreSQL: `pg_advisory_xact_lock(1195591745, 1)`, где первый компонент резервирует пространство GChat, второй обозначает административное отключение. Значение — константа backend, не параметр клиента или переменная окружения. Она берётся до блокировок конкретных аккаунтов. Повторная проверка актуального аккаунта и сессии исполнителя, запрет самоотключения, запись `disabled_at` и отзыв сессий цели выполняются в одной транзакции. После COMMIT отключённый исполнитель уже не может выполнить встречное отключение, даже если прошёл HTTP guard раньше. При подтверждённом откате первой операции следующая может продолжить после повторных проверок.

Все захваты освобождаются завершением транзакции. Бюджеты PostgreSQL берутся из Database; новые значения таймаутов не вводятся без необходимости. CLI только создаёт новых администраторов и не меняет доступ существующих.

## Зависимости и регистрация

`BackofficeModule` — обычный NestJS-модуль в AppModule; импортирует AuthModule, GroupsModule и DatabaseModule. Регистрирует BackofficeController, BackofficeService и AdminGuard. ErrorService и LoggerService получает через существующий DI. Новых `forRoot()` и глобальных модулей нет.

Разделение внутренних интерфейсов; точные TypeScript-сигнатуры оформляются при реализации по контрактам владельцев:

| Владелец | Дополнение |
| --- | --- |
| Auth | Актуальная роль в личности и JWT; административное чтение безопасной проекции аккаунтов; создание аккаунта в переданной транзакции; генерация данных; смена пароля/disable/enable; массовый отзыв и протокол блокировок; CLI создания администраторов. |
| Groups | Административные подсказки групп; чтение всех групп набора аккаунтов; получение/создание нормализованной группы и членства в переданной транзакции. |
| Backoffice | HTTP DTO, проверка административной роли, координация создания, сборка административных ответов и пагинации. |

Backoffice не получает AuthRepository/AuthSessions через обход экспорта модуля. Чтение страницы аккаунтов и её групп использует один переданный снимок, без отдельной выборки для каждой строки. Auth не импортирует Backoffice или Groups, чтобы не создавать цикл зависимостей. Groups продолжает применять обычный AuthGuard к клиентским маршрутам.

## Ошибки и частичное выполнение

Оболочка ошибок и фабрики принадлежат [Error](errors.md). До проверки прав нельзя читать целевой аккаунт или возвращать сведения о его существовании.

| HTTP / code | Условие |
| --- | --- |
| 400 `VALIDATION_ERROR` | Ошибочные UUID, DTO, query, пустые нормализованные значения. |
| 401, коды Auth | Отсутствующий/просроченный токен, недействительная сессия. Операция не начата, если guard отказал. |
| 403 `FORBIDDEN` | Исполнитель не администратор либо пытается отключить собственный аккаунт. |
| 404 `NOT_FOUND` | Администратор запросил неизвестный аккаунт. |
| 409 `LOGIN_TAKEN` | Явный логин занят, без создания аккаунта и членства. |
| 503 `SERVICE_UNAVAILABLE` | Отказ зависимости, исчерпание попыток генерации или бюджета ожидания блокировки. Потеря подтверждения COMMIT может оставить результат неизвестным. |
| 500 `INTERNAL_ERROR` | Неожиданная ошибка; также не гарантирует отсутствия изменений. |

Создание атомарно внутри PostgreSQL, но потеря подтверждения COMMIT оставляет результат неизвестным. Список/карточка помогают проверить наличие аккаунта; пароль повторно получить нельзя. Если он утрачен, требуется отдельная подтверждённая смена пароля. При сгенерированном и утраченном логине поиск по имени не даёт строгой идентификации новой записи; неизвестный результат не разрешает слепое повторное создание.

При подтверждённом откате смена пароля/отключение/включение не изменяют аккаунт и сессии. При потере подтверждения COMMIT результат неизвестен; карточка показывает состояние доступа, но не доказывает установку конкретного пароля. Автоматический повтор запрещён. Требуются проверка и явное решение администратора о следующем действии.

Все клиенты должны отключить автоматические повторы изменяющих запросов при сетевом сбое/5xx. Допустим однократный повтор после `ACCESS_TOKEN_EXPIRED`, полученного от guard до начала операции, с предварительным refresh по контракту Auth. Разрыв HTTP не является командой отмены уже начатой операции.

Логи и диагностика не содержат DTO целиком, пароли, хеши или токены. HTTP body/response logging не включается для этих маршрутов. Аудит административных действий не вводится через обычные логи под видом гарантированного журнала.

## Конфигурация

Отдельных аккаунтов, подключения к БД, ключей JWT и pepper бэк-офис не имеет. Используются существующие настройки владельцев. Секрет первого администратора в `.env` не добавляется.

Для транзакций и блокировок используются бюджеты [Database](database.md). Доступ через браузер использует существующую политику CORS и Bearer token; cookie-сессии не вводятся.

## Критерии приёмки и проверки

Это план будущих проверок; тестов Backoffice пока нет.

- HTTP-проверки всех административных маршрутов: отсутствие сессии — 401, обычный пользователь — 403 до чтения цели; отключённый администратор теряет доступ. Подделка claim роли не даёт прав.
- Актуальная роль БД определяет доступ даже со старым JWT; login/refresh выпускают актуальную роль, а идемпотентный повтор refresh сохраняет исходную пару.
- В каждом `AdminUser` статус согласован с `disabled_at`: `active` только при `null`, иначе `disabled`. Проверяются список, карточка, создание, смена пароля, отключение/включение и их повторы; в схеме нет отдельного статуса.
- Для аккаунтов проверяется размер страницы по умолчанию 25, для подсказок групп — 20; оба маршрута принимают `limit` от 1 до 100 и отклоняют значения за границами.
- Список и карточка видят отключённые аккаунты вне групп администратора, все членства и ни одного сессионного секрета. Проверяются поиск по части имени и логина без учёта регистра (в том числе `андр` → `Андрей`), буквальные `%`/`_`, фильтры, пустые результаты, границы пагинации и согласованность `total`.
- Подсказки групп доступны администратору независимо от его членства, не создают группу и не требуют прав на отдельное управление группами. Форма предупреждает о создании новой группы; конкурентное создание той же группы корректно переиспользует её.
- Создание нормализует данные по владельцам, генерирует логин при необходимости и принимает обязательный пароль, атомарно сохраняет аккаунт и членство. Конкурентное создание с одной группой не дублирует группу; занятый явный логин не оставляет лишних записей.
- Смена пароля отзывает все сессии и результаты ротации, сохраняет исходное отключение; проверяются обычный пользователь, другой администратор и собственный аккаунт администратора с обязательным новым входом; disable/enable не восстанавливают старый доступ. Проверяются несколько устройств и ранее выданный WS-билет.
- Повторный disable отключённой цели возвращает 200, сохраняет время отключения и удаляет оставшиеся сессии с результатами. Повторный enable активной цели возвращает 200 и сохраняет её новые сессии. Недействительная сессия исполнителя не обходится повтором.
- Барьерные интеграционные тесты гонок login/refresh с disable, enable и password: поздняя запись не создаёт пригодную старую сессию после включения. Конкурентные изменения одной цели сериализуются.
- Откат PostgreSQL, потеря подтверждения COMMIT и завершение процесса не дают ложного успеха. Проверяются атомарность аккаунта и отзыва сессий, освобождение транзакционных блокировок и ограничение ожидания.
- Схема допускает только роли `user | admin` и обеспечивает ограничения нормализованных названий групп. CLI проверяется отдельно: создаёт новый аккаунт администратора и не предоставляет других операций. Отключение другого администратора через API отзывает его сессии. Другой действующий администратор может включить его через API: роль, пароль и группы сохраняются, старые сессии не восстанавливаются; откат транзакции включения оставляет аккаунт отключённым. Попытка самоотключения, включая прямой запрос к API, возвращает 403 без изменения аккаунта и сессий. При одновременных встречных отключениях только одна операция фиксирует отключение; другая обнаруживает отключённого исполнителя и не изменяет цель. При откате первой транзакции вторая может выполниться после повторных проверок.
- Успешные и ошибочные ответы имеют `no-store`; пароли отсутствуют в телах всех ответов, секреты отсутствуют в логах, ошибках и обычных DTO групп. После сборки проверяется сгенерированный OpenAPI.

Порядок реализации: схема и транзакции Auth, WS-билеты и cron-очистка, внутренние методы Auth/Groups и CLI создания администратора, затем Backoffice API. Каждая часть реализуется с относящимися проверками; до этого статусы реализации не меняются. Веб подключается после проверки контракта API. Команды code-check — в [README backend](../../../applications/backend/README.md#сборка-и-проверки), документации — `pnpm docs:check` из корня.

## Открытые решения

Открытых продуктовых и архитектурных вопросов в согласованном объёме нет. Правила API, ролей, CLI, операций с администраторами, повторов и неизвестного результата описаны выше; схема Auth и фоновая очистка — в контракте владельца.

Документ утверждён и готов к работе. Следующий этап — реализация. Перенос существующих production-данных и обратная совместимость не входят в задачу.

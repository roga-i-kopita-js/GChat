# Logger

## Назначение и границы

LoggerModule предоставляет общий сервис логирования backend. Сервисы получают LoggerService через конструктор. Модуль регистрируется только через `LoggerModule.forRoot()` один раз в AppModule. Динамическая регистрация задаёт `global: true` и экспортирует LoggerService; повторный импорт в бизнес-модулях, включая ErrorModule, не требуется. Обычный импорт LoggerModule не регистрирует сервисы, настройки или инициализацию контекста.

В текущий объём входят глобальный сервис с автоматической привязкой модуля и компонента, JSON-вывод, совместимость с Nest, безопасная сериализация и подключение ErrorModule.

Не входят автоматическая корреляция запросов, генерация request_id, HTTP access log, метрики, трассировка и внешняя доставка логов. `request_id` в `/auth/refresh` остаётся ключом идемпотентности Auth и автоматически не логируется.

## Публичный API

```ts
constructor(private readonly logger: LoggerService) {}

// В CallsService, зарегистрированном в CallsModule:
this.logger.log('Call created', { callId });

// В PushService, зарегистрированном в PushModule:
this.logger.warn('Push delivery failed', { callId });
```

Контракт совместим с Nest LoggerService: `log`, `warn`, `error`, `debug`, `verbose`, `fatal`. Методы ничего не возвращают. Сервисы передают сообщение и необязательные структурированные данные. Модуль и компонент определяются автоматически при внедрении логгера. Последний строковый аргумент контекста сохраняется для совместимости с Nest и не требуется в бизнес-коде.

### Формат и вывод

Одна запись — одна строка JSON:

```json
{"timestamp":"2026-11-02T19:00:00.000Z","level":"info","service":"gchat-backend","module":"CallsModule","context":"CallsService","message":"Call created","metadata":[{"callId":"…"}]}
```

- `timestamp` — время события в UTC, ISO 8601.
- `level` — `info`, `warn`, `error`, `debug`, `verbose` или `fatal`; метод `log` соответствует `info`.
- `service` — `gchat-backend`.
- `module` — автоматически определённое имя модуля-владельца провайдера; `null` для записей без доступной DI-привязки.
- `context` — автоматически определённое имя провайдера; для записей Nest — переданный контекст. Отсутствует, если контекст неизвестен.
- `message` — безопасное описание события.
- `metadata` — массив дополнительных данных; отсутствует, если данные не переданы.

Уровни `error` и `fatal` выводятся в stderr, остальные — в stdout. Файлы и внешнее хранилище логов сервис не создаёт. На первом этапе выводятся все уровни, настройки порога нет. Ошибка сериализации или записи не должна ломать бизнес-операцию.

## Правила и инварианты

### Автоматический модуль и компонент

Каждая запись из внедрённого логгера содержит:

- `module` — имя Nest-модуля, в котором зарегистрирован вызывающий провайдер, например `CallsModule`.
- `context` — имя провайдера-потребителя, например `CallsService`.

Привязка определяется через DI и метаданные контейнера при создании логгера. Используется transient-провайдер LoggerService, получающий непосредственного потребителя через `INQUIRER`; модуль определяется по регистрации этого потребителя в контейнере. `INQUIRER` сам по себе сообщает потребителя, но не его модуль, поэтому определение модуля требует отдельного сопоставления с регистрациями Nest.

Имя модуля не вычисляется по имени файла, stack trace или обрезанием суффикса `Service`. На каждом вызове логирования обход контейнера не выполняется. Контекст хранится в экземпляре логгера потребителя; общего изменяемого `setContext()` нет, поэтому параллельные сервисы не перезаписывают модуль друг друга.

Модуль означает владельца провайдера, который пишет лог. Например, запись из RedisService содержит `RedisModule`, даже если RedisService вызван из AuthService. Импорт экспортированного провайдера в другой модуль не меняет его владельца. При нескольких регистрациях одного класса привязка должна учитывать конкретную регистрацию; нельзя выбирать первый найденный модуль по одному имени класса.

Для сообщений фреймворка Nest, статических вызовов Nest Logger и запуска до создания контейнера автоматического владельца может не быть. Такие записи получают `module: null`, а `context` сохраняет переданный Nest контекст либо `Bootstrap` для запуска. Неизвестный модуль явно обозначается как `null`, а не угадывается. Обычный внедрённый провайдер должен получать свой модуль автоматически.

При инициализации LoggerModule дополнительно привязывает transient-экземпляры логгера по ID конкретных регистраций потребителей в Nest. Это обеспечивает различение повторных регистраций и фабричных провайдеров. Для фабрики контекстом служит имя её DI-токена. До завершения инициализации у фабричного провайдера без объекта INQUIRER модуль может быть `null`; после инициализации он привязан к владельцу. Привязка использует API InstanceWrapper установленной версии Nest и покрыта регрессионными тестами. Для request-scoped или динамически создаваемых потребителей, не найденных однозначно, применяется `module: null`, без выбора произвольного владельца.

Вызывающий модуль передаёт безопасное название события и выбранные служебные поля. Нельзя передавать целиком HTTP-запросы, тела, заголовки, пароли, токены, SDP, SQL с пользовательскими данными и конфигурацию подключения.

## Зависимости и регистрация

LoggerService подключается как логгер Nest на этапе запуска. Существующие вызовы Nest Logger и сообщения фреймворка используют общий формат. До создания DI-контейнера используется отдельный экземпляр того же класса для сообщений запуска с включённым маскированием. После успешного создания приложения Nest использует отдельный непривязанный экземпляр с проверенными настройками окружения. Bootstrap и сообщения Nest без владельца получают `module: null`.

Глобальный фильтр ErrorModule записывает HTTP-ошибки 5xx с безопасными полями `status` и `code`. Ожидаемые ответы 4xx автоматически не логируются. Healthcheck сохраняет свой контракт, отрицательная readiness сама по себе не создаёт запись об ошибке HTTP-запроса. Автоматического журнала всех HTTP-запросов нет.

## Ошибки и частичное выполнение

Независимо от `LOG_REDACTION_ENABLED` циклические ссылки, bigint, глубокие объекты и длинные значения обрабатываются без падения. Пользовательские getters и toJSON не вызываются; ошибка сериализации или потока вывода не прерывает бизнес-операцию. Ограничения глубины, длины строк и количества элементов сохраняются. Настройка отключает маскирование, но не устойчивость логгера.

Маскирование — дополнительная защита, а не гарантия распознавания произвольного секрета в свободном тексте. Основная ответственность за состав события остаётся у вызывающего модуля. Безопасное сообщение об отказе зависимости предпочтительнее передачи исходного сообщения драйвера.

## Конфигурация

Маскирование чувствительных данных управляется переменной окружения `LOG_REDACTION_ENABLED`:

| Значение | Поведение |
| --- | --- |
| Не задано или `true` | Маскирование включено по умолчанию |
| `false` | Маскирование отключено |

Допускаются только строковые значения `true` и `false`; другое значение останавливает запуск с ошибкой конфигурации. Значение читается при запуске, изменение требует перезапуска. В `.env.example` указывается `LOG_REDACTION_ENABLED=true`. Настройка реализована в проверке окружения и LoggerSettings.

При `true` применяется дополнительная защита чувствительных данных:

- Чувствительные поля, включая пароли, токены, секреты, credentials, Authorization, Cookie, URL подключения и приватные ключи, маскируются.
- URL, Bearer-токены, JWT и простые присваивания секретов в строках маскируются.
- У объектов Error не выводятся исходное сообщение, stack trace, cause и дополнительные свойства; сохраняется только безопасный маркер ошибки.
- Строковый stack trace в стандартном вызове Nest `error(message, stack, context)` пропускается.

При `false` чувствительные поля и строки не маскируются; сообщения и stack trace объектов Error могут включаться в запись. Вывод остаётся структурированным: Error преобразуется в явные поля, а не сериализуется вслепую. Настройка не разрешает автоматически добавлять запросы, конфигурацию или другие данные в события: состав записи по-прежнему определяет вызывающий код. Глобальный HTTP-фильтр продолжает писать только безопасные `status` и `code`.

## Критерии приёмки и проверки

- Сервис внедряется в конструктор отдельного модуля-потребителя.
- Логи двух параллельно работающих сервисов содержат собственные `module` и `context` без передачи этих полей вручную.
- Импорт экспортированного провайдера не меняет его модуль-владелец.
- Повторная регистрация одного класса в разных модулях не приводит к неверной привязке.
- Записи Nest и bootstrap без DI-привязки получают `module: null`.
- Запись соответствует JSON-формату и занимает одну строку, включая сообщения с переносами.
- Ошибки направляются в stderr, остальные события — в stdout.
- При `LOG_REDACTION_ENABLED=true` чувствительные поля и внутренние данные Error не попадают в вывод.
- При `false` маскирование отключено, при этом защита от циклов, getters, toJSON и ошибок вывода сохраняется.
- Отсутствующая настройка включает маскирование; некорректное значение не позволяет запустить приложение.
- Циклы и нестандартные значения не ломают логирование.
- Ошибка потока вывода не прерывает бизнес-код.

API бизнес-кода: `logger.log(message, metadata)`. Модуль и компонент добавляются автоматически в пределах описанной DI-привязки. Вывод — JSON для всех окружений, все уровни включены. Stack trace скрывается при включённом маскировании и доступен при `LOG_REDACTION_ENABLED=false`.

`src/logger/logger.service.spec.ts` проверяет глобальный DI, повторные регистрации, импорт провайдера, фабричного потребителя, параллельные записи, формат JSON, stdout/stderr, оба режима маскирования и устойчивость сериализации.


## Открытые решения

Новых согласованных расширений нет. Настройка порога уровней, access log и корреляция запросов не входят в текущий объём. Ограничения привязки для ранних фабрик и неоднозначных request-scoped потребителей перечислены в правилах.

# RedLock

## Назначение и границы

RedlockModule предоставляет ограниченную по времени блокировку ресурса поверх клиента [RedisModule](redis.md). Модуль используется в [cron-очистке Auth](auth.md#фоновая-очистка--реализовано) для координации нескольких процессов на ресурсе `auth:cleanup`. Модуль не содержит бизнес-логики Auth и не предоставляет HTTP API.

В MVP используется один Redis. Это аренда на одном узле, без кворума независимых Redis и без гарантии взаимоисключения при потере данных узла или переключении на устаревшую реплику. Несколько подключений к одному серверу не превращают схему в отказоустойчивый Redlock. Ограничения относятся к потребителям аренд; автоматическое переключение узла не входит в текущую схему. См. [описание алгоритма и ограничений Redis](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/).

Аренда не является транзакцией PostgreSQL и Redis. Она не откатывает завершённые изменения и не останавливает физически уже отправленный запрос. Для критичных записей нужны атомарные проверки предусловий и идемпотентность в модуле-владельце данных. Поле `LockContext.redisOwnership` позволяет будущему потребителю проверять владельца внутри Lua; текущий HTTP Auth не использует этот механизм. Это не обеспечивает fencing для PostgreSQL и не устраняет ограничения потери данных одного Redis. Административные изменения аккаунтов и сессий согласовано выполнять одной транзакцией PostgreSQL по контракту Auth. Redlock для них не используется; аренда нужна только фоновой очистке, которая дополнительно проверяет SQL-предусловия.

## Публичный API

```ts
interface LockContext {
  readonly signal: AbortSignal;
  readonly redisOwnership: { readonly key: string; readonly owner: string };
  assertHeld(): void;
}

interface LockService {
  withLock<T>(resource: string, action: (context: LockContext) => Promise<T>): Promise<T>;
}
```

Контракт реализован классом `RedlockService`. Используется существующий клиент node-redis: `SET NX PX` для захвата и Lua для сравнения владельца при продлении и освобождении. Дополнительная библиотека не устанавливается. Ресурс передаётся без `lock:`, сервис добавляет этот сегмент и префикс Redis. Вложенные захваты отклоняются через AsyncLocalStorage.

`withLock` ограниченно ожидает захват, запускает callback один раз после успеха, поддерживает аренду и освобождает её в `finally`. Автоматический повтор callback запрещён. Сигнал отмены передаётся во вложенные операции, которые умеют его обрабатывать.

`assertHeld()` синхронно проверяет известную потерю или истечение аренды по локальному сроку с запасом. Он не доказывает сохранение владения на сервере и не устраняет гонку между проверкой и записью. Callback проверяет состояние после долгих ожиданий и перед каждым следующим побочным эффектом. Если продление не удалось в пределах действующей аренды, сигнал отменяется и новые шаги прекращаются.

Результат возвращается только после завершения callback и обработки освобождения. Если callback завершился ошибкой, ошибка освобождения не подменяет её и фиксируется отдельно. Если callback успешен, но освобождение не подтверждено, вызывающий код получает отдельную ошибку с признаком возможного выполнения изменений; повтор допускается только по правилам бизнес-операции.

## Правила и инварианты

Текущий HTTP Auth не использует аренды. Его атомарные операции и обработка конкуренции описаны в [Auth](auth.md#конкурентные-операции). CLI только создаёт администраторов; административные изменения аккаунтов и сессий выполняются транзакциями PostgreSQL. Cron-очистка Auth использует аренду по контракту владельца.

На каждый захват создаётся уникальное непредсказуемое значение владельца. Захват использует условную запись с TTL; продление и освобождение атомарно сравнивают владельца перед изменением ключа. Обычный `DEL` для освобождения запрещён: просрочившийся владелец не должен удалить аренду следующего процесса.

Для MVP операция берёт один ресурс. Повторный вход в ту же блокировку из callback не поддерживается; вложенный захват запрещён контрактом. Захват нескольких ресурсов требует отдельного протокола порядка и освобождения, до его определения такой API не предоставляется.

## Зависимости и регистрация

`RedlockModule.forFeature()` регистрируется в модуле-потребителе; в AppModule не подключается. Использует глобальный клиент RedisService и конфигурацию окружения.

```ts
@Module({ imports: [RedlockModule.forFeature()], providers: [ConsumerService] })
export class ConsumerModule {}
```

Это пример регистрации потребителя; AuthModule импортирует RedlockModule.forFeature() для очистки. `redisOwnership.key` уже включает префикс окружения; `owner` — секрет владения, его нельзя логировать или возвращать клиенту. Потребитель сравнивает владельца внутри того же Lua-скрипта, который изменяет данные. Поле само по себе не заменяет `assertHeld()` и проверки предусловий.

## Ошибки и частичное выполнение

| Ситуация                                          | Поведение                                                                   |
| ------------------------------------------------- | --------------------------------------------------------------------------- |
| Ресурс занят до конца бюджета                     | Callback не запускается, ошибка захвата                                     |
| Redis недоступен или результат захвата неизвестен | Callback не запускается; возможная аренда истечёт по TTL                    |
| Продление не подтверждено до безопасного срока    | Потеря аренды, отмена callback, запрет следующих шагов                      |
| Таймаут или авария callback                       | Освобождение в `finally`, без автоматического повтора                       |
| Процесс завершён аварийно                         | Аренда освобождается истечением TTL                                         |
| Освобождение не подтверждено                      | Фиксируется неизвестный результат, ключ не удаляется без проверки владельца |

Потребитель определяет отображение `LockError` и правила повтора. Для ошибок после начала callback нельзя обещать отсутствие изменений. В HTTP-операции Auth ошибки аренд не передаются. В cron-очистке Auth ошибка захвата откладывает запуск; потеря аренды прекращает новые шаги, а SQL-предусловия обеспечивают безопасность уже отправленной пачки.

При штатной остановке запрещаются новые захваты, активные операции завершаются либо отменяются в пределах общего срока, освобождение выполняется до закрытия Redis-клиента. Нельзя принудительно удалять все lock-ключи.

После аварийного восстановления применяются [эксплуатационные правила](../operations/recovery.md).

При завершении приложения используется `beforeApplicationShutdown`: сервис запрещает новые захваты, отменяет активные операции и ждёт не более двух таймаутов команды Redis. После этого RedisService закрывает соединение. Callback, игнорирующий отмену, может продолжить работу; завершённые изменения не откатываются. Максимальное удержание проверяется также по монотонным часам в `assertHeld()`, поэтому пауза event loop не позволяет считать аренду действующей только из-за задержанного таймера.

Поправка на дрейф составляет `ceil(lease × 0.01) + 2` мс. При неизвестном результате захвата callback не запускается; возможный ключ истекает по TTL. При первом сбое продления аренда считается потерянной без повторов. Ошибки сервиса типизированы через `LockError` с кодом и признаком `mayHaveExecuted`; обработку определяет потребитель; AuthCleanup безопасно откладывает очистку.

## Конфигурация

| Параметр                      | Значение | Смысл                                             |
| ----------------------------- | -------- | ------------------------------------------------- |
| `REDLOCK_LEASE_MS`            | 10000 мс | Срок одной аренды                                 |
| `REDLOCK_ACQUIRE_TIMEOUT_MS`  | 2000 мс  | Общий бюджет ожидания, включая команды и задержки |
| `REDLOCK_RETRY_DELAY_MS`      | 100 мс   | Базовая задержка повторного захвата               |
| `REDLOCK_RETRY_JITTER_MS`     | 100 мс   | Дополнительный случайный разброс от 0 до значения |
| `REDLOCK_EXTEND_THRESHOLD_MS` | 3000 мс  | Запас времени для начала продления                |
| `REDLOCK_MAX_HOLD_MS`         | 30000 мс | Предельная длительность callback под арендой      |

Эти переменные окружения реализованы и валидируются при запуске. Длительности согласуются с таймаутом команды Redis и временем операций БД. Запас продления должен покрывать команду, сетевую задержку, паузы процесса и поправку на дрейф часов; окончательные значения проверяются нагрузкой.

Ожидание не должно превышать общий бюджет из-за внутренних повторов библиотеки. Время получения аренды и поправка на дрейф уменьшают её полезный срок. По достижении максимального времени удержания операция отменяется, продления прекращаются. Нельзя считать callback завершённым, если он игнорирует сигнал и продолжает работу: такой случай должен фиксироваться как ошибка реализации.

## Критерии приёмки и проверки

Планируемые метрики: время ожидания и удержания, неудачи захвата, продления и освобождения, отмены и превышения максимального времени. Экспорт метрик пока не реализован; есть безопасные предупреждения о превышении времени callback и неподтверждённом освобождении. Идентификаторы пользователей и ресурсы не используются как метки метрик. Секрет владельца блокировки не записывается в логи.

Интеграционные тесты с настоящим Redis включаются через `REDLOCK_INTEGRATION_URL`. Проверки сервиса и интеграции Auth (последняя описана в контракте Auth):

- Backend и CLI конкурируют за один ключ; callback второго владельца начинается после освобождения или истечения аренды.
- Разные пользователи не блокируют друг друга.
- Старый владелец не может продлить или удалить новую аренду.
- Продление поддерживает долгую операцию, а его сбой отменяет следующие шаги.
- Ожидание захвата и максимальное удержание ограничены; callback автоматически не повторяется.
- Пауза процесса дольше TTL обнаруживается после возобновления; проверяется защита от запоздавших записей в пределах выбранного контракта.
- Исключение, отключение сети и завершение процесса не оставляют бессрочный ключ.
- Частичные изменения Auth допускают безопасное восстановление; тесты не предполагают автоматического отката.

До production необходимо проверить численные бюджеты. Транзакции сессий и административных изменений в PostgreSQL описаны в Auth. Redlock применяется к cron-очистке, а не вместо транзакционной защиты. Один Redis и кооперативная отмена не обеспечивают fencing PostgreSQL.

## Открытые решения

Проверить численные бюджеты под production-нагрузкой. Контекст предоставляет данные для атомарной проверки владельца в Redis Lua; потребитель обязан выполнить эту проверку в скрипте записи. Fencing для PostgreSQL не определён; текущая аренда сама по себе не даёт гарантии защиты от запоздавшей записи. Это ограничение не следует трактовать как обещание отсутствия частичных изменений.

# История звонков: расширение DirectCalls API

## Назначение и границы

Принятый контракт API для [согласованного интерфейса истории](../../../design/calls-history.md). Пользователь подтвердил бессрочное хранение, рассмотрел изменения БД и поручил реализацию полного предложенного контракта 2026-11-11.

Это расширение существующего DirectCallsModule, а не отдельный движок или Nest-модуль. REST используется для чтения завершённых звонков, существующий WSS — для управления звонком и уведомлений. Разделение согласовано в [основном контракте DirectCalls](README.md#публичный-api) и [D003](D003-direct-calls-transport.md).

История содержит только собственные завершённые вызовы аккаунта. Текущий звонок продолжает читаться через `call.current`/`call.get`. Не входят удаление истории, отметки прочтения, счётчики новых пропущенных, поиск, группировка нескольких вызовов, административный доступ к чужой истории, запись аудио и новый HTTP-метод создания звонка.

Бизнес-решения принадлежат [требованиям продукта](../../../product/requirements.md#история-звонков--проект-расширения). Таблицы и API ниже описывают требуемое поведение на основе этих правил; наличие кода отражается implementation_status.

## Публичный API

Все маршруты требуют Bearer access token, активный аккаунт, действующую сессию и её актуальный device binding по [Auth](../auth.md). Аккаунт берётся из авторизации; `user_id`, роль участника и устройство в query не принимаются. Право чтения не ограничивается устройством, выбранным для разговора. AuthGuard проверяет токен; в транзакции чтения дополнительно проверяются актуальное состояние аккаунта, сессия через Auth и binding через Devices в существующем порядке блокировок. Одного успешного AuthGuard недостаточно для разрешения чтения по старому JWT.

Backend-пути приведены без внешнего префикса `/api`: например, клиентский URL списка — `/api/calls/history`. Ответы, включая ошибки, получают `Cache-Control: no-store`.

| Метод и путь                  | `operationId`      | Ответ 200                                                    |
| ----------------------------- | ------------------ | ------------------------------------------------------------ |
| `GET /calls/history`          | `callsHistoryList` | `{items: CallHistoryItemDto[], next_cursor: string \| null}` |
| `GET /calls/history/:call_id` | `callsHistoryGet`  | `{item: CallHistoryItemDto}`                                 |

### Список

Query-параметры `GET /calls/history`:

| Поле     | Значение                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `filter` | `all` или `missed`; по умолчанию `all`. `missed` выбирает только строки с `outcome = missed` относительно текущего аккаунта.   |
| `limit`  | Целое десятичное число от 1 до 100; по умолчанию 30. Неверные значения отклоняются без clamp.                                  |
| `cursor` | Непустая непрозрачная строка продолжения из предыдущего ответа, не более 2048 ASCII-символов. Для первой страницы отсутствует. |

Неизвестные, повторяющиеся и массивные query-параметры, пустой cursor, неподдерживаемый filter, дробные числа, знаки, пробелы и значения вне диапазона дают `400 VALIDATION_ERROR`. `limit` принимает только запись `[0-9]+` в указанном диапазоне, а не экспоненту или числовой префикс произвольной строки.

Сортировка: `created_at DESC, call_id DESC`, где `created_at` — время создания самого вызова, а UUID сравнивается в порядке PostgreSQL `uuid`. Строки не переставляются при переименовании собеседника. Пагинация по ключу сортировки, без `offset`; сервер выбирает следующую страницу строго ниже последнего возвращённого ключа. Курсор сохраняет точность даты сортировки в БД, не восстанавливает её из округлённой клиентской строки.

Курсор содержит версию формата, аккаунт, filter и ключ продолжения; это внутренний формат, клиент его не разбирает и не изменяет. Курсор другого аккаунта или filter, неверная структура и неподдерживаемая версия дают одинаковую ошибку `400 VALIDATION_ERROR` с полем `cursor`. `limit` разрешено менять между страницами. Курсор не является разрешением на чтение: все его поля недоверенные, участие проверяется по авторизованному аккаунту на каждом запросе. Подпись, секрет для курсора и сторонняя криптография не требуются; произвольный корректный ключ может менять только позицию в собственной выборке.

`next_cursor` возвращается только при наличии хотя бы одной следующей записи в снимке чтения этого запроса; иначе `null`. Пустой список и позиция за концом дают `{items: [], next_cursor: null}`. `total` и отдельный `has_more` не добавляются.

Не гарантируется единый неизменный снимок между HTTP-запросами. Новые завершённые вызовы читаются с начала, клиент объединяет записи по `call_id`. Самостоятельно переданный курсор не гарантирует, что клиент уже загрузил все более новые строки. В рамках одного запроса список и признак продолжения читаются из одного согласованного снимка БД.

Пример первой страницы:

```http
GET /calls/history?filter=missed&limit=30
Authorization: Bearer <access_token>
```

```json
{
  "items": [
    {
      "call_id": "95abcc78-2b5e-41ab-a327-0516a771bf43",
      "version": 1,
      "peer_id": "f5847042-eace-44b9-9f6a-7ba16d6dc624",
      "peer_display_name": "Анна Смирнова",
      "direction": "incoming",
      "outcome": "missed",
      "created_at": "2026-11-11T12:32:00.000Z",
      "started_at": null,
      "ended_at": "2026-11-11T12:32:30.000Z",
      "end_reason": "no_answer",
      "duration_seconds": null
    }
  ],
  "next_cursor": null
}
```

### Сведения о вызове

`call_id` — UUID; регистр нормализуется перед сравнением. Для известной собственной записи возвращается тот же полный DTO, что в списке, без необходимости сначала загружать страницу истории. Неизвестный, чужой и ещё не завершённый вызов возвращают одинаковый `404 NOT_FOUND`. Некорректный UUID даёт `400 VALIDATION_ERROR` с полем `call_id`.

Маршрут читает долговременную историю: удаление технического звонка через 30 суток не меняет результат. Обычный WS `call.get` сохраняет свой технический срок хранения и после удаления технической записи по-прежнему отвечает `NOT_FOUND`.

### CallHistoryItemDto

Поля обязательны; отсутствие времени разговора и длительности обозначается `null`, а не отсутствием поля. Имена соответствуют существующим snake_case DTO DirectCalls и Dialogs.

| Поле                | Тип и смысл                                                                                                                                                                                                                                                                |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `call_id`           | UUID исходного вызова; одинаковый на всех устройствах и в техническом DTO.                                                                                                                                                                                                 |
| `version`           | Финальная версия исходного звонка, целое JSON-число от 0 до 9007199254740991. Не отдельная версия истории.                                                                                                                                                                 |
| `peer_id`           | UUID другого участника относительно текущего аккаунта.                                                                                                                                                                                                                     |
| `peer_display_name` | Текущее `display_name` собеседника из Auth, включая отключённого собеседника и отсутствие общей группы; аналогично [имени в DialogDto](../dialogs/README.md#имя-собеседника). Исторический снимок имени не создаётся.                                                      |
| `direction`         | `incoming` для recipient, `outgoing` для caller.                                                                                                                                                                                                                           |
| `outcome`           | `completed`, `missed`, `unanswered`, `cancelled`, `rejected` или `failed` по таблице ниже.                                                                                                                                                                                 |
| `created_at`        | Серверное время создания вызова; время строки и ключ хронологического порядка.                                                                                                                                                                                             |
| `started_at`        | Серверное время первого перехода в `active` либо `null`, если разговор не установился.                                                                                                                                                                                     |
| `ended_at`          | Серверное время завершения, всегда заполнено.                                                                                                                                                                                                                              |
| `end_reason`        | Одна из существующих причин завершения DirectCalls; новый набор транспортных причин не вводится.                                                                                                                                                                           |
| `duration_seconds`  | `null`, если `started_at = null`; иначе `floor((ended_at - started_at) / 1000)`, неотрицательное безопасное целое JSON-число. Включает восстановление аудио, исключает ожидание ответа и первоначальное соединение. Состоявшийся разговор короче секунды имеет значение 0. |

Все даты сериализуются в UTC как `YYYY-MM-DDTHH:mm:ss.SSSZ`. Локальные часы и разделители «Сегодня»/«Вчера» формирует клиент. `started_at`/`ended_at` имеют ту же семантику, что в общем DTO DirectCalls; хранение не пересчитывает длительность по часам устройства. Несогласованные временные данные считаются ошибкой целостности и не исправляются молча с помощью clamp.

Аватар клиент формирует из имени и существующей палитры. В ответе нет login, роли, членств, онлайна, выбранных устройств, session ID, SDP, ICE, TURN credentials или медиа. Изменение имени меняет `peer_display_name` при следующем чтении, но не финальную `version`: она версионирует звонок, а не профиль.

### Определение результата

Правила применяются сверху вниз; результат относится к аккаунту, а не отдельному телефону.

| Условие                                                     | `direction` | `outcome`    |
| ----------------------------------------------------------- | ----------- | ------------ |
| `started_at != null`, любая допустимая причина завершения   | Любое       | `completed`  |
| Разговора не было, `end_reason = rejected`                  | Любое       | `rejected`   |
| Разговора не было, `end_reason = no_answer` или `cancelled` | `incoming`  | `missed`     |
| Разговора не было, `end_reason = no_answer`                 | `outgoing`  | `unanswered` |
| Разговора не было, `end_reason = cancelled`                 | `outgoing`  | `cancelled`  |
| Разговора не было, остальные допустимые причины             | Любое       | `failed`     |

Таким образом, входящий, отменённый инициатором до ответа, считается пропущенным; отклонённый пользователем — нет. Принятие на другом устройстве не создаёт отдельный пропущенный вызов на остальных устройствах. Если после принятия звук не установился, это `failed`, а не пропущенный. Ошибка `call.create`, включая занятость или отказ доступа, не создаёт строку истории: вызов не был создан.

`completed` подтверждает, что звонок достиг `active`, а не отсутствие ошибки завершения. Например, `completed` вместе с `end_reason = connection_lost` позволяет показать состоявшийся, затем прерванный разговор. `hangup` до `active` даёт `failed`. Все восемь существующих причин завершения должны быть покрыты тестами.

### Обновления на устройствах

Нового WS-события и отдельной долговременной очереди истории не вводится. Существующий `call.updated` с `state = ended` служит сигналом перечитать `GET /calls/history/:call_id` и обновить начало списка. Сам WS DTO не считается полной строкой истории: в нём нет имени и серверной классификации результата. Дубликаты сигнала не создают дубликат строки.

История фиксируется до доступности события, в той же транзакции завершения. Пропуск события восстанавливается HTTP-чтением: при открытии раздела, возвращении приложения на передний план и переподключении WSS клиент перечитывает первую страницу и заново начинает цепочку курсоров. Уже показанные строки не считаются полным зеркалом серверной истории; более старые страницы доступны повторной загрузкой. В открытом разделе клиент дополнительно перечитывает начало раз в 60 секунд, чтобы потерянный сигнал не оставлял список устаревшим бессрочно. При скрытии раздела периодическое чтение останавливается.

Смена filter начинает новую цепочку курсоров. Имя в уже загруженной строке обновляется при HTTP-чтении, даже если финальная версия звонка та же; запоздалые ответы предыдущего аккаунта/сессии не применяются. API не предоставляет delta sync, подтверждения доставки, позиции прочтения или гарантии немедленного обновления отключённого устройства.

## Правила и инварианты

### Доступ и бессрочное хранение

1. Право чтения определяется участием в прошлом звонке. После потери общей группы или отключения собеседника сохраняются запись и разрешённое имя; это не даёт права на новый звонок или на чтение полного профиля.
2. Администратор также читает только звонки, где он участник. Другой аккаунт и чужое устройство не получают историю через переданный UUID, query или cursor. Отключённый текущий аккаунт и отозванная сессия не могут читать API.
3. Одна запись вызова общая для двух участников; direction, peer и outcome вычисляются относительно actor. Все его действующие устройства читают одинаковую историю. Потеря устройства, выход из сессии, очистка локального кеша и переустановка клиента не удаляют серверную историю.
4. Срок хранения истории бессрочный, без TTL и фонового удаления по возрасту. Плановая очистка технических звонков, участников и заданий по действующему 30-дневному правилу не затрагивает историю. API удаления в первой версии не вводится.
5. Физическое удаление аккаунтов этим проектом не вводится. Связи с Auth используют RESTRICT; будущая анонимизация или удаление аккаунта требуют отдельного контракта и не выполняются как побочный эффект очистки звонков.
6. Отсутствие строки не подтверждает отсутствие звонка до внедрения функции. При запуске переносится только сохранившаяся техническая история; уже удалённые записи не восстанавливаются и не имитируются.

### Владелец данных и атомарность

Используется таблица DirectCalls `gchat_direct_call_history`: `call_id` UUID PK без каскадного FK на техническую таблицу; `caller_id`, `recipient_id` с FK Auth RESTRICT; `created_at`, `started_at`, `ended_at`, `end_reason` и финальная `version`. Имя, direction, outcome и duration в таблице не дублируются. Начальные даты и финальное состояние берутся из исходного звонка, а не из получения события клиентом.

CHECK обеспечивают разных участников, допустимую финальную причину, безопасный диапазон версии, `ended_at >= created_at` и при наличии начала `created_at <= started_at <= ended_at`. Индексы `(caller_id, created_at DESC, call_id DESC)` и `(recipient_id, created_at DESC, call_id DESC)` обслуживают выборки участников; для пропущенных используется частичный индекс recipient с условием `started_at IS NULL AND end_reason IN ('cancelled', 'no_answer')` в том же порядке.

При первом переходе в `ended` одна транзакция сохраняет финальное техническое состояние, освобождение участников, неизменяемую строку истории и существующее задание `call.updated`. Это относится к пользовательским командам, серверным таймаутам, отзыву сессии, отключению аккаунта и восстановлению после падения. Отдельная асинхронная архивация или построение истории по доставленным WS-событиям не допускаются. Ошибка записи истории откатывает транзакцию; механизм завершения повторяется по действующим правилам, а не подтверждает частичное завершение.

Повтор допустимой команды не добавляет строку и не меняет исходные времена. PK обеспечивает одну запись на вызов. Повторная вставка проверяет совпадение неизменяемых данных; конфликт содержимого — ошибка целостности, а не разрешение перезаписать историю. Финальная запись не зависит от существования технической строки. Чтение профиля выполняется согласованным join с Auth, без N+1 запросов.

Развёртывание требует отдельной штатной миграции схемы и backfill всех сохранившихся `ended`-звонков. Порядок для единственного backend: остановить обслуживание, применить миграции/backfill, запустить версию с атомарной записью истории и только затем открыть API. Старый writer, не создающий историю, не должен работать одновременно или возвращаться при rollback без отдельного плана сохранения данных. Миграции не запускаются при старте HTTP-сервера. До backfill нельзя запускать 30-дневную очистку технических записей в обход переноса. Повтор backfill идемпотентен и проверяет совпадение уже имеющихся строк. Миграция схемы и backfill находятся в `applications/backend/drizzle/0008_call_history.sql`. Плановая очистка дополнительно требует наличия архивной записи перед удалением технической строки.

## Зависимости и регистрация

Данные и сервис чтения остаются внутри DirectCallsModule; используются существующие DatabaseModule, AuthModule и DevicesModule с AuthGuard и транзакционными проверками сессии/binding. Groups не становится условием чтения истории. Signaling сохраняет текущие события и outbox; новый брокер и второй WSS не добавляются. ErrorService и LoggerService внедряются по общим соглашениям. Имя собеседника читается из Auth по разрешённому участию в звонке.

Контроллер и классы DTO при реализации оформляются по [соглашениям backend](../../conventions.md) и [OpenAPI](../../openapi.md). Для HTTP используются явные `operationId`, Bearer security, DTO ошибок и декораторы кодов ответа. OpenAPI JSON и SDK сейчас не меняются вручную: они будут сгенерированы из реализации после принятия контракта.

## Ошибки и частичное выполнение

Тело HTTP-ошибки следует [ErrorModule](../errors.md): `{error: {code, message, fields?}}`, без деталей внутренних запросов, SQL и курсора в логах.

| HTTP | Код                                                               | Условие                                                                                                                                                 |
| ---- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400  | `VALIDATION_ERROR`                                                | Некорректный UUID, query или cursor; `fields` указывает входное поле.                                                                                   |
| 401  | `ACCESS_TOKEN_INVALID`, `ACCESS_TOKEN_EXPIRED`, `SESSION_INVALID` | Отсутствующий, недействительный или истёкший токен; недействительная/отозванная сессия, отсутствующий или отключённый текущий аккаунт по правилам Auth. |
| 403  | `FORBIDDEN`                                                       | Отсутствующая или не принадлежащая текущему аккаунту привязка сессии/устройства по Devices. Чужая запись этим кодом не раскрывается.                    |
| 404  | `NOT_FOUND`                                                       | Одинаково для неизвестной, чужой и ещё не завершённой записи при get.                                                                                   |
| 429  | `RATE_LIMITED`                                                    | Превышен общий лимит чтений истории аккаунта; заголовок `Retry-After` в секундах.                                                                       |
| 503  | `SERVICE_UNAVAILABLE`                                             | Не удалось проверить авторизацию/прочитать данные из зависимости.                                                                                       |
| 500  | `INTERNAL_ERROR`                                                  | Неожиданная ошибка или нарушение целостности.                                                                                                           |

Оба GET не изменяют состояние и могут повторяться после потери ответа. Повтор не обещает прежнего снимка списка или имени. Отмена HTTP-запроса не удаляет записи. Ошибка чтения не превращается в успешную пустую историю. Недоступность имени из-за ошибки БД не заменяется вымышленным именем.

Ограничение частоты следует принятому в Dialogs принципу: общий для двух GET token bucket аккаунта, 10 запросов/с с запасом 20, устройства и сессии делят один счётчик. Повтор расходует лимит; серверный отказ зависимости лимитера не разрешает неограниченное чтение. Лимит истории независим от звонковых команд и не препятствует ответу/завершению текущего вызова.

## Конфигурация

Новая переменная окружения для срока хранения не вводится: бессрочная история — продуктовое правило. Техническое 30-дневное обслуживание остаётся в основном контракте DirectCalls. Пределы страниц, формат запроса и лимит чтений фиксированы выше; текущие настройки heartbeat, ringing, recovery, TURN и Push этим проектом не меняются.

## Критерии приёмки и проверки

1. Список и get требуют авторизацию, действующую сессию и binding, возвращают только собственные завершённые вызовы, включая устройства, не выбранные для разговора. Администратор не получает чужую историю; неизвестный/чужой/незавершённый UUID не различается по публичной ошибке.
2. На один завершённый вызов существует ровно одна серверная запись и по одному представлению у каждого участника; одна строка одинакова на всех устройствах аккаунта. Ошибки создания и промежуточные состояния не создают историю.
3. В таблице исходов проверены обе роли, все end_reason, наличие/отсутствие started_at, ответ и отклонение с другого устройства, отменённый инициатором входящий и разговор короче секунды. Фильтр missed не включает rejected, failed и исходящие без ответа.
4. Длительность и даты соответствуют исходному состоянию, включая восстановление аудио. Порядок не нарушается при совпадающих временах; cursor не теряет точность БД.
5. Проверены первая/последняя/пустая страницы, limit 1/30/100, неправильные query, смена filter, изменение limit, подмена cursor, другой actor, одинаковые timestamps и поступление новых звонков между чтениями. В пределах одного обхода неизменяемых ранее видимых данных записи не пропускаются и не дублируются.
6. После удаления технических записей/участников/outbox и после искусственного продвижения времени больше чем на 30 дней история доступна; обычный call.get может уже вернуть NOT_FOUND. Выход, переустановка, удаление устройства и потеря группы не удаляют историю.
7. Все пути завершения атомарны с историей и outbox. Rollback, неизвестный commit, повтор команды, падение и повтор backfill не теряют подтверждённую историю и не меняют её поля. Backfill переносит доступные данные, не обещая восстановить ранее удалённые.
8. Переименование обновляет peer_display_name при следующем чтении без изменения финальной версии звонка. Отключённый собеседник и отсутствие общей группы обрабатываются по согласованному правилу метаданных; возможность нового звонка по-прежнему проверяет call.create.
9. Обновления после события, его дубликата и пропуска, переподключения, фокуса и периодического чтения восстанавливают список HTTP-чтением. Никакой ACK или гарантии доставки истории через WS не подразумевается.
10. Ошибки зависимостей не маскируются пустым результатом. Общий rate limit действует между устройствами, 429 содержит Retry-After и не влияет на звонковые команды. Ответы и ошибки имеют no-store, технические и секретные поля не раскрываются.
11. При реализации необходимы unit-тесты классификации/курсоров/лимитов, HTTP-тесты авторизации/DTO/ошибок, интеграционные проверки PostgreSQL/Redis, миграции/backfill/очистки и OpenAPI из Nest CLI build с последующей генерацией SDK. Команды берутся из [README backend](../../../../applications/backend/README.md#сборка-и-проверки) и [backend-api](../../../packages/backend-api.md). Тестовые пути перечислены в метаданных; запуск интеграционных проверок использует CALLS_INTEGRATION_DATABASE_URL и CALLS_INTEGRATION_REDIS_URL и отдельные временные БД/ключи. Наличие тестов не означает их автоматического запуска в каждом окружении.

## Открытые решения

Для backend API истории открытых решений нет: HTTP-контракт, бессрочное хранение, таблица, доступ к метаданным, классификация результатов, лимиты и миграция согласованы пользователем. Клиентская интеграция и расположение контактов относятся к отдельной задаче и не блокируют реализацию backend.

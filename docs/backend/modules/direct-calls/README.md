# DirectCallsModule

## Назначение и границы

DirectCalls управляет жизненным циклом голосового звонка между двумя пользователями: создание, принятие, отклонение, отмена, завершение и серверные таймауты. Владеет состоянием звонка и правилами переходов. Исходные требования — в [требованиях продукта](../../../product/requirements.md).

Контракт принят; backend-реализация добавлена. Реальные iPhone, APNs credentials и отдельный coturn требуют настройки и проверки. Детали завершены по поручению пользователя 2026-11-03; мотивация — в [D004](D004-direct-calls-consistency.md). Выбор транспорта зафиксирован отдельно: [D003: транспорт DirectCalls, solution record с диаграммами C1–C3](D003-direct-calls-transport.md). Транспорт и отдельный WebRTC-контур согласованы; статус реализации не меняется от принятия контракта.

Навигация по диаграммам: [C1 — контекст](D003-direct-calls-transport.md#c1--контекст-системы), [C2 — контейнеры](D003-direct-calls-transport.md#c2--контейнеры), [C3 — компоненты backend](D003-direct-calls-transport.md#c3--компоненты-backend-вокруг-directcalls). Блоки Mermaid отображаются в Markdown-preview с поддержкой Mermaid; в текстовом редакторе виден их исходный код.

Auth владеет аккаунтами и сессиями, Groups — членством. Signaling отвечает за авторизованные WebSocket-соединения, доставку состояний и адресный обмен SDP / ICE; Push — за доставку VoIP push в APNs; Devices — за устройства и push-токены. Эти соседние модули не входят в реализацию DirectCalls автоматически. Аудио передают клиенты.

Исключение для инициатора-администратора реализовано: актуальная роль проверяется до проверки занятости и повторно в транзакции создания.

## Публичный API

Команды управления звонком, получение его актуального состояния, пинги, изменения состояния и обмен SDP / ICE используют JSON-сообщения через обычный WebSocket (WSS) в Signaling. Отдельные HTTP endpoints DirectCalls не предусматриваются. Команды и запросы содержат `request_id`; ответ, включая ошибку, возвращается с тем же `request_id`. Этот идентификатор связывает запрос с ответом, но не является ключом идемпотентности создания звонка. Для входящего вызова в фоне используется APNs VoIP push.

Согласованный состав операций DirectCalls: создать звонок, получить состояние по `call_id`, запросить «мой текущий звонок», принять, отклонить, отменить и завершить, подтвердить установленное соединение и отправить WS-пинг состояния устройства и аудиосоединения. Потеря и восстановление аудио сообщаются в этих пингах. Конверт, DTO запросов, успешных ответов и события `call.updated` определены ниже; специфичные коды ошибок и внутренние интерфейсы определены в разделах ниже. Оформление следует [соглашениям backend](../../conventions.md) с отдельным описанием WS-протокола.

### Формат WS-сообщений — согласовано

Запрос содержит `type`, `request_id` и `payload`. Клиент задаёт уникальный идентификатор запроса, сервер возвращает его без изменения. Пример принятия звонка:

```json
{
  "type": "call.accept",
  "request_id": "request-123",
  "payload": { "call_id": "call-456" }
}
```

Успешный ответ имеет `type: "response"`, тот же `request_id` и результат в `payload`. Для `call.accept` результат имеет структуру `{ "call": <общий DTO состояния> }`, описанную ниже; возвращается полный DTO, а не только изменившиеся поля.

При ошибке ответ содержит `error` вместо `payload`; коды ошибок определены в разделе «Ошибки и частичное выполнение»:

```json
{
  "type": "response",
  "request_id": "request-123",
  "error": { "code": "<код ошибки>", "message": "<описание ошибки>" }
}
```

Серверные события передаются без `request_id`, с типом события и данными в `payload`; для изменения состояния звонка используется `call.updated`. Событие содержит общий DTO состояния в обёртке `payload.call`, описанной ниже.

`call.updated` направляется через Signaling всем авторизованным устройствам обоих участников с действующей сессией и подключённым WebSocket, включая устройства, не выбранные для разговора. Все они получают тот же общий DTO состояния. Это синхронизирует состояние между устройствами и позволяет остальным устройствам получателя закрыть входящий вызов после принятия. Получение события не расширяет права управления звонком или обмена SDP / ICE. Доставка входящего вызова устройству в фоне через APNs VoIP push остаётся отдельным механизмом.

Отдельного клиентского ACK для `call.updated` нет; получение каждого промежуточного события не гарантируется. После переподключения клиент запрашивает актуальное состояние через WS-команды `call.get` или `call.current` с проверкой прав. Восстановление выполняется получением актуального состояния, а не воспроизведением всех пропущенных событий. Эти запросы используют тот же WSS-протокол, отдельные HTTP endpoints не вводятся.

### Общее состояние звонка — согласовано

Успешный ответ на `call.create` возвращает полное актуальное состояние звонка. Один и тот же DTO состояния используется в ответах `call.create`, `call.get`, `call.current` при наличии текущего звонка и в событии `call.updated`. Событие передаёт полное состояние, а не частичное изменение. Полный согласованный состав DTO перечислен ниже. Данные профилей участников, включая имена и аватары, в него не входят: клиент получает их отдельно по `caller_id` и `recipient_id`.

Успешные ответы `call.create`, `call.get`, `call.accept`, `call.reject`, `call.cancel`, `call.end`, `call.connected` и событие `call.updated` используют обёртку `payload: { "call": <общий DTO состояния> }`. Поле `call` обязательно и всегда содержит объект. При допустимом повторе команды возвращается актуальное состояние в той же обёртке. Та же обёртка используется в ответе `call.current`, где только при отсутствии текущего звонка допускается `call: null`. Ответы `call.ping` и `call.ice_config` имеют отдельные форматы ниже.

Согласованные поля общего DTO состояния:

| Поле | Тип | Значение |
| --- | --- | --- |
| `call_id` | `string` | Обязательный уникальный идентификатор звонка, создаваемый сервером. Не меняется при переподключении и восстановлении аудио. |
| `state` | `"ringing" \| "connecting" \| "active" \| "ended"` | Обязательное текущее состояние звонка. Во время восстановления аудио остаётся `active`; сведения о восстановлении описываются отдельно. |
| `caller_id` | `string` | Обязательный идентификатор пользователя, начавшего звонок. Определяется сервером по авторизованному WS-соединению при создании и не меняется на протяжении звонка. |
| `recipient_id` | `string` | Обязательный идентификатор пользователя-получателя. Задаётся при создании звонка, проверяется сервером и не меняется на протяжении звонка. |
| `created_at` | `string` | Обязательное серверное время создания звонка в UTC в формате `YYYY-MM-DDTHH:mm:ss.SSSZ`, например `2026-11-03T12:30:00.000Z`. Не меняется на протяжении звонка. |
| `started_at` | `string \| null` | Обязательное поле: серверное время первого перехода в `active` в том же формате UTC либо `null`, если звонок ещё не переходил в `active`. После установки не меняется, включая восстановление соединения и завершение звонка. От него отсчитывается длительность разговора, включая периоды восстановления. |
| `ended_at` | `string \| null` | Обязательное поле: серверное время перехода в `ended` в том же формате UTC; до завершения — `null`. После установки не меняется. Если разговор состоялся, его длительность равна разнице `ended_at` и `started_at`. |
| `end_reason` | `string \| null` | Обязательное поле: причина завершения звонка из набора ниже. До перехода в `ended` — `null`; в `ended` обязательно содержит причину и больше не меняется. |
| `recovery_id` | `string \| null` | Обязательное поле: идентификатор текущего открытого окна восстановления соединения; при отсутствии окна — `null`. Каждое новое окно получает новый идентификатор. |
| `recovery_deadline` | `string \| null` | Обязательное поле: серверный срок окончания текущего открытого окна восстановления в формате UTC `YYYY-MM-DDTHH:mm:ss.SSSZ`. При отсутствии окна — `null`, как и `recovery_id`. |
| `ringing_deadline` | `string \| null` | Обязательное поле: серверный срок ожидания ответа в формате UTC `YYYY-MM-DDTHH:mm:ss.SSSZ`. Заполнено только в `ringing`; в остальных состояниях — `null`. Позволяет клиенту показывать оставшееся время без самостоятельного расчёта таймаута. |
| `connecting_deadline` | `string \| null` | Обязательное поле: серверный срок первоначального установления соединения в формате UTC `YYYY-MM-DDTHH:mm:ss.SSSZ`. Заполнено только в `connecting`; в остальных состояниях — `null`. |
| `version` | `number` | Обязательное целое число: версия общего состояния в рамках звонка. Начальная версия при создании звонка — `0`. Сервер увеличивает её на `1` при каждом изменении общего состояния, включая открытие и закрытие окна восстановления. Обычный пинг без изменений общего состояния не увеличивает версию. Версия сохраняется на backend и не сбрасывается после перезапуска. |

Клиент сравнивает версии в рамках одного `call_id` и применяет только более новую версию общего состояния. Если сохранённого состояния этого звонка ещё нет, клиент принимает полученное состояние. Повтор полного DTO с той же версией или сообщение с меньшей версией не перезаписывает сохранённое состояние; правило одинаково для ответов и событий `call.updated`. Если эта версия известна только из компактного ответа пинга, полный DTO той же версии заполняет отсутствующие поля по правилам ответа `call.ping`.

Допустимые значения `end_reason` — согласовано:

| Значение | Условие завершения |
| --- | --- |
| `cancelled` | Инициатор отменил вызов в `ringing`, до принятия получателем. |
| `rejected` | Получатель отклонил вызов. |
| `no_answer` | Истёк срок ожидания ответа в `ringing`. |
| `connection_timeout` | После принятия истёк срок первоначального соединения в `connecting`. |
| `hangup` | Участник завершил принятый звонок командой `call.end` в `connecting` или `active`. |
| `connection_lost` | Истекло окно восстановления соединения без подтверждений обоих выбранных устройств. |
| `session_revoked` | Отозвана закреплённая за звонком сессия одного из участников. |
| `account_disabled` | Отключён аккаунт одного из участников. |

Причину завершения определяет backend; клиент передаёт команду, а не значение `end_reason`. Занятость и отсутствие разрешения на звонок являются ошибками создания звонка и не входят в этот набор.

Валидация входящих WS-запросов выполняется на backend: сервер проверяет структуру сообщения, обязательные поля, типы и допустимые значения до выполнения команды. Проверки прав и бизнес-правил также выполняются сервером. `caller_id` не принимается от клиента при создании звонка и не может подменить инициатора, определённого по авторизованному соединению. Механизм валидации и ошибки определены в [Signaling](../signaling.md).

### Типы запросов

| Тип запроса | Назначение |
| --- | --- |
| `call.create` | Создать звонок |
| `call.get` | Получить состояние по `call_id` |
| `call.current` | Получить текущий незавершённый звонок пользователя либо его отсутствие |
| `call.accept` | Принять входящий звонок |
| `call.reject` | Отклонить входящий звонок |
| `call.cancel` | Отменить исходящий звонок до принятия |
| `call.end` | Завершить принятый звонок |
| `call.connected` | Подтвердить первоначальное WebRTC-соединение текущей попытки |
| `call.ice_config` | Получить временную конфигурацию ICE/TURN выбранному участнику |
| `call.ping` | Передать доступность и состояние аудио; подтвердить восстановление с текущим `recovery_id` |

Этот конверт относится к прикладным JSON-сообщениям, включая `call.ping`, а не к управляющим кадрам WebSocket Ping/Pong. Форматы SDP / ICE определяются вместе с Signaling.

### Создание звонка: `call.create` — согласовано

`payload` содержит только `recipient_id` — идентификатор пользователя-получателя:

```json
{
  "type": "call.create",
  "request_id": "request-123",
  "payload": { "recipient_id": "user-456" }
}
```

Инициатора, его устройство и сессию сервер определяет по авторизованному WS-соединению. Клиент не передаёт эти значения в `payload` и не может подменить их полями сообщения. Созданный звонок закрепляется за этим устройством и сессией инициатора. Проверки аккаунтов, разрешения на звонок и занятости выполняются по правилам контракта. Успешный ответ содержит общий DTO состояния в обёртке `payload.call`.

### Запросы существующего звонка — согласовано

Для `call.get`, `call.accept`, `call.reject`, `call.cancel`, `call.end` и `call.ice_config` поле `payload` содержит только `call_id`:

```json
{
  "type": "call.get",
  "request_id": "request-124",
  "payload": { "call_id": "call-456" }
}
```

Пользователь, устройство и сессия определяются по авторизованному WS-соединению; сервер проверяет права на указанный звонок и допустимость команды по текущему состоянию. Само знание `call_id` не предоставляет доступ.

Читать состояние через `call.get` и `call.current` могут все устройства аккаунта участника с действующей авторизованной сессией, включая устройства, не выбранные для разговора. Они получают тот же общий DTO состояния. Право чтения не предоставляет права управления звонком, отправки SDP / ICE, подтверждения соединения или пингов от имени выбранного устройства. Правила принятия и отклонения входящего вызова до выбора устройства получателя сохраняются.

Запрос `call.current` не принимает идентификатор пользователя или звонка; его `payload` — пустой объект. Текущий незавершённый звонок определяется для пользователя авторизованного WS-соединения:

```json
{
  "type": "call.current",
  "request_id": "request-125",
  "payload": {}
}
```

Успешный ответ `call.current` содержит в `payload` обязательное поле `call`: общий DTO состояния при наличии текущего незавершённого звонка либо `null` при его отсутствии. Отсутствие звонка является успешным результатом, а не ошибкой:

```json
{
  "type": "response",
  "request_id": "request-125",
  "payload": { "call": null }
}
```

При наличии звонка структура `payload` — `{ "call": <общий DTO состояния> }`. Успешные ответы остальных команд, перечисленных выше, возвращают общий DTO состояния в той же обёртке. Формат `call.ping` описан ниже.

### Пинг: `call.ping` — согласовано

`payload` содержит четыре поля:

```json
{
  "type": "call.ping",
  "request_id": "request-126",
  "payload": {
    "call_id": "call-456",
    "sequence": 1,
    "audio_connected": true,
    "recovery_id": null
  }
}
```

- `call_id` — идентификатор звонка.
- `sequence` — возрастающий номер пинга выбранного устройства в рамках звонка.
- `audio_connected` — булев признак исправности WebRTC-аудиосоединения по правилам ниже.
- `recovery_id` — идентификатор окна восстановления, полученный от сервера; `null`, пока клиент не получил идентификатор открытого окна восстановления.

Клиентские даты в пинге не передаются. Устройство и сессия определяются по авторизованному WS-соединению; правила доступа, порядка пингов и подтверждения текущего восстановления применяются независимо от значений, переданных клиентом. Формат успешного ответа на пинг согласован ниже.

### Ответ на `call.ping` — согласовано

Успешный ответ использует общий конверт `response` с тем же `request_id`. Его `payload` содержит состояние звонка и текущее окно восстановления:

```json
{
  "type": "response",
  "request_id": "request-126",
  "payload": {
    "state": "active",
    "version": 3,
    "recovery_id": null,
    "recovery_deadline": null
  }
}
```

`version` — версия общего состояния звонка из того же согласованного снимка, что остальные поля ответа. Клиент хранит наибольшую известную версию в рамках `call_id` совместно для полного DTO и компактных ответов пинга. Ответ пинга с меньшей версией не меняет состояние или окно восстановления. При равной версии поля совпадают; их повторное применение допустимо. Компактный ответ не заменяет полный DTO: если он опередил полный DTO, полный DTO той же версии допускается для заполнения остальных полей. Более старый полный DTO не перезаписывает состояние.

При открытом окне `recovery_id` содержит его идентификатор, а `recovery_deadline` — серверный срок завершения. Если окна нет или оно закрылось, оба поля равны `null`; клиент очищает сохранённый `recovery_id`. Следующие пинги используют идентификатор открытого окна из ответа либо `null`, если окно отсутствует. Ошибки пинга используют общий конверт ошибки; этот успешный ответ не отменяет правило отклонения пингов завершённого звонка. Все серверные даты в WS-контракте DirectCalls передаются строками UTC с миллисекундами и суффиксом `Z`: `YYYY-MM-DDTHH:mm:ss.SSSZ`, например `2026-11-03T12:30:00.000Z`. Это правило применяется и к `recovery_deadline`; отсутствие срока представляется значением `null`.

## Правила и инварианты

Правила DirectCalls уточняют [общую архитектуру системы](../../../architecture/system.md#5-жизненный-цикл-звонка):

- В звонке ровно два пользователя. До подтверждения исходящего вызова клиентом серверный звонок не создаётся.
- Создание требует проверки действующей сессии, активности аккаунтов, разрешения по общей группе либо роли инициатора-администратора и занятости. Проверка Groups сама по себе не резервирует доступ на время создания звонка.
- Основной путь состояний: `ringing → connecting → active → ended`. Отклонение, отмена, отсутствие ответа и ошибка завершают звонок с отдельной причиной.
- Принять вызов может только одно устройство получателя. Конкурентные ответы и встречные вызовы разрешаются транзакционно.
- Клиент не повторяет создание автоматически при ошибке; команды существующего звонка проверяют допустимость перехода по `call_id`.
- Сервер контролирует таймауты независимо от подключения клиента. После восстановления связи клиент получает актуальное состояние.
- Создание звонка и задания VoIP push сохраняются в одной транзакции PostgreSQL. Успешный ответ APNs не подтверждает, что устройство звонит.
- Доступ к состоянию звонка и сигнализации проверяется на сервере. Отключение аккаунта и отзыв сессии должны закрывать доступ и к существующему WebSocket-соединению.

Схема таблиц, атомарные проверки и таблица переходов определены ниже. Бизнес-таблицы используют префикс `gchat_` по общим соглашениям.

### Аудиотранспорт через coturn — согласовано

Основной сценарий DirectCalls — WebRTC-аудио через собственный coturn в отдельном контуре GChat. Клиенты используют ICE-политику `relay`: соединение устанавливается через TURN без предварительной попытки прямого P2P-соединения и без автоматического перехода на него при отказе TURN. Эта политика применяется и при восстановлении соединения.

coturn пересылает зашифрованные аудиопакеты; аудио расшифровывается на устройствах участников. Backend управляет звонком и передаёт SDP/ICE через Signaling, но не обрабатывает аудиопоток. Клиенты получают временные TURN credentials; общий секрет coturn остаётся на сервере.

Если доступный TURN-путь установить не удалось, применяются существующие сроки первоначального соединения и восстановления аудио: `connection_timeout` в `connecting`, `connection_lost` после истечения окна восстановления в `active`. Весь аудиотрафик проходит через coturn, поэтому его доступность и пропускная способность необходимы для звонков. Backend выдаёт временные credentials; развёртывание coturn и клиентская ICE-политика требуют отдельной проверки на iPhone.

### Получение конфигурации ICE/TURN: `call.ice_config` — согласовано

DirectCalls владеет выдачей временной конфигурации собственного coturn. Запрос содержит `payload: {call_id}`; доступен только выбранным устройствам и сессиям в `connecting` и `active`, включая восстановление. Применяются актуальные проверки Auth, прав и сроков звонка. Остальным устройствам участника возвращается `FORBIDDEN`, в `ringing` и `ended` — `CALL_STATE_CONFLICT`.

Успешный ответ: `payload: {ice_servers: [{urls: string[], username: string, credential: string}], expires_at: string}`. `urls` содержит настроенные TURN URL; `expires_at` — серверное UTC-время истечения credentials в общем формате дат DirectCalls. Секрет coturn не передаётся. Credentials формируются сервером для участника и звонка, действуют 1 час; ответ не сохраняется в state-заданиях, событиях или логах и не меняет `version`.

Клиент запрашивает конфигурацию до первого offer/answer, обновляет её не позднее чем за 60 секунд до `expires_at` и перед новой попыткой, если прежняя конфигурация истекла. Повторный запрос разрешён, возвращает новую действующую конфигурацию и не продлевает сроки звонка. Обновление применяется к PeerConnection до следующего сбора ICE-кандидатов; оно само по себе не требует прерывать исправное аудио. При ошибке клиент может повторить запрос в пределах действующих сроков соединения/восстановления; P2P не используется. Выдача credentials не гарантирует доступность TURN и не означает принудительный отзыв уже выданных credentials при завершении звонка.

### Занятость — согласовано

Пользователь может участвовать только в одном незавершённом звонке. Состояния `ringing`, `connecting` и `active` занимают обоих участников независимо от числа устройств и сессий; переход в `ended` освобождает их.

Если любой участник занят, новый звонок не создаётся, инициатор получает результат «занято». Ожидания второго вызова нет. При одновременных встречных вызовах создаётся один звонок, второй запрос получает «занято»; автоматическое принятие или объединение запросов не выполняется. Занятость хранится в Redis как временные данные DirectCalls. Один Lua-скрипт атомарно проверяет и резервирует обоих пользователей для конкретного `call_id`: если хотя бы один уже занят, резервирование не выполняется и запрос получает «занято». Состояние самого звонка остаётся в PostgreSQL.

Резервирование выполняется до транзакции создания звонка и задания VoIP push. Если транзакция заведомо откатилась, резерв снимается; при неизвестном результате сначала проверяется наличие звонка в PostgreSQL. После завершения звонка резерв освобождается только при совпадении `call_id`, чтобы поздняя очистка не сняла занятость другого звонка. Общей транзакции между Redis и PostgreSQL нет.

Потеря данных Redis и восстановление занятости после такой потери не входят в рассматриваемые сценарии DirectCalls. Это ограничение не меняет общие эксплуатационные правила Redis и Auth.

### Ожидание ответа — согласовано

Таймаут состояния `ringing` отсчитывается с момента создания звонка на сервере и настраивается через переменную окружения из раздела [Конфигурация](#конфигурация). Если за это время получатель не принял вызов, сервер переводит звонок в `ended` с причиной «нет ответа» и освобождает обоих участников. Задержка доставки VoIP push не продлевает ожидание.

### Установление соединения — согласовано

Таймаут состояния `connecting` отсчитывается с момента принятия вызова сервером и настраивается через переменную окружения из раздела [Конфигурация](#конфигурация). Если соединение не установлено в этот срок, сервер переводит звонок в `ended` с причиной «не удалось соединиться» и освобождает обоих участников. Повторные команды принятия не продлевают срок.

В `connecting` действует только таймаут первоначального соединения: наличие или отсутствие пингов его не меняет и не запускает дополнительное окно восстановления. Окно восстановления применяется только после начала разговора.

### Переход в active — согласовано

Оба выбранных устройства участников подтверждают установление WebRTC-соединения. Сервер переводит звонок из `connecting` в `active` после получения второго подтверждения; с этого момента отсчитывается длительность разговора. Одного подтверждения недостаточно: до второго действует таймаут `connecting`. Повторное подтверждение одного устройства не считается подтверждением второго участника.

Выбранное устройство отправляет `call.connected` с `payload: {call_id, negotiation_id}`, где оба поля — UUID, когда его WebRTC-соединение переходит в `connected`. Используется тот же критерий исправности соединения, что для `audio_connected: true` в пинге. Наличие слышимого звука не требуется: молчание и выключенный микрофон не препятствуют подтверждению. Сервер по-прежнему ожидает подтверждения обоих выбранных устройств.

Подтверждение относится только к текущей зарегистрированной попытке `negotiation_id`. Неизвестная или заменённая попытка даёт `CALL_STATE_CONFLICT`, включая повтор в `active`. При регистрации нового offer в `connecting` сервер атомарно устанавливает текущий ID и сбрасывает оба первоначальных подтверждения. Повтор offer с тем же ID их не сбрасывает. Переход в `active` требует двух подтверждений одной текущей попытки; смена попытки не продлевает `connecting_deadline`. В `active` новая попытка не обнуляет `started_at` и не заменяет подтверждения восстановления через пинги. ID текущей попытки и привязка подтверждений сохраняются в PostgreSQL; после перезапуска Signaling требует новый offer до приёма новых `call.connected`, даже если в БД остались прежние подтверждения.

### Доступ администратора — согласовано

Администратор может инициировать звонок любому другому активному пользователю без общей группы, в том числе не состоя ни в одной группе. Backend определяет право по актуальной роли аккаунта инициатора из Auth; роль из клиентского сообщения или JWT не служит основанием обхода проверки членства. Предварительная проверка выполняется до раскрытия занятости, окончательная — в транзакции создания с проверкой аккаунтов. Для инициатора-администратора общая группа и блокировки членства не требуются. Для обычного инициатора сохраняется проверка общей группы, даже если получатель — администратор.

Исключение касается только разрешения по членству: действующая сессия и привязка устройства, активность обоих аккаунтов, запрет звонка самому себе, занятость и остальные ограничения сохраняются. Получатель может принять и продолжить такой звонок по обычным правилам.

### Потеря общего членства — согласовано

Удаление последней общей группы или членства после создания звонка не прерывает этот звонок в состояниях `ringing`, `connecting` и `active`. Участники могут принять, установить и завершить уже созданный вызов; отсутствие общей группы запрещает создание новых звонков обычным инициатором. Для инициатора-администратора действует исключение выше. Это правило относится к членству и не определяет последствия отключения аккаунта или отзыва сессии.

Создание обычным инициатором использует транзакционную проверку `GroupsService.lockCommonGroup(tx, callerId, recipientId)`: в транзакции создания выбирается одна общая группа, строки группы и обоих членств блокируются `FOR SHARE` до commit. Предварительная проверка также использует `lockCommonGroup` в отдельной короткой транзакции после блокировки аккаунтов и чтения актуальной роли; её блокировки не заменяют повторную проверку в транзакции создания. Если удаление последнего общего членства зафиксировано раньше получения блокировки, создание запрещается. Если создание первым удержало блокировки, удаление ждёт завершения создания и уже созданный звонок сохраняется. Другие общие группы достаточны для создания; блокировки выбираются в порядке UUID. Отказ/таймаут блокировки даёт базовую ошибку зависимости, не разрешение по устаревшему чтению. [Семантика блокировок PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html) используется только как механизм, правило доступа принадлежит этому контракту.

### Обрыв WebSocket — согласовано

Обрыв WebSocket не завершает звонок немедленно, но прекращает доставку пингов. В `active` отсутствие пингов до истечения срока доступности запускает окно восстановления, даже если WebRTC-аудио продолжает работать. Если оба устройства не подтвердят восстановление до конца окна, сервер завершает звонок. Клиент переподключается к Signaling и получает актуальное состояние с проверкой действующей сессии. Серверные таймауты `ringing` и `connecting` продолжают действовать без продления из-за переподключения.

Поведение при потере аудиосоединения и обнаружение недоступности участников через WS-пинг определены ниже.

### Восстановление аудиосоединения — согласовано

При потере WebRTC-аудиосоединения во время разговора предоставляется окно восстановления, настраиваемое через `DIRECT_CALLS_RECONNECT_TIMEOUT_SECONDS` (см. [Конфигурацию](#конфигурация)). Во время восстановления звонок остаётся в `active` и сохраняет занятость обоих участников. Открытое окно восстановления содержит `recovery_id` и серверный срок завершения; клиенты показывают «Восстанавливаем соединение».

О потере аудиосоединения сообщает одно из выбранных устройств участников в WS-пинге с признаком неисправного аудиосоединения. Сервер запускает окно восстановления с момента получения первого такого сообщения либо обнаружения недоступности по WS-пингам (см. ниже). Повторные сообщения о потере и обнаружения недоступности в пределах текущего окна не продлевают срок.

Для успешного восстановления оба выбранных устройства должны прислать в пределах текущего окна WS-пинги с признаком исправного аудиосоединения и текущим `recovery_id`; повторы подтверждения одного устройства не заменяют подтверждение второго. После второго подтверждения окно восстановления закрывается, разговор продолжается в том же звонке в состоянии `active`. По истечении срока без подтверждений обоих устройств сервер переводит звонок в `ended` с причиной «соединение потеряно» и освобождает участников.

При открытии каждого окна сервер назначает новый `recovery_id`, который не переиспользуется в пределах звонка, и возвращает его в ответах на WS-пинги. Клиент передаёт полученный идентификатор в следующих пингах и указывает состояние аудиосоединения на момент их отправки. Задержавшийся пинг без текущего `recovery_id` или с идентификатором другого окна не подтверждает восстановление. Подтверждения первоначального соединения также не заменяют подтверждения текущего восстановления. Повторы пингов не продлевают срок окна и не заменяют подтверждение второго устройства.

Длительность разговора считается непрерывно по серверному времени от первого перехода в `active` до перехода в `ended`, включая все периоды восстановления аудио. Во время восстановления клиентский таймер продолжает идти; закрытие окна не обнуляет отсчёт.

Поля запроса и успешного ответа `call.ping` согласованы в разделе публичного API.

### Проверка доступности во время звонка — согласовано

Пинги начинаются, когда оба участника приняли звонок: инициатор подтвердил исходящий вызов при создании, получатель принял его, и сервер перевёл звонок в `connecting`. Они продолжаются в `active` и во время восстановления аудио. В `ringing` пинги не отправляются и контроль доступности по ним не ведётся; действует таймаут ожидания ответа. Устройства отправляют короткий WS-сообщение, привязанный к конкретному звонку и содержащий признак исправности WebRTC-аудиосоединения. Пинг сообщает о доступности отправившего его устройства и состоянии его аудио; штатную работу обоих устройств сервер определяет по пингам каждого из них. Пинги передаются по тому же авторизованному WebSocket-соединению. Во время разговора отсутствие пингов в течение установленного срока запускает окно восстановления; в `connecting` применяется только таймаут первоначального соединения.

Пинги принимаются только от выбранных устройств и сессий участников после принятия вызова и до его завершения. После завершения клиент прекращает отправку. Сервер отклоняет пинги в `ringing`, для завершённого или несуществующего звонка, а также запросы от остальных устройств и сессий. Пинг не создаёт звонок и не возобновляет завершённый.

Каждый пинг содержит `audio_connected`: `true`, когда WebRTC-соединение находится в состоянии `connected`, и `false`, когда оно находится в `disconnected`, `failed` или `closed`. До установления соединения значение также `false`. Признак описывает состояние соединения, а не наличие звука: молчание и выключенный микрофон не означают неисправность аудио.

Каждый пинг содержит возрастающий `sequence` в рамках звонка для отправившего его выбранного устройства. Счётчик не сбрасывается при открытии или закрытии окна восстановления. Сервер отдельно для каждого выбранного устройства принимает только номер больше последнего принятого; повторные и запоздавшие пинги не обновляют доступность, состояние аудио и подтверждения восстановления. `recovery_id` привязывает подтверждение к окну восстановления, а `sequence` определяет порядок пингов внутри окна и между окнами.

Сведения о доступности устройств в рамках звонка хранятся в Redis отдельно от сессий Auth. Для сохранения порядка пингов и атомарности восстановления после перезапуска принятый `sequence`, время пинга, состояние аудио и подтверждение восстановления также фиксируются в PostgreSQL в транзакции обработки пинга. PostgreSQL — источник истины; Redis содержит обновляемую после commit проекцию доступности, которая не может отменить более новое состояние. Сбой обновления проекции не откатывает уже принятый пинг; фоновый обработчик восстанавливает её из PostgreSQL.

Получение пинга подтверждает доступность клиента для backend. Пинг с исправным аудио и текущим `recovery_id` также подтверждает восстановление со стороны этого устройства по правилам выше. Пинг с неисправным аудио во время разговора запускает окно восстановления, если оно ещё не открыто. Получение любых пингов не продлевает текущее окно восстановления. Таймауты считаются по времени сервера; клиентские даты для привязки к окну не требуются.

Клиент отправляет пинги с фиксированным интервалом 10 секунд. Интервал не передаётся сервером в WS-протоколе и не настраивается через окружение backend. Срок обнаружения недоступности настраивается через `DIRECT_CALLS_HEARTBEAT_TIMEOUT_SECONDS` (см. [Конфигурацию](#конфигурация)). Если с последнего принятого сервером пинга устройства прошёл этот срок без нового пинга, сервер считает его недоступным. Во время разговора за обнаружением следует отдельное окно восстановления, а не немедленное завершение звонка.

Контроль обоих выбранных устройств начинается при переходе в `connecting`. До первого пинга каждого устройства срок отсчитывается от этого перехода, затем — от последнего принятого сервером пинга данного устройства.

### Несколько устройств получателя — согласовано

Входящий вызов отправляется на все зарегистрированные устройства получателя с действующей сессией. Первое принятое сервером подтверждение ответа атомарно выбирает устройство получателя для разговора. Остальные устройства прекращают показывать входящий вызов; их последующие попытки ответа не меняют выбранное устройство.

Перенос разговора между устройствами в первой версии не поддерживается. Связь устройства с сессией определена в [Devices](../devices.md), адресация — в [Signaling](../signaling.md), результаты проигравших команд — в таблице переходов ниже.

### Отклонение на одном устройстве — согласовано

Отклонение входящего вызова на одном из устройств получателя означает отказ от звонка целиком. Сервер переводит звонок из `ringing` в `ended` с причиной «отклонён», остальные устройства прекращают показывать вызов, оба участника освобождаются.

При конкурентных ответе и отклонении побеждает первая атомарно выполненная сервером команда. Если первым выполнено отклонение, последующий ответ не возобновляет звонок. Если первым выполнено принятие, последующее отклонение не завершает разговор. Отклонение и завершение принятого звонка — разные операции; проигравшая команда обрабатывается по таблице переходов ниже.

### Устройство инициатора — согласовано

Исходящий звонок закрепляется за устройством и сессией, которые его создали. Только они могут со стороны инициатора отправлять SDP / ICE, подтверждать соединение, отменять исходящий вызов и завершать разговор. Остальные устройства и сессии того же аккаунта не могут управлять этим звонком или перехватить его.

Проверки выполняет backend для WebSocket-сообщений. Привязка к устройству и сессии должна сохраняться вместе со звонком в PostgreSQL. Схема хранения определена ниже, связь устройства с сессией — в [Devices](../devices.md).

### Устройство получателя после ответа — согласовано

После принятия вызова управление со стороны получателя закрепляется за выбранным устройством и сессией, выполнившими принятие. Только они могут отправлять SDP / ICE, подтверждать соединение и завершать разговор со стороны получателя. Остальные устройства и сессии аккаунта не могут вмешиваться в принятый звонок или перехватывать его.

Привязка сохраняется в PostgreSQL, проверки выполняются backend для WebSocket-сообщений симметрично правилам устройства инициатора.

### Отзыв участвующей сессии — согласовано

При отзыве сессии, за которой закреплён звонок со стороны инициатора или ответившего получателя, сервер при обнаружении отзыва переводит незавершённый звонок в `ended` и освобождает обоих участников. Клиенты при получении завершения отключают аудио. Отзыв другой сессии того же аккаунта, не участвующей в звонке, не влияет на разговор.

До ответа устройство и сессия получателя ещё не выбраны: отзыв одной из его сессий сам по себе не завершает входящий вызов для остальных устройств с действующими сессиями.

Проверка отзыва и конкуренции определена в разделе «Проверка доступа во время звонка» ниже; причина завершения — `session_revoked`. Серверное завершение не означает принудительного мгновенного отключения WebRTC-аудио на недоступном клиенте.

### Отключение аккаунта — согласовано

При отключении аккаунта любого участника сервер при обнаружении отключения переводит его текущий незавершённый звонок в `ended` и освобождает обоих участников. Правило действует в `ringing`, `connecting` и во время разговора, включая окно восстановления аудио. Клиенты при получении завершения отключают аудио и прекращают показывать вызов.

Новые звонки с отключённым аккаунтом запрещены независимо от того, инициатор он или получатель. Проверка отключения и конкуренции определена в разделе «Проверка доступа во время звонка» ниже; причина завершения — `account_disabled`.

### Ошибка создания звонка — согласовано

Если создание звонка завершилось ошибкой, клиент сразу сообщает об этом пользователю и не повторяет запрос автоматически. Предложение передавать клиентский ключ попытки для повторного создания не принято.

При явном отказе сервера показывается понятная причина. Если ответ потерян и результат неизвестен, клиент сообщает, что не удалось подтвердить создание звонка, не утверждая, что звонок точно не создан. Обрыв запроса не отменяет уже выполненную сервером транзакцию. После восстановления WS-соединения клиент отправляет отдельный запрос «мой текущий звонок». Сервер возвращает незавершённый звонок текущего пользователя либо отсутствие такого звонка; запрос не создаёт вызов. Наличие звонка не даёт другому устройству права управлять им. Отсутствие текущего звонка не доказывает, что предыдущая попытка никогда не создавала уже завершённый вызов. Новая попытка создания выполняется только вручную; серверные правила занятости продолжают действовать.

### Повторы и конкурентные команды — согласовано

Правила применяются к авторизованным командам существующего звонка с проверкой прав устройства и сессии; повтор не обходит эти проверки.

- Повтор принятия с уже выбранного устройства и сессии получателя в `connecting` или `active` возвращает актуальное состояние, не меняет выбранное устройство и не продлевает таймаут соединения.
- Отмена, отклонение и завершение для звонка в `ended` возвращают его конечное состояние без изменения исходной причины завершения и без повторных побочных эффектов. Это правило действует и если звонок завершился по другой причине.
- В остальных случаях команда, неприменимая к текущему состоянию, возвращает конфликт: например, отмена после принятия или принятие после отмены. Принятие после `ended` не возобновляет звонок.
- При конкурентных командах побеждает первая атомарно выполненная смена состояния в PostgreSQL. Остальные команды обрабатываются относительно полученного состояния по правилам выше; завершённый звонок не меняет причину завершения.

Создание звонка не входит в эти правила повторов: автоматический повтор создания по-прежнему запрещён.

### Проверка доступа во время звонка

DirectCalls проверяет активность обоих аккаунтов и закреплённых сессий перед изменяющей командой и независимо от WS-подключений фоновым обходом каждые 5 секунд. В `ringing` закреплена только сессия инициатора. Используется проверка Auth по ID сессии, без повторной проверки срока старого JWT: истечение JWT после handshake не завершает соединение или звонок.

Перед созданием и принятием Auth блокирует строки обоих аккаунтов `FOR SHARE` в порядке UUID, повторно проверяет `disabled_at` в этой транзакции. Отключение аккаунта обновлением той же строки либо предшествует операции, либо ждёт её commit. Сессии проверяются непосредственно перед фиксацией изменения. Общей атомарной транзакции PostgreSQL и Redis нет: отзыв после последней успешной проверки может пересечься с commit. Такой звонок завершается при следующем обнаружении отзыва. После commit создания/принятия выполняется дополнительная проверка; её сбой не выдаётся за откат уже выполненной команды.

Pub/Sub и новая очередь фактов Auth не вводятся. Фоновый обход читает актуальное состояние через Auth даже для звонков без подключённых клиентов. После обнаружения отключения аккаунта применяется `account_disabled`, иначе при отсутствии закреплённой сессии — `session_revoked`; первое зафиксированное завершение остаётся неизменным. Обнаружение занимает до 5 секунд плюс бюджеты зависимостей и обработки. Если backend недоступен, проверка выполняется при восстановлении; мгновенное серверное завершение при недоступном сервере не обещается. Недоступность зависимости не равна отзыву и не меняет причину на `session_revoked`; обработчик повторяет проверку, WS закрывается по правилам Auth. Просроченные таймауты применяются при первой успешной обработке.

### Таблица команд и переходов

Перед результатами таблицы всегда выполняются Auth, проверка участника и устройства. `NOT_FOUND` скрывает чужой звонок, `FORBIDDEN` запрещает действие неподходящему устройству. В таблице конфликт означает `CALL_STATE_CONFLICT`. Изменения сериализуются блокировкой строки звонка `FOR UPDATE`; после ожидания перечитываются состояние и серверные сроки. Истёкший срок обрабатывается до команды, команда не продлевает дедлайн.

| Команда | `ringing` | `connecting` | `active` | `ended` |
| --- | --- | --- | --- | --- |
| `call.get` | Текущее состояние | Текущее состояние | Текущее состояние | Конечное состояние до удаления по сроку хранения |
| `call.accept` | Получатель: выбор устройства, переход в `connecting` | Повтор выбранного получателя: текущее состояние | Повтор выбранного получателя: текущее состояние | Конфликт |
| `call.reject` | Получатель: `ended/rejected` | Конфликт | Конфликт | Повтор с сохранением конечного состояния |
| `call.cancel` | Выбранный инициатор: `ended/cancelled` | Конфликт | Конфликт | Повтор с сохранением конечного состояния |
| `call.end` | Конфликт | Выбранный участник: `ended/hangup` | Выбранный участник: `ended/hangup` | Повтор с сохранением конечного состояния |
| `call.connected` | Конфликт | Подтверждение текущей попытки выбранного устройства; второе переводит в `active` | Повтор выбранного устройства для текущей попытки: текущее состояние | Конфликт |
| `call.ice_config` | Конфликт | Конфигурация выбранному участнику | Конфигурация выбранному участнику | Конфликт |
| `call.ping` | Конфликт | Обновление доступности | Обновление доступности и обработка восстановления | Конфликт |

`call.current` во всех состояниях возвращает единственный незавершённый звонок пользователя или `null`. `call.create` разрешён только при свободных обоих участниках и успешных проверках доступа. Все устройства получателя могут принять/отклонить входящий `ringing`; после выбора устройства остальные не получают право управлять разговором. Для повторов в `ended` проверяется сохранённая привязка: отмена — исходное устройство/сессия инициатора, завершение — выбранное устройство/сессия участника, отклонение — действующее зарегистрированное устройство/сессия аккаунта получателя. Повтор отклонения не даёт этому устройству иных прав управления завершённым звонком. Чтение доступно всем действующим сессиям участника.

Повторный/меньший `sequence` пинга возвращает текущий компактный ответ пинга без обновления доступности. Первый номер — `1`; номер — положительное безопасное целое JSON, счётчик клиент хранит до завершения звонка, включая переподключения. Повтор `call.connected` для текущей попытки не меняет время первого подтверждения этой попытки. Первое подтверждение не меняет общий DTO и `version`; переход в `active` меняет. Все поля DTO одной версии читаются из одного согласованного снимка; версия увеличивается один раз на транзакцию изменения DTO.

При восстановлении пинги, обрабатываемые сервером строго раньше `recovery_deadline`, могут подтверждать окно; обработчик сначала проверяет истечение срока по серверному времени. При открытии окна подтверждения обоих устройств пусты, прежние пинги не учитываются. Принятый пинг с `audio_connected: false` снимает подтверждение своего устройства в текущем окне. После второго актуального подтверждения окно закрывается в той же транзакции. На точной границе срока завершение имеет приоритет.

### PostgreSQL: схема и атомарность

Идентификаторы звонков, устройств, сессий и окон восстановления — UUID; серверные ID генерируются сервером. Даты — `timestamptz`, сериализация UTC; `version` и `sequence` — неотрицательные/положительные `bigint` с ограничением безопасного целого JSON `9007199254740991`. Сырые токены доступа, refresh token, SDP и ICE в таблицы DirectCalls и логи не записываются.

| Таблица | Данные и ограничения |
| --- | --- |
| `gchat_direct_calls` | UUID `id`; `caller_id`, `recipient_id` (FK Auth, удаление RESTRICT); `state`; все согласованные даты, причина и версия; `connecting_started_at`; `recovery_started_at`; `negotiation_id` (UUID, nullable до первого offer). CHECK разных пользователей, допустимых состояний/причин, соответствия `ended_at/end_reason` состоянию и согласованной пары recovery-полей. `started_at` сохраняется при завершении. |
| `gchat_direct_call_participants` | `(call_id, role)` PK, role `caller/recipient`; `user_id`, выбранные `device_id/session_id`, `connected_at`, `connected_negotiation_id`, `last_sequence` (начально 0), `last_ping_at`, `audio_connected`, `confirmed_recovery_id`, `released_at`. Ровно две записи создаются со звонком; инициатор выбран сразу, получатель — при принятии. Уникальный частичный индекс `user_id WHERE released_at IS NULL` защищает от двух незавершённых звонков даже при истечении резерва Redis. |
| `gchat_direct_call_deliveries` | UUID `id`, FK `call_id`, `kind` (`state/voip`), `version`, неизменяемый JSON DTO для `state`, `device_id/session_id` для `voip`; `status` (`pending/processing/done/cancelled`), `attempts`, `next_attempt_at`, `lease_token`, `lease_until`, `created_at/completed_at`. Уникальность `(call_id, version)` для state и `(call_id, device_id, session_id)` для voip. Не хранит push-токен: он разрешается Devices при попытке. |

Индексы: `(caller_id, created_at)` и `(recipient_id, created_at)`; частичные индексы сроков незавершённых звонков; `(next_attempt_at)` для pending-доставок и `(lease_until)` для processing; индекс участников по `session_id`. Даты обновляются сервером внутри транзакции; `created_at` и начальный дедлайн берутся после получения необходимых блокировок, а не в начале ожидания.

Создание в одной транзакции записывает звонок, обоих участников, state-задание версии 0 и задания VoIP зарегистрированным устройствам получателя с действующими сессиями. Принятие атомарно выбирает устройство и сессию, задаёт срок `connecting` и отменяет ещё не отправленные задания VoIP. Завершение атомарно задаёт конечные поля, освобождает участников в PostgreSQL, отменяет неактуальные задания VoIP и создаёт state-задание. Освобождение Redis выполняется после commit и безопасно повторяется.

Обработка пинга под блокировкой звонка сохраняет номер, доступность и изменения восстановления в той же транзакции. Проекция Redis обновляется только после commit с проверкой, что её номер не новее записываемого. PostgreSQL-копия нужна для согласования пинга, версии и события; она не создаёт отдельного пользовательского события на каждый пинг. Ошибка после commit означает неизвестный клиенту результат, а не откат; `call.get/current` и повторы разрешённых команд возвращают актуальное состояние.

Порядок блокировок: аккаунты по UUID → выбранная общая группа и членства (только создание обычным инициатором) → advisory lock call_id для создания/очистки → звонок → участники → задания. Таймаут ожидания и deadlock дают `SERVICE_UNAVAILABLE`; автоматического повторного создания от имени клиента нет. Другие обработчики используют тот же порядок и не держат транзакцию во время сетевой отправки.

### Redis: резервы, доступность и восстановление

Все логические ключи проходят через `RedisService.key()`:

| Ключ | Значение | Срок |
| --- | --- | --- |
| `direct-calls:busy:<user_id>` | UUID `call_id` | 60 секунд, продление каждые 10 секунд для незавершённого звонка |
| `direct-calls:presence:<call_id>:<role>` | `version`, `sequence`, `last_ping_at`, `audio_connected`, `confirmed_recovery_id` | 60 секунд; восстановление из PostgreSQL при отсутствии |

Lua резервирует обоих участников целиком или никого. Повтор внутренней проверки с тем же `call_id` идемпотентен; чужое значение не перезаписывается. Ошибка Redis не означает «свободен». Предварительная проверка аккаунтов и разрешения на звонок выполняется до раскрытия занятости; окончательная проверка выполняется в транзакции создания. Если оба заняты, приоритет ошибки — `CALLER_BUSY`.

Успех Redis не создаёт звонок. После резерва транзакция PostgreSQL повторно проверяет доступ и уникальность занятости. Частичный индекс участников — окончательная защита от гонки после истечения Redis TTL; конфликт преобразуется в соответствующий код занятости. Подтверждённый откат освобождает только свои резервы. При неизвестном commit сначала проверяется PostgreSQL по заранее созданному `call_id`; до разрешения результата резерв не снимается вручную. Падение до commit оставляет лишь временный резерв, который истечёт. Поздний commit не может обойти уникальный индекс. Нельзя освобождать резерв по одному факту клиентского таймаута.

При запуске до допуска новых созданий и затем каждые 10 секунд обработчик сопоставляет незавершённые звонки PostgreSQL с резервами. Восстанавливает отсутствующие свои ключи и продлевает только совпадающий `call_id`. При чужом временном резерве создание всё равно запрещает PostgreSQL; обработчик не стирает чужой ключ без проверки его звонка. Резерв завершённого/отсутствующего звонка снимается сравнением `call_id`; неизвестный результат БД запрещает очистку. Проверка и очистка сериализуются с транзакцией того `call_id` через транзакционный advisory lock PostgreSQL от хеша UUID, в том числе до появления строки звонка. Создание после получения этой блокировки повторно проверяет принадлежность обоих резервов; при утрате резерва не выполняет commit создания. Коллизия хеша лишь сериализует независимые операции. Этот lock берётся после блокировок аккаунтов/членства и до строки звонка; обработчик очистки не запрашивает обратным порядком аккаунты или группы. TTL остаётся страховкой от падения до появления строки звонка.

Истечение/потеря presence не считается потерей аудио само по себе: обработчик читает сохранённые сведения PostgreSQL. Для каждого устройства используется его `last_ping_at` или момент перехода в `connecting`. После восстановления backend все просроченные сроки обрабатываются до допуска новых команд изменения; переподключение клиентов их не продлевает. Аварийная потеря всего Redis с сессиями Auth по-прежнему относится к отдельной эксплуатационной процедуре, а не к автоматическому восстановлению доступа.

### Срок хранения и обслуживание

Метаданные завершённого звонка, участники и задания хранятся 30 суток от `ended_at`, затем удаляются каскадно. Это технические записи, история звонков в UI не добавляется. После удаления `call.get` возвращает `NOT_FOUND`. Pending-задание state не повторяется дольше 24 часов от создания: состояние восстанавливается по WS-запросу, задание помечается cancelled с безопасной причиной. Незавершённый звонок по сроку хранения не удаляется. Удаление не должно оставлять активную обработку задания: lease проверяется при завершении попытки. Очистка выполняется ежедневно; при недоступности БД повторяется после восстановления.

Обработчик сроков запускается при старте и далее каждую секунду; обработчик проверки Auth — каждые 5 секунд. Пропущенные циклы не накапливаются параллельно. Защита строк и lease допускает безопасный повтор работы после перезапуска; это не обещание горизонтального масштабирования первой версии.

## Зависимости и регистрация

DirectCallsModule — обычный NestJS-модуль без `@Global()`, `forRoot()` и `forFeature()`. Импортирует DatabaseModule, GroupsModule, AuthModule и DevicesModule. Использует глобальные RedisService, ErrorService и LoggerService через DI. В AppModule подключается вместе с Signaling; SignalingModule импортирует DirectCallsModule. Прямая зависимость DirectCalls от SignalingModule и циклический импорт не вводятся.

Экспортирует DirectCallsService. Репозиторий, обработчик таймаутов и восстановление резервов — внутренние провайдеры. Фоновая доставка заданий `call.updated` принадлежит SignalingModule; отправка APNs — PushModule. Оба обработчика читают задания из таблиц владельца через экспортируемый `DirectCallsDeliveryStore`, без прямой записи в чужую схему. Обработчики работают в том же единственном backend, отдельного брокера или процесса нет.

Внутренние интерфейсы реализации:

```ts
// Контекст создаётся Signaling после Auth и Devices, не из payload команды.
type CallActor = { userId: string; sessionId: string; deviceId: string };
// Методы возвращают общий CallDto, обёртку payload.call формирует Signaling.
create(actor: CallActor, recipientId: string): Promise<CallDto>
get(actor: CallActor, callId: string): Promise<CallDto>
current(actor: CallActor): Promise<CallDto | null>
accept(actor: CallActor, callId: string): Promise<CallDto>
reject(actor: CallActor, callId: string): Promise<CallDto>
cancel(actor: CallActor, callId: string): Promise<CallDto>
end(actor: CallActor, callId: string): Promise<CallDto>
connected(actor: CallActor, callId: string, negotiationId: string): Promise<CallDto>
iceConfig(actor: CallActor, callId: string): Promise<CallIceConfigDto>
ping(actor: CallActor, input: CallPingDto): Promise<CallPingResponseDto>
// Для rtc.* проверяет выбранного участника и выполняет callback(tx) под блокировкой звонка.
withSelectedPeer<T>(actor, callId, callback: (tx, call, peer, isCaller) => Promise<T>): Promise<T>
// Signaling вызывает внутри callback при принятии нового offer; сброс подтверждений в той же tx.
registerNegotiation(tx, call, negotiationId): Promise<void>
// DeliveryStore: claim(kind, limit), complete(id, leaseToken), retry(id, leaseToken).
```

Auth предоставляет `checkSession(userId, sessionId)`, `lockActiveAccounts(tx, userIds)` и `lockActiveAccountRoles(tx, userIds)`; Groups — `lockCommonGroup(tx, firstId, secondId)`. Auth остаётся владельцем проверки сессии и активности аккаунта, Groups — SQL членства; DirectCalls не читает их Redis-ключи и таблицы самостоятельно. Реализация и ограничения этих методов описаны в контрактах владельцев.

## Ошибки и частичное выполнение

Общий формат и базовые коды ошибок задаёт [ErrorModule](../errors.md#коды-и-http-статусы), включая `SERVICE_UNAVAILABLE` и `INTERNAL_ERROR`. DirectCalls использует эти коды с определённым там смыслом, без отдельного определения в своём контракте.

Для отсутствующего звонка и звонка, в котором пользователь не участвует, возвращается одинаковый базовый код `NOT_FOUND`, без раскрытия существования чужого звонка. Если пользователь участвует в звонке, но его устройство или сессия не имеет права выполнить команду, используется базовый код `FORBIDDEN`.

Специфичные коды DirectCalls — согласовано:

| Код | Условие отказа |
| --- | --- |
| `CALL_NOT_ALLOWED` | Создание запрещено: звонок самому себе, отсутствие общей группы у обычного инициатора, получатель отсутствует или отключён. Безопасное сообщение: «Не удалось позвонить этому пользователю». |
| `CALLER_BUSY` | У инициатора уже есть незавершённый звонок. |
| `RECIPIENT_BUSY` | У получателя уже есть незавершённый звонок. |
| `CALL_STATE_CONFLICT` | Команда недопустима в текущем состоянии с учётом согласованных правил повторов. |

Проверки доступа выполняются до проверки занятости, чтобы пользователь без права на звонок не мог узнать занятость получателя. Серверные таймауты звонка отражаются переходом в `ended` с соответствующим `end_reason`, а не отдельным кодом ошибки команды.

Потеря ответа на WS-команду не доказывает, что команда не выполнена. Для создания клиент сообщает об ошибке без автоматического повтора (см. [Ошибка создания звонка](#ошибка-создания-звонка--согласовано)); остальные команды учитывают текущее состояние звонка. Поведение при обрыве сигнализации определено в разделе [Обрыв WebSocket](#обрыв-websocket--согласовано), при потере аудио — в разделе [Восстановление аудиосоединения](#восстановление-аудиосоединения--согласовано).

### Передача изменений в Signaling — согласовано

Каждое state-задание содержит неизменяемый полный DTO конкретной версии, сохранённый в транзакции изменения. Повтор отправляет тот же DTO и ту же `version`, а не перечитывает состояние для подмены содержимого задания. Строгий порядок доставки между заданиями не требуется; клиент применяет правила версий общего DTO и компактного ответа пинга: меньшие версии игнорируются, полный DTO уже известной только по пингу версии может заполнить отсутствующие поля. Отдельные ответы на команды и события могут приходить в разном порядке.

DeliveryStore выбирает готовые задания через `FOR UPDATE SKIP LOCKED`, выдаёт случайный `lease_token` с арендой 30 секунд и завершает транзакцию до передачи в сеть. Подтверждение/повтор принимаются только с текущим токеном аренды; просроченные processing-задания снова доступны. Первая попытка — сразу после commit, повторы через 1, 2, 4, 8, 16 и далее 30 секунд со случайным увеличением до 20%. Лимита числа попыток до предельного возраста задания нет. Неизвестный результат отправки разрешается повтором того же задания; возможен дубликат. Исчерпание срока, ошибки и возраст очереди отражаются безопасными логами без DTO, SDP и токенов.

При создании и каждом изменении общего состояния звонка состояние и задание на доставку `call.updated` сохраняются в одной транзакции PostgreSQL. Фоновый обработчик передаёт событие в Signaling и повторяет попытку при сбое. Повторная доставка может приводить к дубликатам; клиент обрабатывает их по `version` согласно правилам общего DTO состояния. Механизм реализован через DirectCallsDeliveryStore и обработчик Signaling.

Задание доставки `call.updated` не ожидает подключения отключённых устройств. Signaling отправляет событие текущим авторизованным WS-подключениям участников; отсутствие подключения у одного или всех устройств само по себе не препятствует завершению задания. Отключённые устройства получают актуальное состояние WS-запросом после подключения. Доставка APNs VoIP push для входящего вызова выполняется отдельно и не заменяется этим заданием. Сбой передачи в Signaling по-прежнему требует повторной попытки.

После перезапуска backend восстанавливает незавершённые задания доставки и завершает просроченные звонки. Доставка push ограничена сроком жизни вызова. Успех задания означает, что Signaling обработал актуальный набор подключений: поставил сообщение в очередь отправки доступных соединений, а неисправные или медленные соединения закрыл. Это не подтверждение получения клиентом. Клиентский ACK не используется; после переподключения клиент получает актуальное состояние по WS согласно правилам выше. Чтение состояния из PostgreSQL не означает наличия готового механизма доставки.

### Web Push в outbox — проект расширения

Предложение по [D010](../../../architecture/decisions/D010-web-push-pwa.md). Принятый outbox выше описывает `state/voip`; для браузерного контура предлагается дополнительный `kind: web_push` в той же таблице `gchat_direct_call_deliveries`.

- В транзакции создания звонка сохраняются отдельные адресные задания для зарегистрированных Web Push-подписок получателя с действующей сессией. Выбор целей принадлежит [Devices](../devices.md#web-push--проект-расширения).
- Задание содержит `call_id`, device/session и служебные поля доставки; endpoint, ключи подписки и access token в него не копируются. Уникальность `(call_id, device_id, session_id)` задаётся отдельным частичным индексом для `web_push`.
- Принятие, отклонение, отмена и иные выходы из `ringing` отменяют ожидающие и обрабатываемые `web_push` по тому же правилу, что VoIP. Отправка, уже находящаяся в сети, транзакцией не отзывается.
- Аренда, повтор и защита от устаревшего lease используют существующий DeliveryStore. Правила провайдера и сроков принадлежат [Push](../push.md#web-push--проект-расширения).
- WSS, Web Push и APNs независимы; отсутствие браузерной подписки не отменяет звонок. Состояния, выбор победившего устройства и дедлайны звонка не меняются.

Изменение требует следующей миграции: таблица подписок по контракту Devices, расширение CHECK `kind` и новый частичный индекс outbox. Существующие миграции не редактируются, применение выполняется отдельно от старта приложения. Начатая миграция не означает готовности интеграционных проверок.

## Конфигурация

Настройки серверных таймаутов:

| Переменная | Значение по умолчанию | Формат |
| --- | --- | --- |
| `DIRECT_CALLS_RINGING_TIMEOUT_SECONDS` | `60` | Положительное целое число секунд |
| `DIRECT_CALLS_CONNECTING_TIMEOUT_SECONDS` | `30` | Положительное целое число секунд |
| `DIRECT_CALLS_RECONNECT_TIMEOUT_SECONDS` | `30` | Положительное целое число секунд |
| `DIRECT_CALLS_HEARTBEAT_TIMEOUT_SECONDS` | `30` | Положительное целое число секунд |

При отсутствии переменной используется её значение по умолчанию. Некорректное значение любой из переменных должно приводить к ошибке конфигурации при запуске backend. Настройки добавлены в валидацию окружения и `.env.example`.

Подключения к хранилищам принадлежат [Database](../database.md) и [Redis](../redis.md). Конфигурация APNs принадлежит Push. DirectCalls валидирует обязательные `DIRECT_CALLS_TURN_URLS` (непустой JSON-массив непустых `turn:`/`turns:` URL) и `DIRECT_CALLS_TURN_SHARED_SECRET` (непустой секрет, совпадающий с настройкой собственного coturn). Отсутствие/некорректное значение запрещает запуск включённого модуля; значений по умолчанию нет. Секрет не логируется и не включается в мобильное приложение. Срок credentials — 3600 секунд; часы backend и coturn должны быть синхронизированы.

## Критерии приёмки и проверки

- `call.ice_config` выдаёт конфигурацию только выбранным участникам в допустимых состояниях; проверяются срок credentials, повторное получение, обновление во время длительного звонка и безопасный отказ конфигурации без раскрытия секрета.
- `call.connected` принимает `call_id` и `negotiation_id`; старое подтверждение не объединяется с новой попыткой. Новый offer сбрасывает оба подтверждения в `connecting`, повтор того же offer — нет; дедлайн сохраняется. После перезапуска новый offer предшествует новым подтверждениям.

- Первоначальное соединение и восстановление используют ICE-политику `relay`; выбранный ICE-маршрут подтверждает передачу аудио через coturn даже при доступном прямом пути.
- При недоступном TURN-пути прямое P2P-соединение не используется; звонок завершается по действующим таймаутам соединения или восстановления.

- WS-запросы содержат `type`, `request_id` и `payload`; ответы `response` возвращают тот же `request_id` и либо `payload`, либо `error` с `code` и `message`. Событие `call.updated` не содержит `request_id`.
- Команды, запросы состояния и прикладные пинги DirectCalls передаются через WSS; ответы и ошибки коррелируются по `request_id`. После потери ответа на создание отдельный WS-запрос «мой текущий звонок» возвращает незавершённый звонок пользователя либо его отсутствие без повторного создания.

- `call.create.payload` содержит только `recipient_id`; инициатор, устройство и сессия определяются по авторизованному WS-соединению, поля сообщения не позволяют их подменить.
- `call.get`, `call.accept`, `call.reject`, `call.cancel`, `call.end` и `call.ice_config` принимают только `call_id` в `payload`; `call.current` принимает пустой объект и определяет пользователя по WS-соединению. Все запросы сохраняют проверки прав.
- Остальные устройства аккаунта участника с действующей сессией могут читать тот же общий DTO через `call.get` и `call.current`; чтение не расширяет права управления звонком и сигнализации.
- `call.updated` направляется всем авторизованным подключённым по WebSocket устройствам обоих участников, включая не выбранные для разговора; событие не расширяет их права управления или обмена SDP / ICE.
- Создание и каждое изменение общего состояния сохраняются в одной транзакции PostgreSQL с заданием доставки `call.updated`; фоновый обработчик повторяет передачу в Signaling при сбое. Дубликат события не перезаписывает более новое состояние на клиенте.
- `call.ping.payload` содержит `call_id`, `sequence`, `audio_connected` и `recovery_id`; до получения идентификатора открытого окна `recovery_id` равен `null`. Клиентские даты не требуются и не передаются.
- Успешный ответ на `call.ping` содержит `state`, `version`, `recovery_id` и `recovery_deadline`. Задержавшийся ответ с меньшей версией не очищает и не заменяет новое окно; полный DTO той же версии заполняет поля, отсутствующие в компактном ответе. При открытом окне возвращаются его идентификатор и срок; после закрытия оба поля равны `null`, клиент очищает идентификатор для следующих пингов.
- Серверные даты WS-контракта передаются в UTC в формате `YYYY-MM-DDTHH:mm:ss.SSSZ`; отсутствующий `recovery_deadline` — `null`.
- Нельзя создать звонок самому себе или с недопустимым аккаунтом. Обычный инициатор не может звонить без общей группы; администратор может звонить любому другому активному пользователю, включая пользователей других групп и случай отсутствия собственного членства. Право проверяется по актуальной роли аккаунта на backend, в том числе в транзакции создания. Расширение доступа администратора реализовано.
- Ошибка создания сразу отображается пользователю без автоматического повторного запроса. При потере ответа клиент не выдаёт неизвестный результат за подтверждённое отсутствие звонка.
- Потеря последнего общего членства после создания звонка не мешает его принятию, установлению соединения и продолжению разговора, но запрещает новые звонки обычным инициатором; для инициатора-администратора общая группа не требуется.
- Каждый из статусов `ringing`, `connecting` и `active` запрещает новый звонок для обоих участников, в том числе с другого устройства; `ended` освобождает занятость.
- Конкурентные создания с общим участником, включая встречные вызовы, создают только один звонок; проигравший запрос получает «занято».
- Lua-скрипт резервирует обоих участников в Redis целиком либо не резервирует никого. При подтверждённом откате создания резерв снимается; неизвестный результат требует проверки PostgreSQL. Освобождение проверяет `call_id` и не снимает резерв другого звонка.
- Подмена `call_id` не даёт доступа постороннему пользователю к состоянию или SDP / ICE.
- Другое устройство или сессия аккаунта инициатора не может отправлять SDP / ICE, подтверждать соединение, отменять или завершать его звонок; проверки действуют для WebSocket.
- После принятия вызова другое устройство или сессия аккаунта получателя не может отправлять SDP / ICE, подтверждать соединение или завершать разговор; проверки действуют для WebSocket.
- Повторы команд и конкурентные ответы не создают дубликаты и не выбирают два устройства получателя.
- Повтор принятия выбранным устройством и сессией в `connecting` или `active` возвращает актуальное состояние без изменения устройства и срока соединения. Отмена, отклонение и завершение в `ended` возвращают конечное состояние без смены причины и повторных побочных эффектов. Остальные неприменимые команды дают конфликт; при гонках результат определяется первой атомарной сменой состояния с последующим применением правил повторов. Проверки прав сохраняются.
- Вызов направляется всем зарегистрированным устройствам получателя с действующей сессией. После первого принятого сервером ответа остальные прекращают показывать вызов и не могут перехватить разговор; перенос разговора между устройствами отсутствует.
- Отклонение на одном устройстве завершает весь входящий вызов с причиной «отклонён» и освобождает участников. При гонке с ответом побеждает первая атомарно выполненная команда; позднее отклонение не завершает принятый звонок, поздний ответ не возобновляет отклонённый.
- Гонки отмены, ответа, завершения и таймаута дают определённый конечный результат.
- Перезапуск backend и отключение клиента не оставляют просроченный звонок в ожидании.
- Таймаут ожидания ответа использует значение из окружения либо значение по умолчанию. Без ответа получателя звонок завершается с причиной «нет ответа» и освобождением обоих участников; задержка push не сдвигает срок ожидания.
- Таймаут соединения использует значение из окружения либо значение по умолчанию. Без установленного соединения звонок завершается с причиной «не удалось соединиться» и освобождает участников; повтор принятия не сдвигает срок.
- Наличие или отсутствие пингов в `connecting` не меняет таймаут первоначального соединения и не запускает дополнительное окно восстановления.
- Некорректное значение любого из таймаутов отклоняется при запуске backend.
- Переход в `active` и начало отсчёта длительности происходят после подтверждений обоих выбранных устройств. Одно подтверждение или его повторы оставляют звонок в `connecting` с действующим таймаутом.
- После восстановления соединения клиент получает актуальное состояние и корректно обрабатывает повторы и устаревшие сообщения.
- Обрыв WebSocket прекращает пинги: в `active` по таймауту доступности открывается окно восстановления даже при работающем аудио, а без подтверждений обоих устройств до его окончания звонок завершается. Переподключение не продлевает таймауты `ringing` и `connecting`.
- При потере аудио участники остаются заняты на время окна восстановления; клиенты показывают «Восстанавливаем соединение». Восстановление в пределах окна продолжает тот же звонок, истечение срока завершает его с причиной «соединение потеряно» и освобождает участников.
- Во время восстановления звонок остаётся в `active`; окно содержит `recovery_id` и серверный срок завершения. Успешное восстановление закрывает окно без смены состояния, истечение срока без подтверждений обоих устройств переводит звонок в `ended`.
- Длительность непрерывно отсчитывается от первого перехода в `active` до `ended`, включая периоды восстановления. Клиентский таймер во время восстановления не останавливается и после него не обнуляется.
- Окно восстановления аудио использует значение из окружения либо значение по умолчанию.
- Окно восстановления начинается при получении сервером первого сообщения о потере аудио от выбранного устройства либо при обнаружении недоступности по WS-пингам; повторы не продлевают срок. Успешное восстановление требует подтверждений обоих выбранных устройств в текущем окне.
- WS-пинги и контроль доступности обоих выбранных устройств начинаются при переходе в `connecting`, продолжаются во время разговора и восстановления аудио через WebSocket. В `ringing` пинги не отправляются и отклоняются сервером. После завершения отправка прекращается, сервер отклоняет дальнейшие пинги. Пинги передают состояние аудио и не продлевают окно восстановления.
- Сервер возвращает текущий `recovery_id` в ответах на пинги. Только пинги с исправным аудио и идентификатором текущего окна от обоих выбранных устройств подтверждают восстановление; пинги без этого идентификатора, с идентификатором другого окна и подтверждения первоначального соединения не засчитываются. Каждое новое окно получает новый идентификатор; повтор одного устройства не заменяет пинг второго. Клиентские часы не участвуют в проверке окна и расчёте таймаутов.
- Клиент отправляет WS-пинги каждые 10 секунд. Поле `heartbeat_interval_seconds` отсутствует в WS-протоколе; сервер не передаёт интервал и не имеет переменной окружения для его настройки.
- `audio_connected` отражает состояние WebRTC-соединения: `connected` даёт `true`, до установления соединения и при `disconnected`, `failed`, `closed` — `false`. Молчание и выключенный микрофон не меняют исправность соединения.
- Пинги каждого выбранного устройства обрабатываются по возрастающему `sequence` в рамках звонка, без сброса между окнами восстановления. Повторный или меньший номер не обновляет доступность, состояние аудио и подтверждения восстановления; номера двух устройств сравниваются независимо.
- До первого пинга срок отсутствия пингов отсчитывается от перехода в `connecting`, затем — от последнего принятого сервером пинга данного устройства; используется значение из окружения либо значение по умолчанию. Во время разговора по истечении срока запускается отдельное окно восстановления; звонок не завершается немедленно.
- Отзыв сессии закрывает доступ к HTTP и установленному WebSocket.
- Отзыв закреплённой за звонком сессии завершает незавершённый звонок и освобождает обоих участников; клиенты при получении завершения отключают аудио. Отзыв посторонней сессии аккаунта не завершает звонок.
- Отключение аккаунта любого участника завершает текущий звонок при ожидании ответа, соединении, разговоре и восстановлении аудио с освобождением обоих участников; новые звонки с этим аккаунтом запрещены.
- Входящий вызов на реальном iPhone проверяется в открытом приложении, в фоне и на заблокированном экране вместе с Push и iOS-клиентом.

- Гонка удаления последнего членства с созданием соблюдает блокировки; для обычного инициатора отсутствие общей группы не превращается в «занято».
- Падение после резервирования Redis, до/после commit и до/после отправки задания не создаёт два звонка и не оставляет бессрочную ложную занятость.
- Истечение Redis TTL во время паузы процесса не обходит уникальность участников PostgreSQL.
- Отзыв/отключение обнаруживается и без WS-подключений; сбой зависимости не выдаётся за отзыв.
- Перезапуск сохраняет версии, номера пингов и подтверждения восстановления; старый/ложный пинг не закрывает новое окно.
- Фоновая доставка использует неизменяемые снимки и аренды; отсутствие клиентов не удерживает задание, отсутствует клиентский ACK.
- После 30 суток удалённый завершённый звонок возвращает `NOT_FOUND`; очистка не удаляет незавершённый звонок.

`test/direct-calls.integration.spec.ts` проверяет транзакции и конкуренцию на отдельных PostgreSQL и Redis. Включается только при `CALLS_INTEGRATION_DATABASE_URL` и `CALLS_INTEGRATION_REDIS_URL`; создаёт случайную тестовую БД и префикс Redis, удаляет их после проверки. Перечень критериев выше не означает проверки звонка на реальном iPhone. Команды проверок — в [README backend](../../../../applications/backend/README.md#сборка-и-проверки).

`tests/e2e/tests/protocol/direct-calls.e2e.ts` проверяет общий механизм через независимых браузерных участников с реальными HTTP/WS, PostgreSQL, Redis и coturn. Контроль включает декодированные тоны в обе стороны, выбранную relay-пару, жизненный цикл, конкурентное принятие, занятость, дедлайны, восстановление, отзыв сессии и освобождение участников. Это project `protocol` общего системного E2E-модуля; пользовательские сценарии через веб-клиент находятся в project `web` того же модуля. Команды, сценарии и непроверенные границы — в [README стенда](../../../../tests/e2e/README.md).

## Открытые решения

Открытых решений в согласованном объёме DirectCalls первой версии нет. Backend реализован; нагрузочная проверка выбранных значений, реальные iPhone и эксплуатационная настройка остаются отдельными проверками.

Используется отдельный WebRTC-контур GChat с собственным coturn, аккаунтами и данными, без интеграции с Mattermost/Jitsi; продуктовое решение находится в [требованиях](../../../product/requirements.md#7-допущения-и-открытые-вопросы). Продуктовые вопросы истории звонков, распространения приложения и остальных дополнительных функций этим контрактом не закрываются.

# DialogsModule

## Назначение и границы

Серверный модуль диалогов 1х1 в существующем backend GChat. Требования продукта — в [проекте диалогов](../../../product/dialogs.md). Контракт согласован и готов к реализации. Реализованы REST, зашифрованная история, прочтение, лимиты, серверные WS-события и best-effort push. Согласованные расширения DialogDto с именем собеседника и признаком непрочитанных пока отсутствуют, поэтому implementation_status — partial. Клиентская реализация и подготовка production backup не следуют из статуса серверного модуля.

Согласовано: серверное шифрование истории вместо E2EE. Клиент передаёт содержимое по защищённому HTTPS REST API; backend проверяет права, шифрует его перед записью в БД и расшифровывает при разрешённой синхронизации. Сервер имеет доступ к ключам и содержимому в памяти. Это заменяет прежнюю модель локальных приватных ключей и обмена публичными ключами устройств.

Отправка активному разрешённому получателю доступна до его первого входа: нет зависимости от ключа или подключения его устройства. После первого входа получатель получает историю через sync, даже если отправитель офлайн. Новое устройство получает разрешённую историю после обычной авторизации; клиентские recovery codes, подтверждение устройств, cross-signing и API ключей чата не нужны. Загрузка на устройство не отменяет текущие серверные проверки доступа.

Auth владеет аккаунтами/сессиями, Groups — членством, Devices — привязкой устройств, Signaling — WSS. Dialogs владеет диалогами, сообщениями и серверным шифрованием. UI и локальный кеш принадлежат Web/bridge. Групповые чаты, файлы, голосовые сообщения, реакции, серверный поиск по тексту и административный API чтения чужой переписки не входят в объём.

## Публичный API

### Транспорт

Согласовано разделение: WebSocket для диалогов передаёт уведомления о наличии новых сообщений и изменении состояния прочтения; диалог и его история запрашиваются, а прочтение подтверждается через REST. Это заменяет прежнее направление «все операции чата через WSS bridge». Существующие команды Auth/Devices/звонков по WSS не меняются.

REST использует HTTPS, действующую авторизацию GChat и текущие проверки доступа. В native Auth/refresh по-прежнему принадлежат bridge; HTTP-запросы выполняются существующим SDK через `features/auth/session.ts`, как текущие запросы групп/бэк-офиса. Эта обёртка уже получает access token через native runtime и отменяет запросы старого цикла; нового native HTTP-плагина не требуется. WSS-уведомления приходят через существующий native WS bridge; второе соединение не создаётся.

Actor берётся из проверенной сессии, а не из тела/параметров запроса. Для проверки device binding и sender_device_id привязка текущей сессии разрешается через внутренний API Devices; произвольный device_id из payload не является подтверждением. Внутренний метод и транзакционные гарантии описаны в разделе [схемы БД и транзакций](#схема-бд-и-транзакции). REST не требует активного сокета для каждой страницы, но действующая привязка сессии должна быть создана штатной регистрацией устройства.

### Операции REST

Внешнее размещение использует существующий base URL `/api`. Согласованы `POST /dialogs` с `{peer_id}` и `POST /dialogs/:dialog_id/messages` с `{client_message_id, content}` и поведение создания/отправки ниже. Согласованы DialogDto с обёрткой `{dialog}` и MessageDto с обёрткой `{message}`, статусы первого создания 201 и повтора по тому же ключу идемпотентности 200. Также согласованы GET списка, одного диалога, permissions и истории с режимами before/after и ответом `{messages, has_more}`. WS чата остаётся каналом уведомлений. Лимиты отправки, страниц и частоты согласованы ниже.

| Метод и маршрут                       | Данные запроса                                    | Результат                                               |
| ------------------------------------- | ------------------------------------------------- | ------------------------------------------------------- |
| `POST /dialogs`                       | JSON `{peer_id}`                                  | Создать либо вернуть существующий диалог пары           |
| `GET /dialogs`                        | Query `limit?, offset?`                           | `{dialogs: DialogDto[], has_more: boolean}`, HTTP 200   |
| `GET /dialogs/:dialog_id`             | ID в пути                                         | `{dialog: DialogDto}`, HTTP 200                         |
| `GET /dialogs/:dialog_id/permissions` | ID в пути                                         | Контекстные права `{dialogs: {can_read, can_send}}`     |
| `POST /dialogs/:dialog_id/messages`   | JSON `{client_message_id, content}`               | `{message: MessageDto}` после сохранения                |
| `GET /dialogs/:dialog_id/messages`    | Query `after_sequence?, before_sequence?, limit?` | `{messages: MessageDto[], has_more: boolean}`, HTTP 200 |
| `POST /dialogs/:dialog_id/read`       | JSON `{sequence}`                                 | `{last_read_sequence}`, HTTP 200                        |

### Список диалогов

Согласован `GET /dialogs` (внешний URL `/api/dialogs`) с query-параметрами limit/offset и ответом HTTP 200 `{dialogs: DialogDto[], has_more: boolean}`. Возвращаются только собственные диалоги текущего пользователя, включая недоступные для чтения с актуальными разрешёнными метаданными. Порядок сохраняет правило последнего сообщения/создания пустого диалога. Permissions и content в списке отсутствуют, поле total не добавляется.

Пустой список или offset за концом возвращает `{dialogs: [], has_more: false}` с HTTP 200. has_more означает наличие следующей страницы в состоянии чтения запроса; после страницы клиент увеличивает offset на фактически полученное число записей. Новая активность может переставить строки между запросами: клиент объединяет их по dialog_id и при обновлении перечитывает начало. Не гарантируется неизменный снимок всего обхода. Для limit согласованы default 30 и максимум 100, для offset — default 0; общие правила описаны в разделе лимитов страниц.

### Получение одного диалога

Согласован `GET /dialogs/:dialog_id` (внешний URL `/api/dialogs/:dialog_id`) с ответом HTTP 200 `{dialog: DialogDto}`. Actor должен быть активным участником с действующей авторизацией и привязкой устройства. Запрет чтения истории не запрещает разрешённые актуальные метаданные. Permissions и сообщения в ответ не включаются.

Неизвестный и чужой диалог возвращают одинаковый HTTP 404 NOT_FOUND, включая запрос администратора вне диалога; некорректный UUID — HTTP 400 VALIDATION_ERROR. Ошибки авторизации следуют существующему контракту Auth. Ответ имеет Cache-Control: no-store.

### DTO диалога и ответ создания

Согласован единый DialogDto для ответа создания, получения одного диалога и элементов списка:

```json
{
  "dialog_id": "a1b2c3d4-1111-4222-8333-444455556666",
  "peer_id": "b1c2d3e4-1111-4222-8333-444455556666",
  "created_at": "2026-11-07T12:00:00.000Z",
  "last_message_at": null,
  "last_sequence": 0,
  "last_read_sequence": 0,
  "peer_last_read_sequence": 0
}
```

`peer_id` — второй участник относительно текущего пользователя. Для пустого диалога last_message_at равен null, last_sequence — 0; после отправки возвращаются серверное время и числовая позиция последнего сохранённого сообщения. Эти метаданные остаются актуальными и при запрете чтения истории. Имена/аватары и содержимое последнего сообщения в DTO не входят; permissions запрашиваются отдельно.

Согласованы поля `last_read_sequence` — позиция прочтения текущего пользователя, `peer_last_read_sequence` — позиция собеседника. Они входят в единый DialogDto списка, получения и создания/повтора диалога. Обе позиции — безопасные целые JSON-числа, начальное значение 0; они общие для устройств соответствующего аккаунта и монотонны. Это метаданные, а не содержимое сообщений; применяется доступ к DialogDto, включая ранее согласованную выдачу метаданных при запрете чтения истории.

Согласованный ответ `POST /dialogs` — `{dialog: DialogDto}`. Новая запись возвращает HTTP 201 Created, существующий диалог пары — HTTP 200 OK; конкурентный запрос, вернувший существующую запись, тоже получает 200. Повтор не меняет created_at. Профильный API собеседника в объём этого контракта не входит; лимиты страниц определены ниже.

### Планируемое расширение: имя собеседника

Расширение согласовано пользователем и готово к реализации: отображаемое имя собеседника выдаётся участникам диалога, в том числе вне текущих контактов. Расширение ещё не реализовано; приведённый выше реализованный DialogDto и generated SDK пока не содержат имени. Решение не открывает обычному пользователю административный список аккаунтов.

В единый DialogDto списка/get/создания добавляется `peer_display_name: string` — текущее `display_name` второго участника из Auth. Выдача следует тем же проверкам участия, сессии и binding, что остальные метаданные диалога, включая диалог с запретом чтения истории и отключённым peer. Имя возвращается и при повторном создании диалога; после переименования последующие ответы содержат актуальное значение. Чужой/неизвестный диалог по-прежнему возвращает одинаковый NOT_FOUND. Аватар, login и другие профильные данные этим расширением не добавляются.

При реализации нужно обновить OpenAPI/SDK штатной генерацией. Критерии приёмки расширения: имя присутствует в списке/get/создании/повторе, обновляется после переименования, доступно участнику вне общих групп, при отключённом peer и запрете чтения; посторонний пользователь/admin его через диалог не получает. Клиентские документы используют это согласованное расширение как ещё не реализованную зависимость.

### Планируемое расширение: наличие непрочитанных

Расширение согласовано пользователем и готово к реализации: единый DialogDto списка/get/создания и повторного создания включает `has_unread_messages: boolean`. Поле пока отсутствует в реализации и generated SDK, как и в примере реализованного DTO выше. Числовой счётчик не добавляется.

Значение true означает, что в диалоге существует хотя бы одно входящее для actor сообщение с `sequence > last_read_sequence` этого actor; иначе false. Собственные сообщения не создают непрочитанного входящего. Для пустого диалога значение false. Признак общий для устройств аккаунта и вычисляется по серверным метаданным сообщений и позиции прочтения без расшифровки content. Клиенту не требуется загружать историю ради индикатора.

Поле следует доступу к остальным метаданным DialogDto: выдаётся активному участнику с действующими session/device binding, включая запрет чтения истории и отключённого peer. Чужой/неизвестный диалог остаётся NOT_FOUND; разрешение читать content из значения поля не следует. Вычисление использует тот же снимок данных, что позиции и last_sequence соответствующего DTO. Это текущий признак, а не монотонная позиция: он может становиться true после входящего и false после прочтения. Новое WS-событие не вводится; существующие события и REST-сверка используются клиентом по его контракту.

При реализации обновляются OpenAPI/SDK штатной генерацией. Критерии приёмки: поле есть в списке/get/создании/повторе; пустой диалог и только собственные сообщения дают false, входящее выше позиции прочтения — true, частичное прочтение сохраняет true при оставшемся входящем, прочтение всех входящих с другого устройства даёт false в последующем REST-ответе. Отдельно проверяются собственное сообщение после прочтения всех входящих, запрет чтения истории, отключённый peer и одинаковый отказ постороннему пользователю/admin.

### DTO сообщения и ответ отправки

Согласован единый MessageDto для истории и результата отправки:

```json
{
  "message_id": "a1b2c3d4-1111-4222-8333-444455556666",
  "dialog_id": "b1c2d3e4-1111-4222-8333-444455556666",
  "client_message_id": "c1d2e3f4-1111-4222-8333-444455556666",
  "sequence": 121,
  "sender_id": "d1e2f3a4-1111-4222-8333-444455556666",
  "created_at": "2026-11-07T12:00:00.000Z",
  "content": { "kind": "text", "text": "Привет" },
  "status": "sent"
}
```

message_id, sequence и created_at назначает сервер; sender_id берётся из авторизации; client_message_id возвращается для сопоставления локальной отправки. В публичный DTO не входит sender_device_id: устройство остаётся служебной метаинформацией backend. Семантика галочек согласована в разделе [статусов сообщений](#статусы-сообщений); согласовано поле status: "sent" | "read" в едином MessageDto для истории и результата отправки/повтора.

Согласованный content — `{kind: "text", text}` либо `{kind: "sticker", sticker_id}` без неиспользуемых полей. Лимиты текстовой отправки согласованы ниже; допустимые sticker IDs определены в [каталоге](#каталог-стикеров-и-unicode).

### Статусы сообщений

Согласованы два состояния исходящего сообщения в интерфейсе:

- Одна галочка — «Отправлено»: backend сохранил сообщение, commit подтверждён.
- Две галочки — «Прочитано»: получатель открыл диалог и увидел сообщение; клиент подтверждает прочтение серверу.

Отдельного статуса «Доставлено на устройство» нет. Загрузка истории, получение WS-сигнала или системного push сами по себе не подтверждают прочтение.

Согласованная модель: одна позиция `last_read_sequence` на участника диалога, общая для всех устройств его аккаунта, движется только вперёд. Клиент сам определяет момент прочтения и передаёт подтверждение через REST с позицией sequence, до которой сообщения считаются прочитанными включительно. Backend не задаёт правила видимости, таймер или требование загрузить всю предшествующую историю; он проверяет допустимость позиции и права. У исходящего сообщения две галочки, когда позиция собеседника достигла sequence этого сообщения.

Согласован `POST /dialogs/:dialog_id/read` с JSON `{sequence}` (внешний URL `/api/dialogs/:dialog_id/read`). Клиентской WS-команды подтверждения прочтения нет. Повтор подтверждения безопасен; проверяются участие, право чтения истории, актуальные сессия и device binding. Позиция выше последнего сообщения не принимается. Подтверждение прочтения не зависит от can_send: право читать не всегда даёт право отвечать. Расширение реализовано в backend.

Согласовано: backend уведомляет об изменении прочтения через серверное WS-событие; получение сообщений через REST возвращает статус. REST остаётся источником состояния при загрузке истории. Клиент подтверждает прочтение через REST, сервер сообщает об изменении событием dialog.read_updated по WS.

Согласованные поля DTO и события:

- Единый MessageDto включает `status: "sent" | "read"`, в том числе в истории и ответе отправки/повтора. Статус вычисляется относительно получателя сообщения: это позиция участника, отличного от sender_id, независимо от того, кто запросил DTO. `read` означает, что эта позиция достигла sequence сообщения; иначе `sent`. Галочки в UI показываются для исходящих сообщений. Статус является текущим состоянием: повтор отправки сохраняет исходные ID/content/sequence/время, но может вернуть уже обновлённый status.
- Ответ подтверждения: HTTP 200 `{last_read_sequence}`, фактическая сохранённая позиция участника, в том числе при повторной или меньшей позиции. Начальная позиция 0; sequence — безопасное целое от 0 до last_sequence. Устаревшее подтверждение возвращает текущий максимум без отката.
- WS-событие `dialog.read_updated` с payload `{dialog_id, reader_id, last_read_sequence}` без content и request_id. reader_id — аккаунт участника, подтвердившего прочтение, а не устройство. last_read_sequence передаётся JSON-числом в безопасном целочисленном диапазоне.

Пример согласованного события:

```json
{
  "type": "dialog.read_updated",
  "payload": {
    "dialog_id": "b1c2d3e4-1111-4222-8333-444455556666",
    "reader_id": "d1e2f3a4-1111-4222-8333-444455556666",
    "last_read_sequence": 121
  }
}
```

Согласованные HTTP-ошибки подтверждения в общем формате ErrorModule:

- HTTP 400 VALIDATION_ERROR — некорректный sequence или позиция выше last_sequence; для позиции указывается поле sequence. Некорректный UUID диалога также даёт VALIDATION_ERROR по общим правилам.
- HTTP 403 DIALOG_NOT_ALLOWED — actor является участником, но право читать историю отсутствует.
- HTTP 404 NOT_FOUND — одинаковый ответ для неизвестного и чужого диалога; его позиции не раскрываются.
- Ошибки сессии и device binding следуют согласованным контрактам Auth/Devices. Отказы зависимости и внутренние ошибки проходят через ErrorModule без утечки данных.

Согласована доставка события прочтения: после commit продвижения позиции событие направляется разрешённым подключениям обоих участников, включая другие устройства читателя. Перед доставкой повторно проверяются сессия, binding, участие и право чтения. Повтор без продвижения позиции не создаёт событие. Клиент применяет максимум; события могут теряться или приходить повторно/не по порядку. Ошибка доставки не отменяет сохранённое прочтение.

Согласовано восстановление после reconnect через `GET /dialogs` или `GET /dialogs/:dialog_id`: обе позиции приходят в DialogDto. Клиент обновляет галочки локально сохранённых исходящих сообщений по peer_last_read_sequence, не перечитывая историю. Позиция текущего пользователя также восстанавливается из last_read_sequence. Позиции прочтения не заменяют локальную позицию загрузки сообщений: более высокий read sequence с другого устройства не позволяет пропустить REST sync недостающей истории. В рамках текущего аккаунта/диалога поздний ответ или событие с меньшей позицией не откатывает известный максимум.

Хранение позиций и атомарное продвижение согласованы в [разделе схемы](#хранение-и-продвижение-прочтения--согласовано). Лимит подтверждений согласован в разделе [частоты запросов](#частота-запросов). Момент прочтения определяет клиент. REST-подтверждение использует общий формат HTTP-ответов/ошибок; при ограничении частоты — HTTP 429 RATE_LIMITED и Retry-After. Новое поле MessageDto учитывается в существующем байтовом бюджете страниц.

### Каталог стикеров и Unicode

Начальный набор — **Animal Pals, 5 статичных стикеров**: Curious cat, Puppy pal, Little fox, Sleepy bear, Bunny hop из [страницы автора](https://www.assetpolish.com/assets/colour-animals/), где для набора заявлена CC0 1.0. Состав выбора фиксирован, расширение — отдельное обновление каталога.

| sticker_id             | Название исходного изображения |
| ---------------------- | ------------------------------ |
| `animal-pals-v1-cat`   | Curious cat                    |
| `animal-pals-v1-dog`   | Puppy pal                      |
| `animal-pals-v1-fox`   | Little fox                     |
| `animal-pals-v1-bear`  | Sleepy bear                    |
| `animal-pals-v1-bunny` | Bunny hop                      |

Пять изображений поставляются статичными PNG с прозрачностью 512×512, без изменения пропорций; исходники, SHA-256 файлов, копия лицензии и URL происхождения фиксируются при подготовке ресурсов до реализации каталога. Ресурсы подготовлены в `packages/dialog-assets/`: исходники, PNG, SHA-256 и копия лицензии; это не приёмка клиентского UI. Если источник/лицензия конкретного файла не подтверждаются, он не заменяется произвольным аналогом: подготовка ресурсов останавливается до решения пользователя.

Версия каталога — 1; одно общее описание IDs используется backend и Web из workspace-пакета `@gchat/dialog-assets` без runtime-зависимостей. В нём — manifest и изображения, backend импортирует только список IDs; native показывает общий Web UI. Внутренний пакет реализован; provenance и контрольные суммы находятся в его manifest. Файлы распространяются вместе с frontend с того же origin, CDN/удалённого каталога нет. ID навсегда связан с изображением и сохраняется для старой истории; новые IDs добавляются совместимым обновлением. Каталог и файлы выпускаются до backend, принимающего новые IDs. Неизвестный sticker_id при отправке — HTTP 400 VALIDATION_ERROR с полем content.sticker_id; неизвестный локальному старому клиенту ID в истории — нейтральный placeholder «Стикер» без загрузки произвольного URL. Content не содержит версии/URL/картинки и не увеличивает состав DTO.

Unicode emoji в text разрешены как обычный текст с платформенным отображением, без загрузки изображений emoji. Их code points, включая variation selectors и ZWJ, учитываются существующим правилом длины; один визуальный emoji может занимать несколько code points. Сообщения не нормализуются и не переписываются сервером.

### Лимиты одного сообщения

Согласовано: text содержит до 4000 символов Unicode, подсчитанных по code points, включая пробелы и переносы. Пустая строка и строка только из пробельных символов не принимаются. В непустом сообщении исходные пробелы и переносы сохраняются; сервер не обрезает и не сокращает текст автоматически.

Тело JSON-запроса `POST /dialogs/:dialog_id/messages` ограничено 64 КиБ (65536 байт UTF-8), включая все поля и JSON-представление. Ограничение применяется также к отправке стикера, независимо от ограничения длины text. Бюджет оценивается по декодированному телу до разбора JSON, а не по размеру сжатой сетевой передачи; нельзя обойти его сжатием. Чтение запроса ограничивается до полного накопления/разбора превышающего лимит тела.

Пустой/пробельный или превышающий 4000 code points текст даёт HTTP 400 VALIDATION_ERROR с указанием поля content.text. Превышение размера тела даёт HTTP 413 PAYLOAD_TOO_LARGE в общем HTTP-формате ошибок без исходного тела. Успешный ответ не возвращает укороченную версию вместо отклонённого текста. Ограничения backend и reverse proxy должны быть согласованы, чтобы отказ не раскрывал тело запроса.

Ответ `POST /dialogs/:dialog_id/messages` — `{message: MessageDto}`. HTTP 201 Created означает первую запись, HTTP 200 OK — возврат ранее сохранённого сообщения по тому же ключу `(dialog_id, sender_id, client_message_id)`, без сравнения content. Отличающееся содержимое повторного запроса не изменяет сохранённое сообщение и не создаёт конфликт. Повтор возвращает первоначальные серверные ID, sequence и время, не создаёт новую запись и не обновляет активность.

### Параметры истории и содержимое

Пример синхронизации после сохранённой позиции:

```http
GET /api/dialogs/a1b2c3d4-1111-4222-8333-444455556666/messages?after_sequence=120&limit=30
Authorization: Bearer <access-token>
```

UUID идентифицируют сущности, время сервера передаётся в ISO 8601 UTC. Согласовано числовое представление `sequence`, `last_sequence` и позиций: безопасные целые числа до `Number.MAX_SAFE_INTEGER` (9007199254740991), номера сообщений положительные, начальная позиция — `0`. В JSON числа передаются без кавычек. Query URL передаётся текстом по правилам HTTP, но параметры описываются в OpenAPI как целые и строго разбираются в числовой тип; это не строковый sequence в DTO.

Числовые строки в JSON, отрицательные/дробные позиции и переполнение отклоняются с `VALIDATION_ERROR`. Query-парсер принимает только десятичную запись по `^(0|[1-9][0-9]*)$` с проверкой безопасного диапазона и ограничения параметра. Знак, пробелы, пустое значение, ведущие нули, exponent/hex и повтор одного query-параметра отклоняются с VALIDATION_ERROR; неявного приведения и выбора первого значения из массива нет. В JSON sequence должен быть числом, не строкой. Content принимает только поля соответствующего kind; лишние поля content и тела отправки/read отклоняются с VALIDATION_ERROR. Bigint в PostgreSQL ограничивается безопасным диапазоном и точно преобразуется в number; исчерпание диапазона не приводит к округлению, сбросу или повторному использованию номера.

Backend валидирует согласованную форму content и [лимиты отправки](#лимиты-одного-сообщения); каталог стикеров определён в этом контракте. Лимиты чтения и частоты согласованы ниже. Серверные криптографические поля не выдаются клиентам. Контроллеры/DTO становятся источником OpenAPI и генерируемого `backend-api` по [соглашениям](../../conventions.md#http-контроллеры-и-swagger); вручную править снимок OpenAPI/SDK не предлагается.

### Лимиты страниц

Согласовано для GET списка диалогов и GET истории: limit по умолчанию 30, допустимый диапазон — целые от 1 до 100 включительно. Отсутствующий offset списка равен 0; переданный offset должен быть неотрицательным безопасным целым. limit=0, отрицательные/дробные значения и limit>100 дают HTTP 400 VALIDATION_ERROR с указанием параметра, без автоматического исправления.

Сериализованный JSON-ответ страницы истории, включая messages, has_more и обёртку, занимает не более 512 КиБ (524288 байт UTF-8) до сжатия. Это отдельный бюджет HTTP-ответа, не размер сообщения или WS-фрейма. Сервер включает только целые MessageDto и не обрезает content. Если байтовый бюджет закончился раньше limit и остались записи в выбранном направлении, возвращаются меньше сообщений и has_more=true; продолжение использует sequence последней полученной записи.

Согласованные лимиты одной отправки позволяют поместить одно допустимое сообщение в страницу истории. Пустая страница с has_more=true из-за одного не помещающегося сообщения не допускается; нарушение такого инварианта — безопасная серверная ошибка, а не молчаливое пропускание записи. Пустой результат сохраняет HTTP 200 и has_more=false.

### Частота запросов

Согласованы четыре независимых token bucket на аккаунт, общие для всех его сессий и устройств:

| Группа            | Операции                                                         | Скорость пополнения | Ёмкость полного запаса |
| ----------------- | ---------------------------------------------------------------- | ------------------- | ---------------------- |
| Отправка          | POST /dialogs/:dialog_id/messages                                | 5 запросов/с        | 10 запросов            |
| Прочтение         | POST /dialogs/:dialog_id/read                                    | 5 запросов/с        | 10 запросов            |
| Создание/открытие | POST /dialogs                                                    | 1 запрос/с          | 5 запросов             |
| Чтение            | GET списка, одного диалога, истории и permissions диалога вместе | 10 запросов/с       | 20 запросов            |

Полный запас допускает указанный краткий всплеск, затем восстанавливается с постоянной скоростью. Это не дополнительная квота поверх скорости в фиксированном секундном окне. Создание новой сессии, второго устройства или reconnect не создаёт отдельный запас. Существующие лимиты Auth login/refresh не заменяются этими группами.

Подтверждения прочтения имеют отдельный запас на аккаунт, общий для всех его диалогов, устройств и сессий. Клиент объединяет прочтение нескольких сообщений в одну максимальную позицию для соответствующего диалога. Каждый повтор POST read расходует лимит, даже если позиция не выросла. При превышении возвращается HTTP 429 RATE_LIMITED с Retry-After по общему правилу ниже; позиция не изменяется и событие прочтения не создаётся. После ожидания клиент подтверждает актуальную максимальную позицию.

Повтор с тем же client_message_id тоже расходует запрос группы отправки, сохраняя идемпотентность. Загрузка истории не расходует запас отправки. При исчерпании возвращается HTTP 429 RATE_LIMITED в общем формате ErrorModule и Retry-After с целым числом секунд до следующей допустимой попытки, округлённым вверх. Отклонённая попытка не создаёт сообщение, sequence или уведомление. Это не доказывает отсутствие commit предыдущей попытки с потерянным ответом.

Клиент ждёт Retry-After и повторяет логическую отправку с исходным client_message_id/content, не создаёт новый ID для обхода ограничения. Хранение и атомарное обновление счётчиков определены в [подразделе ниже](#хранение-счётчиков); лимит не является разрешением обойти проверку прав или размера payload.

#### Хранение счётчиков

Используется существующий Redis через RedisService, без новой зависимости и без изменения лимитов Auth. Логический ключ `dialogs:rate:<user_id>:<send|create|get|read>` проходит через `RedisService.key()`. Один hash содержит `credit_ms` (целое число накопленного бюджета) и `updated_at_ms`; весь расчёт/списание/TTL выполняется одним коротким Lua-скриптом. [Redis гарантирует атомарность исполнения скрипта](https://redis.io/docs/latest/develop/programmability/eval-intro/); предусловия/тип ключа/числа проверяются до первой записи, отката уже выполненных команд Lua нет.

Время — Redis TIME, округлённое до миллисекунд; `now = max(redis_now, updated_at_ms)`, чтобы обратный ход часов не дал дополнительный запас. Для скорости r и ёмкости C: максимум `C*1000`, пополнение `(now-updated_at_ms)*r`, стоимость запроса 1000. Большой интервал сначала ограничивается временем полного пополнения, затем умножается: операции не выходят из безопасного целого диапазона. Если credit_ms >= 1000, списать 1000; иначе отказать и вычислить `ceil((1000-credit_ms)/r)` миллисекунд ожидания. HTTP Retry-After — положительное целое число секунд, округлённое вверх. TTL ключа при каждом обращении — 60 секунд; это больше полного восстановления всех четырёх bucket. Истечение ключа после бездействия эквивалентно полному запасу.

Лимит проверяется после Auth guard и проверки формата/размера запроса, перед бизнес-транзакцией. Каждая допущенная до лимитера попытка, в том числе повтор и последующий отказ по бизнес-правам, расходует бюджет; токен после rollback не возвращается. Все процессы используют общий namespace. NOSCRIPT допускает загрузку скрипта и повтор только после явного ответа NOSCRIPT, когда исполнение не состоялось. Таймаут/отказ/повреждённое состояние Redis — HTTP 503 SERVICE_UNAVAILABLE без бизнес-записи, выдачи истории или продвижения прочтения; неизвестный результат списания не повторяется автоматически, запас мог уменьшиться. Локального fallback нет.

Перезапуск backend не сбрасывает запас. Потеря/очистка Redis может восстановить полный запас — это согласованный краткий повторный burst, а не восстановление сессий или отмена прав. Новых метрик-инфраструктуры и cron для очистки лимитов не требуется; действуют TTL и существующее безопасное логирование. Глобальные настройки Redis/noeviction остаются по его контракту.

### Permissions

Согласовано: permissions возвращаются отдельным endpoint, в ответе есть объект `dialogs`. Поля can_read/can_send исключаются из DTO самого диалога, ответы создания/get/list их не дублируют. DTO диалога и статусы создания согласованы отдельно выше.

Права чтения/отправки зависят от конкретного собеседника и участия в диалоге; один глобальный can_send для всех диалогов не отражает принятую политику. Согласован отдельный ресурсный endpoint `GET /dialogs/:dialog_id/permissions` (внешний URL `/api/dialogs/:dialog_id/permissions`), возвращающий права текущего пользователя для указанного диалога:

```json
{
  "dialogs": {
    "can_read": true,
    "can_send": true
  }
}
```

dialog_id — обязательный UUID в пути, не query общего permissions endpoint. Существующая согласованная форма ответа с объектом dialogs и boolean-полями can_read/can_send сохраняется. Контроллер и расчёт принадлежат DialogsModule; Auth предоставляет проверенную личность и сессию. Отсутствующий/некорректный ID не позволяет получить права, некорректный UUID даёт VALIDATION_ERROR, чужой/неизвестный диалог — NOT_FOUND.

Общие permissions приложения проектируются в [AuthModule](../auth.md#permissions-приложения--запланировано) отдельно, без dialog_id. Они не заменяют проверку конкретного собеседника/диалога. Обратный импорт DialogsModule в AuthModule для обслуживания контекстного endpoint больше не нужен: Dialogs использует существующую зависимость от Auth. Общая форма и поля глобальных permissions не принимаются этим разделением автоматически.

Permissions описывают текущий снимок для UI и не выдают capability/token на последующую операцию. Каждый запрос истории/отправки проверяет права заново. Действующая Auth-сессия и проверка участия обязательны; чужой/неизвестный dialog_id не раскрывается отдельным ответом. HTTP-ответ имеет Cache-Control: no-store. Отказ зависимости возвращает безопасную ошибку, не кешированное разрешение.

### Уведомление WebSocket

Согласован тип `dialog.messages_available`; это серверное событие, не команда и не ответ, поэтому request_id отсутствует:

```json
{
  "type": "dialog.messages_available",
  "payload": {
    "dialog_id": "a1b2c3d4-1111-4222-8333-444455556666",
    "last_sequence": 121
  }
}
```

Согласованный payload содержит только dialog_id и last_sequence. last_sequence — JSON number в принятом безопасном целочисленном диапазоне. Текст, ID стикера и объект сообщения по WS не передаются; payload системного push с текстом — отдельный согласованный канал.

Согласовано: событие формируется только после успешного commit сообщения. Уведомляются действующие подключения обоих участников, включая другие устройства отправителя; перед отправкой проверяются сессия, binding, участие и право чтения. Для диалога с запретом чтения актуальные метаданные остаются доступны через REST list/get по ранее принятому правилу; уведомление не даёт нового права.

Получение события запускает REST-синхронизацию после локальной позиции; last_sequence события нельзя сразу принять за уже скачанную позицию. Уведомления допускают потерю, повтор, объединение нескольких сообщений и иной порядок. При reconnect/foreground клиент перечитывает список и историю через REST, даже если событий не было. Сбой доставки WS после commit не отменяет сохранённое сообщение и не создаёт повторную отправку. Клиентский ACK события не требуется.

### Синхронизация

Согласован `GET /dialogs/:dialog_id/messages` (внешний URL `/api/dialogs/:dialog_id/messages`) с ответом HTTP 200 `{messages: MessageDto[], has_more: boolean}`. Backend проверяет права до расшифровки/выдачи; содержимое возвращается в HTTP-ответе после проверки доступа и не передаётся в WS-событии. Ответы с историей/метаданными имеют Cache-Control: no-store.

- `after_sequence` возвращает записи строго после позиции, по возрастанию sequence. Клиент сохраняет страницу и продолжает от последней сохранённой записи, пока `has_more: true`.
- `before_sequence` возвращает записи строго раньше позиции, от новых к старым, для загрузки предыдущей истории.
- Без обеих позиций возвращается последняя страница, от новых к старым. Одновременно задавать after и before нельзя.
- Синхронизация не требует клиентского ключа чата. На новом устройстве разрешённая история доступна после входа; прежний ключ, прежнее устройство и отправитель онлайн не нужны.
- На reconnect клиент получает список и повторяет sync с локальной позиции. Полученное объединяется по message_id; новая позиция сохраняется только вместе с соответствующей локальной страницей.

Согласовано: after_sequence=0 начинает загрузку с первого сообщения; границы before/after строго исключающие. Для следующей страницы используется sequence последней записи полученной страницы в выбранном направлении. has_more относится к этому направлению и состоянию на момент запроса, не гарантирует неизменный снимок между страницами. Пустой результат — HTTP 200 `{messages: [], has_more: false}`.

Одновременные before/after и некорректный UUID дают HTTP 400 VALIDATION_ERROR. Свой диалог с запретом чтения истории — HTTP 403 DIALOG_NOT_ALLOWED; чужой/неизвестный — одинаковый HTTP 404 NOT_FOUND. Ошибки авторизации следуют Auth. Размеры страниц и байтовый бюджет истории согласованы в разделе лимитов страниц.

Клиент самостоятельно хранит позицию синхронизации. Транспортные ACK, watermarks загрузки устройств, подписанные курсоры и гарантированное воспроизведение WS-событий не входят в минимальную синхронизацию. Подтверждения прочтения выполняются по [согласованной семантике статусов](#статусы-сообщений). Уведомление по WS ускоряет REST sync; открытие, reconnect и периодическая сверка восстанавливают пропуски. Системные push следуют [контракту уведомлений](#уведомления).

Список диалогов использует согласованные limit/offset и правила раздела [«Список диалогов»](#список-диалогов). Это отдельная пагинация от sequence-позиций истории.

## Правила и инварианты

### Создание и идемпотентность

Согласован один постоянный диалог на неупорядоченную пару аккаунтов, независимо от групп и устройств. Участники неизменны. Повторное и конкурентное создание возвращает тот же диалог. Смена пароля, устройства, серверных ключей шифрования или доступных групп не создаёт новый диалог.

`POST /dialogs` проверяет текущее право начать переписку и создаёт пустой диалог сразу, без первого сообщения; получатель может быть офлайн или ещё ни разу не входить. Повтор возвращает существующий диалог пары после проверки текущих прав создания. Конкурентные запросы участников не создают дубликат. Существование диалога само по себе не разрешает отправку; доступные для чтения диалоги, которые сейчас нельзя создавать/продолжать, читаются через GET.

Обеспечение в PostgreSQL — упорядоченные UUID участников и UNIQUE пары; подробности — в разделе [схемы БД](#схема-бд-и-транзакции). Самодиалог и третий участник запрещены. Наличие диалога не резервирует право чтения или отправки.

Согласовано: идемпотентность определяется только ключом `(dialog_id, sender_id, client_message_id)`. Если ключ уже сохранён, сервер возвращает исходное сообщение с HTTP 200, независимо от отличий content в повторном запросе. Содержимое для определения повтора не сравнивается и не хешируется; сохранённое сообщение не изменяется. Повтор не выдаёт новый sequence, не обновляет активность и не создаёт уведомлений. Общие проверки DTO, размера, частоты и актуальных прав сохраняются.

Согласовано: клиент создаёт новый client_message_id для новой логической отправки и сохраняет его при повторе после потери ответа. Одинаковый текст с разными client_message_id разрешён: каждая такая отправка сохраняется отдельным сообщением со своими message_id и sequence и обычными уведомлениями после commit. Дедупликации по тексту, хешу содержимого или временному окну нет; проверка повтора относится только к одному ключу `(dialog_id, sender_id, client_message_id)`. `POST /dialogs/:dialog_id/messages` каждый раз проверяет участие и актуальные права; офлайн-получатель разрешён, отключённый — нет. После проверки сервер шифрует content и одной транзакцией сохраняет сообщение, sequence и метаданные активности. Успешный HTTP-ответ означает commit. Уведомление WS и системный push выполняются после сохранения; ошибка их доставки не отменяет сообщение, повтор по тому же ключу идемпотентности не создаёт новую логическую отправку или уведомление.

### Доступ

| Операция            | Условия                                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| Создание/отправка   | Действующие actor/session/device binding; оба аккаунта активны; отправитель admin либо есть общая группа      |
| Чтение истории/sync | Actor — активный участник, session/device binding действуют; общая группа либо один участник — активный admin |
| Метаданные list/get | Активный участник с действующей session/device binding, даже после запрета чтения истории                     |
| Чужой диалог        | Недоступен, в том числе администратору вне диалога                                                            |

Обычный участник без общей группы читает входящее от администратора, но не отвечает. Потеря последней общей группы обычного диалога запрещает последующие чтение и отправку; исключение активного администратора сохраняется.

Согласовано: отключение собеседника не запрещает оставшемуся активному участнику читать прежнюю историю при соблюдении остальных условий доступа. Для history/sync требуется активность actor, а не обоих аккаунтов; продолжают проверяться участие, сессия, привязка устройства и общая группа либо наличие активного участника-admin. Отключённый admin не даёт исключения по своей роли. При потере общей группы и отсутствии активного участника-admin чтение запрещено независимо от сохранности истории. Отправка отключённому аккаунту запрещена; сам отключённый аккаунт не получает доступ.

Каждый запрос и повтор проверяет актуальные права через владельцев Auth/Groups/Devices. Чужой и неизвестный dialog_id дают одинаковый `NOT_FOUND`; участник с запретом запрошенной операции получает `DIALOG_NOT_ALLOWED`. Роль из payload/JWT не заменяет текущую роль Auth. Отказ зависимости закрывает доступ.

Согласованный вариант В: запрет чтения не скрывает актуальные метаданные собственного диалога, включая время последнего сообщения и признак активности. Состав DialogDto, включая позиции прочтения, определён в [разделе DTO](#dto-диалога-и-ответ-создания). Permissions запрашиваются [отдельно](#permissions), не включаются в записи списка/get/создания. Содержимое сообщения и ключи через REST list/get не возвращаются. Новое зарегистрированное устройство тоже получает разрешённые метаданные.

Согласован порядок по убыванию серверного времени последнего сохранённого сообщения, для пустого диалога — по созданию, с устойчивым дополнительным порядком по ID. Правило действует и для недоступных диалогов. Черновик, открытие, повторное создание и reconnect не поднимают строку.

### Сохранение и конкурентные операции

Сообщение, необходимые криптографические данные, следующий sequence и метаданные диалога сохраняются одной транзакцией PostgreSQL. Успех REST-отправки означает COMMIT, а не формирование уведомления. Диалог блокируется на выдачу sequence; неполное сообщение не подтверждается.

Таблицы, внутренние методы владельцев и порядок блокировок согласованы ниже. Транзакционные расширения Auth/Devices реализованы; существующие lockActiveAccountRoles и lockCommonGroup сами по себе не обеспечивают проверку session/device binding.

Отзыв доступа запрещает следующую авторизуемую операцию. Ответ, разрешённый до отзыва и уже переданный транспорту, может прийти позже. Локальные сообщения и уже переданные байты дистанционно не отзываются. Истечение или отзыв сессии не сохраняет право синхронизации через старый сокет.

### Схема БД и транзакции

Схема, порядок блокировок и алгоритмы записи согласованы. Dialogs владеет двумя бизнес-таблицами и служебной таблицей учёта бюджета ключей; все они реализованы в схеме и миграции `0007_dialogs.sql`. Запросы к данным Auth/Devices/Groups выполняются через транзакционные API владельцев.

#### Таблицы Dialogs

Две бизнес-таблицы — `gchat_dialogs` и `gchat_dialog_messages`, без отдельной таблицы участников. Служебная `gchat_dialog_encryption_keys` описана в [формате записи и бюджете ключа](#формат-записи-и-бюджет-ключа). Ниже приведены поля схемы бизнес-модуля по [правилам миграций](../../operations/migrations.md). Все перечисленные поля обязательны, кроме явно nullable. UUID назначаются сервером, кроме `client_message_id`, полученного от клиента; timestamps — `timestamptz`, время назначает БД.

`gchat_dialogs`:

| Поле                                  | Тип и ограничение                                 | Назначение                              |
| ------------------------------------- | ------------------------------------------------- | --------------------------------------- |
| `id`                                  | UUID, PK                                          | Постоянный ID диалога                   |
| `participant_low_id`                  | UUID, FK `gchat_users.id`, ON DELETE RESTRICT     | Меньший UUID пары                       |
| `participant_high_id`                 | UUID, FK `gchat_users.id`, ON DELETE RESTRICT     | Больший UUID пары                       |
| `created_at`                          | timestamptz                                       | Время первого создания                  |
| `last_sequence`                       | bigint, default 0, CHECK от 0 до 9007199254740991 | Последняя сохранённая позиция           |
| `last_message_at`                     | timestamptz, nullable                             | Время последнего сохранённого сообщения |
| `participant_low_last_read_sequence`  | bigint, NOT NULL, default 0                       | Позиция прочтения participant_low_id    |
| `participant_high_last_read_sequence` | bigint, NOT NULL, default 0                       | Позиция прочтения participant_high_id   |

Согласованные ограничения пары: CHECK `participant_low_id < participant_high_id` по сравнению UUID PostgreSQL, UNIQUE `(participant_low_id, participant_high_id)`. Они запрещают самодиалог и дубликат пары, в том числе при конкуренции. Участники после создания не обновляются; отдельной таблицы изменяемого состава нет. Согласован CHECK пустого состояния: `last_sequence = 0 AND last_message_at IS NULL` либо `last_sequence > 0 AND last_message_at IS NOT NULL`.

Согласованы индексы списка: `(participant_low_id, COALESCE(last_message_at, created_at) DESC, id DESC)` и аналогичный по `participant_high_id`. Это индексы выражения, а не дополнительное поле активности. Запрос выбирает обе ветки участия и применяет общий `ORDER BY COALESCE(last_message_at, created_at) DESC, id DESC` до limit/offset; CHECK исключает попадание одной строки в обе ветки. UNIQUE пары также обслуживает поиск существующего диалога.

`gchat_dialog_messages`:

| Поле                 | Тип и ограничение                               | Назначение                                 |
| -------------------- | ----------------------------------------------- | ------------------------------------------ |
| `id`                 | UUID, PK                                        | Серверный message_id                       |
| `dialog_id`          | UUID, FK `gchat_dialogs.id`, ON DELETE RESTRICT | Диалог                                     |
| `sender_id`          | UUID, FK `gchat_users.id`, ON DELETE RESTRICT   | Аккаунт отправителя                        |
| `sender_device_id`   | UUID, без FK — согласовано                      | Исторический ID устройства первой отправки |
| `client_message_id`  | UUID                                            | ID логической отправки клиента             |
| `sequence`           | bigint, CHECK от 1 до 9007199254740991          | Позиция внутри диалога                     |
| `created_at`         | timestamptz                                     | Время сохранения под блокировкой диалога   |
| `encryption_version` | integer, CHECK = 1                              | Версия формата шифрования                  |
| `encryption_key_id`  | text, непустой                                  | Ссылка на внешний серверный ключ           |
| `iv`                 | bytea, CHECK octet_length = 12                  | IV AES-GCM                                 |
| `ciphertext`         | bytea, CHECK octet_length > 0                   | Зашифрованный content                      |
| `auth_tag`           | bytea, CHECK octet_length = 16                  | Тег подлинности                            |

Согласованные UNIQUE: `(dialog_id, sequence)` для порядка и обоих направлений истории; `(dialog_id, sender_id, client_message_id)` для идемпотентности независимо от устройства. Согласовано использование второго индекса для поиска повтора, первого — для страниц по before/after в обоих направлениях, без отдельных дублирующих индексов сообщений по dialog_id и created_at. Не добавляются plaintext preview, content kind, ID стикера, хеш текста, session_id отправителя, транспортные ACK/watermarks загрузки или задания уведомлений. Позиции прочтения хранятся в gchat_dialogs по согласованному разделу ниже.

Принадлежность sender_id одному из двух участников проверяется модулем в транзакции перед INSERT; обычный CHECK не проверяет другую таблицу. Равенство last_sequence максимальному sequence, соответствие last_message_at последнему сообщению и неизменность участников обеспечиваются единственным путём записи Dialogs и проверяются интеграционно, не выдаются за гарантию перечисленных CHECK/FK. Триггеры и новые роли БД не вводятся.

Для сообщений дополнительно действует UNIQUE `(encryption_key_id, iv)`; точный формат ключей, AAD и долговечный бюджет попыток определены в [разделе шифрования](#формат-записи-и-бюджет-ключа). Криптографический счётчик не заменяет sequence и не откатывается вместе с сообщением.

#### Хранение и продвижение прочтения — согласовано

Позиции хранятся в двух полях `gchat_dialogs`, перечисленных выше; отдельная таблица прочтения не создаётся. Для каждого поля действует CHECK `0 <= позиция AND позиция <= last_sequence`. Начальные позиции равны 0. Поля DialogDto отображаются относительно actor: собственная позиция — last_read_sequence, второго участника — peer_last_read_sequence.

Подтверждение прочтения использует общую транзакционную проверку доступа к истории и согласованный порядок блокировок; после аккаунтов, сессии, binding/устройства и необходимого членства строка диалога блокируется `FOR UPDATE`. Под блокировкой проверяется верхняя граница sequence и атомарно сохраняется максимум текущей и полученной позиции только для actor. Позиция другого участника не изменяется. Результат подтверждается после commit; rollback не продвигает прочтение. Одновременные подтверждения с устройств одного аккаунта не теряют больший максимум.

Продвижение прочтения не создаёт сообщение, не меняет last_sequence/last_message_at и не поднимает диалог в списке. Отправка нового сообщения сохраняет обе позиции прочтения. В ответе и статусах используются сохранённые позиции; жизненный цикл устройства не сбрасывает их.

#### Транзакционные интерфейсы владельцев

Согласовано: после HTTP guard каждая операция Dialogs повторно проверяет через Auth/Devices актуальную сессию, её привязку и владельца устройства в той же транзакции PostgreSQL, в которой выполняется операция. Подтверждающие строки блокируются до завершения транзакции. Если logout/отзыв сессии завершился первым, запрос отклоняется; если запрос первым успешно проверил и заблокировал сессию, он может завершиться, а отзыв ждёт окончания транзакции. Блокировки освобождаются до сетевой доставки ответа. Общий порядок блокировок согласован в следующем разделе; методы и режимы блокировок Auth/Devices согласованы в контрактах владельцев.

Guard по-прежнему проверяет подпись, claims и срок access token до входа в Dialogs. Его результата недостаточно для защиты от отзыва сессии между guard и SQL. Все методы ниже используют **переданный `DatabaseTransaction`**, без собственного соединения, вложенной независимой транзакции или обращения к кешированному разрешению. Dialogs не импортирует таблицы других владельцев для запросов; декларативные FK схемы не являются таким доступом.

Реализованные транзакционные расширения:

- Auth: `lockAccountStates(tx, userIds)` и `lockSession(tx, userId, sessionId)` — состояния аккаунтов, включая отключённого peer, и действующая принадлежащая actor сессия. Режимы блокировок, результаты и ошибки определены в [контракте Auth](../auth.md#транзакционная-проверка-сессии-для-dialogs--реализовано).
- Devices: `lockSessionBinding(tx, userId, sessionId)` — проверенный deviceId текущей сессии. Блокировки binding/устройства и ошибки определены в [контракте Devices](../devices.md#транзакционная-проверка-binding-для-dialogs--реализовано).

`Groups.lockCommonGroup(tx, actorId, peerId)` уже существует и удерживает выбранную общую группу и обе строки членства `FOR SHARE`. Для admin-исключения общая группа не запрашивается. Для permissions при отсутствии общего членства возвращаются false по матрице, для запрещённой операции истории/отправки — согласованный `DIALOG_NOT_ALLOWED`.

#### Порядок блокировок и граница допуска

Согласован следующий единый порядок блокировок для операций Dialogs. Согласован уровень изоляции `READ COMMITTED`: права защищаются подтверждающими блокировками, отправки сериализуются на строке диалога. Страница истории и has_more вычисляются в одном SQL-снимке; общего неизменного снимка между страницами нет. При конкурентном создании запрос после конфликта INSERT читает существующий диалог отдельным statement той же транзакции.

1. Для запроса с dialog_id прочитать только неизменные ID участников собственной строки без блокировки диалога; неизвестный/чужой ID не раскрывается. Это предварительное чтение не разрешает доступ. При создании пара определяется из actor и peer_id.
2. Через Auth заблокировать необходимые аккаунты в порядке UUID: actor и peer для создания, отправки, истории и permissions; только actor для list/get метаданных. Проверить активность actor; состояние/роль peer применять по согласованной матрице, без требования активности peer при чтении.
3. Через Auth заблокировать текущую сессию, затем через Devices binding и устройство. session_id/user_id берутся из проверенной личности, device_id — только из результата Devices.
4. При необходимости через Groups заблокировать подтверждающую общую группу и членства. Для permissions рассчитать can_read/can_send по одному набору состояний.
5. Для отправки или подтверждения прочтения заблокировать строку диалога `FOR UPDATE`; повторно проверить её участие. Для создания использовать UNIQUE пары, как описано ниже. Чтение истории не блокирует строку диалога `FOR UPDATE`.

Все полученные блокировки удерживаются до завершения транзакции. Ни один путь Dialogs не берёт аккаунт/сессию/членство после блокировки диалога. Операции владельцев, участвующие в этой интеграции, должны сохранять совместимый порядок; при реализации отдельно проверяются logout/refresh, административный отзыв, удаление группы/членства, регистрация и cleanup Devices. Redis/Redlock не обеспечивает сериализацию этой записи.

Отзыв, успевший зафиксироваться до захвата соответствующей блокировки, виден проверке и запрещает операцию. Если Dialogs первым удержал подтверждающие строки, отзыв ждёт окончания короткой транзакции; такая операция считается допущенной до отзыва. Удаление/изменение выбранного членства ждёт `FOR SHARE`; отсутствие общей группы не резервирует будущие права — следующий запрос пересчитывает их. Новая выдача после завершённого отзыва не допускается по старому guard или permissions. Срок access token проверяется при входе в запрос, как в Auth; отдельного права завершать новые запросы после его истечения нет.

List/get и permissions читают метаданные в рамках транзакции с заблокированными actor/session/binding; история проверяет также peer и необходимое членство. Выборка одной страницы, позиций прочтения для вычисления MessageDto.status и определение has_more используют один SQL-снимок (до limit + 1 записей); для истории байтовый бюджет может уменьшить страницу и пересчитать has_more по уже выбранным записям. Расшифровка и формирование разрешённой страницы происходят до завершения транзакции; HTTP-байты выдаются только после её успешного завершения. Транзакция не удерживается до сетевой доставки ответа. Общего неизменного снимка между страницами нет.

#### Создание и отправка

`POST /dialogs`: после проверок права создания выполнить INSERT канонической пары с `ON CONFLICT (participant_low_id, participant_high_id) DO NOTHING RETURNING`. Вставивший получает 201. При конфликте прочитать существующую строку отдельным statement в той же транзакции `READ COMMITTED`, после ожидания конкурента; вернуть 200 без обновления created_at/активности. Конфликт UNIQUE пары не превращается в публичную ошибку. Успех возвращается после commit; откат конкурента позволяет запросу создать строку самому.

Согласовано для отправки: под блокировкой строки диалога берётся `last_sequence + 1`; зашифрованное сообщение и `last_sequence`/`last_message_at` сохраняются одной транзакцией. Rollback не расходует номер и не меняет активность. Повтор по тому же ключу идемпотентности возвращает исходное сообщение без нового номера. WS/push запускаются только после commit. Все шаги алгоритма ниже обязательны.

`POST /dialogs/:dialog_id/messages`:

1. Проверить DTO/лимиты и актуальный доступ, взять блокировки в указанном порядке. Проверка актуального can_send обязательна и для повтора; прежний успех не обходит отключение peer, отзыв сессии или утрату группы.
2. Под блокировкой диалога искать `(dialog_id, sender_id, client_message_id)`. Если запись найдена, вернуть исходный MessageDto с HTTP 200: расшифровать сохранённый content для ответа, но не сравнивать с content запроса. Сохранённые поля, включая sender_device_id, остаются неизменными и при повторе с другого разрешённого устройства. Это согласованное правило повтора только по ID.
3. Согласовано: для новой записи вычислить `last_sequence + 1` под блокировкой строки, без PostgreSQL sequence/nextval. Получить серверное время БД после ожидания блокировки, назначить message_id и зашифровать content. Порядок сообщений определяется sequence, даже при совпадении timestamps. Время не является позиционным курсором.
4. Одной транзакцией вставить все поля сообщения и обновить last_sequence/last_message_at. Согласовано: при исчерпании безопасного диапазона отказать через существующий ErrorModule с безопасным INTERNAL_ERROR, без округления, новой записи или изменения активности. Повтор уже сохранённого ключа возвращает исходное сообщение и не требует нового номера. Любая ошибка шифрования/SQL откатывает оба изменения; откат не оставляет зарезервированного номера.
5. Только после подтверждённого commit вернуть 201 и инициировать согласованные best-effort WS/push. Блокировки БД не удерживаются во время обращений к Signaling/провайдерам; их проверки перед доставкой выполняются отдельно. Повтор с 200 не инициирует уведомления.

При двух одновременных отправках в один диалог второй запрос ждёт строку диалога и видит завершённый результат первого: одинаковый ключ идемпотентности даёт одну запись независимо от content, разные ID получают последовательные номера. Параллельные диалоги не делят счётчик sequence. UNIQUE остаются защитой целостности, а не заменой блокировки.

Согласовано: подтверждённый rollback не даёт успешного ответа. При потере подтверждения COMMIT backend не сообщает ни доказанный успех, ни доказанное отсутствие сообщения: возвращается безопасная ошибка по [ErrorModule](../errors.md), клиент повторяет исходный client_message_id/content. Повтор заново проверяет актуальный доступ. Если commit состоялся, повтор вернёт сохранённую запись; иначе создаст её один раз. Слепой повтор всей транзакции сервером и восстановление пропущенных уведомлений после неизвестного commit не выполняются; при создании сообщения повторным запросом уведомления следуют обычному правилу после подтверждённого commit. Таймаут/дедлок не обходят проверки и не раскрывают SQL; действуют бюджеты [Database](../database.md).

#### Сохранность истории при cleanup

Согласовано: `sender_device_id` — неизменный исторический UUID, полученный из проверенного binding при первой записи, **без FK на `gchat_devices` или `gchat_device_sessions`**. Отдельная сессия в сообщении не сохраняется. После физического удаления устройства UUID остаётся в сообщении, но не используется для авторизации, поиска текущего push-адреса или требования повторно создать прежнее устройство. История и идемпотентность не зависят от существования прежнего устройства. Повтор с другого разрешённого устройства возвращает исходное сообщение, не меняя сохранённый `sender_device_id`.

Удаление Auth-сессии отзывает доступ сразу, даже пока binding ещё хранится. Cleanup Devices может удалить старый binding и его push-адреса, затем устройство по собственным правилам; сообщения не удерживают эти записи и не пополняют retainedSessionIds звонков. Уже существующие ограничения DirectCalls сохраняются. При гонке удаления с допущенной операцией `FOR SHARE` на binding/устройстве удерживает строки до её завершения; если удаление завершилось первым, проверка не проходит. История ни в одном порядке не удаляется и не обнуляется.

Согласовано: FK участников/sender на аккаунты и сообщений на диалог используют ON DELETE RESTRICT. Отключение аккаунта меняет доступ и отзывает сессии, но не удаляет аккаунт/диалог/сообщения. Будущий hard delete аккаунта потребует отдельного согласованного контракта; незаметное каскадное уничтожение истории запрещено. Утрата группы, logout, переустановка и очистка устройств не изменяют sequence, идемпотентность или метаданные активности. Ключи для оставшихся сообщений сохраняются независимо от жизненного цикла устройств.

### Серверное шифрование и ключи

Согласовано: AES-256-GCM через встроенный `node:crypto`, без новой криптографической зависимости. Применяется случайный 32-байтовый ключ из согласованного набора окружения, для новой записи — 12-байтовый криптографически случайный IV; authentication tag фиксирован на 16 байт. Ключ и IV передаются криптобиблиотеке как bytes, не как пароль/текст. Ссылки: [Node crypto](https://nodejs.org/docs/latest-v24.x/api/crypto.html), [OWASP authenticated modes](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html#cipher-modes).

Общее ограничение на новые криптографические зависимости закреплено в [корневом AGENTS.md](../../../../AGENTS.md#криптография). Для Dialogs сторонние криптобиблиотеки не подключаются; системный криптографический API всё равно требует соблюдения параметров и эксплуатации ключей, перечисленных в этом контракте.

Согласованные поля БД: encryption_version=1, encryption_key_id, iv, ciphertext, auth_tag. Двоичные поля хранятся как bytea, без открытого дубля content или base64-расширения ciphertext. В plaintext для шифрования сериализуется только валидированный content. ID сообщения/диалога/отправителя, client_message_id и sequence криптографически связываются с ciphertext через AAD; точная кодировка AAD, ограничения IV и предел попыток заданы в [формате записи](#формат-записи-и-бюджет-ключа).

Расшифрованный content выдаётся только после успешной проверки tag и серверных прав. Ошибка целостности — безопасная ошибка через ErrorModule, без выдачи частично расшифрованных данных. Идемпотентный повтор возвращает уже сохранённую запись, не шифрует её заново и не создаёт новый IV. Алгоритм, размеры ключа/IV/tag и поля хранения приняты; формат и эксплуатационные инварианты конкретизированы ниже.

Ключи шифрования истории принадлежат backend и не отправляются клиентам через WSS или локальный bridge. Данные шифруются до сохранения в PostgreSQL. Алгоритм и поля зашифрованной записи согласованы выше, источник и способ передачи ключей — ниже.

Ключевой материал хранится отдельно от таблиц сообщений, не попадает в репозиторий, логи или обычный dump БД. Для штатной ротации должна сохраняться возможность читать записи со старыми key IDs; неизвестный ключ или ошибка проверки подлинности дают безопасный отказ, а не выдачу повреждённого текста. Ключи Auth/JWT/TURN не переиспользуются для истории.

Серверное шифрование защищает отдельную копию БД без ключей, но не оператора с доступом к работающему backend и ключевому материалу. Администратор приложения вне диалога не имеет API-доступа к переписке. Сбросив пароль участника и войдя под его аккаунтом, администратор или другой обладатель credentials технически может получить историю в пределах текущих прав этого аккаунта; отдельной криптографической защиты от такого входа больше нет. Это следствие согласованного отказа от E2EE, а не административный маршрут чтения.

Согласовано: ключи хранятся в GitHub Actions Secrets и передаются backend через окружение Docker при деплое. Secret `DIALOGS_ENCRYPTION_KEYS` содержит JSON-объект `{key_id: base64_key}`; обычная конфигурационная переменная `DIALOGS_ACTIVE_KEY_ID` выбирает активный ключ. Каждый ключ после декодирования base64 должен содержать ровно 32 байта; ограничения key ID заданы ниже. Backend валидирует конфигурацию при старте: отсутствие активного ключа, некорректный формат или пустой набор не приводят к автоматической генерации замены или plaintext fallback.

Workflow явно получает secret/переменную, передаёт по защищённому каналу на сервер и обновляет соответствующие значения в защищённом `backend.env` вне релизов. [Compose](../../../../deployment/gchat/compose.yaml) передаёт их процессу backend через `env_file`; GitHub Secrets не попадают туда автоматически. Отдельный keyring-файл внутри контейнера, `DIALOGS_KEYS_FILE` и новый secret mount не нужны. Значения не включаются в Docker image, frontend bundle, репозиторий, логи или артефакты workflow. Окружение процесса доступно операторам с соответствующими правами и не является защитой от полного захвата хоста.

Набор ключей сохраняется между деплоями и пересозданиями контейнеров, не генерируется workflow при каждом релизе. При плановой смене в secret добавляется новый key ID и выбирается активным для новых записей; старые ключи сохраняются для старой истории и backup. Переключение не перешифровывает прошлые сообщения. Обновление GitHub Secret само по себе не меняет окружение работающего контейнера: нужен деплой/пересоздание с новой конфигурацией.

Workflow передаёт ключи по SSH stdin и атомарно обновляет защищённый `backend.env`, сохраняя исторические ключи. Compose получает DATABASE_URL через CLI env-file для интерполяции; мигратор получает только DATABASE_URL и не монтирует каталог секретов. Ключевой материал получает только backend; он не включается в image, frontend или release-артефакты.

Копия набора ключей резервируется отдельно от dump БД, с ограниченным доступом и защитой резервного носителя. GitHub Secrets — источник для деплоя, но не замена процедуре аварийного восстановления; процедуры определены в [правилах восстановления](#резервирование-и-аварийное-восстановление) и формате ключей ниже.

#### Формат записи и бюджет ключа

- `encryption_key_id`: ASCII `[A-Za-z0-9_-]{1,64}`, регистр значим. Один ID навсегда связан с одним случайным 32-байтовым ключом; одинаковый ключ под разными ID запрещён. Ключи независимы между окружениями и отдельными установками БД. Конфигурация принимает только канонический padded base64: строгое декодирование, проверка 32 байт и обратное кодирование с точным совпадением.
- Plaintext: UTF-8 от компактного `JSON.stringify` валидированного content с фиксированным порядком полей: `{kind,text}` либо `{kind,sticker_id}`. Никакого trim или Unicode-нормализации; непарные UTF-16 surrogate отклоняются как VALIDATION_ERROR, чтобы кодировка не заменяла символы молча. Обычные Unicode emoji в text разрешены и входят в существующий лимит code points; новый emoji picker не добавляется.
- AAD версии 1: UTF-8 компактного JSON-массива `["gchat.dialog.message",1,encryption_key_id,message_id,dialog_id,sender_id,sender_device_id,client_message_id,sequence_decimal,created_at_utc]`. UUID — канонические lowercase строки с дефисами; sequence_decimal — строка целого без ведущих нулей; created_at_utc — ISO 8601 UTC с ровно тремя цифрами миллисекунд и `Z`. Время новой записи БД приводится к миллисекундам до шифрования и сохраняется точно в этом виде. Массив не зависит от порядка полей объекта; AAD при чтении заново строится из метаданных строки. Изменяемые status/позиции прочтения в AAD не входят.
- Используются `createCipheriv`/`createDecipheriv` с явно заданным `authTagLength: 16`, `setAAD` до обработки content и проверка `final()` до разбора JSON и выдачи plaintext. Отсутствующий ключ — SERVICE_UNAVAILABLE; неверный tag/формат расшифрованной записи — INTERNAL_ERROR. При ошибке одного сообщения страница не выдаётся частично. Параметры следуют [официальному API Node.js](https://nodejs.org/docs/latest-v24.x/api/crypto.html).
- Каждый новый вызов шифрования использует `randomBytes(12)`; ключ допускает максимум **16777216 (2²⁴) попыток шифрования** за весь срок, включая rollback. Это согласованный запас относительно ограничений случайных IV из [NIST SP 800-38D, разделы 8 и 8.3](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf), а не утверждение об абсолютной невозможности случайной коллизии. Дополнительно UNIQUE `(encryption_key_id, iv)` запрещает сохранить повтор IV в сообщениях. При обнаруженной коллизии транзакция откатывается с INTERNAL_ERROR, ключ выводится из новых записей оператором; автоматического повторного шифрования нет.

Служебная таблица: `gchat_dialog_encryption_keys` с `key_id text PK`, `key_fingerprint bytea NOT NULL UNIQUE CHECK octet_length = 32` (SHA-256 случайного ключа через node:crypto, без самого ключа), `encryption_attempts bigint NOT NULL DEFAULT 0 CHECK 0..16777216`. Формат key_id проверяется CHECK. Записи/счётчики не удаляются и не сбрасываются при деплое, смене активного ключа или cleanup. При старте backend регистрирует отсутствующие key IDs, сверяет fingerprint; несовпадение ID/ключа либо повтор материала под другим ID останавливает запуск. Мигратор создаёт схему, но не получает ключевой материал и не заполняет fingerprint.

Перед возможным новым шифрованием атомарный условный UPDATE увеличивает encryption_attempts отдельной короткой транзакцией **до** бизнес-транзакции и её блокировок. Только подтверждённый commit резервирования разрешает один вызов AES-GCM; неизвестный исход резервирования даёт SERVICE_UNAVAILABLE без шифрования и слепого повтора. Потраченная попытка не возвращается после отказа/rollback. Так счётчик охватывает все процессы и не создаёт ожидание второго соединения внутри уже удерживаемой бизнес-транзакции.

Предварительный поиск существующего ключа идемпотентности может пропустить резервирование для повтора, но не выдаёт сообщение и не заменяет последующую транзакционную проверку прав. Если предварительно записи не было, резервирование может потратиться зря при конкурентном повторе — это допустимо. Если резервирование отказало из-за исчерпания бюджета, бизнес-транзакция ещё может вернуть существующее сообщение после проверки доступа; новую запись она не создаёт и отвечает SERVICE_UNAVAILABLE. Поэтому исчерпанный бюджет не блокирует разрешённое чтение и повторы сохранённых сообщений. Резервирование не расходует sequence.

Новые ключи готовятся до исчерпания лимита; при остатке менее 10% выводится безопасный сигнал оператору с key ID и счётчиком, без содержимого. Подтверждённое резервирование является единственным допуском к шифрованию; проверка количества сообщений не заменяет счётчик попыток. После восстановления старой БД/клонирования новые записи обязательно переводятся на новый независимый ключ и новый ID; исторические ключи остаются только для чтения. При компрометации остановить новую выдачу/запись истории, закрыть доступ к ключам и credentials, развернуть новый активный ключ; возобновление — после проверки доверенного окружения. Уже раскрытый plaintext/ключ отозвать невозможно. Автоматическое массовое перешифрование и удаление старых ключей не входят в этот объём.

### Минимальная схема хранения

Таблицы, поля, индексы и правила удаления описаны в [схеме БД](#схема-бд-и-транзакции). В зашифрованном поле хранится content целиком, включая текст/ID стикера; открытого дубля или plaintext preview нет. Отдельных таблиц клиентских ключей/доверия, транспортных ACK и outbox нет. Позиции прочтения хранятся в двух полях gchat_dialogs без отдельной таблицы. Обычные резервные копии БД содержат шифротекст и метаданные; для восстановления нужен отдельно сохранённый соответствующий серверный ключевой материал.

## Зависимости и регистрация

Обычный `DialogsModule` импортирует DatabaseModule, AuthModule, GroupsModule и DevicesModule; для лимитов получает глобальный RedisService без повторного forRoot; экспортирует DialogsService. REST-контроллеры Dialogs вызывают бизнес-сервис. SignalingModule импортирует DialogsModule для отправки серверных событий о новых сообщениях и прочтении; WS-команды dialog.sync/message.send не вводятся. Обратной зависимости бизнес-сервиса от сокетов нет. ErrorService и Logger внедряются по существующим правилам, новый `forRoot()` не нужен. HTTP SDK и OpenAPI обновляются только после реализации контроллеров штатной генерацией.

WSS остаётся общим и не привязывается к монтированию страницы диалога. Dispatcher и native bridge принимают два серверных события dialog.messages_available/dialog.read_updated по ссылкам на этот контракт; клиентских WS-команд диалогов нет. Серверная интеграция реализована; клиентская обработка относится к собственному контракту Web/bridge. Текущие примеры `chat.*` в generic bridge-тестах не означают наличия модуля. Брокер, отдельный сервис и Redis-архив не требуются для sync из PostgreSQL.

## Ошибки и частичное выполнение

Согласовано: все ошибки Dialogs проходят через существующий ErrorModule. Бизнес-сервис использует внедрённый ErrorService и выбрасывает полученный AppError; стандартные фабрики используются для существующих кодов, новые бизнес-коды создаются через ErrorService.create с соответствующим HTTP-статусом. ErrorModule подключён глобально, повторный импорт в Dialogs не нужен.

HTTP-статус, оболочку error, безопасное message, fields и Retry-After формирует общий HTTP-фильтр ErrorModule. Контроллеры диалогов не собирают ошибочные ответы вручную, не вводят отдельный формат/фильтр и не перехватывают исключения только ради сериализации. Ответы Auth, ошибки DTO/JSON и payload-limit интегрируются в тот же механизм по существующим соглашениям. Необработанная внутренняя ошибка также нормализуется ErrorModule, без выдачи исходных подробностей.

HTTP-ошибки и статусы соответствуют [ErrorModule](../errors.md). Ошибки авторизации и закрытие канала WS-уведомлений сохраняют контракт Signaling; HTTP-ошибка истории сама по себе не является WS-ответом. Базовые ошибки — Auth/FORBIDDEN, VALIDATION_ERROR, NOT_FOUND, RATE_LIMITED, SERVICE_UNAVAILABLE и INTERNAL_ERROR. Специфичная ошибка — DIALOG_NOT_ALLOWED. Недоступность серверного ключевого материала запрещает операцию и преобразуется в безопасную ошибку зависимости без вывода ключа или содержимого.

Потеря ответа или подтверждения COMMIT означает неизвестный результат. Клиент повторяет исходный client_message_id с текущей авторизацией, не создаёт новую отправку автоматически. Утрата прав может запретить повтор уже сохранённого сообщения; такой отказ не доказывает rollback.

Первый вход, переустановка и другое устройство не требуют восстановления ключей истории: backend отдаёт разрешённое содержимое через sync. Очистка локального кеша не уничтожает серверную переписку. Потеря серверных ключей, напротив, делает соответствующий шифротекст недоступным; backup БД без этих ключей недостаточен.

Скомпрометированный клиент может прочитать выданные ему сообщения. Обязательны защита от XSS, безопасный вывод текста и [процедура восстановления БД](../../operations/recovery.md), не возвращающая отозванный доступ. Серверный ключевой материал восстанавливается отдельно от обычного dump; аварийная процедура определена в [правилах резервирования](#резервирование-и-аварийное-восстановление) и проверяется до production.

## Конфигурация

Используются переменные `DIALOGS_ENCRYPTION_KEYS` (секретный набор ключей из GitHub Secrets) и `DIALOGS_ACTIVE_KEY_ID` (обычная конфигурационная переменная). Правила источника, доставки и плановой смены описаны в разделе [серверного шифрования](#серверное-шифрование-и-ключи). Переменные подключены к валидатору backend, `.env.example` и workflow; Compose передаёт `backend.env` только приложению.

Для списка и истории согласованы limit=30 по умолчанию и максимум 100; offset списка по умолчанию 0. Ответ истории ограничен 512 КиБ до сжатия, включая JSON-обёртку. Подробные правила — в разделе [лимитов страниц](#лимиты-страниц). Согласованные ограничения частоты находятся в [отдельном разделе](#частота-запросов); новые env-переменные для их изменения не вводятся этим контрактом.

Для отправки уже согласованы 4000 code points текста и 64 КиБ тела JSON; подробные правила — в разделе [лимитов одного сообщения](#лимиты-одного-сообщения). Эти значения не являются лимитом страницы истории или WS-фрейма.

Согласовано бессрочное хранение диалогов и сообщений: нет TTL, автоматической очистки истории или пользовательского удаления в текущем объёме. Потеря общей группы, отключение аккаунта, logout, смена устройства и деплой не удаляют серверную историю; доступ к ней по-прежнему определяется текущими правами. Необходимые для чтения сохранённой истории серверные ключи нельзя удалять при плановой ротации без завершённого перешифрования соответствующих записей. Это правило не задаёт срок хранения отдельных backup-снимков: политика задана в [разделе резервирования](#резервирование-и-аварийное-восстановление).

Серверные ключи, открытые сообщения, полные payload и токены не попадают в логи/диагностику. Оператор с одним dump видит шифротекст/метаданные; с ключами имеет техническую возможность расшифровки. Согласованное включение текста в push ниже является отдельной выдачей содержимого, а не разрешением логировать payload.

### Уведомления

Системные push содержат текст сообщения, для стикера — «Стикер». Это согласованная выдача содержимого: обычный APNs передаёт текст Apple, Web Push использует шифрование существующего транспорта; ОС может показать preview на экране блокировки. Текст и payload не логируются. До первой регистрации действующего адреса уведомление не гарантируется. Ключи истории и credentials не передаются в payload.

Push выполняется best-effort только после commit нового сообщения; ошибка/пропуск не отменяет сообщение и не меняет успешный REST-ответ. Повтор отправки по прежнему ключу идемпотентности не инициирует push. Outbox, устойчивая очередь, автоматические повторы и восстановление пропущенных уведомлений после перезапуска не вводятся. История остаётся доступной через REST по актуальным правам.

Заголовок — **GChat** без имени отправителя; body — исходный text либо «Стикер». Общие прикладные поля: `{type: "dialog.message", dialog_id, message_id, sender_id, sequence}`. Они передаются только в разрешённое устройство получателя, не подтверждают прочтение и не используются как право доступа.

- APNs: общий payload `{aps: {alert: {title: "GChat", body}, sound: "default"}, type, dialog_id, message_id, sender_id, sequence}`; `apns-push-type: alert`, topic — обычный bundle ID без `.voip`, priority 10, expiration 0. Не добавляются badge, mutable-content, content-available или собственный collapse ID. Обычный APNs адрес разрешается через Devices с проверкой версии; он хранится отдельно от VoIP. Окружение и credential используются по правилам Push.
- Web Push: JSON `{type, dialog_id, message_id, sender_id, sequence, title: "GChat", body}` через существующий web-push, encoding aes128gcm, urgency high, TTL 0. Worker различает `type: "dialog.message"` и существующий call payload; показ звонков сохраняет его контракт. Tag уведомления `gchat-message-<message_id>` объединяет повтор одного сообщения, не все сообщения диалога. В notification data остаются только идентификаторы перехода; текст дополнительно туда не копируется.
- Сериализованный JSON APNs не превышает 4096 байт — [лимит Apple](https://developer.apple.com/library/archive/documentation/NetworkingInternet/Conceptual/RemoteNotificationsPG/CreatingtheNotificationPayload.html). Для Web Push применяется собственный более консервативный бюджет 3000 байт plaintext JSON; транспортное шифрование выполняет существующая библиотека по [RFC 8291](https://www.rfc-editor.org/rfc/rfc8291.html). Если требуется сокращение, выбирается наибольший префикс body по границам графем `Intl.Segmenter`, помещающийся вместе с «…» и всеми полями в байтовый бюджет после JSON-сериализации. Полный content в истории не меняется. Даже один текстовый фрагмент с чрезмерно длинной графемой может дать body «…»; частичная графема не выдаётся.
- TTL/expiration 0 запрещает хранить сообщение провайдером до возвращения устройства онлайн; это дополнительно ограничивает шанс уведомления офлайн и соответствует согласованному best-effort режиму. Доставка провайдером не гарантируется; ограничение описано в [RFC 8030](https://www.rfc-editor.org/rfc/rfc8030.html#section-5.2).

После commit доступные адреса получателя обрабатываются одним best-effort заданием **только в памяти**. На backend — максимум 4 одновременно выполняемых задания сообщений, в каждом максимум 4 запроса к адресам; ожидание запуска тоже входит в общий срок 10 секунд от commit. На один запрос к провайдеру — максимум 5 секунд и не больше остатка общего срока. В памяти допускается до 100 ожидающих заданий; при переполнении или истечении срока уведомление пропускается с безопасным счётчиком причины. На каждый адрес не более одной попытки; при прекращении процесса очередь теряется, при shutdown новые задания не принимаются, активные завершаются/отменяются за оставшийся бюджет. REST не ждёт исполнения и не меняет успех из-за пропуска push. Это ограничение исполнения, а не устойчивая очередь или доставка с повторами.

Перед каждой попыткой заново проверяются право чтения, активность аккаунта/адресной сессии и версия адреса. При отказе проверки адрес пропускается. Ошибки credentials, 429/5xx и сетевой таймаут не повторяются. APNs BadDeviceToken/Unregistered/DeviceTokenNotForTopic и Web Push 404/410 инвалидируют только совпадающую версию адреса по существующему механизму Devices; timestamp APNs учитывается, поздний ответ не удаляет новый адрес.

Нажатие уведомления передаёт Web намерение открыть dialog_id через существующий native bridge или same-origin URL приложения с query `dialog_id=<uuid>` в браузере. Native не передаёт токен в Web. Intent сохраняется до восстановления сессии только в текущем цикле приложения; после смены сервера/аккаунта отменяется. Web получает диалог через REST с текущими правами; при неизвестном/чужом контексте показывает общий список без чужого content. URL строится из настроенного start URL, не принимается из push; тело и credentials в URL отсутствуют. Само нажатие не отправляет read: момент прочтения определяет клиент. Обычные push не подключаются к CallKit/PushKit.

Серверный транспорт чата реализован. Контракты VoIP/Web Push звонков в Push/DirectCalls сохраняются; их outbox и повторы не переносятся на чат. Обычный APNs-токен регистрируется отдельной согласованной командой [Devices](../devices.md#обычный-apns-токен-чата--реализовано).

### Резервирование и аварийное восстановление

Согласован минимальный эксплуатационный уровень: **один согласованный snapshot PostgreSQL каждые 24 часа**, хранить последние 30 успешных суточных копий вне рабочего сервера. Целевой RPO — до 24 часов при исправном выполнении; при сбое расписания фактическая потеря может быть больше. Это не гарантия сохранности каждого уже подтверждённого сообщения при утрате БД. Тревога оператору — нет успешного backup более 26 часов. PITR и автоматическое переключение БД не входят в этот объём. Целевой RTO — 4 часа с момента начала восстановления оператором, он подтверждается восстановлением на стенде, а не объявляется достигнутым заранее.

Backup-снимки шифруются штатными средствами выбранного хранилища/ОС, доступ только у операторов восстановления, отдельно от аккаунта рабочего backend; не создаётся собственный криптографический архиватор. Конкретные адреса хранилища/credentials — параметры окружения до production, не публичный API. Набор ключей хранится отдельно от dump в корпоративном хранилище секретов с независимым доступом восстановления; GitHub Secrets остаётся источником деплоя, но не единственной копией. Перед активацией нового key ID подтвердить сохранение его независимой резервной копии. Сохраняются все исторические ключи рабочей истории; удаление старых snapshot не разрешает удалить нужный истории ключ. Manifest backup содержит время, версию схемы/приложения и необходимые key IDs без ключевого материала.

Последовательность восстановления: остановить все процессы записи; выбрать и восстановить snapshot в изолированную БД; получить соответствующие ключи по независимому каналу; проверить manifest и tag всех сохранённых сообщений без выдачи content в логи; инвалидировать восстановленные Auth-сессии/WS-билеты по [общему recovery-контракту](../../operations/recovery.md); создать новый независимый активный ключ/ID с резервной копией, не продолжая старый бюджет шифрования из snapshot; проверить вход, права, историю, sequence и галочки; только после этого открыть доступ. Доказательства полной проверки — число проверенных записей, key IDs и результат, без plaintext. При отсутствии хотя бы одного необходимого ключа или повреждённом tag доступ к истории не открывается до разбора аварии. Состояние read/идемпотентности восстанавливается в пределах snapshot; потерянные после него сообщения/подтверждения не выдаются за сохранённые. Клиентские большие позиции прочтения после восстановления не доказывают серверное состояние. Правило recovery клиента: SESSION_INVALID завершает текущий цикл аккаунта, после нового входа клиент перечитывает список с начала и обнуляет кеш сообщений/позиции sync/read этого аккаунта до повторной загрузки с сервера; максимум позиций применяется только внутри текущего авторизованного цикла. Подтверждения прочтения из прежнего цикла и прежние sync-позиции не переносятся автоматически. Новая история загружается с нулевой позиции; сообщения, утраченные в серверном snapshot, не восстанавливаются из устаревшего read cursor. Это согласованное требование к frontend bootstrap, не описание существующего клиента; точка интеграции зафиксирована ссылкой в контракте Web.

Для полного прохода ciphertext/tag после восстановления используется `pnpm --filter @gchat/backend dialogs:verify` после build. Команда использует только DATABASE_URL и набор ключей из окружения, читает восстановленную БД в read-only repeatable-read транзакции и сообщает число записей/key IDs без content. Пишущие процессы предварительно останавливаются; любой отказ сохраняет доступ закрытым. Она не создаёт backup, не инвалидирует сессии и не подтверждает RPO/RTO.

Полное восстановление на изолированном стенде — перед первым production и затем раз в квартал; проверяется также доступ к резервным ключам и достижимость RTO. Инструменты backup, расписание, безопасные журналы, оповещение об отказе и процедура массовой инвалидации должны быть подготовлены до production; написание Dialogs само по себе их не реализует.

## Критерии приёмки и проверки

Критерии приёмки (фактические результаты запуска указываются в отчёте задачи):

- MessageDto возвращает status sent/read относительно получателя сообщения; ответ подтверждения содержит фактическую last_read_sequence, WS-событие dialog.read_updated — dialog_id/reader_id/last_read_sequence без content. Повтор отправки может вернуть обновлённый status, сохраняя исходные поля сообщения.
- dialog.read_updated отправляется только после commit продвижения позиции разрешённым подключениям обоих участников, включая другие устройства читателя. Повтор без продвижения не создаёт событие; отказ доставки не откатывает прочтение. Дубли/перестановка событий не уменьшают позицию, потеря компенсируется REST-метаданными.
- POST read возвращает HTTP 200 с текущим максимумом при повторе/меньшей позиции; некорректная или слишком высокая позиция даёт HTTP 400 VALIDATION_ERROR с полем sequence без изменения состояния. Запрет чтения даёт HTTP 403 DIALOG_NOT_ALLOWED, чужой/неизвестный диалог — одинаковый HTTP 404 NOT_FOUND; сессия и binding проверяются заново. Момент прочтения определяет клиент.
- CHECK ограничивает обе позиции прочтения диапазоном 0..last_sequence. Конкурентные подтверждения сохраняют максимум, затрагивают только позицию actor и не меняют активность/порядок диалогов; rollback и cleanup устройства не сбрасывают сохранённое прочтение.
- DialogDto списка/get/создания возвращает обе позиции прочтения. После пропущенного WS-события/reconnect REST-метаданные позволяют обновить галочки старых сообщений без загрузки истории заново; позиции с другого устройства не продвигают локальный sync, а поздние меньшие значения не откатывают прочтение.
- Одна галочка означает подтверждённое серверное сохранение, две — подтверждённое прочтение. Загрузка истории, WS-сигнал и push не переводят сообщение в прочитанное; момент прочтения определяет клиент, backend проверяет право и позицию подтверждения.

- Повторное и конкурентное создание возвращает один диалог пары; состав не меняется.
- Диалоги и сообщения не имеют TTL и не удаляются при потере прав, отключении аккаунта, logout или обновлении приложения. Пользовательского API удаления нет; очистка устройств и ротация ключей не разрушают сохраняемую историю.
- Участие, актуальная роль, группа и session/device binding проверяются для каждой операции; посторонний admin не получает переписку.
- Permissions получаются отдельным endpoint внутри объекта dialogs, в DTO диалога отсутствуют. Полученный can_send/can_read не заменяет повторную серверную проверку операции; чужой контекст не раскрывает права или существование диалога.
- Активный участник читает историю с отключённым собеседником, пока соблюдены остальные условия чтения, но отправить ему новое сообщение не может. Без общей группы отключённый admin не даёт исключения; активный admin-участник сохраняет своё исключение. Отключённый actor не читает историю.
- После запрета чтения list/get сохраняют разрешённые актуальные метаданные; sync/отправка закрыты по принятой матрице.
- Сортировка использует серверное время сохранения сообщения, для пустого диалога — создание; повтор не меняет позицию.
- Потеря ответа и повтор с прежним client_message_id не создают дубликатов; сообщение и его криптографические данные атомарны. Одинаковый текст с разными client_message_id сохраняется отдельными сообщениями с разными message_id/sequence; каждое новое сообщение следует обычному правилу уведомлений после commit.
- Проверяются CHECK/UNIQUE/FK: каноническая пара, запрет самодиалога, уникальность sequence и client_message_id в их областях, безопасный диапазон чисел и размеры двоичных полей. FK не позволяет каскадно удалить историю через аккаунт или диалог.
- Конкурентные отправки сериализуются на диалоге; одинаковый ключ идемпотентности даёт одну запись и первоначальный результат, в том числе при отличающемся content повторного запроса; содержимое не сравнивается и не заменяется. Повтор с другого устройства сохраняет исходный sender_device_id. Rollback не расходует sequence и не меняет активность; неизвестный commit разрешается повтором исходного запроса без повторных уведомлений.
- Проверяются оба порядка гонок с logout, сменой пароля, отключением, сменой роли и удалением последней общей группы: завершённый отзыв виден повторной проверке, ранее допущенная транзакция удерживает подтверждающие строки до конца. Чтение с отключённым peer не ломается из-за фильтра активных аккаунтов.
- Cleanup старого binding/устройства физически проходит, не блокируется FK сообщений и сохраняет исторический sender_device_id, ciphertext, позиции и идемпотентность. История читается на новом устройстве; гонка cleanup с операцией не позволяет использовать удалённый binding. Отсутствующий binding с действующей сессией даёт FORBIDDEN; отозванная сессия при ещё существующем binding — SESSION_INVALID.
- Текст в 4000 Unicode code points принимается, 4001 — получает 400 с полем content.text; пустой/пробельный текст отклоняется. Кириллица и многобайтовые символы считаются по code points, пробелы/переносы непустого сообщения не обрезаются. Тело до 65536 байт проходит размерную проверку, больше — получает 413 PAYLOAD_TOO_LARGE без сохранения; сжатие не обходит бюджет.
- Sync загружает новые и старые страницы без потерь, после reconnect продолжается с сохранённой позиции, повторные записи объединяются по ID.
- Список и история используют default limit=30, максимум 100; offset списка без параметра равен 0. Некорректные параметры дают 400 без clamp. История не превышает 524288 байт сериализованного JSON до сжатия, содержит только целые сообщения; при достижении байтового бюджета продолжение по sequence не теряет записи.
- Проверяются граничные позиции: новая запись может получить 9007199254740991; следующая новая отправка получает безопасную ошибку без изменения сообщения, last_sequence и last_message_at. Повтор сохранённого ключа на предельной позиции возвращает исходное сообщение. Время новой записи назначается БД после ожидания блокировки; совпадение timestamps не нарушает порядок sequence. CHECK отклоняет несогласованные last_sequence/last_message_at пустого состояния.
- Номера и позиции sequence в REST JSON и WS-уведомлении передаются числами в безопасном целочисленном диапазоне, начальная позиция — 0. Числовые строки в JSON, дробные/отрицательные значения и переполнение отклоняются; query-позиции строго разбираются из десятичной записи URL. Преобразование bigint из БД не теряет точность.
- Сообщение отправляется до первого входа получателя; после входа он читает его через sync с отправителем офлайн. Новое устройство/переустановка не требуют клиентских ключей истории.
- Content зашифрован в БД без открытых дублей; серверные ключи не находятся в таблицах/пользовательских DTO. Неизвестный key ID или повреждённый ciphertext не приводят к выдаче содержимого.
- Деплой передаёт сохранённый набор ключей из GitHub Secrets в окружение только backend без включения в образ, логи и артефакты. Повторный деплой/перезапуск сохраняют чтение истории; активный ID существует в наборе. Мигратор не получает ключи, а добавление нового активного ID не удаляет старые ключи.
- История/метаданные загружаются через REST и существующий HTTP SDK с общей Auth-обёрткой. В native Auth/WSS остаются за bridge; подтверждения прочтения идут через REST с общей Auth-обёрткой, уведомления чата — по общему WSS. REST-ошибка, потерянное/дублированное событие и reconnect не приводят к потере сообщений или обходу доступа.
- WS payload не содержит content/текст/ID стикера; событие не отправляется до commit и не продвигает локальную позицию до REST-загрузки. Query-позиции строго преобразуются в безопасные целые, JSON-номера не сериализуются строками.
- Новый текст показывается в body системного push, стикер — как «Стикер»; длинный текст безопасно сокращается. Перед отправкой повторно проверены права и адрес получателя, секретов/текста нет в логах. Переход из push восстанавливает сессию и проверяет права, а разрешённые ОС preview соответствуют содержимому сообщения.
- Падение/ошибка push после commit не отменяют сообщение и успешный REST-результат. После перезапуска push не воспроизводится, повтор исходной отправки не создаёт новую попытку; получатель находит сообщение через REST. Проверка прав перед попыткой сохраняется, устойчивых заданий чата в БД нет.
- Лимиты, отказ зависимостей, гонки с отзывом прав и cleanup устройств проверены без утечки содержимого или разрушения истории.
- Отправка 5/с с запасом 10, создание 1/с с запасом 5, подтверждения прочтения 5/с с запасом 10 и совместные GET 10/с с запасом 20 проверены на виртуальном времени и конкурентных запросах. Устройства/сессии делят счётчик аккаунта; группы независимы. Повторы расходуют лимит; отказ не создаёт новую запись, не продвигает прочтение и не создаёт уведомление. HTTP 429 содержит Retry-After, в том числе для подтверждений прочтения.

- Проверяются точная сериализация AAD и изменение каждого связанного поля, фиксированный tag 16 байт, отказ неизвестного ключа и повреждённого ciphertext без частичной страницы. Ключи не переиспользуются между ID/окружениями.
- Резервирование бюджета ключа учитывает rollback и конкуренцию процессов; неизвестный commit резервирования не допускает шифрование. Исчерпание бюджета запрещает только новые записи; допустимые повторы/чтение сохраняются. Restore использует новый активный ключ.
- Redis-лимиты атомарны между процессами, TTL эквивалентен полному восстановлению запаса; ошибка/таймаут закрывает операцию без локального fallback и повторного списания с неизвестным исходом.
- Push соответствует JSON-бюджету после сокращения по графемам, использует отдельный APNs alert/Web Push и безопасный intent. Проверяются пределы одновременности/очереди/времени, пропуск при перегрузке, отсутствие повторов и инвалидирование только текущей версии адреса.
- Каталог содержит пять фиксированных IDs, проверенные ресурсы/лицензию; неизвестный ID при отправке отклоняется, старый клиент безопасно показывает placeholder. Unicode emoji сохраняются без нормализации, непарные surrogate отклоняются.
- Recovery проверяется на изолированной БД с полным проходом проверки tag, инвалидацией сессий, сменой активного ключа и очисткой прежнего клиентского кеша/позиций после SESSION_INVALID. Настройка backup и достижимость RPO/RTO подтверждаются отдельным эксплуатационным испытанием.

Для документации — `pnpm docs:check` и проверка diff. Для кода — проверки из [README backend](../../../../applications/backend/README.md#сборка-и-проверки).

## Открытые решения

Для backend DialogsModule открытых решений нет. Контракт accepted; базовый backend реализован. Расширения с [именем собеседника](#планируемое-расширение-имя-собеседника) и [признаком непрочитанных](#планируемое-расширение-наличие-непрочитанных) согласованы и готовы к реализации, но ещё отсутствуют в коде/SDK. Криптография, схема хранения, лимиты и семантика прочтения не пересматриваются.

Пять файлов стикеров с лицензией, интеграции Push/Devices/Signaling и миграция добавлены. Настройка независимого backup/ключевого хранилища и полное эксплуатационное испытание восстановления остаются обязательной подготовкой окружения до production. Реальные credentials, адреса backup-хранилищ и ответственный оператор задаются при подготовке окружения до production.

Frontend bootstrap, конкретные интерфейсы локального кеша, UI-библиотека и визуальная приёмка остаются в [клиентском проекте](../../../web/bootstrap.md) и [продуктовых требованиях](../../../product/dialogs.md). Готовность backend-контракта не объявляет весь Web-клиент готовым к реализации.

### Запуск интеграционных тестов

`DIALOGS_INTEGRATION_DATABASE_URL` и `DIALOGS_INTEGRATION_REDIS_URL` должны указывать на выделенные тестовые зависимости. Тест создаёт/удаляет случайную БД и собственный Redis-префикс; PostgreSQL-пользователю нужны права CREATE DATABASE. Запуск из корня: `pnpm --filter @gchat/backend test --watchman=false --runTestsByPath test/dialogs.integration.spec.ts`. Без обеих переменных интеграционная группа пропускается.

# Действия над сообщениями: расширение DialogsModule

## Назначение и границы

Конкретный технический проект для [согласованного продуктового поведения](../../../product/message-actions.md). Расширяет [DialogsModule](README.md), [редактирование](message-editing.md), [Web](../../../web/dialogs.md) и [bootstrap](../../../web/bootstrap.md). Технический контракт целиком согласован пользователем 2026-11-14. Он готов к реализации; наличие контракта не означает наличия кода.

Dialogs владеет пересылкой, состоянием реакций, проверками доступа и серверным шифрованием. Web/PWA владеет меню, буфером обмена, выбором получателя и единственным локальным кешем. Используются текущие DI, HTTPS REST, generated SDK, device/runtime и существующий WSS. Нового Nest-модуля, сокета, криптографической библиотеки, очереди или внешнего сервиса нет. Публикация/production-миграция в эту работу не входят.

## Публичный API

Все маршруты имеют внешний префикс `/api`, текущие Auth/device binding, транзакционные проверки прав, `Cache-Control: no-store` и общий формат ошибок. UUID нормализуются в нижний регистр; неизвестные поля и повторные query отклоняются. Тела ограничены 65536 байт до JSON-разбора, позиции/версии — безопасные целые JSON-числа без строковых чисел и clamp.

| Метод и путь | operationId | Вход | Ответ |
| --- | --- | --- | --- |
| `POST /dialogs/:dialog_id/forwards` | `dialogsMessageForward` | `{client_message_id, source_dialog_id, source_message_id, expected_source_version}` | `{message: MessageDto}`, 201 при создании, 200 при повторе |
| `GET /dialogs/:dialog_id/messages/by-client-id/:client_message_id` | `dialogsMessageGetByClientId` | UUID целевого диалога и ключ отправки текущего actor | `{message: MessageDto}`, 200; 404, если сохранённой отправки actor нет |
| `PUT /dialogs/:dialog_id/messages/:message_id/reactions` | `dialogsMessageReactionSet` | `{client_reaction_id, emoji, selected, expected_version}` | `{message: MessageDto}`, 200 |
| `GET /dialogs/:dialog_id/message-reactions` | `dialogsMessageReactions` | `after_reaction_sequence?`, `limit?` | `{messages: MessageDto[], next_reaction_sequence, has_more}`, 200 |

`expected_source_version` — положительная content-версия исходника из предпросмотра. `expected_version` реакции — версия состояния **своего конкретного emoji**, начиная с 0; это не `MessageDto.version` и не общая версия реакций. `client_reaction_id` — UUID одной логической команды для тройки message/actor/emoji. `selected` — строго boolean: сервер не принимает команду toggle. `emoji` принадлежит фиксированному каталогу продукта после нормализации ниже.

Для ленты реакций `after_reaction_sequence` по умолчанию 0, `limit` — 30, диапазон 1..100. Существующие GET, отправка, редактирование, история и превью сохраняют маршруты. Статический сегмент `by-client-id` не трактуется как UUID сообщения. GET by-client-id выдаёт только сообщение от текущего actor, даже если похожий ключ использовал собеседник.

### Расширение MessageDto

Обязательные поля во всех ответах, включая `DialogDto.last_message`, обычную отправку, повтор, правку и обе ленты изменений:

| Поле | Форма и смысл |
| --- | --- |
| `forward` | `null` для обычного сообщения; `{author: null}` для анонимной пересылки; `{author: {id, display_name}}` для разрешённого снимка автора |
| `reaction_version` | Безопасное целое от 0; общая монотонная версия полного снимка реакций сообщения |
| `reaction_sequence` | Последняя позиция реального изменения реакций в диалоге, изначально 0 |
| `reactions` | `[{emoji, user_ids: UUID[]}]`, только выбранные реакции; от одного до двух участников на emoji |
| `own_reaction_states` | `[{emoji, selected, version, last_operation_id}]` для всех когда-либо изменённых своих emoji, включая снятые |

`version` внутри `own_reaction_states` начинается с 1, `last_operation_id` — UUID последней реальной команды этой ячейки. Отсутствующая ячейка означает selected=false/version=0/last_operation_id=null. Массивы отсортированы по каталогу, user_ids — по UUID. Счётчик UI равен длине user_ids. Данные о последней операции чужой ячейки не выдаются. DTO различается по `own_reaction_states` для двух участников; кеш изолирован аккаунтом.

У обычного сообщения `forward=null`, у новой пересылки forward не null; у обоих сначала reaction_version=0, reaction_sequence=0 и пустые массивы. Пересылка не наследует реакций исходника. Исходный dialog_id/message_id, цепочка пересылок, membership и прочие данные автора не входят в forward. Имя не становится ссылкой на профиль.

В доступном диалоге PATCH пересланного сообщения возвращает 403 FORBIDDEN даже его отправителю. Обычный send с прежним client_message_id, которым уже сохранена пересылка, возвращает текущую запись по принятому правилу первого сохранённого результата; содержимое не переписывается. Forward-запрос с ключом уже сохранённого обычного сообщения возвращает 409 MESSAGE_OPERATION_CONFLICT, а не объявляет его пересылкой.

### Пересылка и идемпотентность

`dialog_id` в пути — целевой диалог. Для контакта без диалога клиент после подтверждения сначала вызывает действующий POST /dialogs, затем пересылку. Если создание диалога успешно, а пересылка отклонена, может остаться пустой диалог: его создание не означает отправки сообщения. До подтверждения эти запросы не выполняются.

Ключ идемпотентности остаётся `(target_dialog_id, actor_id, client_message_id)`, общий с обычными отправками. Он не зависит от устройства. При уже сохранённой пересылке возвращается её текущий MessageDto после проверки целевого участия и права отправки; исходник заново не копируется, версия/снимок имени не пересчитываются, новых событий и push нет. Смена source-полей при повторе не меняет первый результат. Потеря права чтения исходника после успешной пересылки не запрещает получить уже доступную копию из целевого диалога. GET by-client-id требует текущее право чтения целевого диалога; ключ не заменяет авторизацию.

Новая пересылка проверяет can_read источника и can_send цели по действующему контракту, ожидаемую версию источника, целостность шифротекста и допустимость content. Новое сообщение получает sender_id пересылающего, sender_device_id текущего binding и обычные ID/sequence/created_at. Сохранённый content берётся только из проверенного источника. После commit используется обычный путь new-message WSS/push; заголовок push — пересылающий, содержимое — текст/стикер. Дополнительного имени исходного автора в push нет.

Если source.forward=null, первоначальный автор — source.sender_id. Если source.forward.author присутствует, используется его id. Если source.forward.author=null, новая копия тоже анонимна: первоначальное авторство не восстанавливается, скрытый id в её payload не сохраняется. При разрешённом авторе backend проверяет общую группу с конечным получателем в транзакции и берёт текущее display_name автора из Auth как снимок новой копии. Старые копии после переименования не меняются.

Проверка принадлежности к группе не имеет административного обхода. Для author_id=recipient_id условие означает наличие у этого пользователя хотя бы одной группы: пустое членство не считается общей группой с собой. Для этого Groups получает отдельный внутренний метод `lockAttributionGroup(tx, authorId, recipientId)`, блокирующий подходящую группу и membership `FOR SHARE`; существующий `lockCommonGroup` с запретом одинаковых ID не меняется. Эта проверка управляет только forward.author, а не правом пересылки содержимого.

Пересылка в тот же диалог допустима при обычном праве отправки. Диалог с самим собой по-прежнему не создаётся. Наличие исходного автора в иной группе с пересылающим не раскрывает его конечному получателю.

### Запись реакций и повторы

Для PUT нужны can_send, действующая сессия и binding, сообщение текущего диалога и допустимый emoji. Собственный/чужой текст, стикер и пересланная копия равноправны. Автор ячейки всегда текущий actor, user_id в запросе отсутствует.

Под блокировкой диалога читается актуальный проверенный envelope. Если last_operation_id своей ячейки совпадает с client_reaction_id и selected совпадает, это повтор: возвращается актуальный MessageDto без изменения. Тот же ID последней операции с другим selected даёт 409 REACTION_VERSION_CONFLICT. Иначе expected_version сравнивается с версией своей ячейки; несовпадение даёт тот же 409 без снимка в ошибке. При равной версии и уже достигнутом selected операция — no-op, версии и последняя операция не меняются.

Реальное изменение меняет только свою ячейку emoji: selected, version+1, last_operation_id. Общие reaction_version и last_reaction_sequence диалога увеличиваются на 1; строка получает новую reaction_sequence. Снятая ячейка сохраняется как selected=false с новой версией. Это ограниченные tombstone: не более двух участников × размер фиксированного каталога, без неограниченного журнала операций. Переполнение любого счётчика отклоняет операцию до шифрования.

Разные emoji и разные участники имеют независимые expected_version, поэтому их одновременные изменения не конфликтуют и не затираются. Два устройства одного участника, изменяющие один emoji одной версии, дают один commit и один конфликт. Старый повтор после последующего снятия/добавления не возвращает прежний selected автоматически. No-op и повторы не создают позицию, WSS или push.

После неизвестного результата клиент выполняет GET одного сообщения. Совпадение своего last_operation_id подтверждает применённую команду; достигнутое selected можно показать как актуальное состояние без утверждения об истории команды. При более новой версии ячейки показывается актуальное состояние и явная возможность нового действия; автоматической перезаписи нет. При неизменной ожидаемой версии пользователь может повторить исходный ID/selected. Новое намерение всегда получает новый UUID и текущую версию ячейки.

## Правила и инварианты

### Транзакции и блокировки

Повторная проверка прав находится в записывающей транзакции. Порядок существующих Auth/Devices/Groups сохраняется: account states в порядке UUID → сессия → binding → membership → диалоги → сообщения. Для пересылки нужны оба диалога, их блокировки `FOR UPDATE` берутся по UUID, при совпадении — один раз. Это предотвращает инверсию при одновременных пересылках A→B и B→A. Реакции/правки/отправки берут ту же блокировку диалога.

Чтобы узнать первоначального автора без нарушения порядка блокировок, новая пересылка использует предварительную разрешённую read-транзакцию источника: проверяет участие/read/session/binding, расшифровывает envelope и получает origin id. После завершения этой транзакции отдельной подтверждённой операцией резервируется бюджет шифрования. Основная транзакция блокирует полный набор аккаунтов actor/source peer/target peer/origin по UUID и повторно проверяет доступ, версию и происхождение источника. Прочитанный предварительно content не считается основанием записи без этой повторной проверки. Несогласованное происхождение при той же content-версии — ошибка целостности, а не выбор удобного снимка.

Проверка существующего целевого idempotency key выполняется до требования повторно прочитать источник; под основной блокировкой цели она повторяется, чтобы конкурентный успешный запрос имел приоритет над конфликтом версии источника. Для нового результата can_read источника и can_send цели удерживаются до commit. Снятие membership, отключение/смена роли и отзыв сессии используют действующие блокировки владельцев; оба порядка гонки покрываются интеграционно.

Резерв шифрования выполняется вне бизнес-транзакции до её блокировок, как в существующей отправке/правке. Неиспользованный резерв при повторе/no-op/rollback допустим и не возвращается. Отказ подтверждения резерва запрещает новое шифрование; получить уже сохранённый результат/no-op можно без нового encrypt. Ошибка WSS после commit не отменяет запись.

### Схема PostgreSQL

Новая последовательная Drizzle-миграция добавляет:

- `gchat_dialogs.last_reaction_sequence bigint NOT NULL DEFAULT 0`, CHECK 0..9007199254740991.
- `gchat_dialog_messages.reaction_version bigint NOT NULL DEFAULT 0` и `reaction_sequence bigint NOT NULL DEFAULT 0`, с тем же диапазоном.
- CHECK: оба значения равны 0 либо оба положительны. encryption_version допускает 1/2/3; для 1/2 оба новых поля обязаны быть 0. Существующие проверки content-version/edit-state сохраняются независимо от реакций.
- Частичный UNIQUE `(dialog_id, reaction_sequence) WHERE reaction_sequence > 0`, используемый для ленты реакций.

Отдельной таблицы открытых emoji/происхождения нет. Состояния ячеек и forward входят в зашифрованный payload строки. CHECK и внутренняя валидация после расшифровки проверяют не более двух текущих участников, уникальность actor/emoji, версии ячеек, каталог и согласованность снимка с reaction_version. Сумма положительных версий ячеек равна reaction_version. Положительная reaction_sequence не превосходит last_reaction_sequence диалога.

Существующие строки мигрируют без расшифровки: encryption_version=1/2 означает forward=null и пустое состояние реакций. ID, content-version, sequence, времена, read-позиции, позиции правок и idempotency key сохраняются. Миграция не создаёт реакций и сообщений. Реакции не меняют last_sequence, last_message_at, version/edited_at/edit_sequence, read и порядок списка. Правка текста сохраняет все ячейки реакций и их позиции.

### Шифрование и AAD v3

Используется существующий AES-256-GCM через `node:crypto`: те же ключи/реестр/долговечный бюджет, случайный IV 12 байт, tag 16 байт и уникальность key_id/IV. Новых примитивов и криптографических зависимостей нет. Форматы 1 и 2 читаются без изменения прежних AAD. Все новые сообщения, реальные правки и реальные изменения реакций записываются как encryption_version=3.

Plaintext v3 — UTF-8 JSON объекта с полями `{content, forward, reaction_state}`. `content` сохраняет нынешнюю строгую text/sticker-схему. `forward` имеет публичную форму выше и не содержит скрытого происхождения. `reaction_state` — массив `{user_id, emoji, selected, version, last_operation_id}` всех затронутых ячеек, включая selected=false; порядок — каталог, затем UUID. Массив/forward валидируются после успешной проверки GCM tag. Полные сообщения, emoji, имена, origin id, plaintext payload и их хеши в БД/логах отдельно не добавляются.

AAD v3 — UTF-8 от компактного JSON.stringify массива:

```text
["gchat.dialog.message",3,encryption_key_id,lower(message_id),lower(dialog_id),lower(sender_id),lower(sender_device_id),lower(client_message_id),String(sequence),created_at.toISOString(),String(version),edited_at === null ? null : edited_at.toISOString(),String(edit_sequence),last_edit_id === null ? null : lower(last_edit_id),String(reaction_version),String(reaction_sequence)]
```

Новая запись начинается с version=1/edited_at=null/edit_sequence=0/last_edit_id=null/reaction_version=0/reaction_sequence=0. Реакция переупаковывает текущий content/forward без их изменения, меняет ячейку и реакционные счётчики, использует новый IV и резерв. Правка переупаковывает текущие реакции, сохраняя их версии. Параллельные операции сериализованы и шифруют актуальный полный снимок. Замена любого поля AAD либо payload без корректного tag отклоняется. Обнаруженная коллизия IV не перезаписывает запись и не возвращает бюджет; автоматического encrypt-повтора нет. Ограничение против восстановления целого старого согласованного снимка БД остаётся прежним.

### Лента реакций и WSS

Лента использует ту же модель долговечной позиции, что редактирование, но отдельные счётчики. В одном стабильном снимке диалога фиксируется B=last_reaction_sequence; выбираются последние состояния сообщений с reaction_sequence в `(after, B]` по возрастанию. Возвращаются полные актуальные MessageDto, включая снятые реакции и content. Дублирующей таблицы истории реакций нет. Многократные изменения одного сообщения между страницами могут схлопнуться в последний снимок; пользователю нужна актуальная реакция, не журнал.

Ограничение ответа — 524288 байт полного JSON до сжатия и limit сообщений. При has_more=true next_reaction_sequence равна позиции последней включённой строки; при has_more=false — B. Пустая страница допустима только с has_more=false. after>B даёт 400 VALIDATION_ERROR, курсор не сбрасывается. Позиции выделяются под блокировкой диалога до commit, без независимой PostgreSQL sequence; rollback не расходует позицию.

После реального commit оба разрешённых участника получают существующим WSS событие `dialog.message_reactions_available` с `{dialog_id, last_reaction_sequence}`. Содержимого/emoji/actor/message_id в событии нет; ветка push не вызывается. Сигнал — invalidation, не применённый курсор. Проверки доставки текущего доступа переиспользуются.

Открытие, foreground, reconnect, межвкладочная invalidation и периодическая сверка выбранной переписки проверяют реакции независимо от WSS. В существующем sync-lock и GET-планировщике один цикл выполняет по странице истории, правок и реакций; has_more продолжает цикл без вытеснения любого из трёх потоков. Фоновые диалоги обновляют метаданные без массового скачивания истории.

### Кеш и совместимость

IndexedDB поднимается с версии 2 до 3 в той же базе/namespace/epoch. Все сообщения, включая last_message, дополняются forward=null/reaction_version=0/reaction_sequence=0/reactions=[]/own_reaction_states=[]; каждый record получает `reaction_sync_sequence=0`. Из метаданных сервера не выводится применённый курсор. Черновики/revision, outbox, ranges, before/edit/sync cursors и read сохраняются. Миграция из v1 последовательно нормализует оба расширения в той же upgrade-транзакции.

Legacy-сообщения получают локальный `actions_verified=false` (это поле кеша, не HTTP DTO). Старый Web мог уже получить новую пересылку от обновлённого backend и отбросить её неизвестные поля, поэтому заполненное по умолчанию forward=null не считается доказательством обычного происхождения. Строго проверенный полный сетевой DTO получает actions_verified=true. При первом таком ответе forward и реакционные поля заменяют неподтверждённые значения даже при равной content-версии; сам текст и edit metadata всё равно проверяются по действующим инвариантам. До проверки происхождения редактирование, пересылка и изменение реакций требуют GET/sync; копирование видимого разрешённого текста остаётся доступным. Равноверсионные проверки новых полей ниже применяются к двум подтверждённым снимкам. Legacy export при JS fallback нормализуется тем же способом. Это сохраняет историю/черновики и позволяет безопасно восстановить отброшенные старым клиентом поля без очистки кеша.

Видимые неподтверждённые сообщения переобновляются через GET одного сообщения в действующем GET-планировщике, с объединением одинаковых запросов. Страницы истории также подтверждают поля. Пока ответ не получен, интерфейс обозначает обновление сведений сообщения и не утверждает, что у него нет происхождения/реакций. Ошибка оставляет кеш доступным для чтения с этим состоянием; массового удаления старой истории или сброса непрочитанности нет.

Объединение content и forward идёт по MessageDto.version. Forward неизменен для данного message_id; при равной content-версии содержимое, происхождение и edit metadata обязаны совпадать. Реакции и own_reaction_states выбираются **целиком** из большей reaction_version, включая пустой активный набор после снятия; отдельные массивы не объединяются union. При равной reaction_version весь снимок/sequence должны совпадать. Status/read по-прежнему объединяются независимо монотонно. Противоречие равных версий — ошибка протокола с REST-перепроверкой, не произвольный выбор.

Команда storage `commitReactions` с CAS expectedRevision атомарно объединяет сообщения и продвигает reaction_sync_sequence только от ожидаемой позиции и только вместе с сохранёнными строками. Обработчик проверяет диапазон/строгий порядок reaction_sequence и next/has_more по правилам ленты. Снимки старых сообщений сохраняются вне ranges без расширения непрерывной истории; позже устаревшая страница не возвращает прежние реакции/текст. Ответ PUT/GET сохраняется тем же merge без продвижения ленты. Превью последнего сообщения объединяется теми же независимыми версиями.

Outbox v3 сохраняет существующую форму обычной отправки с новым discriminator `operation: "send"` по умолчанию для старых записей. Пересылка имеет `operation: "forward"`, неизменяемые client_message_id/source_dialog_id/source_message_id/expected_source_version, preview content, время и существующие состояния prepared/sending/unknown/rejected. Preview служит только локальному пузырьку и не отправляется как доверенный content. При успехе клиент атомарно сохраняет серверное сообщение и удаляет pending по actor/client_message_id. Черновик получателя и исходника не очищается.

При неизвестной пересылке выполняется GET by-client-id, а не новая логическая отправка. 200 завершает outbox; 404 не доказывает rollback ещё выполняющегося POST, но разрешает явный повтор с тем же ключом — целевая уникальность исключает дубль. Повторы не меняют source snapshot. При конфликте источника новый предпросмотр и новый ID создаются только явным действием после подтверждённого отказа старой операции. На reload pending сохраняет исходный ключ и не отправляется с новым ID.

Команды реакций существуют в runtime до разрешения результата, отдельно от message outbox: они не являются новыми сообщениями и не меняют обычный черновик. Для одной ячейки повторный тап заблокирован до завершения/сверки; другие emoji доступны. На reload/возврате восстанавливается серверное состояние без автоматического применения прежнего намерения. Поздние ответы старой сессии/диалога не меняют текущий экран; запоздалые снимки проходят общий merge версий.

Нативные исходники/SQLite/bridge не меняются: iOS deprecated. Для новой Web в существующей оболочке со storage v1/v2 нельзя писать v3 DTO через строгий SQLite bridge. Web использует действующий постоянный fallback: beginFallback → exportFallbackPage с нормализацией legacy данных в v3 → staging/проверка сохранения черновиков и outbox → selectIndexedDb. Если уже выбран indexeddb, выполняется его upgrade. Источник не удаляется до подтверждённого выбора; ошибка останавливает переключение, а не выдаёт пустую историю. Новых native-команд или capability v3 не требуется. Проверки JS-адаптера выполняются; физическая поддержка deprecated iOS не заявляется.

Старая вкладка закрывает IndexedDB handle на versionchange и требует обновления; блокирующая вкладка должна закрыться до upgrade. Старые Web-клиенты могут игнорировать аддитивные поля DTO: их данные не считаются подтверждением новых снимков, они не получают новые действия; сервер запрещает правку forwarded даже старым клиентом. Поведение старой неизменённой native-оболочки со старым Web/строгим storage после обновления backend не считается поддержанным сценарием этого этапа.

### Каталог emoji и UI

Точные emoji и порядок принадлежат [продуктовому каталогу](../../../product/message-actions.md#каталог); реализация добавляет их с русскими доступными именами в существующий общий пакет `@gchat/dialog-assets`, используемый backend и Web. Custom/paid emoji, модификаторы кожи и произвольные строки не принимаются. Канонические ключи — последовательности Unicode из каталога без U+FE0F; входные варианты нормализуются удалением только U+FE0F и затем проверяются по полному ключу. ZWJ, гендерные знаки, U+FE0E и остальные символы не удаляются. Таким образом ❤/❤️ и ☃/☃️ — одна реакция, а иные emoji не превращаются в разрешённые. UI использует emoji presentation там, где она предусмотрена каталогом; идентичность задаёт канонический ключ.

Общее меню доступно всем сохранённым сообщениям при can_read, включая чужие и стикеры. Copy не зависит от can_send. Пересылка требует чтения источника и доступного получателя, реакция — can_send, редактирование — can_send/свой text/forward=null. В режиме только чтения реакционные chips доступны для просмотра авторов, без изменения. Клавиатурный ↑ пропускает forwarded при поиске последнего редактируемого текста.

Визуальное поведение «Фокус на сообщении», превью, размещение полного каталога, порядок команд и основания закрытия принадлежат [общему меню действий](../../../product/message-actions.md#общее-меню). Быстрая строка и кнопка полного каталога сохраняют области 44 CSS px. Стрелки перемещают фокус по сетке, Home/End — к границам строки, Escape возвращает к раскрывающей кнопке. Выбранные emoji отмечены aria-pressed. Авторов реакций открывает отдельно подписанное действие, доступное клавиатуре, без зависимости от hover. На мобильном viewport смещения/клавиатура и прокрутка меняют положение, сохраняя меню; отпускание исходного пальца и начало внешнего жеста не закрывают его.

Выбор получателя использует существующие runtime-диалоги, разрешённые контакты Groups и существующий административный список только для admin; поиск локально фильтрует загруженные display_name. Данные получателей загружаются штатными loaders через context.get(deviceContext), без нового SDK singleton/кеша. Прокрутка пагинированного списка подгружает остальные страницы; совпадения не объявляются полными до их загрузки. Отправка подтверждается отдельно с именем получателя и предпросмотром. Успех оставляет исходную переписку открытой, показывает «Переслано: <имя>» и ссылку на целевой диалог. Отказ остаётся в окне с возможностью проверки/повтора, навигация/обновление не уничтожают durable pending.

### Ссылки и Clipboard

Распознавание URL локальное и общее для единственного/множественного выбора адресов. Кандидат начинается с `http://` или `https://` без учёта регистра, если перед ним начало текста либо символ, не являющийся Unicode-буквой/цифрой/`_`. Он заканчивается перед символом Unicode White_Space или категории Cc, `<`, `>`, кавычками U+0022/U+0027/U+00AB/U+00BB/U+2018/U+2019/U+201C/U+201D либо обратным апострофом U+0060. Терминальные `. , ! ? ; :` убираются безусловно. Терминальная закрывающая `)`, `]` или `}` убирается только тогда, когда скобок этого типа в кандидате больше соответствующих открывающих. Удаление повторяется до устойчивого конца. Внутренняя и сбалансированная пунктуация сохраняется.

Кандидат проверяется штатным URL без base: допустимы только http:/https: и непустой host. Невалидный кандидат не даёт действие копирования адреса. Результат копирования — исходная подстрока после удаления внешней пунктуации, не сериализованный URL.href: регистр, percent encoding, query, fragment и Unicode из текста сохраняются. Повторы объединяются по точному равенству этой строки. Открытие/запрос URL и link preview не выполняются; разметка сообщений остаётся текстовой, распознавание не превращает строку в HTML.

Примеры: `(https://example.org/a(b))` → `https://example.org/a(b)`; `https://example.org/a?q=1#x,` → без запятой; `https://a.example https://b.example` → выбор из двух; `example.org` и `javascript:...` не дают адреса. Внешняя завершающая пунктуация, являющаяся частью реального URL, должна быть percent encoded, чтобы не отделяться по правилу выше.

Web вызывает navigator.clipboard.writeText непосредственно в click/tap выбранного действия. Одна ссылка копируется этим же жестом; при нескольких жест выбора строки копирует ровно её. Успех объявляется доступным status, отказ — alert с read-only полем для ручного выделения/копирования. Небезопасный origin/отсутствие API используют тот же ручной путь. Clipboard read и устаревший execCommand не нужны. Эти локальные функции не добавляют HTTP API.

## Зависимости и регистрация

Существующие Dialogs/Database/Auth/Devices/Groups/Signaling/Crypto и DI; каталог emoji — `@gchat/dialog-assets`. Groups остаётся владельцем membership, Auth — отображаемого имени. Новых env, runtime-зависимостей, forRoot или импортов raw bridge в features нет. HTTP DTO/Swagger и SDK генерируются по [процессу пакета](../../../packages/backend-api.md), generated-файлы вручную не редактируются.

## Ошибки и частичное выполнение

Некорректные UUID/query/DTO/emoji/версии — 400 VALIDATION_ERROR с точным полем; большой body — 413 PAYLOAD_TOO_LARGE. Чужой/неизвестный источник, цель или message_id вне своего указанного диалога — одинаковый 404 NOT_FOUND. Запрет по актуальным правам — 403 DIALOG_NOT_ALLOWED; правка forwarded — 403 FORBIDDEN. Конфликт версии источника — существующий 409 MESSAGE_VERSION_CONFLICT; конфликт ячейки — 409 REACTION_VERSION_CONFLICT; collision вида операции — 409 MESSAGE_OPERATION_CONFLICT. Ошибки не содержат source text/author/актуальный DTO; для восстановления нужен отдельный разрешённый GET.

GET by-client-id при отсутствии собственной записи — 404, без раскрытия чужих ключей. Auth/session/binding, ошибки целостности и недоступность БД/ключей используют действующие ошибки владельцев. Redis/лимиты работают без локального fallback. Содержимое, происхождение и тела команд не добавляются в диагностику. При ошибке копирования значение остаётся только в локальном интерфейсе ручного копирования.

Пересылка расходует общий существующий send-бюджет, отдельное создание целевого диалога — create-бюджет. Для реакций добавляется независимый per-account bucket `reaction`: 5 запросов/с, запас 10, общий для устройств и всех диалогов; повторы/no-op расходуют его. Он не вытесняет текст из send-бюджета. Все GET делят текущий get-бюджет 10/с, запас 20. Превышение — 429 RATE_LIMITED с Retry-After; изменяющие операции после ожидания не повторяются с новым ID и не применяют автоматически устаревшее намерение.

## Конфигурация

Новых переменных окружения нет. Применяется текущий реестр/ключи DIALOGS и отдельная последовательная миграция до запуска нового backend; DDL на старте HTTP не выполняется. До выпуска сохраняются backup БД и все используемые ключи, останавливаются старые backend-процессы, применяется миграция, запускается новый backend, затем размещается новая Web. Старый backend не может читать v3 и после первой v3-записи не является допустимым rollback. Исправление — совместимая новая версия; исторические ключи не удаляются. Деплой/производственная миграция требуют отдельного запроса пользователя.

## Критерии приёмки и проверки

Обязательны критерии продукта и следующие сценарии:

- Forward REST не доверяет content/author клиента, проверяет текущие права и source version; конкурентные одинаковые ключи создают одну запись. Повтор после смены source/потери доступа источника возвращает сохранённую разрешённую целевую копию. Обычный ключ не объявляется пересылкой.
- Общая группа проверяется для origin и получателя, включая admin, одинаковые origin/recipient, снятие membership и переименование. Анонимный этап не оставляет исходного id в payload и не раскрывает его дальше. Встречные пересылки, обычные отправки, правки, реакции и отзыв прав не создают инверсий блокировок.
- PUT selected/CAS выдерживает повтор, no-op, одновременные разные emoji, двух участников и конфликт двух устройств одной ячейки. Снятие сохраняет tombstone; старый retry не восстанавливает её. Изменение поля чужой ячейки невозможно через payload.
- Форматы 1/2 читаются; v3 передаёт неизменённый content и проверяет AAD/tag. Изменение каждого поля AAD/forward/reaction_state отклоняется. Отказ резерва, rollback, исчерпание бюджета, коллизия IV и ошибка commit не создают некорректного snapshot/события.
- Лента реакций восстанавливает старые сообщения после офлайна/потерянного WSS, все снятия, concurrent commit и схлопывание строки между страницами. Проверяются пустая страница, after>B, лимиты количества/байтов и независимый порядок content/reaction версий.
- IndexedDB v1/v2→v3 атомарно сохраняет черновики/outbox/ranges/read. Старые вкладки не пишут поверх v3. Курсор не продвигается без сохранённых строк; старый send/history/edit/reaction ответ не откатывает реакцию, текст или превью. JS fallback legacy storage не теряет данные при прерывании до/после выбора адаптера.
- UI проверяется на узких и широких размерах: долгий жест/отпускание/тап, текст/стикер/forward/readonly, клавиатура/IME/экранный диктор, раскрытие полного каталога, счётчики/авторы, конфликт и неопределённый результат. URL/Clipboard проверяются на Unicode, скобках, нескольких адресах, отказе API и ручном пути. Физическая PWA-проверка iPhone учитывается отдельно от Chromium.

При реализации: unit/integration backend и миграции на отдельной PostgreSQL; Web model/storage/runtime/UI; OpenAPI/SDK consistency; системный E2E нескольких аккаунтов/устройств с пересылкой/реакциями/офлайном. Команды берутся из package.json и AGENTS приложений. Для документации достаточно `pnpm docs:check` и diff. До реализации эти проверки не объявляются выполненными.

## Открытые решения

Открытых решений нет. Пользователь согласовал REST/DTO, идемпотентность/CAS, encrypted envelope/AAD v3, отдельную ленту реакций, миграцию storage и legacy JS fallback, лимиты, нормализацию emoji и границы URL. Реализация и проверки учитываются отдельно.

# Редактирование сообщений: расширение DialogsModule

## Назначение и границы

Технический проект для [согласованных продуктовых правил](../../../product/message-editing.md). Расширяет [DialogsModule](README.md), [Web](../../../web/dialogs.md) и [storage bridge](../../../web/bootstrap.md). Продуктовые правила, конкретные API, схема, AAD и миграция согласованы пользователем 2026-11-14. Реализованы backend, SDK, Web и storage bridge v2; физическая приёмка iPhone учитывается отдельно.

Dialogs остаётся владельцем записей и шифрования. Нового Nest-модуля, очереди уведомлений, отдельного WSS и криптографических зависимостей нет. Исправления не создают новых сообщений или пользовательской истории версий. Хранится последняя версия содержимого.

## Публичный API

Все маршруты используют текущие Auth/device binding, актуальные проверки доступа внутри транзакции, `Cache-Control: no-store`, общий формат ошибок и внешний префикс `/api`. UUID нормализуются; JSON/query проверяются по действующим строгим правилам Dialogs. Неизвестные поля не принимаются.

| Метод и путь | operationId | Вход | Ответ 200 |
| --- | --- | --- | --- |
| `GET /dialogs/:dialog_id/messages/:message_id` | `dialogsMessageGet` | UUID диалога и сообщения | `{message: MessageDto}` |
| `PATCH /dialogs/:dialog_id/messages/:message_id` | `dialogsMessageEdit` | `{client_edit_id, expected_version, content: {kind: "text", text}}` | `{message: MessageDto}` |
| `GET /dialogs/:dialog_id/message-edits` | `dialogsMessageEdits` | `after_edit_sequence`, `limit` | `{messages: MessageDto[], next_edit_sequence, has_more}` |

`client_edit_id` — новый UUID штатного runtime для одной логической правки. `expected_version` — версия, которую редактирует пользователь. Обе позиции и версии — числа от 1 до `Number.MAX_SAFE_INTEGER`, начальная позиция изменений — 0. Для `after_edit_sequence` по умолчанию 0, для limit — 30, диапазон 1..100. Неизвестные/повторные query, отрицательные, дробные, строковые JSON-числа и переполнение отклоняются без clamp.

Тело PATCH ограничено 65536 байт до JSON-разбора. Правила text и ошибок размера совпадают с отправкой. GET обоих новых маршрутов расходуют существующий общий бюджет чтения; PATCH — существующий бюджет отправки. Все повторы расходуют соответствующий бюджет.

### Расширение MessageDto

Во всех ответах истории, отправки, повтора, превью, чтения одного сообщения и редактирования добавляются обязательные поля:

| Поле | Значение |
| --- | --- |
| `version` | Положительное безопасное целое, изначально 1 |
| `edited_at` | ISO 8601 UTC или null для неизменённого сообщения |
| `edit_sequence` | Последняя позиция правки в диалоге, изначально 0 |
| `last_edit_id` | UUID последней успешной изменяющей правки, изначально null |

`last_edit_id` — только идентификатор операции, без авторизации, содержимого и секретов. Он позволяет сопоставить потерянный ответ с текущим состоянием; не является журналом всех операций. Положительный edit_sequence соответствует version > 1, ненулевым edited_at и last_edit_id. Поля первоначальной отправки, sender_device_id и sequence не меняются.

### Запись и повторы

Порядок: текущая авторизация и участие → блокировки владельцев Auth/Devices/Groups в порядке основного контракта → блокировка диалога `FOR UPDATE` → чтение сообщения и проверка собственного автора/текстового kind → проверка повтора/версии → запись. GET используют право чтения; PATCH — право отправки. Собеседник не обязан иметь действующий сокет, но должен быть активен по правилу отправки.

1. Если last_edit_id совпадает с client_edit_id и текущая version равна expected_version + 1, это повтор успешно сохранённой правки: вернуть актуальное сообщение, не сравнивать и не менять content.
2. Иначе несовпадение expected_version с текущей version даёт `409 MESSAGE_VERSION_CONFLICT`. Это верно и при совпадающем тексте.
3. При совпадении версии и побайтово одинаковом UTF-8 text вернуть текущее сообщение без изменения версии, времени, идентификатора правки, позиции и шифротекста. Повтор такого no-op допустим при сохранении версии.
4. Для реального изменения увеличить version и last_edit_sequence диалога на 1, записать edit_sequence сообщения, client_edit_id и edited_at из серверных часов после блокировки. Перешифровать content и атомарно сохранить все поля. При исчерпании безопасного диапазона — 503 без записи; no-op и допустимый повтор остаются доступны.

Узкая идемпотентность не обещает восстановить старый результат после последующих правок: повтор старой операции относительно старой версии даст конфликт. Это предотвращает повторное применение и перезапись новых данных без хранения истории содержимого или неограниченного журнала операций. Один client_edit_id не используется клиентом для разных правок.

После неизвестного результата клиент выполняет GET одного сообщения: совпадающий last_edit_id подтверждает commit; неизменная expected_version позволяет предложить ручной повтор исходного запроса; другая версия открывает конфликт с собственным текстом пользователя. Автоматического PATCH-повтора нет. Если состояние невозможно получить, UI сохраняет введённый текст и показывает неизвестный результат; нельзя обещать отсутствие commit. AbortSignal не отменяет серверный commit.

Повтор POST первоначальной отправки возвращает актуальный MessageDto этой записи, включая правку, и сохраняет старые ID/sequence/created_at. POST не возвращает исходный текст и не перезаписывает правку. Это согласованное продуктовое уточнение прежней формулировки основного контракта.

### Синхронизация правок

В диалоге есть независимый монотонный last_edit_sequence. Новая отправка его не увеличивает. Выборка message-edits возвращает последние версии строк с `edit_sequence > after_edit_sequence` по возрастанию edit_sequence. Несколько правок одной записи могут объединиться в одну текущую строку; пропуски номеров нормальны, исторические версии не возвращаются.

В рамках одного согласованного снимка БД фиксируется верхняя граница B = last_edit_sequence и выбираются строки `(after, B]`. `has_more` определяется наличием следующей подходящей строки в этом снимке после ограничения limit и бюджета 524288 байт полного JSON. При has_more=true next_edit_sequence равна позиции последнего включённого сообщения, иначе B. Поэтому пустая страница допустима только с has_more=false и может продвинуть курсор. Один допустимый MessageDto обязан помещаться; пустая страница с has_more=true — ошибка протокола. after больше B даёт 400 VALIDATION_ERROR с полем after_edit_sequence, а не сброс позиции.

Общий снимок между HTTP-страницами не обещается. Изменённая между страницами строка получает большую позицию и попадает в последующий запрос; строка, переместившаяся за B, не пропускается навсегда. Это требует сериализации выделения позиций на диалоге до commit, без независимой PostgreSQL sequence и номеров незавершённых транзакций.

После commit реальной правки существующий WSS доставляет обоим разрешённым участникам событие `dialog.message_edits_available` с `{dialog_id, last_edit_sequence}`. Содержимое, message_id и last_edit_id в сигнал не входят. Нового push нет. Повтор/no-op/rollback события не создают. Сигнал — только invalidation, не подтверждённая позиция. Существующая проверка права доставки выполняется заново; ветка push не вызывается.

Открытие, foreground, reconnect и периодическая сверка выбранной переписки запускают также REST-сверку правок независимо от WSS. Фоновые диалоги обновляют метаданные без скачивания истории. GET-планировщик и sync-lock переиспользуются, второй планировщик не создаётся. За цикл после обычной страницы истории выполняется страница правок; при has_more обе задачи продолжаются без вытеснения другой.

## Правила и инварианты

### Схема и миграция PostgreSQL

Новая последовательная Drizzle-миграция добавляет:

- `gchat_dialogs.last_edit_sequence bigint NOT NULL DEFAULT 0`, CHECK 0..9007199254740991.
- `gchat_dialog_messages.version bigint NOT NULL DEFAULT 1`, CHECK 1..9007199254740991.
- `edited_at timestamptz NULL`, `last_edit_id uuid NULL`, `edit_sequence bigint NOT NULL DEFAULT 0`, CHECK 0..9007199254740991.
- CHECK согласованности: version=1/позиция=0/оба nullable поля null либо version>1/позиция>0/оба поля не null. Ограничение encryption_version допускает 1 и 2; формат 1 допускается только для неизменённой записи version=1.
- Частичный UNIQUE `(dialog_id, edit_sequence) WHERE edit_sequence > 0`, используемый и для выборки правок. Дополнительной таблицы версий/изменений нет.

Существующие строки получают начальные значения без расшифровки/перешифрования. ID, sequence, авторы, время, outbox-ключи и read-позиции сохраняются. Равенство last_edit_sequence максимальной сохранённой позиции обеспечивает единственный путь записи Dialogs под блокировкой и проверяют интеграционно. Правка не меняет last_sequence, last_message_at, read-позиции и сортировку списка. Превью последнего сообщения строится из актуальной версии.

### Шифрование и AAD

Используется только существующий `node:crypto`, AES-256-GCM, ключ 32 байта, случайный IV 12 байт, tag 16 байт, прежний реестр ключей и долговечный бюджет попыток. Каждая фактическая попытка encrypt резервирует бюджет отдельной подтверждённой транзакцией до вызова шифрования; rollback бизнес-записи не возвращает бюджет. Отказ/неизвестный результат резерва не позволяет шифровать. IV создаётся заново; обнаруженная коллизия `(key_id, iv)` не перезаписывает запись, попытка шифрования остаётся учтённой, автоматического повтора нет.

Старый encryption_version=1 читается с прежним AAD без изменений. Новые сообщения и реальные правки записываются с encryption_version=2. AAD v2 — UTF-8 от компактного `JSON.stringify` следующего массива, без дополнительных пробелов:

```text
["gchat.dialog.message",2,encryption_key_id,lower(message_id),lower(dialog_id),lower(sender_id),lower(sender_device_id),lower(client_message_id),String(sequence),created_at.toISOString(),String(version),edited_at === null ? null : edited_at.toISOString(),String(edit_sequence),last_edit_id === null ? null : lower(last_edit_id)]
```

У новой отправки последние четыре значения — `"1", null, "0", null`. У правки sender_device_id остаётся устройством первой отправки. Изменение любого поля AAD без нового корректного tag отклоняется; version из БД не считается доверенной до проверки tag. Открытый text, его хеш и дополнительные plaintext preview не хранятся. Формат 2 не обещает защитить от восстановления оператором целого согласованного старого снимка БД; отдельного внешнего anti-rollback реестра нет.

### Кеш и bridge

Storage schema 2 добавляет в record `edit_sync_sequence: 0` и расширенные поля MessageDto, включая вложенное last_message. Миграция IndexedDB поднимает версию существующей базы с 1 до 2, не меняя namespace/epoch. SQLite транзакционно переводит user_version 1 → 2. Старые MessageDto дополняются version=1, edited_at=null, edit_sequence=0, last_edit_id=null. Для мигрируемых диалогов edit_sync_sequence=0: курсор из метаданных не считается уже применённой историей. Черновики, их revision, outbox и read-позиции сохраняются без перезаписи.

Добавляется storage-команда `commitEdits` с существующим CAS expectedRevision. Она атомарно сохраняет сообщения и продвигает edit_sync_sequence от ожидаемой исходной позиции. Новые строки правок хранятся даже вне загруженных диапазонов для защиты от поздней устаревшей страницы. Они не расширяют ranges, не двигают sync_sequence/before_sequence и не считаются доказанной непрерывной историей. Лента показывает только записи из ranges; при будущей загрузке страницы используется уже сохранённая более новая версия. Лимиты 100 сообщений/512 КиБ и разбиение bridge-запросов сохраняются; курсор продвигается только с полностью сохранённой частью страницы.

При объединении по message_id content и метаданные берутся из большей version; status/read-позиции объединяются монотонно независимо от версии. Более старая страница, send-retry или metadata не откатывает content, включая last_message. При одинаковой version ожидается одинаковый content и metadata правки; противоречие — ошибка протокола с REST-перепроверкой, без произвольного выбора текста. Ответ PATCH/GET одного сообщения сохраняет версию через commitEdits без продвижения edit_sync_sequence. Прочтение не считается причиной сохранять новую версию content.

Новый native публикует optional capability `dialogStorageVersion: 2`, контекст schemaVersion=2 и принимает envelope version=2, включая commitEdits. Namespace, epoch, adapterEpoch, команды очистки и постоянный fallback сохраняются. Новая Web поддерживает storage v2 и legacy export v1. При старой оболочке v1 выбирается существующий постоянный fallback в IndexedDB: beginFallback → exportFallbackPage с нормализацией legacy DTO → staging/проверка сохранения черновиков и outbox → selectIndexedDb. Источник не удаляется до успешного выбора; ошибка миграции блокирует переключение, а не подменяется пустой историей. Выбранный ранее IndexedDB не мигрируется обратно автоматически.

При versionchange старая браузерная вкладка закрывает handle и требует обновления, не пишет в новую схему. Блокирующая вкладка должна быть закрыта/обновлена до завершения upgrade. Серверные DTO расширяются аддитивно; старая Web не получает действие редактирования, её данные не считаются подтверждением новой версии. В native строгая проверка v1 не получает v2 envelope/DTO: либо v2, либо описанный fallback.

## Зависимости и регистрация

Существующие Dialogs/Database/Auth/Devices/Groups/Signaling/Crypto и их DI. HTTP SDK обновляется из контроллеров/Swagger по [процессу backend-api](../../../packages/backend-api.md); генерируемые файлы вручную не редактируются. Web вызывает операции через действующий device/runtime и сохраняет единственный кеш. Нативный storage остаётся на системной SQLite.

Продуктовые UX, сохранение обычного черновика, конфликты, меню и защита навигации определены в [требованиях редактирования](../../../product/message-editing.md). При конфликте GET загружает актуальную версию отдельно от введённого текста; явное действие «Применить мой текст» создаёт новую логическую правку относительно показанной актуальной версии.

Управление ↑/Escape/Enter определяется [контрактом клавиатуры компьютера](../../../product/message-editing.md#клавиатура-компьютера) и реализуется локально в поле ввода через стандартные события клавиатуры Web. Отдельный native bridge или глобальный обработчик горячих клавиш не требуется.

## Ошибки и частичное выполнение

Неверные UUID/DTO/позиции — 400 VALIDATION_ERROR; большой body — 413 PAYLOAD_TOO_LARGE. Неизвестный/чужой диалог либо message_id не из указанного диалога — одинаковый 404 NOT_FOUND. Запрет операции по текущему доступу — 403 DIALOG_NOT_ALLOWED; изменение чужого сообщения или стикера в доступном диалоге — 403 FORBIDDEN. Конфликт версии — 409 MESSAGE_VERSION_CONFLICT без содержимого или актуального DTO в ошибке. Истекшая/отозванная сессия и binding — существующие ошибки Auth/Devices.

Лимиты и недоступность Redis/БД/ключей следуют основному контракту: без локального fallback авторизации/лимитов. Ошибка доставки WS после commit не отменяет правку. Прерванная миграция хранилища не разрешает очистку черновиков/outbox. Содержимое и идентификаторы операций не добавляются в диагностические сообщения.

## Конфигурация

Новых переменных окружения и зависимостей нет. Существующие DIALOGS_ENCRYPTION_KEYS/DIALOGS_ACTIVE_KEY_ID и лимиты остаются действующими. Миграции применяются отдельной командой до нового backend; действующее приложение не запускает DDL.

Порядок выпуска: сохранить backup БД и ключей → остановить старые backend-процессы (они не умеют читать формат 2) → применить миграцию → запустить новый backend → разместить новую Web → выпустить совместимую native-оболочку. До обновления native новая Web использует описанный fallback. Откат к backend без поддержки encryption_version=2 после первой новой записи недопустим; исправление выполняется новой совместимой версией. Самостоятельный production-деплой в эту задачу не входит.

## Критерии приёмки и проверки

Критерии продукта обязательны вместе со следующими техническими сценариями:

- PATCH соблюдает авторство, kind, доступ, лимиты и оба порядка гонок с отзывом сессии/прав; одновременные правки одной версии дают ровно один commit.
- No-op, повтор последней операции и старый повтор после другой правки ведут себя по описанным правилам; потеря ответа не меняет newer content. POST send-retry возвращает текущую версию без дополнительных уведомлений.
- Правка за пределами хвоста, несколько правок одной строки между страницами, изменение уже прочитанной строки и страница с пропусками позиций не теряют данные после reconnect.
- Снимок B и next_edit_sequence корректны для пустой/короткой страницы, лимита байтов, исчерпания диапазона и concurrent commit. Сообщения и курсор кеша атомарны; старый ответ не откатывает ленту или превью.
- Старая v1-запись читается после миграции; новая v2-запись и её правка проходят проверку tag. Изменение каждого поля AAD, неверные IV/tag/key и исчерпание бюджета отклоняются без утечки content. Rollback/коллизия IV не возвращают резерв шифрования.
- IndexedDB/SQLite мигрируются с сохранением черновиков, outbox, namespace/epoch и read; legacy-native fallback проверяется с обрывом до/после выбора адаптера. Старая вкладка не пишет поверх v2.
- Unit/integration backend проверяют REST, транзакции, миграцию и криптографию; Web — объединение версий, планировщик, UI/конфликт/черновик; iOS — schema/bridge/fallback. Общий E2E проверяет двух участников и офлайн-восстановление. Реальная приёмка меню/клавиатуры/прокрутки на iPhone учитывается отдельно.
- Web-проверки клавиатуры покрывают вход через ↑, выбор кандидата, сохранение обычного черновика, Escape/Enter, штатные стрелки в тексте, фокус, IME, модификаторы, repeat и выполняющийся запрос по продуктовому контракту.

Команды берутся из package.json и инструкций приложений. Для документации — `pnpm docs:check`; для кода — typecheck/build и относящиеся тесты backend/Web, XCTest iOS и проверка генерации SDK. Отчёт фиксирует фактически выполненные проверки, а не объявляет критерии выполненными заранее.

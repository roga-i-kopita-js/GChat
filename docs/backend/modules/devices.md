# Devices

## Назначение и границы

Владеет идентификаторами установок приложения, привязками к сессиям и push-адресами. VoIP и Web Push звонков реализованы в указанном ниже объёме; реализована также отдельная регистрация обычного APNs-токена диалогов. Управление пользовательскими профилями в объём не входит; интеграция с реальной установкой iOS требует проверки.

## Публичный API

Регистрация выполняется после авторизации WS через [Signaling](signaling.md), до команд звонка, с общим конвертом request/response:

- `device.register`: `payload: {device_id: string | null}`. При `null` сервер создаёт UUID устройства, при UUID проверяет принадлежность текущему аккаунту. Устройство другого аккаунта или неизвестный ID не присваиваются — `NOT_FOUND`. Ответ: `payload: {device_id: string}`. Повтор с тем же ID и сессией идемпотентен; устройство после регистрации закрепляется за соединением. Повтор с `null` в уже зарегистрированном соединении возвращает его ID. После потерянного первого ответа может остаться неиспользуемая запись без push-токена; секретом или разрешением она не является.
- `device.push_token`: `payload: {voip_token: string | null, environment: "sandbox" | "production"}`. Привязка берётся из соединения, аккаунт и сессия из Auth. Ответ: `payload: {}`. Токен — hex-строка чётной длины от 2 до 512 символов, нормализуется в нижний регистр, конкретная длина токена APNs не фиксируется. `null` удаляет текущую регистрацию токена.

Внутренние методы: `bind(userId, sessionId, deviceId)`, `assertBinding(userId, sessionId, deviceId)`, `listVoipTargets(userId)`, `resolveVoipTarget(deviceId, sessionId)`, `invalidateVoipTarget(deviceId, tokenVersion)`. Список целей включает лишь привязки с действующей сессией Auth. Неизвестный результат проверки зависимости не превращается в пустой список. Смена push-токена и инвалидирование используют версию записи: поздний ответ APNs не удаляет новый токен.

### Транзакционная проверка binding для Dialogs — реализовано

Согласован новый внутренний метод `lockSessionBinding(tx, userId, sessionId)`: в переданном `DatabaseTransaction` разрешает устройство по сессии, блокирует binding, затем устройство `FOR SHARE`, проверяет владельца обеих записей и возвращает `{deviceId}`. Блокировки удерживаются до завершения транзакции; независимая транзакция не открывается. Отсутствующий или несогласованный binding при действующей сессии даёт `FORBIDDEN`. Метод не создаёт и не переносит устройство автоматически.

Потребитель предварительно проверяет актуальную сессию и активность actor через транзакционные методы Auth. `inactive_since` служит очистке и не заменяет проверку Auth. Расширение реализовано. Граница допуска при гонке с logout и общий порядок блокировок определены в [контракте Dialogs](dialogs/README.md#порядок-блокировок-и-граница-допуска).

### Обычный APNs-токен чата — реализовано

Согласована отдельная WS-команда `device.apns_token` в DevicesModule после авторизации и `device.register`. Payload: `{token: string | null, environment: "sandbox" | "production"}`. Аккаунт/сессия/устройство берутся из текущего авторизованного соединения, не из payload. Успешный ответ — стандартный response с исходным request_id и `payload: {}`. NativeCore получает токен обычных уведомлений от ОС и регистрирует его самостоятельно; Web-интерфейс не получает сырое значение.

Токен валидируется и нормализуется как существующий APNs-токен: hex-строка чётной длины от 2 до 512 символов, нижний регистр, без фиксации конкретной длины токена Apple. null удаляет текущую обычную APNs-регистрацию этой привязки; повтор того же значения идемпотентен. Токен не попадает в ответы чтения, permissions, WS-события диалога, логи или диагностику. Отозванная сессия не используется как цель доставки. Ошибки и правила привязки следуют существующим Auth/Devices/ErrorModule.

Регистрация хранится отдельно от VoIP-токена: `device.push_token` и его контракт не меняются. Обновление/удаление обычного токена не удаляет VoIP-регистрацию звонков. Браузерная Web Push-регистрация переиспользуется из существующего контура. Команда регистрации адреса не является передачей сообщений по WSS: создание/отправка/история диалогов остаются REST. Правила best-effort доставки — в [DialogsModule](dialogs/README.md#уведомления).

## Правила и инварианты

- Одна сессия привязывается максимум к одному устройству; повтор с другим ID даёт `FORBIDDEN`. Одно устройство может иметь несколько сессий своего аккаунта. Сервер проверяет пару device/session, знание UUID не даёт права действовать от имени сессии.
- Повторный вход создаёт новую сессию; старая привязка не переносит право управления существующим звонком. При переподключении с прежней сессией используется сохранённый device_id. Непривязанная сессия не может принимать команды звонка.
- Push-токен маршрутизирует одну актуальную пару device/session: повторная регистрация того же `(environment, token)` в другой действующей сессии переносит только push-адрес, не управление звонком и не право читать чужой звонок.
- Токены не выводятся в ответы чтения, логи, события `call.updated` или таблицы звонков. Отозванные сессии исключаются из доставки, даже если их строка привязки ещё не очищена.

Хранение: `gchat_devices(id UUID PK, user_id FK Auth RESTRICT, created_at)`; `gchat_device_sessions(session_id UUID PK, device_id FK, user_id FK, created_at, inactive_since)` с UNIQUE `(device_id, session_id)` и проверкой владельца; `gchat_device_voip_tokens(device_id, session_id, environment, token, version, updated_at)` с PK `(device_id, session_id)`, FK на соответствующую привязку и уникальностью `(environment, token)`. Сессии Auth находятся в PostgreSQL. В текущей схеме Devices FK на Auth-сессию отсутствует: binding может сохраняться после её отзыва до cleanup; действительность сессии проверяет Auth. Запись/смена адреса выполняется транзакционно в PostgreSQL.

## Зависимости и регистрация

Обычный DevicesModule импортирует DatabaseModule и AuthModule, экспортирует DevicesService. Signaling и Push импортируют DevicesModule. Чужие таблицы и сессии Auth не читаются напрямую — проверка Auth через её внутренний API. Собственный `forRoot()` не нужен.

## Ошибки и частичное выполнение

Коды принадлежат [ErrorModule](errors.md): `VALIDATION_ERROR`, `FORBIDDEN`, `NOT_FOUND`, `SERVICE_UNAVAILABLE`, `INTERNAL_ERROR`. При сбое зависимости регистрация не подтверждается. Неизвестный commit разрешается повторной регистрацией с известным device_id; повтор не перепривязывает сессию к другому устройству.

## Конфигурация

Собственных env-переменных нет. Окружение токена должно совпадать с используемыми [Push](push.md) APNs credentials. Первое фоновое обнаружение отзыва фиксируется в `inactive_since`. Неактивные записи без действующей сессии очищаются ежедневно через 30 суток от этого момента, кроме привязок, на которые ещё ссылаются сохраняемые записи звонков.

## Критерии приёмки и проверки

- Чужое устройство нельзя присвоить, один sid нельзя привязать к двум device_id.
- Повторный вход не переносит звонок, переподключение с прежней парой его не перехватывает другой сессией.
- Изменение токена не теряется из-за позднего ответа APNs; отозванная сессия не получает push.
- Отказ Auth/БД не превращается в успешную регистрацию или отсутствие устройств.

Проверки привязок и версий токенов входят в `test/direct-calls.integration.spec.ts`; условия запуска принадлежат [DirectCalls](direct-calls/README.md#критерии-приёмки-и-проверки).

### Web Push

Web Push реализован по принятому [D010](../../architecture/decisions/D010-web-push-pwa.md). Регистрация выполняется через WSS после `device.register`; существующая разрешённая подписка привязывается к текущей сессии при повторном входе. Правила APNs VoIP сохраняются.

После авторизации WSS и `device.register` доступны команды:

| Команда                  | Payload                                                          | Ответ                |
| ------------------------ | ---------------------------------------------------------------- | -------------------- |
| `device.web_push_config` | `{}`                                                             | `{public_key: string | null}`; публичный VAPID-ключ или `null`, если Web Push отключён |
| `device.web_push`        | `{subscription: {endpoint: string, p256dh: string, auth: string} | null}`               | `{}`; `null` удаляет подписку текущей пары device/session       |

Аккаунт и сессия берутся из авторизованного соединения, device — из его binding. Произвольные user/session/device ID в payload не принимаются. Приватный VAPID-ключ клиенту не передаётся. Конфигурация VAPID принадлежит [Push](push.md#web-push).

Правила хранения:

- Одна сессия имеет максимум одну Web Push-подписку. Один endpoint маршрутизирует одну актуальную пару device/session. Его повторная регистрация переносит адрес, но не право управления звонком.
- Подписка хранится в `gchat_device_web_push`: `session_id` PK, `device_id`, уникальный `endpoint`, `p256dh`, `auth`, UUID `version`, `updated_at`; составной FK на binding с каскадным удалением. Перенос endpoint и замена записи выполняются транзакционно.
- Перед постановкой задания и каждой отправкой Auth подтверждает активность аккаунта и сессии. Выход, отзыв сессии и отключение аккаунта исключают последующие отправки. Уже переданный провайдеру push отозвать невозможно.
- Смена подписки создаёт новую версию. Ответ провайдера о старой подписке удаляет только совпадающую версию, сохраняя новую.
- Endpoint и ключи подписки не возвращаются в списках, не логируются и не включаются в `call.updated` или outbox. Worker разрешает текущий адрес через Devices.

Валидация: endpoint до 4096 символов; HTTPS без credentials, нестандартного порта и fragment. Разрешённый список провайдеров: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com` и поддомены `.push.apple.com`. Другие адреса отклоняются, чтобы пользовательский endpoint не превращал backend в произвольный HTTP-клиент. Это ограничивает поддержку провайдеров; расширение списка требует проверки. `p256dh` — непаддированный base64url публичной P-256 точки, 65 байт; `auth` — base64url 16 байт. Некорректные входные данные и регистрация непустой подписки при выключенном Web Push дают `VALIDATION_ERROR`.

Приёмка: проверяются чужие binding, конкурентный перенос endpoint, замена версии, отзыв сессии, запрет произвольных адресов, удаление подписки и восстановление после неизвестного результата регистрации. Тесты валидации уже подготовлены; интеграционная приёмка нового контура не завершена.

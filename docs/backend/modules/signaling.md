# Signaling

## Назначение и границы

Владеет авторизованными WSS-соединениями, маршрутизацией команд, рассылкой состояния и адресным обменом SDP/ICE. Работает внутри единственного backend GChat в отдельном WebRTC-контуре, без Socket.IO, брокера и HTTP API звонков. Жизненный цикл, DTO, права и задания состояния принадлежат [DirectCalls](direct-calls/README.md). Backend-модуль реализован через Nest WsAdapter и ws; TLS завершает внешний reverse proxy. Проверки реального iOS-клиента остаются отдельным этапом.

## Публичный API

Подключение — `wss://<host>/ws`, адаптер `@nestjs/platform-ws`. Адаптер включён в зависимости backend. JWT передаётся только в `Authorization: Bearer …`. Правила срока токена и повторных проверок принадлежат [Auth](auth.md#websocket). После upgrade первым прикладным запросом является `device.register` из [Devices](devices.md); до регистрации команды звонков не выполняются. Никакой передачи refresh token по WS нет.

Прикладные запросы имеют `type`, `request_id`, `payload`; успешный ответ — `type: response`, тот же `request_id`, `payload`; ошибка — `error` вместо `payload`. События не содержат `request_id`. Идентификатор запроса — непустая строка до 128 символов, уникальная среди ожидающих ответов соединения; он не обеспечивает идемпотентность. Обёртки состояния, версия компактного ответа пинга, выдача конфигурации ICE/TURN через `call.ice_config` и подтверждение попытки через `call.connected` определены только в DirectCalls.

| Запрос | `payload` | Назначение |
| --- | --- | --- |
| `call.*` | По контракту DirectCalls | Команды, чтение и пинги звонка |
| `device.register`, `device.push_token` | По контракту Devices | Привязка устройства и VoIP-токена |
| `rtc.offer` | `{call_id, negotiation_id, sdp}` | Предложение выбранного инициатора |
| `rtc.answer` | `{call_id, negotiation_id, sdp}` | Ответ выбранного получателя на текущее предложение |
| `rtc.ice` | `{call_id, negotiation_id, candidate}` | ICE от выбранного участника |
| `rtc.restart` | `{call_id}` | Просьба выбранного получателя к инициатору начать новую согласованную попытку |

Проект браузерных команд `device.web_push_config` и `device.web_push` находится в [Devices](devices.md#web-push--проект-расширения); это предлагаемое расширение после `device.register`, не принятая часть таблицы выше.

`call_id` и `negotiation_id` — UUID. Последний создаёт клиент-инициатор для каждой новой попытки, включая ICE restart. SDP — непустая строка до 64 KiB UTF-8; тип SDP определяется командой, аудиосессия допускает только audio, видео и data channel не разрешаются. `candidate` — объект `{candidate: string, sdp_mid: string | null, sdp_mline_index: number | null}` либо `null` (конец кандидатов); строка до 4096 байт, индекс — целое от 0 до 65535, `sdp_mid` — до 256 символов; хотя бы один из mid/index задан для ненулевого кандидата. Незнакомые поля отклоняются. При преобразовании в WebRTC API клиент использует соответствующие camelCase-имена SDK.

Успешный ответ `rtc.*` содержит `payload: {}`: сервер принял и маршрутизировал сообщение, но это не ACK получателя и не подтверждение аудиосоединения. Адресное событие имеет тот же `type` и `payload`, без `request_id`; ID получателя или отправителя клиент не задаёт. Сервер определяет второе выбранное устройство из звонка. SDP и ICE не рассылаются остальным устройствам аккаунта.

### Браузерный handshake — реализовано

Браузерный путь реализован для [веб-клиента GChat](../../web/README.md) наряду с header-based handshake. Выдачей и одноразовым погашением билета владеет [Auth](auth.md#браузерный-ws-билет--реализовано); мотивация — в [D005](../../architecture/decisions/D005-web-client.md).

Браузер подключается к тому же `/ws` с двумя подпротоколами:

```js
new WebSocket(wsUrl, ["gchat", "ticket." + ticket]);
```

`wsUrl` не содержит токенов или билетов. В запросе передаются ровно `gchat` и один `ticket.<секрет>`; секрет имеет формат 43 символов base64url без padding. Сервер выбирает и возвращает только `Sec-WebSocket-Protocol: gchat`. Секретный подпротокол не отражается в ответе и не становится согласованным протоколом соединения.

Проверки до upgrade:

1. При наличии Authorization используется только существующий путь Auth. Одновременное предъявление Authorization и билетного подпротокола отклоняется `400 VALIDATION_ERROR`; попытка с неправильным Authorization не переключается на билет.
2. Браузерный путь требует точного набора подпротоколов, одного непустого Origin и его присутствия в allowlist. Запрос с query credentials, дубликатами, неподдержанными подпротоколами или неверным форматом билета отклоняется до его погашения. Ошибка структуры — `400 VALIDATION_ERROR`; отсутствующий, `null` или запрещённый Origin — `403 FORBIDDEN`.
3. Signaling передаёт билет и разрешённый Origin в Auth. При успешном погашении соединение получает user/session identity; ошибки возвращаются стандартным HTTP-отказом Auth/Error до upgrade. Секрет не включается в ответ.
4. После upgrade первым прикладным запросом остаётся `device.register`, затем клиент выполняет `call.current`. Дедлайн регистрации и остальные ограничения действующего WS-контракта не меняются. Билет не задаёт device_id и не переносит выбранный звонок другой сессии.

Настройка `SIGNALING_BROWSER_ORIGINS` — JSON-массив точных origin, например `["https://gchat.example.test", "http://localhost:5173"]`. Значение по умолчанию — пустой массив, запрещающий браузерный билетный путь и выдачу билетов. Wildcard, `null`, userinfo, path, query и fragment не допускаются; localhost HTTP разрешён только для локальной разработки. Для прочих адресов требуется HTTPS. Порты являются частью Origin; нормализация не должна расширять список разрешённых адресов. Некорректная конфигурация запрещает запуск. HTTP endpoint Auth и WS используют одну общую политику разрешения origin; дублирующиеся списки не вводятся.

Наличие совпадающего Origin не заменяет билет или проверку сессии. Origin и заявленный подпротокол не подтверждают, что запрос создан настоящим браузером. Ограничение Origin применяется к браузерному пути; нативный iOS-клиент продолжает использовать существующий Authorization без требования браузерного Origin.

Reverse proxy и прикладные логи не должны сохранять Authorization, ticket-подпротокол или исходный Sec-WebSocket-Protocol. Доступ к `/ws` остаётся через WSS, кроме локальной разработки на localhost. Браузерный WebSocket API может скрыть статус и тело отказа handshake от приложения: один `onerror` не доказывает отзыв сессии. Клиент определяет последующее действие по HTTP-результату получения нового билета, с ограниченными задержками переподключения и без повторного использования старого секрета.

Путь реализован в адаптере; проверки: выбран только `gchat`, секрет не отражается/не логируется, повторное использование не проходит, смешанные способы авторизации и запрещённый Origin отклоняются, прежний header-based путь сохраняет поведение.

## Правила и инварианты

- До каждого запроса проверяются текущая сессия и аккаунт, затем DTO и права операции; сырое сообщение ограничивается до разбора. Контекст пользователя/сессии/устройства формируется сервером. JWT после handshake не перепроверяется по сроку; текущая сессия проверяется по её ID.
- Входные классы DTO проверяются `class-validator` и `class-transformer`: `transform: true`, `whitelist: true`, `forbidNonWhitelisted: true`, без неявного преобразования примитивов. Ошибки и безопасные коды полей — из [ErrorModule](errors.md#валидация-dto). Не вводится параллельный стандарт валидации.
- Только выбранные устройство и сессия могут отправлять `rtc.*`, в `connecting` или `active`. Чтение состояния не даёт права на медиасигнализацию. Команды сериализуются через `DirectCallsService.withSelectedPeer`; после ожидания повторно проверяются состояние и сроки. Методы не держат транзакцию во время фактической сетевой отправки: постановка в локальную ограниченную очередь не ожидает сеть.
- Инициатор — единственная сторона, создающая offer. Получатель отправляет answer только на текущий `negotiation_id`. При необходимости восстановления получатель посылает `rtc.restart`, инициатор начинает новую попытку. Таким образом одновременные offer двух сторон не допускаются.
- Для каждого звонка Signaling хранит в памяти текущий `negotiation_id` и фазу (`offered/answered`). Повтор того же offer/answer допускается только с тем же SDP; сравнивается хеш. Другой SDP с тем же ID, answer до offer или устаревшие ICE дают `CALL_STATE_CONFLICT`. При принятии нового offer Signaling вызывает `DirectCallsService.registerNegotiation` в транзакции `withSelectedPeer`: текущий ID в PostgreSQL и сброс первоначальных подтверждений в `connecting` фиксируются атомарно. Повтор того же offer подтверждения не сбрасывает. Signaling публикует новую фазу в локальном реестре и ставит offer в очередь только после успешного commit; при неизвестном результате перечитывает ID через DirectCalls под блокировкой. Новая попытка отменяет прежнюю; кандидат относится только к текущей попытке и ставится в очередь после offer. Клиент буферизует ICE до установки remote description.
- Перед передачей `call.connected` в DirectCalls Signaling проверяет наличие текущей попытки в локальном реестре и совпадение `negotiation_id`; отсутствие или несовпадение даёт `CALL_STATE_CONFLICT`. DirectCalls повторно проверяет сохранённый ID под блокировкой звонка. После перезапуска реестр пуст: новый offer с ID, отличным от сохранённого в PostgreSQL, обязателен перед новыми подтверждениями; сохранённые подтверждения прежней попытки сбрасываются при его регистрации. Попытка переиспользовать сохранённый ID при пустом реестре даёт `CALL_STATE_CONFLICT`. Сырые SDP не нужны для этой проверки.
- Если выбранный адресат не подключён, `rtc.*` возвращает базовый `SERVICE_UNAVAILABLE`. После переподключения выбранных устройств инициатор создаёт новый `negotiation_id`; состояние звонка и сроки не сбрасываются. SDP/ICE не сохраняются в PostgreSQL, Redis, outbox или логи; они не воспроизводятся после перезапуска. За каждую новую попытку не увеличивается версия общего DTO звонка.
- После регистрации клиент выполняет `call.current`. При первом событии для неизвестного `call_id` клиент получает актуальный `call.get` по WS до изменения интерфейса вызова и учитывает наибольшую полученную версию. Это исключает показ старого `ringing` по запоздавшему снимку после пропущенного завершения. После `NOT_FOUND` устаревший снимок не открывает входящий вызов. Сервер может отменить ещё не отправленное state-задание, если его версия меньше актуальной, но никогда не заменяет сохранённый DTO задания другим содержимым.
- Новое зарегистрированное соединение той же пары `(device_id, session_id)` заменяет прежнее: старое закрывается, его ожидающие сообщения не исполняются, счётчик пингов клиента не сбрасывается. Иная сессия не перехватывает выбранную сессию звонка.
- Рассылка `call.updated` и критерий успеха её задания определены в DirectCalls. При каждой рассылке используются только текущие авторизованные зарегистрированные соединения. Отозванные сессии не получают новые события. При ошибке проверки зависимости сообщение этому соединению не отправляется, соединение закрывается.
- Закрытие WS при отзыве доступа/ошибке проверки не заменяет независимый фоновый контроль звонков DirectCalls. Проверки всех соединений выполняются с интервалом Auth, также при отсутствии команд.

## Зависимости и регистрация

Обычный SignalingModule импортирует AuthModule, DevicesModule, DirectCallsModule, регистрирует gateway, реестр соединений, диспетчер DTO и обработчик state-доставок. Экспортирует только локальный транспорт отправки для собственных обработчиков; DirectCalls от него не зависит. Redis/Logger/Error используются через существующий DI. Отдельного глобального EventsModule нет.

Очередь state принадлежит DirectCallsDeliveryStore; Signaling получает аренду, рассылает сохранённый DTO и подтверждает обработку. Рассылка не ожидает клиентского ACK или подключения офлайн-устройств. Сроки, повторы и неизменяемость снимков определены в DirectCalls.

## Ошибки и частичное выполнение

При отказе до upgrade возвращается стандартный HTTP-отказ Auth/ErrorModule; это отказ установки WS, а не отдельный HTTP endpoint звонков. После upgrade ошибок с HTTP-статусом в сообщениях нет: используется `error.code/message` и при валидации известного поля — `error.fields`. Базовые коды и безопасные сообщения определены в ErrorModule, четыре кода звонков — в DirectCalls. Неизвестный `type` с корректным request_id даёт `VALIDATION_ERROR`.

При синтаксически неверном JSON или отсутствии корректного `request_id` связать ответ с запросом нельзя: соединение закрывается кодом 1008, выдуманный/нулевой request_id не отправляется. Бинарные сообщения закрываются 1003, превышение лимита — 1009, недопустимый UTF-8 — 1007. При отзыве/отключении — 1008, недоступной зависимости или внутреннем сбое проверки — 1011. Подробности и токены не помещаются в close reason. Значения кодов следуют [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.4.1).

Сбой отправки после принятия команды не отменяет commit звонка. Переподключение и получение состояния выполняются по WS; автоматический повтор `call.create` запрещён. SDP/ICE можно повторить в рамках текущей попытки по правилам выше. Клиент не считает успешный ответ `rtc.*` подтверждением удалённой обработки; установление соединения подтверждают обе стороны через `call.connected`.

## Конфигурация

Для первой версии фиксированы: максимальное прикладное сообщение 128 KiB после сборки фрагментов, без сжатия; ожидание `device.register` 10 секунд; максимальная очередь исходящих данных одного соединения 1 MiB. Медленное соединение закрывается 1011, его очередь освобождается; задание state не ждёт его бесконечно. Это проектные лимиты, не результаты измерений. Интервал проверки доступа задаёт Auth, интервалы пингов — DirectCalls. Собственных env-переменных на этом этапе нет. TLS, домен и reverse proxy настраиваются для отдельного GChat.

### Ограничения Web-сообщений через native bridge

Согласована конфигурация запретов в PostgreSQL для [общего нативного WSS и Web bridge](../../web/README.md#общий-websocket-через-native). Реализованы Drizzle-схема, миграция, SQL-скрипт настройки и доставка правил в native через WSS. Native применяет запреты перед отправкой Web и перед доставкой входящих сообщений Web. Административный API/UI ещё не реализованы.

Таблица `gchat_native_websocket_restrictions` принадлежит Signaling и содержит глобальные для инстанса запреты только для Web, работающего через native. Автономный браузерный WebSocket и собственные запросы/обработка нативных модулей под эти запреты не подпадают. Обычные серверные проверки прав сохраняются для всех клиентов.

| Поле | Правило |
| --- | --- |
| `direction` | `send` — отправка Web через native; `receive` — передача native → Web |
| `message_pattern` | Точный тип сообщения либо префикс с завершающим `.*`, например `call.ice_config` или `rtc.*`; до 128 символов |
| `created_at` | Время добавления правила, `timestamptz`, по умолчанию `now()` |

Первичный ключ — `(direction, message_pattern)`. DB CHECK ограничивает направление и синтаксис шаблона: сегменты из строчных латинских букв, цифр и `_`, начинающиеся с буквы и разделённые точкой; `*` допустима только отдельным последним сегментом после точки. Сопоставление регистрозависимое; `rtc.*` соответствует типам с префиксом `rtc.`, но не `rtc`. Шаблоны не являются регулярными выражениями или SQL LIKE. Любое совпадение запрещает сообщение в соответствующем направлении; исключений и приоритетов нет. Без совпадения передача разрешена; пустая таблица означает отсутствие запретов. Добавление нового типа сообщений вне запрещённых префиксов не требует обновления оболочки.

Для входящего `type: response`, включая ошибки, используется тип исходного запроса, а не строка `response`. Ответы на собственные запросы native также не передаются Web при совпадении `receive`-правила. Общий native-транспорт хранит соответствие request ID исходному типу команды; одного анализа входящего `type` недостаточно. Сам native продолжает получать и обрабатывать исходное сообщение целиком. Запрещённая отправка Web должна отклоняться до отправки команды в общий WSS; проверка реализована в NativeCore.

#### Доставка политики в native

После `device.register` доступна команда `native.bridge_policy` с `payload: {}`. Ответ: `{restrictions: [{direction, message_pattern}]}`. Действуют обычная проверка сессии и строгая валидация пустого payload; до регистрации возвращается `FORBIDDEN`. Команда читает текущие строки PostgreSQL без кеша. Максимум — 512 правил; превышение возвращает `SERVICE_UNAVAILABLE`, частичная политика не выдаётся. Ошибка чтения не подменяется пустым списком. Это служебное чтение политики, не административный API, и само по себе не меняет серверные права.

Native запрашивает политику при каждом подключении и затем каждые 30 секунд. Срок локального снимка — 60 секунд; при ошибке обновления политика сразу удаляется, Web-обмен прекращается и WSS переподключается. Без успешно полученной действующей политики Web не может отправлять или получать сообщения. Изменения SQL начинают действовать после следующего успешного обновления; мгновенная доставка изменений не гарантируется. Нативные модули не ограничиваются этой политикой. Ответ самой загрузки политики не публикуется в Web.

Согласованный начальный scope:

| Направление относительно Web | Запрещённые типы |
| --- | --- |
| Отправка | `device.*`, `call.*`, `rtc.*` |
| Получение | `rtc.*`, ответы на `device.*`, `call.ice_config`, `rtc.*` |

`call.updated` и прочие не совпавшие с правилами сообщения доступны Web. Ответы на чтение `call.current`/`call.get` также не запрещены начальным scope. Регистрация устройства, управление звонком и медиасигнализация остаются у native; Web использует отдельные команды bridge и снимки состояния звонка. Сырые запрещённые сообщения не подменяются маскированным payload. Env-настройки и новое поле скрытия в WS-конверте не вводятся.

Миграция [0005](../../../applications/backend/drizzle/0005_native_websocket_restrictions.sql) создаёт пустую таблицу. Начальные запреты оператор добавляет отдельно [SQL-скриптом](../../../applications/backend/scripts/native-websocket-restrictions.sql) после применения миграций:

```sh
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f applications/backend/scripts/native-websocket-restrictions.sql
```

Команда выполняется из корня репозитория с явно настроенным `DATABASE_URL` целевой БД; `.env` автоматически не загружается. Скрипт работает в транзакции и повторно добавляет отсутствующие начальные правила через `ON CONFLICT DO NOTHING`, сохраняя остальные правила. Для изменения конфигурации оператор выполняет явные `INSERT`/`DELETE`/`UPDATE`; повторный запуск скрипта восстановит удалённые начальные запреты. Миграции и скрипт не запускаются при старте приложения. В будущем управление этой таблицей добавляется в раздел администрирования; маршруты и UI пока не определены.

Интеграционный тест таблицы и SQL-скрипта использует `MIGRATION_INTEGRATION_URL` выделенного PostgreSQL с правом создавать и удалять БД; он создаёт собственную временную БД, применяет историю миграций и удаляет БД после проверки. Запуск: `pnpm --filter @gchat/backend test --watchman=false --runTestsByPath test/native-websocket-restrictions.integration.spec.ts`. Без явно заданного URL тест пропускается.

## Критерии приёмки и проверки

- Авторизация заголовком, отказ токенов в URL, регистрация устройства до команд; истечение JWT после upgrade не разрывает действующую сессию.
- Отзыв и недоступность зависимости закрывают WS по правилам Auth; свежие проверки выполняются перед командами и доставкой.
- Строгие DTO, неизвестные поля, JSON, бинарные и чрезмерные сообщения дают определённый безопасный результат.
- Чужой пользователь и невыбранные устройства не получают SDP/ICE; оба участника получают state на всех действующих подключениях.
- Offer/answer/ICE, повторы, старая попытка, одновременные сообщения и переподключение сохраняют адресацию, ограничения и сроки звонка. Новый offer атомарно сбрасывает первоначальные подтверждения прежней попытки в `connecting`; гонка offer с `call.connected` не объединяет подтверждения разных попыток. После рестарта подтверждение до нового offer отклоняется.
- Дубликаты state, пропавший клиент и медленное соединение не блокируют очередь; восстановление выполняется запросом состояния по WS.

Gateway и DTO реализованы. `test/signaling.e2e.spec.ts` проверяет реальный локальный WS-сервер без PostgreSQL, Redis и APNs; внешние зависимости заменены. Критерии приёмки не являются отчётом о проверках на iPhone.

## Открытые решения

Открытых решений в указанном объёме первой версии нет. Горизонтальное масштабирование, межпроцессная маршрутизация и изменение лимитов требуют отдельного решения после измерений.

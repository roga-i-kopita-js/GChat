# Push

## Назначение и границы

Отправляет входящий вызов GChat в APNs VoIP для PushKit/CallKit. Не владеет состоянием звонка или общим WS-протоколом. Собственных публичных HTTP/WS-команд нет. Backend-модуль реализован через HTTP/2 из Node.js и jose; реальные credentials пока не настроены.

## Публичный API

Фоновый обработчик использует `DirectCallsDeliveryStore` для аренды voip-заданий из транзакции создания звонка и DevicesService для актуального адреса. Формат задания, аренда и повторы определены в [DirectCalls](direct-calls/README.md#передача-изменений-в-signaling--согласовано).

Прикладной payload VoIP: `aps: {}`, `call_id`, `caller_id`, `caller_display_name`, `recipient_id`, `created_at`, `ringing_deadline` в формате общего DTO. `caller_display_name` — снимок отображаемого имени инициатора на момент создания задания, строка длиной до 80 символов по ограничению Auth account. Иные профильные данные (логин, аватар, email), сессии, SDP/ICE и токены не включаются. Имя нужно только для немедленного системного представления звонка; оно не является источником идентичности или прав. Клиент после пробуждения использует текущие Auth/Devices и получает актуальное состояние через WS, не считает push источником состояния. Обработка системного вызова, включая уже завершённый вызов, реализуется iOS по требованиям PushKit/CallKit; ожидание сетевого ответа не должно препятствовать обязательной [системной обработке PushKit/CallKit](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit).

## Правила и инварианты

- Перед каждой попыткой проверяются `ringing`, неистёкший ringing_deadline, активные аккаунты и действительность адресной сессии. Неактуальное задание отменяется. Отсутствие VoIP-устройств не отменяет сам звонок: он ожидает ответа/таймаута, WS-подключения получают state.
- APNs-запрос использует push type `voip`, topic `<bundle-id>.voip`, priority 10, expiration 0. Отдельный APNs request ID равен UUID задания для диагностики; это не обещание дедупликации APNs. Параметры следуют [официальному APNs API](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns).
- Ответ APNs 200 завершает задание, но не доказывает доставку на iPhone или показ вызова. Повторы временных отказов и сетевых ошибок ограничены сроком `ringing`. При неизвестном результате возможна повторная доставка; клиент связывает обработку по `call_id`.
- `BadDeviceToken`, `Unregistered`, `DeviceTokenNotForTopic` отменяют адресное задание и инвалидируют только совпадающую версию токена. Ответ `Unregistered` учитывает timestamp провайдера: новая регистрация после него сохраняется. HTTP 429/5xx повторяются с учётом Retry-After и оставшегося срока; ошибки credentials/topic логируются как отказ конфигурации и не инвалидируют пользовательский токен.
- Принятие/отклонение/отмена звонка отменяет pending-задания. Запрос APNs, уже находящийся в сети, невозможно отозвать транзакцией PostgreSQL; поздний push обрабатывается как устаревший по `call_id` и серверному состоянию. Завершение задания с устаревшим lease не меняет актуальную запись.

## Зависимости и регистрация

Обычный PushModule импортирует DirectCallsModule, DevicesModule и AuthModule; регистрирует один APNs HTTP/2-клиент и обработчик voip-заданий. Импортируется AppModule. Сам DirectCalls не импортирует Push: создаёт задания в собственной транзакции. Отдельный брокер, Pub/Sub и Redis-очередь не вводятся.

## Ошибки и частичное выполнение

Провайдерские ошибки не становятся ошибкой успешно созданного звонка и не меняют его state. Участники освобождаются только по правилам DirectCalls. Неизвестная отправка повторяется тем же заданием до истечения срока; данные и токены не попадают в логи. Отказ PostgreSQL не подтверждает завершение задания. После перезапуска незавершённые задания возобновляются по арендам.

## Конфигурация

`APNS_ENABLED` принимает `true/false`, по умолчанию `true`. При `false` backend запускается без Apple credentials: ключ не читается, APNs-соединения не создаются, worker не забирает VoIP-задания. Браузерные звонки продолжают работать через Signaling и TURN; фоновые iOS push недоступны. VoIP-задания сохраняют свои сроки и при включении worker проверяются по обычным правилам актуальности.

Переменные включённого APNs: `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY_FILE`, `APNS_BUNDLE_ID`, `APNS_ENVIRONMENT` (`sandbox/production`). При включённом Push обязательны, не имеют production-default; ключ хранится вне репозитория. Отсутствующая/некорректная конфигурация не даёт запустить включённый модуль. Окружения не смешиваются; HTTP/2-запрос имеет бюджет 5 секунд, дополнительно ограниченный остатком ringing_deadline. Секреты никогда не передаются клиенту. Подключение APNs и реальные iPhone проверяются отдельно, credentials этой задачей не создаются.

## Критерии приёмки и проверки

- Создание звонка и адресных voip-заданий атомарно; откат не отправляет push.
- Нет отправки после обнаруженного завершения/таймаута или отзыва адресной сессии.
- Временные отказы, неизвестный результат, повтор, рестарт и устаревшая аренда не меняют состояние звонка.
- Инвалидирование старой версии не удаляет новый токен; 200 APNs не считается подтверждением звонка на устройстве.
- Реальные iPhone: открытое приложение, фон и заблокированный экран; повторный и поздний push корректно обрабатываются CallKit.

Unit-тесты `push.client.spec.ts` и `push.worker.spec.ts` проверяют подпись и заголовки, обработку ответов провайдера и повторы с подменённым HTTP/2-транспортом. Обращения к настоящему APNs и проверки iPhone в них нет; критерии не являются отчётом этих проверок.

## Открытые решения

Открытых решений в описанном объёме iOS VoIP-доставки нет. Credentials, bundle ID и эксплуатационные адреса задаются при развёртывании отдельного контура. Android не включён в этот контракт.

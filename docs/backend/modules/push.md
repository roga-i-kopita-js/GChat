# Push

Расширение для диалогов реализовано в [DialogsModule](dialogs/README.md#уведомления): согласованы системные push с текстом сообщения и best-effort отправкой после commit без устойчивых заданий и повторов. Потеря такого уведомления допускается; очередь и повторы звонков ниже этим решением не меняются. Обычный APNs-токен чата регистрируется отдельной согласованной командой [device.apns_token в Devices](devices.md#обычный-apns-токен-чата--реализовано). Серверная доставка диалогов и команда реализованы; это не изменение call-specific payload ниже.

## Назначение и границы

Отправляет входящий вызов GChat в APNs VoIP для PushKit/CallKit. Не владеет состоянием звонка или общим WS-протоколом. Собственных публичных HTTP/WS-команд нет. Backend-модуль реализован через HTTP/2 из Node.js и jose; реальные credentials пока не настроены.

## Публичный API

Фоновый обработчик использует `DirectCallsDeliveryStore` для аренды voip-заданий из транзакции создания звонка и DevicesService для актуального адреса. Формат задания, аренда и повторы определены в [DirectCalls](direct-calls/README.md#передача-изменений-в-signaling--согласовано).

Прикладной payload VoIP: `aps: {}`, `call_id`, `caller_id`, `caller_display_name`, `recipient_id`, `created_at`, `ringing_deadline` в формате общего DTO. `caller_display_name` — снимок отображаемого имени инициатора на момент создания задания, строка длиной до 80 символов по ограничению Auth account. Иные профильные данные (логин, аватар, email), сессии, SDP/ICE и токены не включаются. Имя нужно только для немедленного системного представления звонка; оно не является источником идентичности или прав. Клиент после пробуждения использует текущие Auth/Devices и получает актуальное состояние через WS, не считает push источником состояния. Обработка системного вызова, включая уже завершённый вызов, реализуется iOS по требованиям PushKit/CallKit; ожидание сетевого ответа не должно препятствовать обязательной [системной обработке PushKit/CallKit](https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit).

### Push диалогов — реализовано

Обычный APNs alert и Web Push чата добавляются отдельно от VoIP/Web Push звонков. Точный payload, байтовые бюджеты, сокращение body, переход в диалог, однократные попытки после commit и ограничения исполнения принадлежат [DialogsModule](dialogs/README.md#уведомления). У чата нет устойчивого outbox и повторов. Указанные выше задания и worker звонков сохраняют действующий контракт. Адреса/версии разрешает Devices, обычный APNs-токен регистрируется его отдельной командой device.apns_token. Зависимости транспортной интеграции должны сохранять отсутствие обратного импорта Push в Dialogs: обработчик Push получает commit-факт от Dialogs и использует его проверку доступа перед попыткой; ошибка доставки не меняет сохранённое сообщение.

## Правила и инварианты

- Перед каждой попыткой проверяются `ringing`, неистёкший ringing_deadline, активные аккаунты и действительность адресной сессии. Неактуальное задание отменяется. Отсутствие VoIP-устройств не отменяет сам звонок: он ожидает ответа/таймаута, WS-подключения получают state.
- APNs-запрос использует push type `voip`, topic `<bundle-id>.voip`, priority 10, expiration 0. Отдельный APNs request ID равен UUID задания для диагностики; это не обещание дедупликации APNs. Параметры следуют [официальному APNs API](https://developer.apple.com/documentation/usernotifications/sending-notification-requests-to-apns).
- Ответ APNs 200 завершает задание, но не доказывает доставку на iPhone или показ вызова. Повторы временных отказов и сетевых ошибок ограничены сроком `ringing`. При неизвестном результате возможна повторная доставка; клиент связывает обработку по `call_id`.
- `BadDeviceToken`, `Unregistered`, `DeviceTokenNotForTopic` отменяют адресное задание и инвалидируют только совпадающую версию токена. Ответ `Unregistered` учитывает timestamp провайдера: новая регистрация после него сохраняется. HTTP 429/5xx повторяются с учётом Retry-After и оставшегося срока; ошибки credentials/topic логируются как отказ конфигурации и не инвалидируют пользовательский токен.
- Принятие/отклонение/отмена звонка отменяет pending-задания. Запрос APNs, уже находящийся в сети, невозможно отозвать транзакцией PostgreSQL; поздний push обрабатывается как устаревший по `call_id` и серверному состоянию. Завершение задания с устаревшим lease не меняет актуальную запись.

## Зависимости и регистрация

Обычный PushModule импортирует DirectCallsModule, DevicesModule и AuthModule; регистрирует один APNs HTTP/2-клиент и обработчик voip-заданий. Импортируется AppModule. Сам DirectCalls не импортирует Push: создаёт задания в собственной транзакции. Отдельный брокер, Pub/Sub и Redis-очередь не вводятся.

## Ошибки и частичное выполнение

Провайдерские ошибки не становятся ошибкой успешно созданного звонка и не меняют его state. Участники освобождаются только по правилам DirectCalls. Неизвестная отправка повторяется тем же заданием до истечения срока; данные и токены не попадают в логи. Отказ PostgreSQL не подтверждает завершение задания. После перезапуска незавершённые задания возобновляются по арендам.

## Конфигурация

`APNS_ENABLED` принимает `true/false`, по умолчанию `true`. При `false` backend запускается без Apple credentials: ключ не читается, APNs-соединения не создаются, worker не забирает VoIP-задания. Браузерные звонки продолжают работать через Signaling и TURN; фоновые iOS push недоступны. VoIP-задания сохраняют свои сроки и при включении worker проверяются по обычным правилам актуальности.

Переменные включённого APNs: `APNS_TEAM_ID`, `APNS_KEY_ID`, `APNS_PRIVATE_KEY_FILE`, `APNS_BUNDLE_ID`, `APNS_ENVIRONMENT` (`sandbox/production`). При включённом Push обязательны, не имеют production-default; ключ хранится вне репозитория. Отсутствующая/некорректная конфигурация не даёт запустить включённый модуль. Окружения не смешиваются; HTTP/2-запрос имеет бюджет 5 секунд, дополнительно ограниченный остатком ringing_deadline. Секреты никогда не передаются клиенту. Подключение APNs и реальные iPhone проверяются отдельно, credentials этой задачей не создаются.

## Критерии приёмки и проверки

- Создание звонка и адресных voip-заданий атомарно; откат не отправляет push.
- Нет отправки после обнаруженного завершения/таймаута или отзыва адресной сессии.
- Временные отказы, неизвестный результат, повтор, рестарт и устаревшая аренда не меняют состояние звонка.
- Инвалидирование старой версии не удаляет новый токен; 200 APNs не считается подтверждением звонка на устройстве.
- Реальные iPhone: открытое приложение, фон и заблокированный экран; повторный и поздний push корректно обрабатываются CallKit.

Unit-тесты `push.client.spec.ts` и `push.worker.spec.ts` проверяют подпись и заголовки, обработку ответов провайдера и повторы с подменённым HTTP/2-транспортом. Обращения к настоящему APNs и проверки iPhone в них нет; критерии не являются отчётом этих проверок.

### Web Push

Реализация по принятому [D010](../../architecture/decisions/D010-web-push-pwa.md); существующий APNs-контракт выше сохраняется. Браузерные подписки принадлежат [Devices](devices.md#web-push), задания — [DirectCalls](direct-calls/README.md#web-push-в-outbox). Сам Push публичных команд не добавляет.

#### Доставка

Отдельный worker обрабатывает `web_push` из общего outbox. Перед каждой попыткой разрешает актуальную подписку и проверяет действующую сессию, активный аккаунт, `ringing` и будущий `ringing_deadline`. При отсутствии действующей цели или актуального звонка отменяет задание. Подписки, добавленные после создания звонка, задним числом в его outbox не включаются; открытый клиент получает состояние по WSS.

Payload: `{call_id, ringing_deadline}`. Профильные данные, токены, SDP/ICE и адрес для произвольного перехода не передаются. Service worker показывает общее уведомление GChat; push не становится источником состояния звонка.

Отправка через стандартный Web Push с VAPID и шифрованием библиотеки `web-push`. `urgency: high`; TTL ограничен оставшимся сроком ringing, округлённым вниз до целых секунд; сетевой timeout — не более 5 секунд и остатка срока. Ответ 2xx не подтверждает доставку, показ уведомления или принятие звонка.

Первая отправка доступна сразу после создания звонка. После ответа провайдера 2xx то же задание возвращается в pending со следующей отправкой через 2,5 секунды от успешного ответа; счётчик последовательных попыток сбрасывается. Перед каждым повтором заново выполняются проверки актуальности. Интервал является серверной задержкой планирования: время запроса, опрос worker и ограничения провайдера могут увеличить промежуток. Повторы прекращаются после выхода из ringing, истечения срока либо утраты действующей цели; уже отправленный запрос отозвать нельзя. APNs VoIP эти регулярные повторы не затрагивают.

Ответы 404/410 инвалидируют только совпадающую версию подписки. HTTP 429/5xx и неизвестный результат отправки повторяются по правилам outbox, с учётом Retry-After. Прочие отказы завершают адресное задание с безопасным логом HTTP-статуса, сохраняя подписку. Полные ответы провайдера и endpoint не логируются. Повтор может дать дубликат; уведомления связываются по `call_id`.

#### Настройки

Используется независимый от APNs `WEB_PUSH_ENABLED=true/false`, по умолчанию `false`. При выключении worker не забирает задания и клиент получает `public_key: null`; WSS и кеш фронта продолжают работать. Включение требует:

| Переменная             | Назначение                                       |
| ---------------------- | ------------------------------------------------ |
| `WEB_PUSH_SUBJECT`     | Контакт оператора: `mailto:` или HTTPS URL       |
| `WEB_PUSH_PUBLIC_KEY`  | Публичный VAPID P-256 ключ в base64url           |
| `WEB_PUSH_PRIVATE_KEY` | Приватный VAPID-ключ в base64url; секрет backend |

Включённый контур с отсутствующими, некорректными или несовпадающими ключами не запускается. Ключи создаются один раз и сохраняются между релизами. После установки зависимости пару можно получить командой `pnpm --filter @gchat/backend exec web-push generate-vapid-keys`; вывод содержит приватный ключ и не сохраняется в репозитории или общем логе. Значения задаются через защищённое окружение backend. При вынужденной смене пары браузерная подписка перевыпускается при следующем открытии GChat по согласованному правилу ниже.

#### Контекст и вопрос смены VAPID-ключей

VAPID — идентификация отправителя перед push-службой браузера. Для каждого окружения GChat создаётся пара ключей: публичный используется при оформлении подписки, приватный хранится только на backend и подписывает отправки. Это отдельные ключи от паролей пользователей, HTTPS-сертификата и APNs. Ключи шифрования отдельной браузерной подписки (`p256dh/auth`) также не являются VAPID-парой. [Назначение applicationServerKey](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe).

При обычном деплое или перезапуске менять VAPID-пару не требуется. Проблема возникает при утрате приватного ключа, его компрометации либо намеренной смене пары. Существующие подписки ограничены прежним публичным ключом: новый приватный ключ не позволяет продолжать отправку в них как прежде. Перевыпуск подписки требует исполнения клиента в браузере; сервер самостоятельно не может переподписать закрытую PWA.

Рассмотрены два варианта:

- Одна стабильная пара и восстановление подписок при следующем открытии после вынужденной смены. Проще в реализации; до открытия GChat часть устройств не получает push.
- Плановая миграция с временным хранением старой и новой пар, привязкой подписки к версии ключа и постепенным перевыпуском при открытии клиента. Уменьшает перерыв при плановой смене, но усложняет хранение, отправку и эксплуатацию. При утрате старого приватного ключа продолжить старые отправки невозможно; при его компрометации сохранение старого ключа требует отдельного решения.

Согласовано для первого этапа: одна стабильная VAPID-пара на окружение, сохранение между деплоями и резервное хранение приватного ключа. При вынужденной замене клиент при следующем открытии обнаруживает несовпадение публичного ключа, удаляет старую браузерную подписку, создаёт новую с текущим ключом и регистрирует её для текущей сессии. Ранее выданное разрешение используется без повторного автоматического запроса; запрет уведомлений не обходится. До успешного перевыпуска доставка на старую подписку недоступна. Если восстановление не удалось, клиент показывает ограничение и действие повтора. Параллельная поддержка старой и новой VAPID-пар в первый этап не входит.

#### Приёмка

Для регулярных повторов проверяются задержка после успешной отправки, сброс счётчика последовательных попыток, отсутствие новой отправки до назначенного срока и остановка после выхода из ringing. Устаревшая или истёкшая аренда не должна перепланировать задание, а поздний ответ провайдера после принятия звонка не должен возобновлять отменённую доставку. Service worker использует один tag на вызов и запрашивает повторный сигнал только для неистёкшего payload по [веб-контракту](../../web/README.md#подписка-и-входящий-вызов).

Проверяются независимость от APNs, остановка доставки после отзыва сессии, просроченный вызов, 404/410 после смены подписки, 429/5xx, неизвестный сетевой результат и рестарт worker. Проверяются сохранение ключей между релизами и перевыпуск подписки после вынужденной замены пары: успешное восстановление, отказ браузера и повтор после ошибки. Отдельно проверяются настоящая доставка в поддерживаемых браузерах, закрытая страница, заблокированный телефон и настройки запрета уведомлений. Моки провайдера и сборка этого не подтверждают.

## Открытые решения

Открытых решений в описанном объёме iOS VoIP-доставки нет. Credentials, bundle ID и эксплуатационные адреса задаются при развёртывании отдельного контура. Android не включён в этот контракт.

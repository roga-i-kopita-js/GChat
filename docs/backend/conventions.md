# Соглашения разработки backend

Нормативные правила реализации общие для всех серверных модулей. Контракты конкретных сервисов находятся в [modules](../README.md), команды запуска — в [README backend](../../applications/backend/README.md).

## Организация модулей

Код находится в applications/backend/src. Сервисы получают зависимости через конструктор; инфраструктурные клиенты не создаются заново на каждом запросе. Правила регистрации определяются контрактом конкретного модуля, а не единым требованием forRoot для всех:

- [Redis](modules/redis.md) и [Logger](modules/logger.md): forRoot один раз в AppModule, глобальный экспорт.
- [RedLock](modules/redlock.md): forFeature в потребителе.
- [Error](modules/errors.md): глобальный модуль в AppModule, фабрика ErrorService через DI.
- [Database](modules/database.md): импорт потребителем, экспорт DatabaseService.

Уникальные правила регистрации не дублируются в инструкциях запуска.

## Ошибки и логирование

Сервис выбрасывает ошибку через внедрённый ErrorService. Контроллер не преобразует её в HTTP вручную; это делает глобальный фильтр. Фабрика возвращает AppError, а throw выполняет потребитель. См. [полный контракт Error](modules/errors.md).

LoggerService также внедряется через конструктор. Модуль и компонент определяются автоматически в пределах DI-привязки; данные события передаются явно. Секреты, целые запросы и конфигурация не добавляются в события. Режим маскирования и ограничения — в [Logger](modules/logger.md).

## HTTP-контроллеры и Swagger


HTTP API документируется автоматически через `@nestjs/swagger` и плагин Nest CLI. Источник контракта — контроллеры и классы DTO; отдельный список маршрутов и OpenAPI JSON вручную не поддерживаются. Эти правила применяются ко всем новым HTTP-модулям.

- Входные и выходные данные описываются классами в `*.dto.ts`. Для входных данных используются декораторы class-validator.
- Методы контроллера объявляют тип ответа: `ResponseDto` или `Promise<ResponseDto>`. Плагин извлекает успешные ответы и свойства DTO при сборке.
- Комментарии описывают назначение операций и полей; `@ApiTags` группирует контроллеры.
- Ошибочные ответы указываются явно через Swagger-декораторы; исключения из сервисов автоматически не перечисляются. Для ошибок с телом указывается DTO, соответствующий общему формату ErrorModule.
- Защищённые маршруты отмечаются `@ApiBearerAuth()` и защищаются реальным guard. Swagger-декоратор описывает авторизацию, а проверку доступа выполняет guard.

Пример оформления будущего контроллера контактов; он иллюстрирует соглашение и не означает, что Contacts или AuthGuard уже реализованы:

```ts
@ApiTags('Contacts')
@ApiBearerAuth()
@UseGuards(AuthGuard)
@Controller('contacts')
export class ContactsController {
  constructor(private readonly contacts: ContactsService) {}

  /** Получить доступные контакты. */
  @Get()
  @ApiUnauthorizedResponse({ description: 'Сессия недействительна' })
  list(): Promise<ContactsResponseDto> {
    return this.contacts.list();
  }
}
```

Классы ответа в `contacts.dto.ts`:

```ts
export class ContactDto {
  /** ID пользователя */
  id!: string;

  /** Отображаемое имя */
  displayName!: string;
}

export class ContactsResponseDto {
  contacts!: ContactDto[];
}
```

Swagger покажет `GET /contacts`, описание, успешный ответ 200, вложенную структуру контактов и явно объявленный ответ 401. Если контракт модуля различает несколько причин отказа, они отдельно описываются в DTO, примерах или описании ошибки. Полный контракт ошибок и безопасности дополняется при реализации модуля.

Порядок подключения, адреса UI/JSON и ограничения автогенерации описаны в [Swagger / OpenAPI](openapi.md).


## Схемы и миграции

TypeScript-схемы хранятся рядом с бизнес-модулями в *.schema.ts. SQL и метаданные образуют одну историю backend; уже применённые миграции не редактируются. Инструкция генерации и применения — в [миграциях](operations/migrations.md). Таблицы добавляются вместе с бизнес-модулем. Имена бизнес-таблиц PostgreSQL используют префикс `gchat_`, чтобы отделять данные GChat от таблиц других приложений в общей БД. Имена переменных TypeScript сохраняются без префикса.

## Тесты и проверки

Юнит-тесты *.spec.ts находятся рядом с модулем в src. HTTP/e2e и тесты с реальными зависимостями — в test. Production-сборка исключает тесты. Интеграционные сценарии запускаются только при явном тестовом URL; локальные или рабочие базы по умолчанию не используются.

При изменении кода выполнить typecheck и build, затем относящиеся к изменению тесты. Команды — в [README backend](../../applications/backend/README.md#сборка-и-проверки). Для изменения Swagger дополнительно проверить OpenAPI после Nest CLI build: ts-jest не применяет CLI-плагин. При изменении мигратора проверить отдельную тестовую PostgreSQL и закрытие соединений.

Для документации достаточно docs:check и проверки diff; запускать backend-тесты только из-за перестановки Markdown не требуется. Не сохранять в документации текущие числа пройденных тестов как постоянную характеристику проекта.

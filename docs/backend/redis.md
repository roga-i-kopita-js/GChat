# GChat: модуль Redis

Статус: RedisModule реализован и зарегистрирован один раз через `RedisModule.forRoot()` в AppModule; клиент — node-redis 5. RedlockModule реализован; Auth пока остаётся спецификацией. Локальный Docker Compose уже запускает Redis 8.2 с AOF, noeviction и постоянным томом. Требования Auth сохранены; параметры ниже с пометкой «предложение» требуют проверки при реализации.

## 1. Назначение и границы

RedisModule управляет подключением NestJS backend и CLI к одному Redis. Он предоставляет клиент, конфигурацию, контроль доступности и завершение подключения. Redis используется как хранилище сессий и результатов ротации [Auth](auth.md), а также как хранилище аренд [RedlockModule](redlock.md).

Форматы данных, Lua-скрипты и правила сессий принадлежат Auth. Алгоритм блокировок принадлежит RedlockModule. RedisModule не предоставляет HTTP API и не принимает решения о правах пользователя. Очередь заданий, Pub/Sub, кеш и перенос лимитов Auth в Redis в этот объём не входят.

## 2. Подключение и жизненный цикл

Backend и CLI используют одинаковые настройки адреса, базы и пространства ключей. Корневая регистрация глобально экспортирует RedisService без повторных импортов RedisModule в потребителях. На процесс создаётся один управляемый клиент; RedlockModule получает его через внедрение зависимостей. Подключение на каждый запрос не создаётся. Используется пакет `redis` версии 5, разрешённая версия зафиксирована в pnpm-lock.yaml.

При запуске конфигурация валидируется, подключение устанавливается с ограничением времени, затем выполняется PING. Некорректная конфигурация останавливает запуск. Недоступность Redis не должна приводить к бесконечному ожиданию: процесс завершает запуск с ошибкой в пределах установленного бюджета. CLI сообщает ошибку и завершается с ненулевым кодом.

После потери соединения клиент переподключается с ограниченной задержкой и случайным разбросом. Команды во время отключения не накапливаются для последующего выполнения. Автоматический повтор записей с неизвестным результатом запрещён: решение о повторе принимает вызывающий модуль с учётом идемпотентности.

При остановке backend прекращает принимать новые операции, даёт активным операциям ограниченное время на завершение и освобождение блокировок, затем закрывает клиент. По истечении срока соединение принудительно закрывается. CLI закрывает клиент и при успехе, и при исключении.

## 3. Предлагаемая конфигурация

Имена переменных являются проектным контрактом, для будущего клиента; они уже включены в `.env.example`, но backend пока их не использует.

| Переменная | Назначение | Предложение |
| --- | --- | --- |
| `REDIS_URL` | Адрес, учётные данные, TLS и номер базы | Обязательна, без production-значения по умолчанию |
| `REDIS_KEY_PREFIX` | Префикс окружения перед логическим ключом | Например, `gchat:local:`; обязателен и одинаков для backend и CLI |
| `REDIS_CONNECT_TIMEOUT_MS` | Таймаут одной попытки подключения | 3000 мс |
| `REDIS_COMMAND_TIMEOUT_MS` | Максимальное ожидание команды | 1000 мс |
| `REDIS_STARTUP_TIMEOUT_MS` | Общий бюджет подключения при запуске | 10000 мс |

Значения таймаутов — положительные целые числа. URL и секреты не выводятся в логах. Для локального примера используются только фиктивные учётные данные. В production Redis доступен по закрытой сети с аутентификацией; при передаче через недоверенную сеть требуется TLS с проверкой сертификата.

Префикс разделяет окружения, но не заменяет изоляцию доступа. База и префикс не должны изменяться при обычном перезапуске: иначе действующие сессии станут недоступны, а блокировки разных процессов перестанут координироваться.

## 4. Данные и атомарность

Ниже указаны логические ключи до добавления `REDIS_KEY_PREFIX`.

| Владелец | Ключ | Срок хранения |
| --- | --- | --- |
| Auth | `auth:session:<session_id>` | До отзыва, без TTL |
| Auth | `auth:user-sessions:<user_id>` | Без TTL; пустой индекс удаляется |
| Auth | `auth:rotation:<session_id>` | 30 секунд |
| RedlockModule | `lock:auth:user:<user_id>` | Ограниченная аренда, см. RedlockModule |

Состав записей определён в [Auth](auth.md#5-redis). Пароли и открытые refresh token не сохраняются. Повторный результат ротации содержит зашифрованную пару токенов; её шифрование выполняет Auth.

Создание сессии вместе с индексом, замена хеша вместе с результатом ротации, удаление сессии вместе с результатом и членством в индексе выполняются атомарно. Предпочтительный механизм для условных изменений — короткие Lua-скрипты с проверкой предусловий до записи. Redis не откатывает уже выполненные записи скрипта при последующей ошибке; типы и аргументы должны проверяться заранее.

Массовый отзыв использует индекс пользователя и общий протокол блокировки Auth. Обработку большого числа сессий нужно ограничить по времени и памяти; частичное выполнение должно допускать безопасный повтор. `KEYS`, глобальное сканирование и очистка всей базы не используются в штатных операциях. Переход к Redis Cluster потребует отдельного пересмотра размещения связанных ключей и атомарных операций.

Таймаут команды означает неизвестный результат: запись могла выполниться. Клиентский таймаут не отменяет команду на Redis. Auth восстанавливает результат через свой протокол идемпотентности, а не повторяет запись вслепую.

## 5. Сохранность и восстановление

Redis здесь хранит доступ, поэтому требуется постоянный том и `maxmemory-policy noeviction`. Лимит памяти задаётся с запасом для служебных операций и persistence. При нехватке памяти ошибка записи передаётся вызывающему модулю; успешное чтение само по себе не доказывает возможность записи.

Предложение для production: `appendonly yes`, `appendfsync always`, `no-appendfsync-on-rewrite no`. Это настройки сервера Redis, а не переменные backend. Стоимость синхронной записи нужно проверить нагрузкой. `everysec` допускает потерю последних записей и потому не принимается автоматически для отзывов доступа. RDB сам по себе не обеспечивает требуемую сохранность последних изменений. См. [официальное описание persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

Даже AOF не заменяет процедуру восстановления. Потеря сессий требует повторного входа; восстановление старого состояния может вернуть уже отозванную сессию. При неизвестной актуальности данных доступ не открывается: backend и CLI останавливаются, старые сессии и результаты ротации инвалидируются, затем сервис запускается с требованием нового входа. Процедура должна охватывать все процессы и исключать возврат старых данных при следующем восстановлении.

После аварийного восстановления нельзя немедленно доверять сохранённым блокировкам: порядок остановки процессов и ожидание истечения аренды определены в [RedlockModule](redlock.md). Репликация, Sentinel и автоматическое переключение узла в MVP не предусмотрены.

## 6. Доступность и наблюдаемость

`GET /health` отражает жизнеспособность процесса и не зависит от Redis. Проверка Redis входит в `GET /ready` с ограниченным временем ожидания; при недоступности готовность отрицательная. PING не проверяет сохранность данных, свободное место или возможность записи — эти условия контролируются отдельно.

Сбой Redis переводится в ошибку зависимости: Auth возвращает HTTP 503, CLI завершается с ошибкой, WebSocket действует по правилам Auth. Отсутствующий ключ сессии означает недействительную сессию, а ошибка чтения — недоступность зависимости; эти случаи нельзя смешивать.

Нужны метрики задержки и ошибок команд, переподключений, памяти, отклонённых записей, состояния AOF и свободного диска. Счётчик вытесненных ключей должен оставаться нулевым. Логи не содержат URL с паролем, значения сессий, токены и содержимое скриптов с пользовательскими данными.

## 7. Проверки перед реализацией

- Backend и CLI используют одинаковые настройки и закрывают подключения при завершении.
- Отключённый Redis даёт ограниченное время ответа и отрицательную готовность; команды не исполняются неожиданно после восстановления связи.
- Сессии и индексы не имеют TTL, результат ротации удаляется через 30 секунд.
- Условные изменения сохраняют инварианты при конкуренции и неверных предусловиях.
- Нехватка памяти, ошибка диска и таймаут записи не выдаются за успешную операцию.
- Перезапуск с постоянным томом и аварийное восстановление проверены отдельно; старые отзывы не теряются при штатном восстановлении.

Перед production нужно проверить таймауты, бюджет памяти и производительность AOF, оформить пошаговую процедуру аварийной инвалидации сессий. Эти изменения не выполнены данным документом.

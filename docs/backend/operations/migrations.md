# GChat: миграции PostgreSQL

Статус: реализовано. Drizzle Kit генерирует SQL из схем бизнес-модулей; отдельная команда db:migrate использует стандартный PostgreSQL-мигратор drizzle-orm. Бизнес-схемы описываются в контрактах соответствующих модулей.

## 1. Назначение

Миграции хранят версионируемые изменения схемы PostgreSQL в репозитории. Они позволяют привести локальную, тестовую и рабочую БД к схеме конкретной версии backend. Это часть инфраструктуры DatabaseModule; отдельный Nest-модуль не требуется.

## 2. Процесс

1. Разработчик изменяет TypeScript-описание таблиц.
2. Команда `db:generate` создаёт SQL-миграцию и метаданные Drizzle Kit.
3. Разработчик проверяет SQL, включая влияние на существующие данные.
4. SQL и метаданные коммитятся вместе с изменением кода.
5. Команда `db:migrate` применяет подготовленные миграции к выбранной БД.

Генерация выполняется при разработке. При развёртывании применяется подготовленный SQL из репозитория; заново генерировать миграции на рабочем сервере не предлагается. Прямое изменение схемы через `push` не входит в стандартный процесс.

Уже применённые миграции не редактируются. Исправление оформляется следующей миграцией. Изменения существующих данных при необходимости оформляются явным SQL и проверяются отдельно.

## 3. Размещение схем

Согласовано: TypeScript-описания таблиц хранятся рядом с бизнес-модулями, например `src/auth/auth.schema.ts` и `src/contacts/contacts.schema.ts`. Drizzle Kit собирает схемы по шаблону `src/**/*.schema.ts`. SQL-миграции и метаданные образуют единую историю для всего backend; отдельной истории на каждый модуль нет. Конфигурация — `applications/backend/drizzle.config.ts`, история — `applications/backend/drizzle/`. SQL, snapshots и `meta/_journal.json` хранятся в Git вместе. Пустой `src/database/database.schema.ts` не создаёт инфраструктурных таблиц; бизнес-схемы собираются тем же шаблоном.

## 4. Команды

Из корня монорепозитория:

```sh
pnpm --filter @gchat/backend db:generate
pnpm --filter @gchat/backend build
pnpm --filter @gchat/backend db:migrate
```

`db:generate` запускает Drizzle Kit; подключение к PostgreSQL для генерации не требуется. Параметры генератора можно передать после команды, например `pnpm --filter @gchat/backend db:generate --name=add_users`.

`db:migrate` запускает скомпилированный `dist/database/migrate.js`, поэтому перед первым запуском и после изменений кода требуется `build`. Команда читает локальный `.env` через Node.js; переменные процесса имеют приоритет. Используется только DATABASE_URL, без общего валидатора настроек HTTP/Redis. Путь к миграциям определяется относительно скомпилированного файла, а не текущего каталога. В артефакт развёртывания включаются `dist`, каталог `drizzle` и production-зависимости; Drizzle Kit нужен только при генерации.

Мигратор работает без Redis, HTTP-сервера и загрузки бизнес-модулей, использует отдельный пул PostgreSQL на одно соединение и закрывает его в finally. Ожидание подключения ограничено 5 секундами. Таймаут исполнения DDL в этой команде отдельно не задаётся; нужно учитывать настройки выбранной БД. При ошибке команда возвращает ненулевой код и безопасное сообщение без URL, SQL и исходного сообщения драйвера.

Журнал и SQL хранятся в Git. При пустой истории команда успешно завершается без подключения к БД; это не проверка доступности PostgreSQL. Отсутствующий или повреждённый журнал и отсутствующий SQL — ошибки, а не повод молча пропустить миграции.

## 5. Применение и сбои

Согласовано: миграции запускаются отдельной командой `db:migrate` перед запуском новой версии backend. HTTP-приложение не запускает миграции автоматически и не изменяет схему при старте.

Согласовано: используется стандартный механизм миграций Drizzle, без собственной блокировки PostgreSQL или Redis и без дополнительного протокола ожидания. В одном окружении миграции запускаются последовательно процессом развёртывания.

В установленной версии drizzle-orm PostgreSQL-мигратор хранит журнал в `drizzle.__drizzle_migrations`, читает последнюю применённую миграцию и выполняет следующие миграции в транзакции. Отдельной advisory-блокировки и гарантии сериализации двух параллельных миграторов этот механизм не предоставляет. Повторный последовательный запуск и конкурентный запуск — разные сценарии; безопасность конкурентного запуска не заявляется. Drizzle Kit используется для генерации; применение выполняется через `drizzle-orm/node-postgres/migrator`, без собственного исполнения SQL или дополнительного протокола блокировок.

При ошибке запуск новой версии останавливается. Нельзя считать произвольный SQL автоматически откатываемым: транзакционность и допустимость конкретных DDL-операций проверяются при подготовке миграции. Повторное применение и журнал выполненных миграций проверяются на тестовой БД.

Автоматические down-миграции не предлагаются. Исправления выполняются следующей миграцией; восстановление из резервной копии — отдельная эксплуатационная процедура. Откат версии приложения допустим только при совместимой схеме.

## 6. Границы первого шага

Первый шаг — инструменты, конфигурация, команды и проверка мигратора. Таблица users и другие бизнес-таблицы добавляются вместе с соответствующими модулями. Фиктивные таблицы в основную схему не добавляются.

## 7. Проверки

- Пустая тестовая БД получает ожидаемую схему.
- Повторный запуск не применяет выполненные миграции заново.
- Новая миграция корректно применяется поверх предыдущего состояния.
- Ошибка SQL приводит к ненулевому коду завершения и освобождению соединения.
- Для запуска мигратора не требуются Redis и HTTP-сервер.
- Секреты подключения не попадают в вывод ошибок.

## 8. Проверки реализации

Юнит-тесты находятся рядом с модулем в `src/database/migrations.spec.ts`. Интеграционный тест `test/migrations.integration.spec.ts` включается через MIGRATION_INTEGRATION_URL, создаёт отдельную БД со случайным именем и удаляет её после проверки. Тестовому пользователю нужны права создания и удаления этой БД. При обычном запуске без переменной интеграционный тест пропускается.

Общие команды тестов — в [README backend](../../../applications/backend/README.md#сборка-и-проверки).

Сценарии для отдельной временной PostgreSQL: применение первой миграции, повторный запуск, следующая миграция, откат неуспешной миграции, отсутствие её записи в журнале и закрытие пула. Дополнительно проверять генерацию SQL на временной схеме, отсутствие дубликата при повторной генерации и ненулевой код CLI без утечки секретов при неверной конфигурации.

# Восстановление доступа и Redis

Согласован [перенос сессий, результатов ротации, WS-билетов и ограничения их выдачи Auth в PostgreSQL](../modules/auth.md#хранение-сессий-в-postgresql--согласовано-не-реализовано). Он пока не реализован: правила сохранности Redis-сессий ниже относятся к текущему коду до переноса. После переноса восстановление PostgreSQL также не должно возвращать отозванные сессии; WS-билеты также переносятся в PostgreSQL и проверяют сессию в той же БД; восстановленный билет не должен отменять правила проверки срока и одноразовости.

Это согласованные ограничения и порядок действий, а не готовый production-runbook. HTTP Auth реализован; перенос в PostgreSQL, административные операции и инструменты массовой инвалидации ещё не реализованы. Не следует заменять недостающую процедуру произвольной очисткой Redis.

## Сохранность Redis

Redis здесь хранит доступ, поэтому требуется постоянный том и `maxmemory-policy noeviction`. Лимит памяти задаётся с запасом для служебных операций и persistence. При нехватке памяти ошибка записи передаётся вызывающему модулю; успешное чтение само по себе не доказывает возможность записи.

Предложение для production: `appendonly yes`, `appendfsync always`, `no-appendfsync-on-rewrite no`. Это настройки сервера Redis, а не переменные backend. Стоимость синхронной записи нужно проверить нагрузкой. `everysec` допускает потерю последних записей и потому не принимается автоматически для отзывов доступа. RDB сам по себе не обеспечивает требуемую сохранность последних изменений. См. [официальное описание persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

Даже AOF не заменяет процедуру восстановления. Потеря сессий требует повторного входа; восстановление старого состояния может вернуть уже отозванную сессию. При неизвестной актуальности данных доступ не открывается: backend и CLI останавливаются, старые сессии и результаты ротации инвалидируются, затем сервис запускается с требованием нового входа. Процедура должна охватывать все процессы и исключать возврат старых данных при следующем восстановлении.

После аварийного восстановления нельзя немедленно доверять сохранённым блокировкам: порядок остановки процессов и ожидание истечения аренды определены в [RedlockModule](../modules/redlock.md). Репликация, Sentinel и автоматическое переключение узла в MVP не предусмотрены.

## Потеря аренд

После аварийного перезапуска Redis с возможной потерей lock-ключей все backend- и CLI-процессы, которые могли удерживать старую аренду, должны быть остановлены. До открытия доступа выдерживается как минимум максимальный срок аренды с запасом на дрейф. Это не отменяет уже отправленные записи: состояние частичных операций проверяется отдельно. При восстановлении старого снимка дополнительно применяется описанная выше процедура инвалидации сессий.

## Частичные административные операции

Целевые алгоритмы принадлежат [Auth](../modules/auth.md#последовательности-административных-операций): аккаунт, сессии и результаты ротации изменяются одной транзакцией PostgreSQL. Подтверждённый откат не оставляет частичного выполнения. При потере подтверждения COMMIT результат неизвестен, проверяется вручную; слепой повтор запрещён. CLI только создаёт администраторов и не восстанавливает прерванные административные операции. Устойчивый журнал и автоматическое продолжение не требуются.

## До production

Подготовить исполняемые команды инвалидации и проверки результатов, проверить восстановление на изолированной копии, определить ответственность за резервные копии PostgreSQL и Redis. Проверить нагрузку AOF и актуальность сохранённых отзывов. Численные бюджеты аренды берутся из контракта RedLock; параметры persistence — из Compose и этого документа.

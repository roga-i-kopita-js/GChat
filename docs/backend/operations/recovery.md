# Восстановление доступа, PostgreSQL и Redis

Сессии, результаты ротации и WS-билеты Auth хранятся в [PostgreSQL](../modules/auth.md#хранение-сессий-в-postgresql--реализовано). Восстановление старой копии может вернуть отозванные сессии или использованные билеты. При неизвестной актуальности данных доступ не открывается: backend останавливается, старые сессии с результатами и билетами инвалидируются перед запуском с требованием нового входа. Процедура охватывает все процессы и исключает повторный возврат старых данных.

Это согласованные ограничения, а не готовый production-runbook. Административные операции реализованы; инструменты аварийной массовой инвалидации всех аккаунтов не реализованы. Очистка Redis не отзывает PostgreSQL-сессии.

## История диалогов — согласовано, не реализовано

Политика backup БД/независимого набора ключей, смена активного ключа после restore, проверка tag и критерии испытания описаны в [контракте Dialogs](../modules/dialogs/README.md#резервирование-и-аварийное-восстановление). Восстановление не продолжает прежний бюджет шифрования из старого snapshot; исторические ключи используются для чтения. Применяется обязательная инвалидация восстановленных Auth-сессий из этого документа. Клиентский кеш и позиции после SESSION_INVALID восстанавливаются по ссылке из frontend bootstrap. Эта ссылка фиксирует требования к будущим инструментам и не является отчётом об их наличии.

## Сохранность Redis

Redis хранит состояние доступности звонков и аренды, поэтому требуется постоянный том и `maxmemory-policy noeviction`. Лимит памяти задаётся с запасом для служебных операций и persistence. При нехватке памяти ошибка записи передаётся вызывающему модулю; успешное чтение само по себе не доказывает возможность записи.

Предложение для production: `appendonly yes`, `appendfsync always`, `no-appendfsync-on-rewrite no`. Это настройки сервера Redis, а не переменные backend. Стоимость синхронной записи нужно проверить нагрузкой. `everysec` допускает потерю последних записей и потому не принимается автоматически для отзывов доступа. RDB сам по себе не обеспечивает требуемую сохранность последних изменений. См. [официальное описание persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

Даже AOF не заменяет процедуру восстановления. Сохранность сессий и отзывов относится к PostgreSQL; восстановление Redis не возвращает Auth-сессии.

После аварийного восстановления нельзя немедленно доверять сохранённым блокировкам: порядок остановки процессов и ожидание истечения аренды определены в [RedlockModule](../modules/redlock.md). Репликация, Sentinel и автоматическое переключение узла в MVP не предусмотрены.

## Потеря аренд

После аварийного перезапуска Redis с возможной потерей lock-ключей все backend- и CLI-процессы, которые могли удерживать старую аренду, должны быть остановлены. До открытия доступа выдерживается как минимум максимальный срок аренды с запасом на дрейф. Это не отменяет уже отправленные записи: состояние частичных операций проверяется отдельно. При восстановлении старого снимка PostgreSQL дополнительно применяется описанная выше процедура инвалидации сессий.

## Частичные административные операции

Алгоритмы принадлежат [Auth](../modules/auth.md#последовательности-административных-операций): аккаунт, сессии и результаты ротации изменяются одной транзакцией PostgreSQL. Подтверждённый откат не оставляет частичного выполнения. При потере подтверждения COMMIT результат неизвестен, проверяется вручную; слепой повтор запрещён. CLI только создаёт администраторов и не восстанавливает прерванные административные операции. Устойчивый журнал и автоматическое продолжение не требуются.

## До production

Подготовить исполняемые команды инвалидации и проверки результатов, проверить восстановление на изолированной копии, определить ответственность за резервные копии PostgreSQL и Redis. Проверить нагрузку AOF и актуальность сохранённых отзывов. Численные бюджеты аренды берутся из контракта RedLock; параметры persistence — из Compose и этого документа.

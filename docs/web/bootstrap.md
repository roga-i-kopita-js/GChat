# Bootstrap Web и общий runtime

Принятый контракт запуска общего транспорта, платформенного хранения и синхронизации диалогов. Пользователь явно согласовал объём и решения. Экраны и правила переписки принадлежат [диалогам Web](dialogs.md), REST/WS DTO — [DialogsModule](../backend/modules/dialogs/README.md), действующие Auth/звонки — [Web](README.md). Существующий локальный экран выбора сервера iOS не заменяется.

## Что уже существует

NativeCore владеет Auth, регистрацией устройства и WSS; Web использует wsMessage/wsState/sendWsMessage и общий REST SDK с Auth-обёрткой. Браузерное владение WSS вынесено из GChatClient в shared/runtime/transport.ts. Bootstrap запускает общий транспорт и звонковый клиент выше маршрутов, без второго соединения. Клиентских ключей истории нет: шифрование и выдача содержимого принадлежат backend.

## Контракт runtime и хранения

### Объём и зависимости

реализовать один интерфейс диалогов для браузера и встроенного Web, включая текст, существующие стикеры, локальные черновики, ручной повтор отправок, историю, прочтение и обработку уведомлений. Native SQLite, обычная APNs-регистрация и новые bridge-команды требуют изменений iOS; одним Web-кодом эти требования не закрываются. Backend-доработка ограничена полями `peer_display_name` и `has_unread_messages` по [контракту владельца](../backend/modules/dialogs/README.md#имя-собеседника), затем регенерируется SDK. Значения не выводятся из административного API или сравнения sequence.

Порядок реализации: backend-поля и SDK → общий runtime и browser storage → Web UI → native storage/уведомления и Web-адаптер → платформенная приёмка. Промежуточная браузерная реализация не означает готовности iOS. До появления native storage v1 встроенный Web показывает недоступность чатов с предложением обновить оболочку; Auth, настройки и звонки сохраняют свою работоспособность. Отсутствие capability не трактуется как поломка SQLite и не инициирует fallback.

### Общий runtime и транспорт

`app/bootstrap` как единственный владелец runtime выше Routes. Он получает текущую Auth-сессию и передаёт зависимости в `shared`; общие модули не импортируют `features/auth` или Calls/Dialogs. Авторизованные REST-операции по-прежнему проходят через `features/auth/session.ts::request` и generated SDK. Bootstrap добавляет AbortSignal своего цикла к сигналу TanStack Query; сам не получает и не сохраняет refresh token.

| Фасад     | Предлагаемый интерфейс и ответственность                                                                                                                                     |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime   | `start(context)`, `getSnapshot()`, `subscribe(listener)`, `stop(reason)`; повторный start того же контекста не создаёт второй runtime, stop идемпотентен                     |
| Контекст  | `{serverOrigin, accountId, sessionId, deviceId, cycleId, signal}`; подтверждённая привязка устройства обязательна для сетевых операций диалогов                              |
| Снимок    | Отдельные состояния session, transport, storage и dialogs: `idle`, `starting`, `ready`, `error`, `stopped`; сетевое состояние транспорта — `offline`, `connecting`, `online` |
| Транспорт | `getSnapshot()`, `subscribeState(listener)`, `subscribeMessage(listener)`, `send(type, payload, signal)`; отписка снимает только подписку, а не соединение                   |
| HTTP      | Передаваемая bootstrap функция выполнения операции SDK; общий цикл отменяет запросы и запрещает применение запоздалых результатов                                            |
| Storage   | Фасад из следующего раздела; UI получает записи и состояния через TanStack Query, runtime инвалидирует запросы после сохранения                                              |

`sessionId`/`deviceId` получаются из действующей сессии/подтверждённой регистрации. Для native отдельный результат `getDialogStorageContext({cycleId})` → `{cycleId, accountId, sessionId, deviceId, namespaceId, epoch, adapterEpoch, schemaVersion: 1, adapter: 'sqlite' | 'indexeddb', purgePending, pendingWebPurges: accountId[]}`. Native вычисляет scope из своей сессии и выбранного сервера, проверяет текущий cycle; Web сверяет account/session с текущим Auth. Токены в ответ не входят. При смене сессии контекст недействителен независимо от живого WebView.

Из браузерного GChatClient в общий транспорт выносится владение WSS, регистрация устройства и reconnect. Сохраняются существующие `gchat-ws-owner`, refresh-lock `gchat-refresh`, канал безопасного состояния звонков и барьер `gchat-frontend-update`. Call engine использует транспорт, но продолжает владеть состоянием звонка и медиа. В native адаптер использует существующие `wsState`/`wsMessage`/`sendWsMessage`; `nativeCalls: false` не запрещает диалоги при доступном native WSS.

Browser-владелец WSS пересылает другим вкладкам только проверенные метаданные dialog-событий и состояние соединения в отдельном канале `gchat-dialog-events`, с server/account/session/device и epoch. Content и черновики через BroadcastChannel не передаются. Потерянное уведомление восстанавливается REST-сверкой; событие не считается сохранённым сообщением. Любая вкладка может читать REST и отправлять сообщения по своей действующей сессии, не открывая WSS или микрофон.

подписаться на события до начальной REST-сверки, объединяя пришедшие сигналы в dirty-флаги диалогов. Подготовка storage и REST не ждёт бесконечно WSS: после подтверждённого device binding разрешено показывать кеш и сверять REST при offline WSS. Reconnect запускает повторную сверку. Если binding ещё не подтверждён, показ кеша возможен после проверки сессии и барьера очистки, сетевые операции ожидают binding.

Каждый native foreground начинает новый существующий Web cycle: старые задачи отменяются, storage handles закрываются, выполняется повторная проверка сессии/очистки; это не logout и не повод удалить черновики. Browser-навигация не меняет цикл; смена аккаунта, сервера, сессии или адаптера инвалидирует прежние задачи. Поздний результат может соответствовать серверному commit, но не изменяет новый UI/storage.

### Storage v1: записи, операции и атомарность

одна схема версии 1 для IndexedDB и SQLite. Namespace — непрозрачный идентификатор области `(serverOrigin, accountId, deviceId)`, epoch — поколение данных этой области. Смена server/account/device выбирает другую область; logout/SESSION_INVALID увеличивает epoch и запрещает доступ к прежним поколениям. Все операции проверяют актуальную сессию, epoch и handle в момент commit, а не только до начала ожидания.

| Запись   | поля и ключ                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Диалог   | `dialog_id`, последний DialogDto и permissions с временем проверки; `revision` для CAS                                                                              |
| История  | MessageDto по `message_id`, уникальность `(dialog_id, sequence)` и `(dialog_id, sender_id, client_message_id)`                                                      |
| Sync     | `initialized`, `sync_sequence`, загруженные диапазоны `[first, last]`, `before_sequence`, `has_older`; диапазоны относятся к подтверждённым страницам, не к read/WS |
| Read     | Подтверждённые серверные позиции текущего epoch и кандидат прочтения; кандидат сам не становится серверной позицией                                                 |
| Черновик | `dialog_id`, `text`, монотонная `revision`; время изменения используется только для отображения                                                                     |
| Outbox   | `dialog_id`, `client_message_id`, исходный `content`, локальное время/порядок, состояние `prepared`/`sending`/`unknown`/`rejected`, безопасный код ошибки           |

| Операция         | Предлагаемый результат/транзакция                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `open`           | Проверить scope/epoch, очистку и schemaVersion; вернуть handle и adapterEpoch                                                                           |
| `readDialogs`    | Прочитать локальную страницу метаданных с limit/offset и revision                                                                                       |
| `readDialog`     | Прочитать метаданные, permissions, sync/read, черновик и outbox одного диалога; content истории выдаётся отдельной ограниченной страницей               |
| `readMessages`   | Получить локальную страницу по before/after, включая сведения о границах диапазона; максимум 100 сообщений и 512 КиБ сериализованного ответа            |
| `commitPage`     | Сохранить сообщения и доказанные границы страницы, обновить sync/old cursor и сопоставить outbox в одной транзакции с `expectedRevision`                |
| `commitMetadata` | Сохранить полученные DialogDto/permissions; read-позиции объединить максимумом в текущем epoch; серверный порядок списка не заменять локальным временем |
| `saveDraft`      | CAS по revision; при конфликте вернуть актуальный черновик, не затирать его без решения пользователя                                                    |
| `prepareSend`    | Атомарно сохранить ID/content в outbox и очистить только совпадающую revision черновика; при конфликте не начинать HTTP                                 |
| `markAttempt`    | Перед HTTP перевести запись в `sending`; после ошибки — `unknown` либо `rejected`, сохранив исходный content/ID                                         |
| `commitSent`     | Объединить подтверждённый MessageDto с outbox/историей в одной транзакции; отдельно не продвигать sync_sequence                                         |
| `confirmRead`    | Сохранить подтверждённые сервером позиции максимумом в текущем epoch; не менять sync_sequence                                                           |
| `close`          | Закрыть handle и запретить его последующее использование, не удалять данные                                                                             |
| `purge`          | Зафиксировать новое epoch/запрет старого, удалить записи прежнего поколения и вернуть состояние физической очистки                                      |

Для `commitPage` передаются направление `initial`/`before`/`after`, использованный курсор, messages и has_more. Адаптер проверяет текущую revision и курсор; конфликт возвращает `STORAGE_CONFLICT`, вызывающий перечитывание и повтор вычисления, без слепого применения старой страницы. После initial sync_sequence равен максимуму страницы или 0 для пустой. После after он продвигается только от ожидаемой сохранённой позиции; before меняет только старый курсор. Отдельно загруженный свежий хвост помечается диапазоном без продвижения прежнего sync_sequence. Пересекающиеся доказанные диапазоны объединяются, отсутствие соседних страниц не маскируется.

В IndexedDB операция commit — одна readwrite-транзакция по затронутым object stores, в SQLite — одна транзакция. Сетевые ожидания находятся снаружи. Browser-изменения координируются Web Lock `gchat-dialog-storage:<namespaceId>`; транзакционная CAS остаётся обязательной защитой. Native сериализует изменения namespace и выполняет ту же CAS. Уведомление о revision отправляется после commit, не до него. Читающая вкладка перечитывает storage; событие содержит только scope/epoch, dialog_id и revision.

Черновик сохраняется после 300 мс без ввода, а также перед переходом/отправкой и при уходе страницы в фон; UI различает «Сохраняется», «Сохранено» и ошибку. При закрытии/аварийном завершении гарантируется только уже подтверждённая запись. При конфликте вкладок ввод остаётся в памяти текущей вкладки, показываются действия «Загрузить сохранённый» и «Сохранить мой вариант»; последнее выполняет новую CAS. Молчаливого выбора по часам устройств нет.

Для текстового POST send обязателен успешный prepareSend и markAttempt. Для стикера prepareSend не очищает текстовый черновик; остальные гарантии те же. При перезапуске оставшиеся prepared/sending записи становятся unknown с ручным «Повторить», без автоматического HTTP. Ответ send и sync используют одну операцию объединения. При ошибке записи после успешного HTTP UI объясняет, что сервер подтвердил отправку, а локальное сохранение не завершилось; повторная синхронизация восстанавливает запись с тем же ID.

Миграции выполняются под storage-lock до выдачи handle, последовательно и транзакционно. Более новая неизвестная схема возвращает `STORAGE_VERSION_UNSUPPORTED` без удаления базы или downgrade. Для v1 не существует старой схемы сообщений; последующие миграции должны сопровождаться отдельным описанием преобразования и приёмкой.

### Native bridge для storage и постоянного fallback

Добавлены optional capability `dialogStorageVersion: 1`, `getDialogStorageContext` выше и отдельный метод плагина GChat `dialogStorage`. Это расширение GChat bridge, отдельное от device execute. Старые строгие схемы capabilities требуют предварительного обновления Web; порядок выпуска согласуется с существующим bridge-контрактом.

Запрос dialogStorage: `{version: 1, cycleId, operationId, namespaceId, epoch, adapterEpoch, command, args}`. `operationId` — UUID; command и args соответствуют таблице Storage v1. Ответ: `{version: 1, cycleId, operationId, data}`. Все DTO строго валидируются на обеих сторонах, лишние поля отклоняются. Native связывает namespace с собственной сессией, не доверяет переданному accountId/serverUrl. SQL, путь к базе и произвольные запросы через bridge не принимаются.

Безопасные коды: `STORAGE_UNAVAILABLE`, `STORAGE_FULL`, `STORAGE_CONFLICT`, `STORAGE_VERSION_UNSUPPORTED`, `STORAGE_STALE_CONTEXT`, `STORAGE_PURGE_PENDING`, `STORAGE_INVALID_ARGUMENT`. Произвольные SQLite-ошибки/пути/content в UI и диагностику не передаются. Превышение лимита страницы не обрезает сообщение, а заканчивает страницу перед ним; одно допустимое сообщение обязано помещаться. Изменяющие команды принимают до 100 сообщений и до 512 КиБ сериализованного запроса; при необходимости страницы дробятся без продвижения sync через несохранённую часть.

хранить native control metadata отдельно от SQLite в UserDefaults: выбранный adapter для установки приложения и origin сервера, adapterEpoch, epoch областей и задания очистки. Запись control metadata сериализована NativeCore и подтверждается до разрешения доступа к новому адаптеру. Здесь нет сообщений, черновиков и токенов. Browser хранит аналогичные поколения/задания очистки в отдельном IndexedDB control store; при недоступности control store чат показывает ошибку и не открывает кеш.

Fallback происходит только при `STORAGE_UNAVAILABLE` или `STORAGE_FULL` SQLite; ошибки версии, валидации, stale context и конфликты не переключают адаптер. Порядок:

1. Остановить новые chat-операции, отменить ожидания и закрыть старые handles. Native сериализованно увеличивает adapterEpoch; поздние команды прежнего адаптера больше не могут выполнить commit.
2. Открыть IndexedDB WebView и проверить запись в отдельной staging-области. Если она недоступна, показать ошибку хранения; звонок продолжается, состояние успешного fallback не показывается.
3. Если SQLite ещё читается, native выдаёт отдельный read-only migration handle замороженного snapshot; прежние Web handles остаются недействительными. Через `exportFallbackPage` последовательно перенести ограниченными страницами локальные записи, черновики и outbox в staging. Если прочитать полный согласованный snapshot нельзя, перенос не объявлять завершённым: сохранить лишь подтверждённые данные, доступные в текущем runtime. У всех незавершённых отправок сохранить исходный ID/content и состояние unknown. У неполной истории не переносить sync-позицию, как будто все связанные сообщения сохранены; восстановить её через начальную серверную страницу.
4. До открытия staging для UI native фиксирует постоянный выбор IndexedDB через control metadata; Web подтверждает promotion staging. При сбое между шагами следующий запуск завершает promotion по adapterEpoch, не возвращается к SQLite. Пока native-фиксация не подтверждена, новая отправка запрещена.
5. Доступные только в неисправной SQLite черновики/отправки не считаются перенесёнными; UI сообщает об их возможной недоступности. После переключения SQLite не подмешивается автоматически. Серверная история восстанавливается REST. Автоматического возврата, синхронизации двух баз или повтора отправок нет.

Для control metadata вводятся команды `beginFallback` (инвалидировать handles, выдать новый adapterEpoch и migration handle при доступности snapshot), `exportFallbackPage` (migration handle, cursor, limit; результат — ограниченная страница с nextCursor и has_more) и `selectIndexedDb` (зафиксировать выбор после готовности staging), доступные независимо от открытия SQLite через тот же dialogStorage. Повтор с тем же operationId возвращает тот же переход; повтор после перезапуска разрешается чтением control metadata. Ошибка control metadata блокирует переключение до повтора, а не включает временный fallback без сохранённого выбора. Признак выбора сохраняется при logout; другие серверы имеют собственный выбор. Удаление данных приложения ОС считается потерей локального состояния, после него история восстанавливается с сервера.

### Logout, отзыв сессии и обновление Web

перед завершением авторизованного цикла под общим storage-lock записывать tombstone нового epoch и задание очистки. Native обязан делать это самостоятельно при подтверждённом logout/отзыве сессии, включая отсутствие WebView; browser — перед удалением сохранённой сессии после подтверждённого logout, при SESSION_INVALID — немедленно. Если запись барьера невозможна, доступ к прежнему кешу закрывается, очистка считается незавершённой; успешная очистка не имитируется. Отказ сервера/временная ошибка logout сохраняет действующую Auth-сессию по её контракту.

Для подтверждения очистки IndexedDB Web удаляет записи каждого аккаунта из pendingWebPurges, включая прежний аккаунт при новом входе, и вызывает `completeIndexedDbPurge` с `{accounts: accountId[]}` после удаления и успешного открытия нового epoch; native сохраняет отдельное незавершённое задание Web-очистки, даже когда SQLite уже очищена.

После барьера UI, черновики в памяти, query cache и старые HTTP/handles закрываются во всех вкладках. Затем физически удаляются messages, metadata, ranges, read/sync, drafts и outbox старого epoch в обоих адаптерах. Если SQLite недоступна, native сохраняет purgePending вне неё и при первом успешном открытии сначала удаляет запрещённые поколения, до чтения/экспорта. Если WebView не запущен, очистка IndexedDB выполняется до первого chat-open следующего цикла. Состояние «физически очищено» возможно только после подтверждения обоих адаптеров; до этого показывается незавершённая очистка. После нового входа разрешён только новый пустой epoch, без доступа к прежнему кешу. Если нельзя достоверно прочитать контрольный барьер, чат заблокирован до восстановления control metadata.

Обычный foreground и перезагрузка не вызывают purge. Поколения server/account/device не смешиваются. Для отменённого запроса допустим старый серверный commit; после нового входа сообщение обнаруживается обычным REST.

включить операции storage и диалогов в существующий shared-lock `gchat-frontend-update`: после запроса обновления не начинать новые отправки, дождаться/завершить короткие локальные транзакции, уже начатые HTTP с неизвестным результатом оставить с прежним ID в outbox. После durable-сохранения отдать shared-lock; звонковый engine сохраняет действующую защиту незавершённого вызова. Ошибка сохранения задерживает обновление и показывает повтор; таймаут не объявляет транзакцию успешной. Миграция новой сборки начинается только после закрытия старых handles.

Пока приложение активно, native не показывает дополнительный системный баннер для уже открытой переписки, но передаёт событие для REST-сверки; в остальных состояниях показ зависит от разрешений ОС. optional capability `dialogNotificationsVersion: 1` и native-событие `dialogNotificationIntent: {cycleId, intentId, dialogId}`. Native устанавливает listener до webReady и доставляет не более одного последнего непотреблённого intent после синхронизации нового Web cycle. Intent хранится только в памяти NativeCore текущего запуска, привязан к серверу/аккаунту, сбрасывается при их смене/logout; холодный запуск берёт его из события нажатия ОС. ### Дополнительная приёмка решения

- Два окна одновременно сохраняют страницу/черновик: CAS исключает потерю записей, конфликт ввода разрешается явно; notification не заменяет чтение storage.
- Перезапуск между prepareSend/markAttempt/HTTP/commitSent восстанавливает тот же ID/content и не выполняет автоматическую отправку.
- Потеря WSS, событие во время начального sync и смена владельца не создают второго соединения и не пропускают REST-сверку.
- Отказ SQLite на чтении, записи и во время переноса; перезапуск до/после фиксации выбора; отказ IndexedDB/control metadata; поздний commit прежнего adapterEpoch.
- Logout без WebView и SESSION_INVALID при недоступной SQLite закрывают старое epoch; очистка повторяется до доступа к старой базе, её статус не выдаётся за успешный заранее.
- Старая/новая схема и несколько вкладок при обновлении не выполняют миграции поверх активных handles; работающий звонок продолжает защищать обновление.
- Web Push и native intent проверяются для открытого окна, login, холодного запуска, смены аккаунта, повторного нажатия и неизвестного диалога. Настоящая доставка и iPhone принимаются отдельно от unit-тестов.

## Отправка до первого входа получателя

Backend принимает разрешённое сообщение до первого входа получателя. Получатель после авторизации загружает историю через REST, без присутствия отправителя и ключей прежнего устройства. Системные push являются best-effort дополнением; потеря уведомления не мешает сверке при входе/reconnect. Их payload и раскрытие текста принадлежат [контракту backend](../backend/modules/dialogs/README.md#уведомления).

## Открытые решения

В принятом объёме открытых проектных решений нет. Реальная доставка push, физический iPhone и сценарии отказов являются критериями приёмки, а не неподтверждёнными гарантиями.

# Bootstrap Web и общий runtime

Проект отдельного bootstrap фронтенда для общего транспорта, платформенного хранения и синхронизации диалогов. Текущие контракты — [Web](README.md), [device bridge](device-bridge.md), [Dialogs](../backend/modules/dialogs/README.md). Экраны, отправка, клиентское прочтение и алгоритм синхронизации проектируются в [диалогах Web](dialogs.md). Существующий локальный iOS-экран выбора сервера `gchat-bootstrap://localhost/server` не заменяется: здесь описан запуск основного Web после выбора сервера.

Пользователь согласовал разделение: по общему WSS приходят уведомления о новых сообщениях и изменении прочтения; список, история и подтверждение прочтения используют REST. Это заменяет прежнее требование передавать все операции чата через WSS bridge. Подготовка runtime выполняется отдельным frontend bootstrap; выбор хранилища через bridge зависит от платформы: IndexedDB в браузере, нативная SQLite на iOS. Согласовано серверное шифрование: клиент получает разрешённую историю через sync и не генерирует ключи чата. Документ остаётся draft до завершения интерфейсов runtime и локального кеша; код не реализован.

## Что уже существует

- NativeCore владеет авторизацией, регистрацией устройства и общим WSS, независимо от монтирования Web. Web имеет `sendWsMessage` и подписку на `wsMessage` с изоляцией по cycleId.
- `sendWsMessage` подтверждает постановку в сокет, а не результат backend. Ответ backend приходит отдельно; будущий общий транспорт должен связывать его с request_id.
- Device bridge выбирает browser/native адаптер до React и имеет фиксированный список команд. Нового хранилища ключей чата не требуется; локальный кеш и позиции sync ещё не реализованы.
- В автономном браузере жизненный цикл звонкового клиента пока запускается из CallsProvider. Нельзя подключить чат вторым независимым WebSocket и считать его общим транспортом.

## Предлагаемые границы

`app/bootstrap` координирует запуск, но не хранит состояние звонка и не заменяет Auth. Общий транспорт и платформенные адаптеры находятся в `shared`, разделы Calls/Dialogs используют их. Общие модули не импортируют разделы приложения.

Предлагаемые фасады, не существующее API:

- HTTP API — существующий генерируемый backend-api через Auth request-обёртку, с AbortSignal текущего цикла;
- Подписка WSS — разрешённые уведомления текущего сеанса без содержимого сообщения;
- `storage` — локальные операции хранения с browser/native адаптером и строгой областью server/account/device;
- `bootstrap` — readiness, восстановление и остановка текущего runtime при смене сессии.

В native уведомления приходят через существующий wsMessage. История/список и подтверждение прочтения выполняются по HTTPS через существующие `features/auth/session.ts` и SDK: Auth/refresh остаются у native, обёртка получает access token через runtime и выполняет обычный HTTP-запрос. Native-плагин для нового HTTP-транспорта не создаётся. REST-чтение истории теперь разрешено этим решением, а не является обходом ранее требовавшегося WSS.

В браузере сохраняется один общий WSS с существующей моделью Web Locks; REST не открывает отдельный WebSocket. Смена транспорта чтения не включает browser call engine в native. Локальный кеш и WS-подписка остаются разными возможностями; клиентские криптографические операции не добавляются.

## Порядок запуска

1. Определить платформенный адаптер и выбранный сервер. Auth/WSS-адаптер сохраняет действующие правила; для локального хранения предусмотрен согласованный fallback из SQLite в IndexedDB WebView при недоступности нативного хранилища.
2. Восстановить сессию существующим Auth. До входа bootstrap чата не запрашивает историю.
3. Получить готовый общий WSS и подтверждённую привязку устройства. Native владеет этим процессом; Web не запускает повторную регистрацию от своего имени.
4. Открыть локальный кеш текущих server/account/device. При ошибке показать состояние ошибки, не подмешивать чужие данные и не считать позицию sync сохранённой.
5. Получить список диалогов и синхронизировать переписку с локальной позиции. Backend проверяет права и возвращает содержимое через REST; клиенту не нужны ключи истории.
6. Сохранять полученные записи и позицию согласованно, объединять повторы по ID. На первом устройстве загружать разрешённую историю с сервера, не обращаться к прежнему устройству.
7. Подписаться на dialog.messages_available для REST sync и dialog.read_updated для обновления галочек по [контракту Dialogs](../backend/modules/dialogs/README.md#статусы-сообщений). last_sequence события не становится локальной позицией до успешной загрузки и сохранения. Повторять сверку после reconnect/foreground независимо от получения события.

Согласовано: вся старая история заранее не скачивается. При пустом кеше сначала загружается последняя страница; более старые — при прокрутке вверх. Хранилище должно различать загруженные диапазоны, курсор старой истории и позицию получения новых сообщений; точный алгоритм проектируется в [диалогах Web](dialogs.md#история-и-синхронизация--предложение-алгоритма).

Пользовательские экраны используют состояние runtime, а не запускают подготовку заново при каждом переходе. Сессия, транспорт, локальное хранилище и чат имеют отдельные состояния готовности. Ошибка хранения чата не блокирует вход или работающий звонок; UI диалога показывает загрузку/ошибку и повтор. Асинхронная подготовка не означает гарантированной работы после закрытия вкладки или приостановки приложения iOS.

Переход в другой раздел не закрывает WSS. Logout, смена аккаунта/сервера и новый cycle отменяют старые ожидания и задачи; поздний результат не записывает данные новому пользователю. Reconnect повторяет синхронизацию, не создаёт второй runtime. Работающая сессия не получает параллельные bootstrap; вкладки согласуют общий транспорт и не теряют локальную позицию из-за конкурентного сохранения.

## Принятые границы интеграции Dialogs

[Backend-контракт Dialogs](../backend/modules/dialogs/README.md) accepted, серверный модуль реализован. Семантика галочек, точные REST/WS DTO, состав стикеров и системные push приняты; они не являются открытым выбором bootstrap. Клиент сам определяет прочтение и передаёт позицию через REST. После reconnect обе позиции из DialogDto обновляют галочки старых сообщений без повторного скачивания истории; они не заменяют локальную позицию sync. Правило видимости сообщений для прочтения предлагается в [клиентском проекте](dialogs.md#прочтение--предложение-правила-видимости).

Согласована очистка после отзыва сессии: SESSION_INVALID завершает текущий цикл аккаунта; после нового входа прежний кеш сообщений и позиции sync/read этого аккаунта очищаются до повторной загрузки с сервера. Максимум read-позиций применяется только в текущем авторизованном цикле. Это защищает от продолжения по позициям, опережающим восстановленную БД. Для обычного добровольного logout пользователь также согласовал физическую очистку кеша сообщений и позиций. Точный механизм хранения/удаления в адаптерах ещё проектируется.

Нажатие chat push передаёт безопасный intent dialog_id без текста и credentials; обработка восстановления сессии/смены аккаунта и source URL следует [контракту уведомлений](../backend/modules/dialogs/README.md#уведомления). Принятый intent не подтверждает прочтение автоматически. Реализация bridge/worker и обработчика навигации отсутствует.

## Предложение по хранению

В bootstrap чата нет генерации, публикации, восстановления или локального хранения ключей истории. Серверные ключи остаются на backend. Существующие Auth и Keychain native-сессии сохраняют собственный контракт; новый универсальный API чтения секретов не вводится.

Согласовано: хранилище выбирается по платформе через bridge. В автономном браузере используется IndexedDB через browser-адаптер; при нативной работе на iOS основное хранилище — SQLite в нативной части приложения с доступом из Web через bridge. При недоступности нативного хранилища клиент переключается на IndexedDB внутри WebView и сохраняет данные в приложении. Сообщения, позиции sync/read, черновики и незавершённые отправки используют единый интерфейс storage, экраны не выбирают технологию хранения самостоятельно. Сессия и токены сохраняют действующий контракт Auth/Keychain; fallback хранения не переключает Auth/WSS в браузерный режим.

Это согласованное направление расширения bridge, а не уже существующие команды. Точные имена, аргументы, результаты, ошибки, транзакции, миграции схемы и жизненный цикл хранилища ещё требуется описать и согласовать. Изоляция server/account/device и отмена операций прежнего цикла обязательны в обоих адаптерах. Fallback должен сохранять сообщения, позиции, черновики и незавершённые отправки в IndexedDB, а не только в памяти текущего WebView. Недоступные записи SQLite не считаются перенесёнными: серверная история доступна для повторной загрузки, но локальные черновики и неподтверждённые отправки могут оставаться только в прежнем хранилище.

Согласовано: после fallback приложение постоянно остаётся на IndexedDB WebView, включая последующие запуски. Автоматического возврата в SQLite и последующей синхронизации между локальными базами нет. Выбор должен сохраняться между запусками; его технический маркер относится к конфигурации хранилища, а не к сообщениям аккаунта. Синхронизация сообщений с backend по REST сохраняется.

Открытые детали fallback: механизм сохранения выбора, обработка доступных локальных данных в момент однократного переключения и защита от поздних записей прежнего адаптера. Требуется определить восстановление операций с неизвестным результатом и очистку обоих хранилищ при logout/SESSION_INVALID, включая недоступную в момент выхода SQLite. Записи прежней SQLite не подмешиваются автоматически после её восстановления. Пока эти детали не согласованы, переключение не считается готовым к реализации.

Согласовано локальное сохранение черновиков каждого диалога при переходах и перезагрузке приложения с физической очисткой при logout; поведение описано в [диалогах Web](dialogs.md#навигация-и-экраны--предложение). Storage-фасад должен поддерживать это хранение с изоляцией server/account/device. Конкретные операции и согласование изменений между вкладками ещё проектируются.

Также согласовано сохранение отправок с неизвестным результатом для ручного повтора после перезапуска с прежними client_message_id и content, без автоматической отправки. Клиентское поведение принадлежит [контракту отправки](dialogs.md#отправка--предложение-клиентского-поведения); storage-фасад должен обеспечить восстановление таких записей. Точный механизм сохранения до HTTP-запроса и восстановления прерванных попыток ещё проектируется.

[Браузерное хранилище](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) может быть очищено пользователем или вытеснено. После потери кеша в любом адаптере серверная история восстанавливается после входа и проверки прав. Очистка не удаляет переписку на сервере. Локальные черновики и незавершённые отправки без серверного commit не восстанавливаются с сервера.

Кеш содержит чувствительное содержимое, поэтому изолируется по server/account/device и не попадает в логи или диагностику. При logout runtime немедленно закрывает доступ к кешу, сбрасывает UI и отменяет запросы, затем физически удаляет сообщения и позиции sync/read. Выбор очистки согласован; реализация должна определить межвкладочный барьер и обработку отказа удаления, не позволяющие открыть прежний кеш после нового входа до завершения очистки. Смена аккаунта не читает прежний namespace. Серверный запрет не может дистанционно отозвать уже скачанные записи.

## Отправка до первого входа получателя

Согласовано серверное шифрование вместо E2EE. Сервер принимает разрешённое сообщение активному получателю до его первого входа, шифрует для хранения и после авторизации получателя выдаёт content через REST sync. Подключение отправителя и наличие прежнего устройства получателя не требуются. Отдельное состояние «ждём публичный ключ» и фоновая криптографическая подготовка клиента не нужны.

Контроль доступа к серверной выдаче и разрешённым метаданным сохраняется. Оператор с серверными ключами имеет технический доступ к содержимому; обычный admin вне диалога не получает пользовательский API истории. Полная модель безопасности — в [DialogsModule](../backend/modules/dialogs/README.md#серверное-шифрование-и-ключи).

Согласованы системные push с текстом сообщения в body; для стикера — «Стикер», длинный текст может сокращаться. Показ при свёрнутом/закрытом приложении зависит от разрешений и возможностей платформы. Системное push до первого запуска/регистрации устройства не гарантируется: адреса APNs/Web Push может не быть; при входе сообщение обнаруживается через sync. Полный контракт раскрытия текста и проверки доступа — в [DialogsModule](../backend/modules/dialogs/README.md#уведомления). Push чата отправляется best-effort после сохранения, без устойчивой очереди/повторов; потеря push не должна мешать обнаружению сообщений через REST при входе/reconnect. VoIP push для чатов не используется. Для native обычная APNs-регистрация и её bridge-интеграция ещё не реализованы.

## Критерии приёмки

- Один общий WSS обслуживает звонки и уведомления чата без передачи содержимого переписки; история/список читаются через REST. Native продолжает владеть Auth/WSS; браузер сохраняет одного владельца между вкладками.
- REST-запросы используют текущую Auth-обёртку, generated SDK и отмену старого цикла; WS передаёт только метаданные новых сообщений/прочтения по принятому DTO, без content. Потеря/повтор события восстанавливаются через REST sync, без ложного продвижения позиции.
- Bootstrap идемпотентен для текущей сессии и не перезапускается от навигации; reconnect/foreground продолжают синхронизацию без второго транспорта.
- Потеря кеша не уничтожает серверную историю; после входа он восстанавливается через sync с текущими правами. Данные разных серверов/аккаунтов не смешиваются.
- Browser-адаптер хранит данные диалогов в IndexedDB, native-адаптер на iOS — в нативной SQLite через bridge. При недоступности SQLite выполняется постоянный переход в IndexedDB WebView с сохранением данных и выбора хранилища после перезапуска, без автоматического возврата и синхронизации двух локальных баз; работающий звонок продолжается. Одни экраны работают с общим storage-интерфейсом; native Auth/Keychain сохраняет действующий контракт. Смена storage-адаптера не смешивает namespace и не позволяет поздним операциям прежнего адаптера откатить данные.
- Поздний результат старого cycle не меняет состояние и хранилище новой сессии. Ошибка чата не останавливает текущий звонок.
- При первом входе получатель читает ранее отправленное сообщение с отправителем офлайн. Клиент не генерирует ключи чата и не получает серверный ключ шифрования.

## Открытые решения

1. Точный контракт storage-команд bridge и адаптеров: атомарное сохранение страниц/позиций, черновиков и незавершённых отправок, миграции схемы, ошибки и барьер физической очистки при logout/SESSION_INVALID. Выбор IndexedDB для браузера и нативной SQLite через bridge для iOS с постоянным fallback в IndexedDB WebView согласован; физическая очистка при logout также согласована. Автоматического возврата и синхронизации локальных баз нет. Механизм однократного переключения, сохранения выбора, обработки доступных локальных данных и очистки недоступного хранилища ещё проектируется. Хранение клиентских ключей истории исключено из проекта.
2. Точные интерфейсы общего runtime и WS-подписки, REST-интеграция с текущим SDK/Auth и сохранение Web Locks/барьера обновления. Выбор платформенного хранения согласован, но готовность его интерфейсов и наличие реализации из этого не следуют.
3. Техническая регистрация/обработка системных уведомлений и их интеграция с runtime после регистрации устройства. Наличие push с текстом сообщения уже согласовано; системное поведение iOS не выводится из наличия WSS.

Backend-контракт согласован и больше не является открытым выбором bootstrap; управление серверными ключами принадлежит backend-контракту. Документ остаётся draft до завершения профильных интерфейсов. Для документации выполняются `pnpm docs:check` и проверка diff; код здесь не добавлен.

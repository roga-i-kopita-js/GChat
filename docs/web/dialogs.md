# Диалоги в Web

Принятый клиентский контракт на основе [требований диалогов](../product/dialogs.md) и принятого [DialogsModule](../backend/modules/dialogs/README.md). Документ описывает будущий Web UI в браузере и native WebView; готовность backend не означает наличия клиентской реализации. Пользователь явно согласовал клиентские решения и визуальный референс. Согласованные продуктовые правила и API этим проектом не меняются.

Общий runtime, платформенные адаптеры и остановка сессии принадлежат [bootstrap](bootstrap.md). Действующие маршруты, Auth, звонки и обновления — [контракту Web](README.md). Этот документ владеет экранами диалогов, состояниями отправки, клиентским прочтением и правилами синхронизации переписки.

Для визуального согласования подготовлен [интерактивный макет](../design/dialogs.html). Все операции в нём демонстрационные; цвета, геометрия и типографика приняты с уточнениями ниже. Переключатели формата и состояния находятся вне интерфейса приложения и служат просмотру макета.

## Границы

Согласованы диалоги 1х1, текст, фиксированный набор стикеров, отдельная кнопка переписки у контакта и раздел «Диалоги» в нижнем меню. Одна пара аккаунтов имеет один диалог независимо от групп. Клиент получает разрешённое содержимое через HTTPS REST; общий WSS несёт уведомления. Клиент не создаёт ключей истории, не выполняет E2EE и не получает серверные ключи.

Файлы, голосовые сообщения, реакции, отдельный emoji picker, групповые чаты, редактирование, удаление и поиск по тексту не входят в объём. Бессрочное серверное хранение и текущие проверки доступа задаёт backend. Локальный кеш восстанавливается с сервера и не является резервной копией.

## Навигация и экраны

Маршруты `/dialogs` и `/dialogs/:dialogId` согласованы пользователем, включая прямые ссылки, перезагрузку и историю браузера. Все адреса ниже относительны к существующему basename; в серверном размещении перед ними стоит `/apps/client`. Маршруты реализованы в основном React Router.

| Адрес                | Поведение                                                  |
| -------------------- | ---------------------------------------------------------- |
| `/dialogs`           | Список собственных диалогов; требуется сессия              |
| `/dialogs/:dialogId` | Переписка; требуется сессия и серверная проверка контекста |

«Диалоги» доступны всем авторизованным пользователям в нижнем меню. Пользователь согласовал навигацию как в Telegram: на телефоне список и переписка — отдельные экраны, «Назад» возвращает к списку. Согласовано сохранение положения прокрутки списка при возврате из переписки; при прямом открытии переписки возврат ведёт на `/dialogs`. Для ПК согласована боковая панель со списком диалогов и открытая переписка рядом; переход между диалогами сохраняет панель списка. На ПК без выбранной переписки согласовано пустое состояние: список диалогов слева, справа — «Выберите диалог»; переписка автоматически не выбирается. Точная геометрия задана ниже. Список и выбранная переписка восстанавливаются при перезагрузке и навигации истории браузера. Текст, черновики и credentials в URL не включаются.

Кнопка переписки у контакта выполняет `POST /dialogs` с `peer_id`, затем открывает возвращённый `dialog_id`. Она не запускает звонок. Повторное нажатие во время запроса объединяется с текущей попыткой. Из списка уже существующий диалог открывается через GET, без повторного POST: право чтения может сохраняться при запрете создания/отправки.

Входящий звонок остаётся глобальным и доступным поверх переписки. Переходы между разделами не перезапускают общий runtime, не закрывают WSS и не прерывают разговор. Согласовано: набранный текст сохраняется отдельно для каждого диалога при переходах и после перезагрузки приложения. Черновики хранятся локально в изолированной области server/account/device, не отправляются на сервер и очищаются при выходе из аккаунта. Операции хранения и межвкладочное согласование заданы в bootstrap.

### Список

Серверные и локально сохранённые диалоги объединяются по `dialog_id`. Порядок следует серверной активности: последнее сохранённое сообщение, для пустого диалога — создание; дополнительный порядок по ID задаёт сервер. Черновик, открытие, локальная отправка без подтверждения и reconnect не поднимают строку.

состав строки: имя собеседника, аватар, время серверной активности, состояние доступности. Согласовано: список диалогов не показывает предпросмотр сообщений — ни текст, ни подпись последнего стикера; наличие локально загруженной истории это правило не меняет. История каждого диалога ради заполнения списка не загружается.

Согласовано: аватар — цветной круг с инициалами собеседника; загрузка и отображение фотографий в этот объём не входят. Палитра и геометрия заданы ниже. Согласованное поле `peer_display_name` во всех ответах с диалогом описано в [контракте владельца](../backend/modules/dialogs/README.md#имя-собеседника): актуальное имя доступно участнику, включая собеседника вне текущих контактов, запрет чтения истории и отключённого peer. Поле реализовано и включено в generated SDK.

Согласовано: числовой счётчик непрочитанных не нужен, достаточно индикатора их наличия. Для него согласовано поле `has_unread_messages` в DialogDto по [контракту backend](../backend/modules/dialogs/README.md#наличие-непрочитанных); поле реализовано и включено в SDK. Клиент не скачивает историю ради индикатора и не заменяет поле сравнением `last_sequence > last_read_sequence`, которое может включать собственные сообщения. Значение обновляется через REST после событий новых сообщений/прочтения и при сверке; поздние ответы не должны возвращать индикатор для уже подтверждённого прочтения. Индикатор задан ниже.

Первая страница запрашивается с начала; следующая — с offset, увеличенным на фактически полученное число записей. Из-за перестановок при новых сообщениях страницы объединяются по ID, обновление перечитывает начало. Пустая очередная страница не удаляет локальные строки. Свежесть серверных метаданных и наличие локальной истории отображаются раздельно.

### Переписка

Шапка содержит собеседника и возврат; лента — сообщения по возрастанию `sequence`, время и состояния собственных отправок. Внизу расположены многострочное поле, кнопка стикеров и отправка. Кнопка стикеров находится справа от поля ввода, перед кнопкой отправки; в макете предложена иконка улыбающегося лица. Пустой диалог показывает приглашение написать; отсутствие истории при ошибке не выдаётся за пустой диалог.

Согласовано: при открытии диалога сразу показываются последние сообщения, более старые подгружаются при прокрутке вверх. Загрузка предыдущих сообщений сохраняет видимый якорь и не сдвигает ленту вниз. Также согласовано: если пользователь уже внизу, новое сообщение автоматически показывается с прокруткой к нему; при чтении старой истории положение ленты сохраняется и появляется кнопка перехода к новым сообщениям. Получение страниц и изменение галочек не отбирают фокус у поля ввода.

Состояния экрана различаются: загрузка, пустая переписка, доступная история, загрузка предыдущей страницы, ошибка синхронизации с повтором, запрет чтения, запрет отправки, недоступный контекст. При `can_read=true`, `can_send=false` история доступна, поле отправки заменяется объяснением запрета. Согласовано: при `can_read=false` ранее скачанные сообщения текущего аккаунта продолжают отображаться из локального кеша вместе с разрешёнными метаданными и объяснением ограничения. Серверная история и её незагруженные страницы не запрашиваются до восстановления доступа; при отсутствии кеша показываются метаданные и состояние ограничения, а не пустая переписка. Просмотр локального кеша не обходит запрет REST read и не подтверждает серверное прочтение. При неизвестных permissions поле отправки заблокировано. Правила logout/SESSION_INVALID и изоляции аккаунтов сохраняются: решение не разрешает доступ к кешу после выхода или другому аккаунту.

Мобильные размеры, области нажатия и плотность следуют [правилам дизайна](../design/README.md#мобильный-приоритет-веб-интерфейса). Лента, поле и меню учитывают safe area и экранную клавиатуру без перекрытия последнего сообщения. Элементы доступны с клавиатуры, состояния отправки имеют текстовые подписи для assistive technology. На время IME composition Enter не отправляет сообщение. Пользователь согласовал для ПК: Enter отправляет сообщение, Shift+Enter добавляет перенос строки. Для телефона согласованы перенос строки по Enter на экранной клавиатуре и отправка отдельной кнопкой.

Согласовано использование системной клавиатуры при вводе в браузере и native WebView; собственная экранная клавиатура не создаётся. Unicode emoji вводятся системной клавиатурой, набор стикеров GChat остаётся отдельной панелью справа от поля ввода.

## Интеграция с backend

Точные DTO, маршруты, статусы, числовые диапазоны и лимиты принадлежат [публичному API DialogsModule](../backend/modules/dialogs/README.md#публичный-api). Клиент использует существующий generated SDK через общую Auth-обёртку и отмену запросов прежнего цикла. Таблица ниже определяет использование API, не вводя новых endpoint.

| Действие клиента                                           | Операция backend                         |
| ---------------------------------------------------------- | ---------------------------------------- |
| Открыть переписку из контакта                              | `POST /dialogs`, затем переход по ответу |
| Загрузить/обновить список                                  | `GET /dialogs`                           |
| Прямой переход, обновление метаданных и галочек            | `GET /dialogs/:dialog_id`                |
| Проверить доступные действия                               | `GET /dialogs/:dialog_id/permissions`    |
| Получить хвост, старые либо пропущенные сообщения          | `GET /dialogs/:dialog_id/messages`       |
| Отправить текст/стикер или разрешить неизвестный результат | `POST /dialogs/:dialog_id/messages`      |
| Подтвердить увиденное                                      | `POST /dialogs/:dialog_id/read`          |

Permissions возвращаются в отдельном объекте `dialogs`, отсутствуют в DialogDto и не резервируют право операции. Каждая отправка и страница заново проверяются сервером. Обычный пользователь без общей группы может читать диалог с активным admin, но не отвечать; отключённому собеседнику отправка запрещена. Полная [матрица доступа](../backend/modules/dialogs/README.md#доступ) остаётся единственным источником правил.

## Отправка

Для новой логической отправки создаётся UUID `client_message_id` штатным браузерным API. ID и исходный content фиксируются до HTTP-запроса; повторы используют ту же пару. Редактирование уже начатой отправки не изменяет её payload: сервер возвращает первоначально сохранённый content даже при отличающемся теле повтора.

| Локальное состояние  | Значение и действие                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------- |
| Подготовлено         | ID/content сохранены локально; запрос ещё не начат                                                            |
| Отправляется         | Запрос выполняется; галочки нет                                                                               |
| Результат неизвестен | Ответ потерян, запрос отменён после начала либо результат commit неизвестен; доступен повтор с прежним ID     |
| Отклонено            | Получена ошибка текущей попытки; причина показана, прежний ID сохраняется для повтора неизменённого сообщения |
| Сохранено            | Получен серверный MessageDto через ответ либо sync; одна галочка                                              |
| Прочитано            | Подтверждена позиция получателя; две галочки                                                                  |

Пользователь согласовал: отправка с неизвестным результатом сохраняется локально и после перезапуска показывается с действием «Повторить». Повтор выполняется вручную с прежними client_message_id и content, без автоматической отправки. Если sync уже обнаружил сохранённое сообщение, локальная запись заменяется подтверждённой и повтор больше не требуется.

Для обеспечения этого поведения сохранять незавершённые отправки в том же изолированном хранилище до начала запроса. При ошибке сохранения запрос не начинается. Logout очищает и эти записи. Это не отменяет возможный серверный commit; после нового входа сохранённое обнаруживается через sync. Операции хранения и восстановление прерванного запроса заданы в bootstrap.

HTTP 201 и 200 подтверждают сохранение одной логической отправки. Ответ либо sync заменяет локальную запись серверной по `(dialog_id, sender_id, client_message_id)`; серверные сообщения объединяются по `message_id`. Ответ отправки может прийти позже WS/sync и не должен создавать второй пузырёк. Новый пользовательский ввод получает новый ID, даже при совпадении текста.

Текст проверяется по серверным правилам: непустой, не только пробелы, до 4000 Unicode code points, без непарных surrogate; исходные пробелы и переносы непустого текста сохраняются. Дополнительно учитывается бюджет сериализованного тела 65536 байт UTF-8. Серверные `fields` показываются у поля. HTML из текста не исполняется; сообщения выводятся безопасным текстом.

Стикеры берутся из уже подготовленного `@gchat/dialog-assets`; состав, лицензия и стабильные IDs принадлежат [каталогу backend](../backend/modules/dialogs/README.md#каталог-стикеров-и-unicode). Web распространяет изображения с собственного origin. Неизвестный ID из истории отображается как «Стикер»; URL из сообщения не загружается. Критерии визуальной приёмки панели заданы ниже.

## История и синхронизация

У каждого диалога раздельно хранятся:

- `sync_sequence` — позиция для загрузки новых сообщений после сохранённой начальной последней страницы; она не означает, что скачана вся история от позиции 0;
- границы загруженных диапазонов и курсор подгрузки более старой истории;
- серверные `last_sequence`, `last_read_sequence`, `peer_last_read_sequence`;
- незавершённые локальные отправки.

Согласовано: всю старую историю заранее не скачиваем. На новом/очищенном кеше загружается последняя страница, более ранние страницы — при прокрутке вверх. В кеше остаются последние сообщения, полученные новые и страницы, загруженные пользователем. Фоновое восстановление истории от позиции 0 исключено. Отсутствующие старые сообщения доступны с сервера при наличии сети и текущего права чтения; их отсутствие в кеше не означает удаления на сервере.

Алгоритм: начальная последняя страница атомарно сохраняется вместе с её диапазоном и `sync_sequence`, равным максимальному sequence этой страницы; для пустого диалога — 0. Далее позиция продвигается только последовательными сохранёнными страницами `after_sequence`. Read sequence, WS watermark, последний видимый пузырёк и отдельный ответ отправки её не заменяют. Курсор старой истории движется независимо через `before_sequence`. При повторном открытии существующего кеша отдельный свежий хвост не позволяет перескочить пропуск после прежней sync-позиции; диапазоны должны хранить такой разрыв до его загрузки.

1. После сессии и device binding получить list/get и permissions; для разрешённого диалога открыть кеш и показать доступные локальные записи с состоянием актуальности.
2. Последнюю страницу запросить без before/after; предыдущие страницы — с `before_sequence` минимальной полученной позиции. Эти ответы приходят от новых к старым и перед показом упорядочиваются по sequence.
3. Новые сообщения и пропуски после сохранённой sync-позиции получать через `after_sequence=sync_sequence`; ответ приходит по возрастанию. Сообщения и продвижение позиции сохраняются атомарно. После ошибки записи позиция остаётся прежней. При `has_more=true` продолжать от последней сохранённой позиции, независимо от числа записей: страница может быть короче limit из-за байтового бюджета. Более раннюю историю до начальной страницы эта задача не запрашивает.
4. `dialog.messages_available` объединять в одну задачу sync диалога. Событие содержит только ID и watermark; его получение не создаёт сообщение и не подтверждает прочтение.
5. После reconnect, foreground и открытия экрана сверять REST даже без событий. Согласовано: при возвращении в GChat новые сообщения загружаются сразу, без ожидания 30-секундного таймера и независимо от положения прокрутки. Загрузка сохраняет согласованное поведение ленты и сама по себе не подтверждает прочтение. Дополнительно к WS-уведомлениям открытый видимый раздел диалогов сверяется с сервером раз в 30 секунд; в фоне таймер останавливается. Незавершённая сверка не дублируется. Общий планировщик учитывает лимиты аккаунта и приоритет открытой переписки перед фоновой загрузкой остальных.
6. Повторные/поздние ответы объединять по ID в текущем cycle. Ошибка одного диалога не останавливает звонки и другие разрешённые диалоги.

Синхронизация и пагинация одного диалога сериализуют запись через общий storage-фасад. Конкурентные вкладки не могут откатить позицию либо сохранить её без соответствующих сообщений. Блокировки и интерфейс фасада заданы в bootstrap; отдельный WSS не создаётся.

## Прочтение

Серверная семантика и DTO определены в [статусах сообщений](../backend/modules/dialogs/README.md#статусы-сообщений). Согласовано: сразу после открытия диалога и загрузки последних сообщений клиент подтверждает прочтение до последнего загруженного сообщения включительно. Все более ранние сообщения также считаются прочитанными, без прокрутки и загрузки всей старой истории. Push и фоновая загрузка сами по себе прочтением не считаются; две галочки показываются после серверного подтверждения прочтения.

Согласовано для ПК: прочтение подтверждается только в активном окне GChat; при переключении в другое приложение подтверждение не отправляется, даже если переписка остаётся видимой. При открытии используется максимальный sequence загруженной последней страницы, а не last_sequence из WS или метаданных без загрузки сообщений. Для пустой истории продвижения нет. Подтверждение при открытии не ждёт прокрутки или отдельного таймера видимости. Открытая панель списка и push сами по себе не подтверждают прочтение.

Включение предшествующих сообщений соответствует семантике backend и согласовано пользователем. Оно не продвигает sync-позицию и не запускает скачивание всей истории. Для уже открытого диалога согласовано: при чтении старой истории новые сообщения остаются непрочитанными до перехода к ним; если пользователь находится внизу активной переписки, новые сообщения подтверждаются прочитанными сразу после загрузки и показа. Получение нового сообщения не возвращает пользователя из старой истории к концу ленты автоматически.

При возвращении в GChat и восстановлении активности уже открытого диалога согласовано то же правило: новые сообщения загружаются сразу; если пользователь внизу, прочтение подтверждается после загрузки и показа. Если сохранена прокрутка к старой истории, новые сообщения остаются непрочитанными до перехода к ним. Возвращение активности не считается повторным открытием диалога с безусловным прочтением последней страницы.

Подтверждение при открытии отправляется сразу после загрузки страницы при росте позиции и наличии права чтения. Для новых сообщений внизу активной переписки также не вводится отдельный таймер ожидания видимости. Механизм объединения подтверждений и лимитов задан ниже; отправляется максимальная подходящая позиция, при 429 соблюдается Retry-After. Перед запросом заново проверяются текущий цикл, открытый экран и активность окна; закрытие/скрытие экрана отменяет ещё не отправленное подтверждение. Неуспешная попытка не становится подтверждённым серверным прочтением.

Ответ read, `dialog.read_updated` и обе позиции DialogDto обновляют максимум в рамках текущего авторизованного цикла. `reader_id` определяет, чья позиция выросла. Прочтение с другого устройства обновляет UI, сохраняя обязанность скачать пропущенные сообщения. Поздний MessageDto со статусом `sent` не откатывает уже подтверждённый `read`. После reconnect для обновления галочек достаточно метаданных диалога, повторная загрузка всей истории не требуется.

## Кеш, сессия и уведомления

Согласован выбор хранилища через bridge по платформе: IndexedDB в браузере, основная нативная SQLite на iOS. При недоступности SQLite клиент постоянно переходит на IndexedDB внутри WebView с сохранением сообщений, позиций, черновиков и незавершённых отправок в приложении. После перезапуска выбор сохраняется; автоматического возврата в SQLite и синхронизации двух локальных баз нет. Экраны используют общий storage-интерфейс; механизм однократного переключения определён в [bootstrap](bootstrap.md#storage-v1-записи-операции-и-атомарность). Native Auth/WSS сохраняет свой режим независимо от выбранного хранилища.

Согласовано пользователем: обычный logout физически очищает локальные сообщения, позиции sync/read и сохранённые черновики. Незавершённые отправки очищаются вместе с кешем. Закрытие страницы само по себе не является logout и не удаляет черновики или отправки с неизвестным результатом. Изоляция server/account/device, реализация адаптеров, транзакции и порядок очистки принадлежат [bootstrap](bootstrap.md#storage-v1-записи-операции-и-атомарность).

Принятая очистка после `SESSION_INVALID` выполняется до повторной загрузки после нового входа. Максимум read-позиций не переносится через этот барьер: восстановленная серверная БД может иметь меньшие позиции. Смена аккаунта/сервера отменяет задачи и уведомительные intent прежнего цикла; поздний результат не записывается в новую область хранения. Кеш не попадает в service worker Cache Storage, логи, URL или диагностические отчёты.

Системные уведомления и безопасный intent `dialog_id` следуют [backend-контракту](../backend/modules/dialogs/README.md#уведомления). после восстановления сессии преобразовывать проверенный intent в переход на `/dialogs/:dialogId`; внешние URL и содержимое push не становятся маршрутом. Неизвестный/чужой контекст возвращает к списку с общим объяснением. Сам переход не вызывает read. Push может потеряться; вход и REST-сверка должны обнаруживать сохранённые сообщения самостоятельно.

Обычная APNs-регистрация и intent через native bridge реализованы; реальная доставка требует отдельной приёмки. Их интерфейс определён в bootstrap; этот проект не добавляет команд в принятый device bridge и не обещает доставку на закрытом iOS-приложении.

## Ошибки и восстановление

| Событие                             | Поведение клиента                                                                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `DIALOG_NOT_ALLOWED`                | Обновить permissions; прекратить запрещённые операции, сохранить показ скачанных сообщений и доступных метаданных |
| `NOT_FOUND`                         | Одинаковое безопасное состояние для чужого/неизвестного ID; не раскрывать кеш другого контекста                   |
| `VALIDATION_ERROR`, 413             | Показать безопасную причину и поля, не обрезать текст молча                                                       |
| 429                                 | Ждать `Retry-After`; для отправки сохранить ID/content, для read объединить актуальный максимум                   |
| Ошибка сети, 503, внутренняя ошибка | Сохранить загруженное, показать ошибку актуализации; для начатой отправки учитывать неизвестный результат         |
| Ошибка хранилища                    | Не продвигать sync и не начинать отправку без сохранённого ID; доступен повтор, звонок продолжает работать        |
| `SESSION_INVALID`                   | Завершить цикл и выполнить принятую очистку перед повторной загрузкой                                             |

Отказ повтора после потери прав не доказывает, что предыдущая отправка не сохранилась. Результаты старого цикла игнорируются даже тогда, когда отмена HTTP не остановила серверный commit. Общие правила refresh и инвалидирования принадлежат Auth, чат не создаёт вторую ротацию токенов.

## Критерии приёмки

Это требования к будущей реализации, не отчёт о выполненных тестах. Сценарии обязательны для приёмки.

- Из контакта открывается один диалог пары без звонка; из списка читаемый диалог открывается и при запрете отправки. Прямые URL, login-return, перезагрузка и история браузера сохраняют корректный контекст.
- Пагинация списка при перестановке строк не создаёт дубликаты. Недоступный диалог сохраняет разрешённые актуальные метаданные, content не загружается при запрете чтения.
- При запрете серверного чтения ранее скачанные сообщения остаются видимыми текущему аккаунту, незагруженные страницы не запрашиваются и read не отправляется. Без локальной истории показывается ограничение; logout и SESSION_INVALID сохраняют правила закрытия доступа и очистки кеша.
- Список не содержит предпросмотра текста или последнего стикера, в том числе при наличии локального кеша сообщений.
- Обычный участник читает входящее от admin без общей группы, но не отправляет ответ. История с отключённым peer читается по текущим правилам, новая отправка ему запрещена. Посторонний admin не получает переписку.
- На новом кеше сначала загружается последняя страница; старые страницы не скачиваются без прокрутки вверх. Ответ собственной отправки, read с другого устройства и отдельно загруженный свежий хвост не пропускают разрыв после сохранённой sync-позиции. Ошибка атомарного сохранения не продвигает позицию; потеря кеша приводит к повторной загрузке последней страницы с сервера, без скачивания всей истории.
- Проверяются before/after, пустая история, короткая страница с `has_more=true`, повторные страницы, потеря/дублирование/перестановка WS и сверка без события после reconnect. Открытый видимый раздел сверяется раз в 30 секунд, в фоне таймер остановлен; незавершённая сверка не запускается повторно.
- При возвращении в GChat загрузка новых сообщений начинается сразу и не ждёт периодической сверки, в том числе при прокрутке к старой истории; сама загрузка не вызывает read.
- Потерянный ответ отправки, перезагрузка, ответ после sync и повтор с прежним ID создают один пузырёк и одну серверную запись. Совпадающий текст с разными ID остаётся разными сообщениями. 429 не меняет ключ повтора.
- Одна галочка появляется после серверного сохранения, две — после подтверждённого прочтения. При открытии в активном окне после загрузки последних сообщений сразу подтверждается максимальная позиция страницы, включая прочтение более ранних сообщений без их подгрузки/прокрутки. Скрытое/неактивное окно, push и фоновая загрузка read не отправляют. Поздние меньшие позиции и старый `sent` не откатывают галочки.
- В уже открытой активной переписке новые сообщения при чтении старой истории не подтверждаются до перехода к ним. Если пользователь находится внизу, загрузка и показ нового сообщения сразу запускают подтверждение прочтения. Кнопка перехода к новым не создаёт повторную отправку сообщения и не меняет sync-позицию без загрузки.
- При возвращении активности открытого диалога внизу ленты загруженные новые сообщения подтверждаются прочитанными; при сохранённой прокрутке к старой истории они остаются непрочитанными до перехода к ним.
- Черновик каждого диалога сохраняется при переходах и перезагрузке приложения. Logout удаляет кеш, позиции и сохранённые черновики; `SESSION_INVALID` не позволяет продолжить с позиций до восстановления БД. Новый аккаунт/сервер не получает старые сообщения, черновики, intent и поздние ответы.
- Текст из 4000 code points принимается, превышение/пробельный текст и непарные surrogate отклоняются; переносы и emoji сохраняются. Неизвестный стикер безопасен, произвольный URL/HTML не исполняется.
- Узкий экран, клавиатура, safe area и загрузка старой истории сохраняют фокус и видимый якорь ленты. Новое сообщение при чтении старой истории не меняет прокрутку и показывает кнопку перехода к новым; если пользователь уже внизу, лента прокручивается к новому сообщению. Входящий звонок доступен, действующий звонок и общий WSS переживают переходы между разделами.
- Браузерные вкладки сохраняют одного владельца WSS; native использует текущий Auth/WS bridge и REST-обёртку. Обновление Web соблюдает существующий барьер и не прерывает звонок.

Документация проверяется `pnpm docs:check`. После реализации проверки Web выбираются по [README приложения](../../applications/web/README.md#изолированный-стенд-и-проверки); для настоящего push и iOS нужна отдельная платформенная приёмка.

### Страницы, свежесть и планировщик

limit=30 для списка и страниц истории. Размер короткой страницы не заменяет has_more. Для непустой страницы следующий after — максимальный сохранённый sequence, before — минимальный. Пустая страница с has_more=true считается ошибкой протокола: позиция не меняется, бесконечный цикл запросов не запускается. Атомарные операции/диапазоны описаны только в [Storage v1](bootstrap.md#storage-v1-записи-операции-и-атомарность).

На открытии существующего кеша параллельно показать локальные сообщения и запросить свежий хвост для быстрого перехода к последним. Этот хвост сохраняется как отдельный диапазон; затем after-запросы от прежней sync_sequence закрывают промежуток. UI отображает незагруженный разрыв как «Загрузить пропущенные сообщения», не рисует соседние диапазоны сплошной историей. Сверка продолжается независимо от прокрутки. Подтверждённый ответ собственной отправки сопоставляется с outbox, но не закрывает промежуток и не продвигает sync_sequence.

один GET-планировщик на вкладку с общим для её задач интервалом не меньше 250 мс между стартами запросов и максимум двумя одновременно выполняемыми GET. Приоритет: открытый диалог/permissions → запрошенная пользователем старая страница → начало списка → остальные dirty-метаданные. Для одного диалога одновременно не более одной задачи after-sync; повторные WS/таймеры выставляют dirty-флаг, а не создают новые задачи. Background-диалоги обновляют метаданные/непрочитанное, но без открытия не скачивают историю. Отдельный Web Lock `gchat-dialog-sync:<namespaceId>:<dialogId>` объединяет одинаковую задачу sync между вкладками с повторной проверкой курсора после ожидания; сеть выполняется вне storage-lock и транзакции. Общий storage-lock берётся только для короткого commit с CAS, поэтому ожидание сети не блокирует черновики.

Периодическая сверка раз в 30 секунд работает только в видимом разделе «Диалоги» и не накладывается на предыдущую. Foreground/reconnect/WS инициируют сверку независимо от этого таймера. При 429 до Retry-After приостанавливается вся соответствующая группа запросов текущей вкладки; безопасный срок ожидания рассылается другим вкладкам того же аккаунта. Это не резервирует серверный бюджет между разными устройствами: серверный limiter остаётся окончательным. Для GET после сетевой ошибки предлагаются повторы через 1, 2, 5, 10 и затем 30 секунд до успеха в активном разделе; фоновые задачи ждут следующего события/foreground. Автоповтор POST send не вводится.

Свежий DialogDto с has_unread_messages применяется только если за время запроса не выросла подтверждённая собственная read-позиция или локальная версия invalidation. Иначе ответ не возвращает старый индикатор, а планировщик запрашивает актуальный DTO. Признак не вычисляется по разности sequence. Имена/индикаторы требуют сначала реализации согласованных backend-полей и SDK; это зависимость, не открытый продуктовый выбор.

### Объединение прочтения

один read-планировщик на вкладку: максимум один запрос в работе и не чаще одного старта в 250 мс. Первая подходящая позиция при открытии отправляется немедленно, если предыдущие операции не расходовали интервал; это ограничение частоты, а не дополнительный таймер видимости. Следующие кандидаты одного диалога объединяются максимумом. Перед началом запроса проверяются текущие epoch/cycle, can_read, выбранный диалог, document.visibilityState=visible и document.hasFocus(); на iOS дополнительно требуется активный native cycle. После рендера сообщений открытие хвоста либо нахождение внизу создаёт кандидата; метаданные/WS без сообщения его не создают.

После переключения диалога/потери активности неотправленные кандидаты удаляются. Уже ушедший запрос может подтвердиться на сервере и безопасно обновить подтверждённую позицию текущего epoch; он не считается отменённым сервером только из-за AbortSignal. После восстановления активности кандидат пересчитывается по отображённой ленте, а не восстанавливается безусловно из очереди.

Для browser-вкладок отдельный Web Lock `gchat-dialog-read:<namespaceId>` вокруг read-операции и общий срок следующего разрешённого старта в control storage. Перед отправкой перечитывается подтверждённая позиция: уже достигнутая не отправляется повторно. 429 устанавливает общий read cooldown по Retry-After; после него отправляется заново рассчитанный максимум только для всё ещё активной переписки. Сетевой отказ оставляет UI неподтверждённым; повтор — через 1, 2, 5, 10 и затем 30 секунд при сохранении условий видимости. Другие устройства могут расходовать общий серверный запас, поэтому 429 остаётся штатным исходом.

### Связь с bootstrap

[Принятый bootstrap](bootstrap.md) владеет общим runtime, storage/CAS, outbox, native bridge, fallback, очисткой, обновлением и системными уведомлениями. Его параметры здесь не дублируются. Объём включает Web и необходимые backend/iOS-изменения; браузерная реализация и приёмка iPhone учитываются отдельно.

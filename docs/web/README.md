# Веб-клиент GChat

Целевая платформенная граница определена в принятой [спецификации device](device-api.md), модели страниц и миграция Query — в [потоке данных](data-flow.md). Эти документы задают требуемую архитектуру; код пока использует прежние провайдеры/адаптеры, описанные ниже. При расхождении публичной формы, HTTP-транспорта и загрузки данных применяются новые контракты; продуктовые правила Auth/Calls/Dialogs сохраняются.

Общий запуск чатов и платформенное хранение описаны в [отдельном frontend bootstrap](bootstrap.md) со статусом accepted. Общий runtime сохраняет принятую модель Auth/WSS и одну сессию профиля. Backend-контракт [DialogsModule](../backend/modules/dialogs/README.md) принят: REST для операций/прочтения, общий WSS для уведомлений. Границы frontend recovery и принятые DTO отмечены в bootstrap; backend-ready не означает готовности клиентского проекта.

Экраны переписки, отправка, синхронизация и клиентское правило прочтения описаны в [проекте диалогов Web](dialogs.md) со статусом accepted. Маршруты `/dialogs` и `/dialogs/:dialogId` согласованы с поддержкой прямых ссылок, перезагрузки и истории браузера, реализованы в основном React Router. Клиентский проект принят пользователем; реализация следует его критериям приёмки.

Самостоятельный модуль «Настройки → Основные» описан в принятом [контракте Settings](settings.md); команды устройства — в [Device bridge](device-bridge.md), мотивация — в [D011](../architecture/decisions/D011-native-device-settings.md).

## Назначение и статус

GChat Web — полноценный пользовательский клиент GChat для браузера. Пользователь входит в свой аккаунт, видит доступные по своей роли группы и собеседников, совершает и принимает голосовые звонки. Проверка механизма DirectCalls — один из результатов разработки и приёмки этого клиента.

Веб-клиент реализован по поручению пользователя. Текущий объём включает пользовательский интерфейс и браузерный звонок через общий backend; ручная слышимость, Safari, закрытый браузер и веб ↔ iOS ещё не проверены. Команды разработки и изолированного стенда — в [README приложения](../../applications/web/README.md). Мотивация — в [D005](../architecture/decisions/D005-web-client.md), общие требования — в [требованиях GChat](../product/requirements.md).

Предложение по переиспользованию готового Web-интерфейса в Capacitor и передаче всего мобильного звонка нативному модулю описано в [D008](../architecture/decisions/D008-capacitor-bridge.md). D008 сохраняет статус draft; по поручению пользователя реализована Web-часть bridge, описанная ниже. Создана [iOS-оболочка](../../applications/ios/README.md) со Swift-плагином и нативной сессией; production-загрузка в Capacitor ещё не прошла spike, звонковый движок не реализован.

Веб и iOS используют общий backend, аккаунты, группы, правила доступа, устройства и состояния звонков. Собственного состояния звонка для веба и интеграции с Mattermost/Jitsi нет. Системное поведение адаптируется к браузеру; проверки APNs, PushKit и CallKit остаются частью приёмки iOS.

## Встроенный Web и Capacitor bridge

Web использует общие экраны и два адаптера: `features/auth/session.ts` выбирает browser session либо native transport, `CallsProvider` — `GChatClient` либо `NativeCallsClient`. Браузерная реализация сессии находится в `features/auth/browser-session.ts`. Во встроенном режиме браузерный call engine не создаётся: нет Web Locks, BroadcastChannel, WSS, регистрации устройства, WebRTC, микрофона и звука Web. Управление принятием/завершением и mute принадлежит native UI; Web показывает безопасное состояние и передаёт подтверждённый исходящий вызов через `placeCall` без автоматического повтора и без подмены снимка ответом команды.

Режим фиксируется до запуска React. Native shell должен установить `window.GChatRuntime = 'native'` до загрузки JS, в том числе при недоступном Capacitor bootstrap. Наличие native-платформы Capacitor также включает этот режим; для разработки можно задать `VITE_GCHAT_RUNTIME=native`. Параметр query не выбирает режим. Отсутствующий, несовместимый или неисправный плагин приводит к ошибке с повтором; переключения на browser adapter нет. Этот маркер выбирает режим, но не является механизмом доверия: проверку основного документа/origin и запрет внешней навигации обязан реализовать native shell по D008.

### Внутренний формат GChat bridge v1

Web регистрирует Capacitor-плагин `GChat` через `@capacitor/core`. Внутренний API D008 реализован на Web-стороне и в [Swift-плагине оболочки](../../applications/ios/README.md); звонковая часть Swift ещё отсутствует. JSON-объекты на входе валидируются, неизвестные поля событий и результатов отклоняются. Форматы для native:

| Запрос / событие      | JSON-аргументы и результат                                                                                                                                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getCapabilities()`   | Результат `{bridgeVersion: 1, platform: 'ios', nativeAuth: true, nativeCalls: boolean, nativeWebSocket?: boolean}`; оболочка без call engine возвращает `false`, Web показывает недоступность звонков и сохраняет runtime offline. |
| `webReady(...)`       | Аргументы `{bridgeVersion: 1, cycleId}`. `cycleId` — новый UUID текущего цикла Web. Результат — подтверждение без данных; далее native передаёт `route` и `callSnapshot` с этим ID в любом порядке.                                |
| `login(...)`          | `{serverUrl, login, password}`. Результат — подтверждение без токенов; показ следующего экрана задаётся событием `route`.                                                                                                          |
| `getAccessToken(...)` | `{forceRefresh: boolean}` → `{accessToken}`. Native сериализует refresh независимо от Web.                                                                                                                                         |
| `logout()`            | Без аргументов. Подтверждённый выход/инвалидация сопровождается `loggedOut` и затем `route` на login. Временная ошибка сохраняет текущую сессию.                                                                                   |
| `placeCall(...)`      | `{peerId}` с UUID пользователя. Подтверждение означает приём команды; состояние приходит отдельным событием.                                                                                                                       |
| `route`               | `{cycleId, path, accessToken?, replace?}`. `path` — логический внутренний путь без `/apps/client`; `replace` по умолчанию `true`. Токен извлекается в память до навигации и не передаётся React Router.                            |
| `loggedOut`           | `{cycleId}`. Web отменяет HTTP, очищает токен, состояние звонка и пользовательские кеши; затем ожидает native-маршрут.                                                                                                             |
| `callSnapshot`        | `{cycleId, call, runtime: {status, muted}}`. `call` — полный безопасный DirectCalls DTO или `null`; `status` — `offline`, `connecting` либо `online`, `muted` — boolean.                                                           |
| `callStateChanged`    | `{cycleId, call}`. Формат `call` тот же; старые версии и возобновление завершённого/сменившегося звонка отбрасываются.                                                                                                             |
| `callRuntimeChanged`  | `{cycleId, status: {status, muted}}`. Состояние runtime в том же формате, что в снимке.                                                                                                                                            |

События доставляются через Capacitor `addListener`; Web устанавливает все слушатели до `webReady`. Native обязан упорядочить снимок и последующие обновления, повторять текущий `cycleId` во всех событиях и не доставлять запоздалую авторизацию после logout. Web игнорирует прежний цикл и обновления до начального снимка; повторный снимок текущего цикла не перезаписывает уже полученные обновления. В течение 15 секунд после начала синхронизации требуются совместимые capabilities, маршрут и снимок, иначе Web показывает ошибку с повтором. Ошибки имеют `{code, retryAfter?}` из D008; произвольный текст native не показывается и не попадает в диагностику.

При старте и каждом переходе документа в `visible` Web создаёт новый цикл: отменяет предыдущие HTTP-запросы, очищает пользовательские кеши/UI и токен, затем вызывает `webReady`. До маршрута и полного снимка прежние данные скрыты. События звонка не вызывают навигацию и не перезапускают обычные переходы Link/NavLink. HTTP-ответы и ответы получения токена предыдущей сессии не применяются.

Web получает display claims из access JWT только для интерфейса; права проверяет backend. Access token остаётся в памяти транспорта, пользовательский React context содержит только признак сессии и display claims. Native login, refresh, logout и долговременное хранение токенов не выполняются в Web. После `ACCESS_TOKEN_EXPIRED` HTTP-операция повторяется один раз с `getAccessToken({forceRefresh: true})`; подтверждённый отказ сессии скрывает данные и требует актуального решения native. Ошибка secure storage не интерпретируется как отсутствие сессии.

Основной Web принимает `serverUrl` только как HTTPS-origin текущего документа, без credentials, path, query и hash. Окончательная проверка выбранного сервера и привязки сессии остаётся в native. В `route` разрешены `/`, `/login`, `/calls`, `/admin`, `/admin/users`, карточка пользователя и маршруты Settings из профильного контракта; query `serverUrl` разрешён только у login. Внешние URL, произвольные query, hash и префикс `/apps/client` отклоняются. Пароли и refresh/push tokens не входят в события. Реализованные UI-события не содержат TURN credentials, SDP и ICE; согласованное расширение транспорта описано ниже. `selectServer` относится к отдельному стартовому приложению, которое в этой Web-части не реализовано.

Сборка для серверного размещения описана в [README приложения](../../applications/web/README.md#сборка-для-серверного-web). Реальная загрузка через Capacitor, native-сессия и native-аудио требуют iOS-spike и не считаются проверенными по mock bridge unit-тестам.

### Общий WebSocket через native

Во встроенном режиме Web использует одно WSS-соединение с выбранным backend совместно с нативными модулями через Capacitor bridge, без открытия дополнительного WebSocket. Общий нативный транспорт отделён от движка звонков: он обслуживает нативные модули и Web, в том числе будущие функции переписки. Это решение не добавляет мессенджер в текущий объём продукта. Автономный Web продолжает открывать собственное браузерное соединение по контракту [Signaling](../backend/modules/signaling.md).

- Bridge предоставляет Web только отправку JSON-сообщений и подписку на входящие сообщения существующего соединения. Открытие, закрытие, авторизация, регистрация устройства и переподключение принадлежат native; Web не выбирает произвольный WSS-адрес и не управляет жизненным циклом соединения. Недоступность соединения возвращается как ошибка операции.
- Типы сообщений не зашиты списком в оболочку. Передачу в обоих направлениях ограничивают [правила из БД Signaling](../backend/modules/signaling.md#ограничения-web-сообщений-через-native-bridge); без подходящего запрета сообщение разрешено. Маскирование payload, env-настройки и серверные пометки скрытия не вводятся. Новые типы сообщений вне запрещённых префиксов не требуют обновления оболочки, пока сохраняется совместимость формата транспорта. Native получает действующие правила по Signaling и применяет их к отправке и получению. Детали доставки и срока политики принадлежат контракту Signaling.
- Нативный движок самостоятельно обрабатывает сигнализацию звонка независимо от подписки Web. Получение сырых сообщений не запускает во встроенном Web браузерный call engine. Снимок и UI-события звонка сохраняют свой отдельный формат без SDP/ICE и транспортных секретов.
- Сброс или остановка WebView и отписка Web не закрывают нативное соединение и не останавливают звонок. Обмен относится к текущей сессии и циклу WebView; сообщения прежней сессии не доставляются новому пользователю. Bridge сам по себе не гарантирует фоновую доставку или восстановление пропущенных сообщений будущего мессенджера.

Безопасность обеспечивают проверка доверенного основного документа/origin на native-границе, защита Web от XSS, проверка сессии, прав и содержимого каждой команды на backend, а также ограничения размера, частоты сообщений и очередей. Доступ через bridge не расширяет серверные права сессии. Скомпрометированный Web может читать переданные ему сообщения и отправлять команды в пределах серверных прав сессии и политики bridge. Начальная политика ограничивает доступ к нативной сигнализации; её необходимо установить SQL-скриптом из контракта Signaling. Пустая таблица намеренно означает отсутствие запретов. Маскирование не является защитой данных от авторизованного клиента: автономный Web уже получает необходимые ему данные сигнализации собственных звонков.

Расширение реализовано в NativeCore, Swift-плагине и Web runtime. Оно не включает call engine или мессенджер; работа настоящего WSS/WKWebView на iOS требует интеграционной проверки.

| Метод / событие      | Формат                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `sendWsMessage(...)` | `{cycleId, message: {type, request_id, payload}}` → подтверждение отправки в сокет; результат backend приходит отдельно через `wsMessage`. |
| `wsMessage`          | `{cycleId, message}`; `message` — разрешённое исходное JSON-событие или ответ Signaling.                                                   |
| `wsState`            | `{cycleId, status: 'offline' \| 'connecting' \| 'online'}`; состояние общего транспорта, независимо от runtime звонка.                     |

`nativeWebSocket: true` в capabilities объявляет поддержку расширения; отсутствие поля означает старую оболочку без транспорта. Новый Web сохраняет совместимость с такой оболочкой. Старый Web со строгой схемой capabilities требует обновления перед использованием новой оболочки.

`cycleId` создаёт Web через `crypto.randomUUID()` при каждом `ready()` (старт документа, foreground или повтор после ошибки), передаёт native в `webReady` и повторяет при отправке. Это идентификатор синхронизации WebView, а не сессии, устройства или WSS. Native принимает отправку только для текущего цикла; Web игнорирует прежние события. Слушатели устанавливаются до `webReady`, после снимков native передаёт текущий `wsState`. До авторизованного маршрута Web не отдаёт сырые сообщения потребителям. Сырые сообщения не попадают в React/Query state, диагностику или состояние звонка; `subscribeWs` возвращает локальную отписку, не закрывающую соединение.

Native заменяет исходящие `request_id` уникальными UUID общего соединения и хранит тип команды, исходный Web ID и цикл. Ответ Web восстанавливает его исходный ID; ответы native фильтруются по типу собственной команды и могут поступать Web в том же цикле. Неизвестные ответы отбрасываются. Внутренние ответы загрузки политики не публикуются. Совпавшие ID Web и native не конфликтуют; повтор ожидающего Web ID текущего цикла отклоняется. Смена цикла сохраняет WSS, но отбрасывает ответы запросов прежнего цикла. Смена сессии/выход закрывает соединение и очищает корреляцию.

Native ограничивает сообщение 128 KiB UTF-8, очередь отправки — 1 MiB, ожидающие запросы — 128, частоту Web — 32 команды/секунду. Ожидание ответа ограничено 15 секундами; после таймаута соединение восстанавливается без повтора неизвестной команды. Нет offline-очереди Web. Ошибки bridge: `VALIDATION_ERROR`, `FORBIDDEN`, `RATE_LIMITED` с `retryAfter`, `BRIDGE_UNAVAILABLE` при недоступном соединении/политике. Серверные ошибки приходят обычным ответом Signaling и также проходят receive-фильтр.

## Пользовательские возможности

В реализованный объём первой веб-версии входят:

- Вход в созданный администратором аккаунт, сохранение и восстановление сессии, выход из текущего аккаунта.
- Список доступных по роли групп и просмотр участников выбранной группы с отображаемыми именами по [Groups](../backend/modules/groups.md#выдача-клиенту--реализовано). Для текущего пользователя действие звонка самому себе недоступно.
- Выбор собеседника и подтверждение исходящего вызова из карточки; кнопка с трубкой в списке начинает звонок сразу.
- Входящий вызов в модальном окне поверх текущего интерфейса с именем собеседника, действиями «Принять» и «Отклонить» и доступным в браузере оповещением. Escape не скрывает входящий вызов.
- Ожидание ответа, первоначальное соединение, разговор с таймером, восстановление и понятный результат завершения.
- Отмена исходящего вызова, завершение разговора и выключение своего микрофона.
- Обработка потери сети, переподключения, истечения access token, отзыва сессии и отключения аккаунта.
- Адаптивный интерфейс для настольного и мобильного браузера, управление клавиатурой и доступные подписи элементов.

Пользовательский сценарий не требует знания или ввода UUID. Идентификаторы используются внутри протокола и могут быть доступны в диагностике. Неопределённые HTTP-маршруты групп и участников — необходимая backend-зависимость реализации, а не основание исключать контакты из веб-клиента. Их контракт ведётся в [Groups](../backend/modules/groups.md#выдача-клиенту--реализовано).

Раздел «Администрирование» реализован для роли `admin` из access JWT. Бизнес-сценарии определены в [требованиях бэк-офиса](../product/backoffice.md), административный API — в принятом [контракте Backoffice](../backend/modules/backoffice.md); [HTML-прототип](../design/backoffice.html) служит визуальной основой. Самостоятельная регистрация, отдельное управление группами, групповые и видеозвонки, переписка и звонки на телефонные номера в текущий объём не входят. История звонков и дополнительные возможности звука остаются общепродуктовыми открытыми вопросами; слово «полноценный» не переводит их автоматически в согласованные функции.

Раздел «Звонки» для администратора открывается со списком «Все пользователи», включая активные аккаунты без группы. Список загружается через существующий `GET /admin/users` с фильтром `status=active` и чтением всех страниц; в контактах используются только идентификатор и отображаемое имя. Переключатель позволяет выбрать любую группу по [Groups](../backend/modules/groups.md#выдача-клиенту--реализовано). Звонки без общей группы разрешены инициатору-администратору по [DirectCalls](../backend/modules/direct-calls/README.md#доступ-администратора--согласовано). Доступ реализован; обычному пользователю административный список не запрашивается.

## Маршрутизация и структура исходников

Маршруты `/dialogs` и `/dialogs/:dialogId` требуют сессии; экраны и доступ описаны в [контракте диалогов](dialogs.md). Bootstrap выше маршрутов владеет общим транспортом, CallsProvider хранит состояние звонка, `features/dialogs` использует общие storage/runtime без второго WSS.

В серверной сборке перечисленные ниже маршруты имеют префикс `/apps/client`; backend раздаёт HTML и статику при заданном `GCHAT_WEB_ROOT`. Публичный `/` перенаправляет на `/apps/client`, сохраняя query; HTTP-ответ HTML имеет `no-store`, отсутствующие assets получают 404. Кеш публичной оболочки через service worker описан в [разделе PWA](#pwa-web-push-и-кеширование). Настройка и проверки — в [развёртывании](../operations/deployment.md).

Принятый [D007](../architecture/decisions/D007-web-routing.md) задаёт Data mode с createBrowserRouter, loaders/actions и удалением TanStack Query после миграции потребителей. Текущее дерево в `applications/web/src/app/App.tsx` ещё использует декларативные Routes/BrowserRouter и Query. Целевой router создаётся навигационным адаптером device из переданной app-конфигурации. URL использует History API, ссылки — Link/NavLink; переходы между разделами не перезагружают документ. Точные модели и владельцы данных — в [контракте потока данных](data-flow.md).

| Адрес                             | Содержимое и доступ                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `/`                               | Перенаправление на `/calls` с заменой записи истории.                                                        |
| `/login`                          | Вход; при наличии сессии переход на сохранённый внутренний адрес либо `/calls`.                              |
| `/calls`                          | Люди, группы и звонок; требуется сессия.                                                                     |
| `/admin`                          | Для администратора перенаправление на `/admin/users`.                                                        |
| `/admin/users`                    | Список аккаунтов; требуется сессия и роль `admin`.                                                           |
| `/admin/users/:userId`            | Тот же список с модальной карточкой указанного аккаунта поверх содержимого; требуется сессия и роль `admin`. |
| `/settings` и `/settings/general` | Настройки и основные параметры; требуется сессия.                                                            |
| `/settings/general/:section`      | microphone, audio, push, camera, geolocation, files по контракту Settings.                                   |
| Остальные                         | Страница «Страница не найдена» со ссылкой на звонки.                                                         |

При отсутствии сессии защищённый маршрут переводит на `/login`, сохраняя путь, query и hash в состоянии истории для возврата после входа. Допускается только внутренний адрес; внешние URL и возврат на сам `/login` отклоняются. Обычный пользователь при прямом обращении к административному адресу видит отказ в доступе; административная страница не монтируется и её API не вызывается. Скрытие ссылки и клиентская проверка роли дополняют серверную проверку, а не заменяют её.

Параметры административного списка находятся в query: `q` — поиск, `status=all|active|disabled`, `offset` — смещение страницы по 25 записей. Отсутствующие значения означают пустой поиск, все состояния и нулевое смещение. При чтении URL поиск ограничивается 80 символами, неизвестный статус заменяется на `all`, отрицательное, дробное, небезопасное или превышающее 2147483647 смещение — на 0. API получает нормализованные значения. Поле поиска обновляется сразу, но URL и серверный запрос обновляются только после 350 мс без ввода. Следующий символ перезапускает таймер; уход со страницы и навигация по истории отменяют незавершённый таймер и восстанавливают текст из URL. Выбор фильтра или ручное обновление применяют незавершённый поиск сразу. Изменение поиска заменяет текущую запись истории, фильтр и пагинация создают записи; поиск и фильтр сбрасывают смещение. Карточка открывается модальным окном поверх списка на всех размерах экрана. Escape и кнопка закрытия возвращают на `/admin/users` с текущими параметрами; при прямом открытии адреса и обновлении страницы окно также открывается поверх списка. Подтверждение административной операции временно заменяет окно карточки, после завершения или отмены карточка открывается снова. Ссылка на карточку сохраняет query, поэтому перезагрузка, «Назад» и «Вперёд» восстанавливают параметры списка и выбранный аккаунт. Пароли и токены не включаются в URL и историю. Создание и подтверждения изменений остаются локальными диалогами; уход со страницы закрывает их. Уже отправленная операция продолжает выполняться: подтверждённый пароль может появиться в глобальном окне результата, но завершение операции не возвращает пользователя принудительно в покинутый раздел.

Структура `applications/web/src/`:

```text
app/                     # маршруты, защита страниц и общая оболочка
features/auth/           # вход, сессия, refresh и возврат после входа
features/calls/          # контакты, звонковый клиент, WSS, протокол и медиа
features/settings/       # настройки и представление состояния устройства
shared/device/           # единый командный bridge и адаптеры
features/administration/ # список, карточка и операции с аккаунтами
shared/api/              # создание SDK-транспорта и общие HTTP-ошибки
shared/ui/               # общие аватары и модальные окна
main.tsx                 # BrowserRouter и QueryClientProvider
style.css                # стили приложения
```

`app` собирает разделы и общую оболочку. Общие модули `shared` не импортируют разделы; разделы используют `shared`. Auth владеет сохранённой сессией и обёрткой авторизованного запроса с ротацией и инвалидированием; Calls и Administration обращаются через неё. Administration не зависит от звонкового клиента. Оболочка использует публичные контексты Auth и Calls для профиля и состояния звонка. На всех размерах экрана применяется одна структура без боковой колонки: компактная верхняя шапка с логотипом и кнопкой аккаунта, содержимое и нижнее меню. Внизу окна закреплено меню разделов с иконками и подписями: «Звонки», «Администрирование» и «Настройки». Настройки доступны всем пользователям, административная вкладка — только admin. Административная вкладка отображается только роли `admin`, текущий раздел выделяется и обозначается `aria-current="page"`, включая вложенную карточку аккаунта. Меню доступно на настольном и мобильном экране; содержимое имеет нижний отступ с учётом безопасной области устройства. Переход между вкладками не перезапускает звонковый клиент. Логотип также ведёт к звонкам. При наличии нескольких групп выбор находится внутри панели контактов. Пункт администрирования, список групп и индикатор соединения в шапке не отображаются.

AuthProvider и CallsProvider смонтированы выше Routes. В автономном режиме CallsProvider создаёт и запускает единственного GChatClient, подписывается на его состояние и поддерживает контакты и выбранную группу. Переходы между страницами не останавливают WSS, Web Locks, микрофон, WebRTC и таймер звонка. CallsPage отображает текущий разговор при возврате. Глобальное окно входящего вызова находится над маршрутами и доступно также в администрировании; при нём закрываются диалоги профиля и диагностики. Остановка и отзыв доступа сохраняют правила Auth/DirectCalls. Однократное окно административных данных входа находится выше страниц и переживает завершение собственной сессии после смены пароля.

Веб-сервер должен отдавать `index.html` для клиентских адресов, включая прямое открытие карточки; `/api/*` и `/ws` сохраняют отдельную маршрутизацию. Правила размещения — в [README приложения](../../applications/web/README.md).

## Администрирование

Раздел использует общую сессию и сгенерированный SDK. Обычному пользователю навигация скрыта; backend проверяет актуальные права на каждом запросе. Администратор видит список и карточку аккаунтов со всеми группами, ролью и состоянием доступа. Поиск и фильтр состояния передаются серверу, страницы запрашиваются по 25 записей с общим числом совпадений. Предусмотрены загрузка, отсутствие совпадений, ошибка с повтором чтения и отказ в доступе.

Создание принимает имя, группу, необязательный логин и обязательный пароль. Подсказки групп загружаются с backend; форма предупреждает о возможном создании группы. Браузер генерирует пароль через `crypto.getRandomValues`: 24 независимых символа алфавита из 64 значений, 144 бита энтропии. Можно задать пароль вручную по правилам Auth. В форме создания и смены пароля доступны показ/скрытие введённого значения и копирование в буфер обмена; изначально поле скрыто. Копирование до отправки явно обозначает, что изменения ещё не сохранены, и не является подтверждением установки пароля. При генерации другого значения поле снова скрывается. Перед сменой пароля и изменением доступа показываются аккаунт и последствия; собственное отключение недоступно.

Изменения отправляются один раз, повторная отправка во время выполнения блокируется. Сетевой сбой, некорректный успешный ответ и HTTP 5xx обозначают неизвестный результат: автоматического повтора нет, предлагается проверить список и карточку. Чтение карточки не подтверждает установку конкретного пароля. Ответ успешной операции обновляет карточку, список перечитывается.

Готовый пароль хранится только в памяти формы и однократного окна результата, без Query cache, localStorage и диагностики. Окно появляется только после подтверждённого успеха и позволяет скопировать логин и пароль. Закрытие очищает значение. Смена собственного пароля завершает локальную сессию; окно результата сохраняется поверх формы нового входа. При неизвестном результате пароль очищается без выдачи как установленного.

Звонковый клиент продолжает работать при просмотре раздела; входящий вызов остаётся модальным, к текущему звонку можно вернуться из администрирования. Проверки интерфейса с подменёнными HTTP-ответами находятся в `tests/e2e/tests/web/backoffice.e2e.ts`; они не заменяют серверные интеграционные проверки транзакций и отзыва доступа.

## Экраны и навигация

Общая верхняя шапка с логотипом и профилем отсутствует на всех размерах экрана. Разделы открываются через нижнее меню; профиль и выход доступны в «Настройках». Контент занимает освободившуюся высоту без пустого места под удалённую шапку. Заголовки разделов и шапка переписки с именем собеседника и возвратом сохраняются.

На странице звонков не показываются подпись «Доступ к группам настраивает администратор», подпись «GChat Web» и отдельная кнопка «Включить звук звонков» под содержимым. Пустые блоки и отступы под ними не резервируются. Подготовка звука доступна в настройках; действие «Включить звук» для заблокированного звука текущего звонка сохраняется.

При незавершённом звонке вне `/calls` над содержимым любого раздела показывается закреплённая у верхнего края плашка «Вернуться к звонку» с именем собеседника. Она остаётся видимой при прокрутке, занимает собственное место в раскладке и не перекрывает контент. Нажатие открывает `/calls` и панель текущего звонка, включая мобильную компоновку, без создания нового вызова. После завершения звонка плашка исчезает. На странице звонков плашка не дублируется. Входящий вызов продолжает отображаться глобальным диалогом поверх страниц.

Веб-интерфейс имеет [мобильный приоритет](../design/README.md#мобильный-приоритет-веб-интерфейса): базовые размеры и плотность рассчитаны на телефон, настольная версия расширяет компоновку. Контрольные экраны и правила элементов поддерживаются в дизайн-документе.

| Экран / состояние     | Содержимое и действия                                                                                                                           |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Вход                  | Логин и пароль, понятные ошибки, состояние отправки, восстановление существующей сессии.                                                        |
| Группы                | Только группы текущего пользователя; состояния загрузки, отсутствия групп и ошибки с повтором.                                                  |
| Участники группы      | Имена участников, доступное действие звонка, состояния загрузки, пустого списка и потери доступа. При отсутствии аватара используются инициалы. |
| Подтверждение звонка  | Имя выбранного собеседника, «Отмена» и «Позвонить»; при звонке из карточки до подтверждения серверный звонок не создаётся.                      |
| Исходящий вызов       | Имя собеседника, ожидание ответа и действие отмены.                                                                                             |
| Входящий вызов        | Имя инициатора, принятие и отклонение; понятный результат, если ответило другое устройство или вызов завершился.                                |
| Соединение / разговор | Имя собеседника, состояние, время разговора, микрофон и завершение. При восстановлении таймер продолжается.                                     |
| Завершение            | Понятная причина и возврат к списку собеседников со сбросом выбранного контакта.                                                                |
| Аккаунт               | Текущий пользователь, состояние доступа и выход; при текущем звонке выход требует явного пользовательского действия с понятным последствием.    |

Основной интерфейс использует пользовательские формулировки. Версии DTO, sequence и ICE states относятся к отдельной диагностической панели. Она не является главным экраном и не обязательна для совершения звонка.

Удаление членства обновляет доступные списки. Оно не прерывает уже созданный звонок по действующему DirectCalls; клиент не должен завершать разговор из-за исчезновения собеседника из списка. Имена загружаются из доступных списков участников и сохраняются в памяти открытого клиента. Если после восстановления нет разрешённого источника имени (например, членство уже потеряно), показывается «Собеседник». Нового доступа к профилям или новых полей call DTO это не даёт.

## Стек и размещение

Используется workspace-приложение `applications/web/`: React, TypeScript и Vite. Для проверок — Vitest и Playwright. Точные версии, зависимости и команды находятся в манифесте, lock-файле и README приложения.

HTTP-операции выполняются через внутренний [SDK backend-api](../packages/backend-api.md). Методы и DTO генерируются из OpenAPI; ручных HTTP-маршрутов и схем групп/участников в приложении нет. Loaders/actions React Router используют типизированные методы SDK и передают AbortSignal; TanStack Query удалён. Общий слой `auth.ts` сохраняет browser session policy: Web Lock для refresh, исходный `request_id`, однократное обновление и повтор операции при `ACCESS_TOKEN_EXPIRED`, очистку подтверждённо недействительной сессии. Запоздалый отказ старой сессии не очищает новую. Транспорт сохраняет `cache: no-store`; HTTP-ошибки SDK передаются с метаданными и `Retry-After`. Zod остаётся для сохранённой сессии/JWT и WebSocket-протокола.

Для интерфейса и типовых задач предпочтительны готовые библиотеки. Нативные WebSocket, RTCPeerConnection и getUserMedia используются с существующим протоколом GChat. Библиотека со своим сервером сигнализации не должна подменять общий backend или правила DirectCalls.

Используется один origin для страницы, HTTP API и `/ws`: локальный proxy Vite, при развёртывании — reverse proxy. Секреты backend, ключи APNs и shared secret coturn не включаются в веб-сборку. Браузер получает временную ICE-конфигурацию только через разрешённый серверный запрос.

Микрофон требует разрешения пользователя и secure context: HTTPS либо localhost. Проверка с другого устройства по обычному HTTP с LAN-адреса не считается рабочей конфигурацией веб-клиента. См. [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).

## Авторизация, устройство и вкладки

HTTP-вход, ротация и выход используют [Auth](../backend/modules/auth.md#http-api). Браузерный WebSocket не позволяет задать произвольный Authorization. Выдача и погашение WS-билета определены в [Auth](../backend/modules/auth.md#браузерный-ws-билет--реализовано), а браузерный handshake — в [Signaling](../backend/modules/signaling.md#браузерный-handshake--реализовано). Браузерный билетный путь реализован вместе с прежним header-based путём. См. [WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket).

Требования к проектируемой модели сессии:

- Перезагрузка страницы и восстановление сетевого подключения сохраняют текущую пару session/device; повторный вход не используется как штатный способ reconnect.
- Обновление токенов выполняется одной согласованной операцией с сохранением исходного request_id при неясном результате refresh. Параллельные вкладки не должны независимо ротировать один refresh token.
- Несколько вкладок одного профиля не должны постоянно заменять WS-соединения друг друга, перехватывать выбранный звонок или запускать несколько микрофонов. Владелец соединения и медиаресурсов должен быть определён до реализации.
- Отдельный вход создаёт новую Auth-сессию; другая сессия не получает права управлять уже выбранным звонком. Просмотр общего состояния не равен праву управления.
- Выход и отзыв доступа прекращают локальное аудио и работу сессии. Неизвестный результат logout не отображается как подтверждённый сервером отзыв.
- Токены, WS-билеты и TURN credentials не передаются в URL, логи и экспорт диагностики. Билет используется для одной попытки подключения, после неясного результата запрашивается новый.

Реализованная модель: localStorage одного browser profile хранит access/refresh token, device_id и незавершённую операцию refresh с исходным request_id. Веб-приложение восстанавливает ту же сессию после перезагрузки и повторного открытия браузера, пока её не отозвал сервер. Хранилище доступно JavaScript того же origin; сторонние скрипты к клиентскому origin не подключаются. Это не HttpOnly cookie и не отдельный защищённый системный vault.

Web Locks сериализует ротацию refresh и выбирает одну вкладку-владельца WSS/микрофона. Дополнительная вкладка показывает на основном экране сообщение «Звонками управляет другая вкладка GChat» и кнопку «Открыть здесь» без включения диагностики. Передача управления доступна только при отсутствии незавершённого звонка. Пока вкладка-владелец подключается к серверу, основной экран объясняет временную недоступность кнопок звонка. BroadcastChannel передаёт другим вкладкам состояние интерфейса. Дополнительные вкладки показывают разговор без управления его медиаресурсами. Вне незавершённого звонка кнопка «Открыть здесь» в диагностике передаёт владение другой вкладке. Информация о другой вкладке также показывается только в диагностике, без плашки над содержимым страницы. При закрытии владельца следующая вкладка может восстановить ту же пару session/device; аудио всё равно подчиняется правилам autoplay. Выход действует на все вкладки этого browser profile. Самостоятельный вход другим аккаунтом выполняется в другом профиле/контексте либо после выхода из текущего.

После восстановления `connecting/active` доступ выбранного устройства подтверждается существующим `call.ice_config`; успешная выдача разрешена только выбранной паре device/session. Новые поля общего DTO для этого не вводятся. Счётчик пингов сохраняется по call_id. Для `ringing` используется сохранённый результат создания; неизвестный результат создания не разрешает автоматическое повторение или управление чужой выбранной парой.

После получения доступа клиент устанавливает авторизованный WS, выполняет `device.register`, получает `call.current` и загружает пользовательские списки. Данные интерфейса не заменяют серверные проверки прав перед командами.

## Звонки и медиасоединение

Протокол принадлежит [DirectCalls](../backend/modules/direct-calls/README.md) и [Signaling](../backend/modules/signaling.md). Веб-клиент применяет их DTO, версии, серверные сроки, пинги, выбранные устройства и `negotiation_id`. Собственных состояний backend или автоматического повторного `call.create` нет.

1. Пользователь нажимает кнопку с трубкой у участника группы, чтобы сразу начать звонок, либо открывает его карточку и подтверждает звонок. Перед созданием запрашивается микрофон. Получатель запрашивает его при действии «Принять», до `call.accept`; ожидание разрешения не продлевает серверный дедлайн.
2. После принятия выбранное устройство получает `call.ice_config` и создаёт RTCPeerConnection с `iceTransportPolicy: "relay"`. Только инициатор создаёт offer; получатель отвечает на текущую попытку. ICE буферизуется до remote description.
3. Пинги начинаются в `connecting`. Когда локальное соединение установлено, устройство отправляет `call.connected` для текущей попытки. Интерфейс разговора и его начало определяются серверным DTO.
4. При потере WSS восстанавливаются авторизация и актуальное состояние; сохраняются session/device и sequence. При необходимости медиапереустановки создаётся новая попытка в том же звонке. Дедлайны не продлеваются.
5. При `ended`, отзыве доступа или проигранном принятии освобождаются принадлежащие вкладке медиаресурсы. Проигравшая вкладка или устройство не пытается завершить разговор выбранного устройства.

Отказ микрофона и ошибка воспроизведения remote audio показываются пользователю отдельно от серверного результата звонка. При блокировке autoplay предоставляется явное действие включения звука. Выключенный микрофон и молчание не считаются разрывом соединения. Настройки недоступного в данном браузере аудиоустройства не показываются как работающие.

### Подготовка микрофона и звука

В настройках браузерного клиента рядом с уведомлениями доступны отдельные блоки «Микрофон» и «Динамики и звук». Они позволяют подготовить аудио до звонка, показывают понятное состояние и действия для устранения проблемы. Автоматический запрос разрешений, включение микрофона или тестового звука при открытии страницы не выполняются. Блоки переносятся из окна «Мой аккаунт» в модуль Settings по его принятому контракту; проверка реальных устройств и целевых браузеров остаётся частью приёмки. Во встроенном режиме управление аудио принадлежит нативному клиенту согласно [контракту bridge](#встроенный-web-и-capacitor-bridge).

Микрофон:

- Показываются состояния «Разрешение ещё не выдано», «Доступ разрешён», «Доступ заблокирован» и «Состояние разрешения неизвестно», если браузер не поддерживает его чтение. Отсутствие устройства и ошибка его открытия объясняются отдельно от отказа в разрешении.
- Состояние разрешения читается через Permissions API при наличии поддержки; ошибка или отсутствие API не считаются запретом микрофона. Состояние обновляется при доступном событии изменения разрешения и при возврате в приложение.
- Доступны действия «Разрешить микрофон» и «Проверить микрофон» по состоянию. Они вызывают `getUserMedia()` только по действию пользователя. Успешное открытие подтверждает доступность захвата в момент проверки; разрешение само по себе её не гарантирует. После предварительной проверки все созданные ею дорожки останавливаются; ресурсы текущего звонка не затрагиваются.
- При блокировке показывается инструкция разрешить микрофон в настройках сайта, браузера или ОС. Повторное нажатие не обещает новый системный диалог: его показ определяет браузер.
- Предварительная проверка не заменяет получение рабочего микрофона перед каждым `call.create` и `call.accept`. При отказе эти команды не отправляются; ожидание разрешения не продлевает серверный срок входящего вызова.

Динамики и звук:

- Показываются состояния «Звук ещё не проверен», «Воспроизведение доступно», «Нужно включить звук» при блокировке autoplay и понятная ошибка воспроизведения или выбора устройства. Для обычного воспроизведения через системное устройство не предполагается отдельное универсальное разрешение «на динамики».
- Кнопка «Проверить звук» по действию пользователя воспроизводит короткий тестовый сигнал через используемый клиентом аудиовыход. Тест можно остановить; по завершении его ресурсы освобождаются. Проверка звука не требует доступа к микрофону и не создаёт серверный звонок.
- Успешный запуск воспроизведения не доказывает физическую слышимость: пользователь подтверждает, слышен ли тест. Если звук не слышен, интерфейс предлагает проверить громкость, отключение звука вкладки, системный аудиовыход и подключённую гарнитуру. Без такого подтверждения интерфейс не утверждает, что динамики исправны.
- Выбор устройства вывода доступен только при поддержке браузером соответствующих API и разрешений. Системный выбор через `selectAudioOutput()` вызывается по действию пользователя, разрешённый выход применяется через `setSinkId()`. При отсутствии поддержки используется системный выход по умолчанию с подсказкой о его настройке в ОС; неработающий переключатель не показывается. Ограничения — в [Audio Output Devices API](https://www.w3.org/TR/audio-output/).
- Готовность воспроизведения проверяется по фактическому результату запуска звука звонка и оповещения; предварительный тест не гарантирует autoplay после перезагрузки или восстановления. При блокировке доступна кнопка «Включить звук» для повторного запуска по действию пользователя. Ошибки звука не подменяют серверное состояние звонка и не создают новый вызов.

Предварительные тесты выполняются только вкладкой — владельцем медиаресурсов и вне незавершённого звонка. Во время звонка тестовые действия недоступны с объяснением; включение заблокированного звука текущего звонка остаётся доступным. Сохранённый результат проверки не считается гарантией текущего доступа после изменения разрешений или аудиоустройств.

## Входящие вызовы и ограничения платформы

Полноценный веб-клиент должен иметь законченный сценарий входящего звонка в доступной странице: оповещение, принятие, отклонение и синхронизацию между устройствами. Ограничения autoplay и разрешений браузера должны быть видны пользователю и иметь понятные действия для настройки.

Для установки PWA, Web Push и кеширования фронта поручен отдельный объём; реализация и ограничения приведены в [разделе PWA](#pwa-web-push-и-кеширование). До проверки целевых браузеров нельзя обещать приём вызова при закрытом браузере. Браузер не регистрируется как устройство APNs VoIP.

Проверка открытой браузерной страницы не подтверждает системный входящий вызов на iPhone. Требования iOS по APNs/CallKit продолжают действовать отдельно.

## PWA, Web Push и кеширование

PWA реализована по принятому [D010](../architecture/decisions/D010-web-push-pwa.md): manifest, Web Push, кеширование фронта, кнопка обновления с защитой разговора, повторная привязка разрешённой подписки и восстановление после смены VAPID. Регистрация выполняется через WSS. Настоящая фоновая доставка и целевые браузеры требуют отдельной приёмки.

Отдельная экспериментальная сборка для [перехода Web Push → нативный GChat](../../applications/ios/web-push-launch-spike.md) проверяет открытие приложения без APNs-ключей. Эксперимент не меняет контракт обычной сборки и не подтверждает работу нативных звонков.

### Установка и разрешения

Manifest и существующие иконки адаптируются к размещению сборки: корневые `id/scope: /`, `start_url: /calls`; серверные `id/scope: /apps/client`, `start_url: /apps/client/calls`, иконки под `/apps/icons/`. Режим отображения — `standalone`.

Service worker регистрируется только в production-сборке браузерного режима на HTTPS или доверенном localhost. Scope соответствует базовому пути сборки: `/` либо `/apps/`. Встроенный Capacitor-клиент не регистрирует браузерные push и service worker этого контура. Vite dev не используется как проверка production-кеша.

В «Моём аккаунте» доступны состояние и включение/отключение уведомлений. Системное разрешение запрашивается только по явному нажатию. Отказ браузера, отсутствие Push API, серверное отключение и необходимость открыть основную вкладку объясняются пользователю. На iPhone/iPad Web Push требует поддерживающей ОС и установки на экран «Домой»; поддержка появилась с iOS/iPadOS 16.4. [Ограничения WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

### Подписка и входящий вызов

После `device.register` вкладка-владелец использует [команды Devices](../backend/modules/devices.md#web-push). Существующая подписка с ранее выданным разрешением восстанавливается при входе/переподключении без нового запроса разрешения. Перенос endpoint на новую сессию не переносит право управления звонком. Асинхронный результат прежней сессии не регистрируется для нового аккаунта.

Отключение удаляет серверную регистрацию и браузерную подписку. Logout отзывает сессию, после чего backend исключает её из доставки. Уже переданный провайдеру push может прийти позже; уведомление не содержит имени звонящего или данных аккаунта. Разрешение ОС остаётся настройкой пользователя и не сбрасывается программно.

Service worker показывает видимое уведомление с общей подписью входящего звонка. Повторы используют один tag на `call_id` и запрашивают повторный сигнал через `renotify: true` для неистёкшего вызова. Периодичность отправки принадлежит [Push](../backend/modules/push.md#доставка); звук и точный момент показа зависят от браузера и настроек ОС, непрерывный рингтон не гарантируется. Истёкший или некорректный payload даёт нейтральное уведомление «Откройте GChat, чтобы проверить звонки», без запроса повторного сигнала и без обещания текущего входящего. Это учитывает требование видимого уведомления Web Push; тихое фоновое исполнение не используется.

Нажатие фокусирует существующее окно GChat без перезагрузки, чтобы не прервать разговор, либо открывает фиксированный маршрут звонков своей сборки. URL из payload не исполняется. Клиент получает актуальное состояние через обычный `call.current`/`call.updated`; пуш не принимает вызов автоматически, не выдаёт право управления звонком и не возобновляет завершённый вызов. Service worker не получает refresh/access token и не выполняет команды звонка.

### Кеш фронта и обновления

На этапе сборки формируется версия кеша и список статических ресурсов. При установке worker загружает весь набор и сохраняет HTML той же сборки. Неуспешная загрузка ресурса или получение HTML вместо asset отменяет установку и удаляет неполный кеш.

Стратегия — cache-first для HTML клиентских маршрутов и явно перечисленных ресурсов своей сборки. Корневые клиентские маршруты — `/`, `/login`, `/calls`, `/admin` с вложенными путями; серверные — `/apps/client` с вложенными путями. Остальные запросы worker не перехватывает. HTTP API, WSS, данные аккаунта, ответы авторизации, TURN/SDP/ICE и чужие origin в Cache Storage не попадают. Кеш оболочки отделён от loaderData React Router, DialogRuntime и localStorage сессии.

При готовности новой версии клиент предлагает обновление через [модальный диалог](update-dialog.md); его показ, откладывание и визуальные требования определены в отдельном контракте. Явное подтверждение активирует установленную новую сборку и перезагружает клиент только когда ни в одном окне этого профиля нет незавершённого звонка; иначе обновление откладывается до его завершения. Обновление из другой вкладки также не должно прерывать звонок. Без явного действия worker не вызывает `skipWaiting` и сохраняет штатное ожидание закрытия старых клиентов. Вкладка-владелец удерживает общий Web Lock до закрытия WSS. Обновление ставит исключительный запрос в очередь до уведомления вкладок; свободный владелец закрывает транспорт, занятый ждёт завершения звонка и уже начатых команд. Новые владельцы ждут освобождения исключительного lock, который удерживается до перезагрузки. Смена controller перезагружает открытые клиенты только при замене worker. После безопасной активации удаляются только устаревшие кеши GChat для того же размещения. Корневой и серверный варианты имеют разные пространства имён кеша. При откате действуют те же правила установки и активации.

HTTP-раздача worker и manifest требует повторной проверки свежести (`Cache-Control: no-cache`); HTML с сервера сохраняет `no-store`. Service worker отдельно хранит публичную HTML-оболочку по этому контракту. Хешированные JS/CSS допускают длительный immutable-кеш. Развёртывание должно публиковать согласованную сборку целиком, включая иконки и worker.

Восстановление зависшего обновления старой сборки и предложение отдельной страницы восстановления описаны в [документе восстановления](update-recovery.md). Документ имеет статус draft; отдельная страница пока не реализована. Публикация исправленного JS не меняет код уже открытых старых окон.

Офлайн доступна оболочка; звонки, вход и обновление списков требуют сети. Установка PWA не даёт системного экрана звонка, автоматического ответа или гарантии работы браузерного звонка в фоне. Принудительное закрытие браузера, политика ОС, сеть и запрет уведомлений могут ограничить доставку.

### Приёмка и открытые вопросы

Проверяются обе сборки, прямое открытие вложенного URL офлайн после установки, полнота кеша и отсутствие API/токенов в нём, обновление и откат, старая открытая вкладка с разговором, частично опубликованная сборка, повторный push, поздний push, выход и смена аккаунта. Реальные доставка Web Push, iPhone с закрытой PWA и браузерные ограничения требуют отдельной ручной приёмки.

Целевые браузеры согласованы: Chrome, Edge, Firefox, Safari на macOS и установленная PWA на iOS/iPadOS. Конкретные минимальные версии и результаты проверки фиксируются при приёмке; включение Safari не означает, что проверка выполнена.

Смена VAPID-пары согласована: при следующем открытии клиент сверяет ключ существующей подписки с текущим публичным ключом backend и при несовпадении перевыпускает подписку, затем регистрирует её для текущей сессии. До успешного восстановления доставка на старую подписку недоступна; ошибка показывается с действием повтора. Запрет уведомлений не обходится. Владельцем правил ключей остаётся [Push](../backend/modules/push.md#контекст-и-вопрос-смены-vapid-ключей).

Открыты проверка списка push-провайдеров на целевых браузерах и техническая координация безопасного обновления нескольких окон. Регистрация через WSS, повторная привязка существующей разрешённой подписки и кнопка обновления с защитой звонка согласованы.

## Диагностика и приёмка

Диагностика скрыта для всех ролей по умолчанию. Кнопка и окно доступны только при наличии ключа `debug` в localStorage текущего origin (значение, включая пустую строку, не проверяется). Включение: `localStorage.setItem("debug", "1")`, затем обновление страницы; выключение: `localStorage.removeItem("debug")`, затем обновление. Изменения в другой вкладке синхронизируются через `storage`, при возврате фокуса флаг перечитывается. Флаг управляет только видимостью диагностического UI и не даёт дополнительных серверных прав.

Диагностика доступна отдельно от пользовательских действий: call_id, версия, сроки, попытка согласования, connection/ICE states и безопасные getStats. IP-адреса, SDP, ICE-кандидаты, токены и TURN credentials не включаются в журнал или его экспорт.

Все критерии ниже описывают будущую приёмку. Тестовые аккаунты и зависимости отделяются от рабочих; наличие документа не означает успешного прогона.

Приёмка подготовки аудио включает предварительную проверку микрофона и тестового звука без создания звонка; отказ и отзыв разрешения; отсутствие устройства и неподдерживаемый Permissions API; блокировку autoplay и повторное включение звука; слышимый и неслышимый тест; выбор аудиовыхода при поддержке и системный выход без неё. Отдельно проверяются освобождение тестовых ресурсов, отсутствие конкуренции вкладок, недоступность тестов во время звонка и сохранение обязательного получения микрофона перед созданием и принятием вызова. Эти проверки не считаются выполненными текущими тестами звонков.

| Сценарий                         | Ожидаемый результат                                                                                                                                                                                                                                      |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Вход и возврат в приложение      | Понятный экран входа; сохранённая сессия восстанавливается согласно принятой модели без нового входа при обычной перезагрузке.                                                                                                                           |
| Группы и участники               | Доступ к группам и собеседникам соответствует роли по Groups, включая администратора без собственной группы; отключённые аккаунты исключены сервером.                                                                                                    |
| Пустые списки и ошибки API       | Интерфейс объясняет отсутствие групп/собеседников, предлагает повтор после сбоя и корректно обрабатывает потерю доступа.                                                                                                                                 |
| Исходящий звонок                 | Трубка в списке сразу начинает звонок; из карточки требуется подтверждение, его отмена ничего не создаёт.                                                                                                                                                |
| Входящий и разговор              | Оповещение, принятие и два подтверждения одной попытки дают `active`; слышимость вручную проверена в обе стороны.                                                                                                                                        |
| Аудиомаршрут                     | Через getStats подтверждены relay candidate pair и рост входящих/исходящих RTP-счётчиков. При недоступном coturn P2P не используется.                                                                                                                    |
| Отмена / отклонение / завершение | Оба клиента получают один конечный результат, таймер и микрофон прекращают работу.                                                                                                                                                                       |
| Повторный звонок                 | Новый исходящий после завершённого начинает переговоры без перезагрузки страницы и закрытия карточки результата. Очистка прежнего звонка не останавливает микрофон новой попытки; порядок ответа call.create и события call.updated не меняет результат. |
| Занятость / встречные вызовы     | Один незавершённый звонок на пользователя; конкурентный запрос получает предусмотренную ошибку.                                                                                                                                                          |
| Несколько устройств и вкладок    | Выбран один медиаклиент; остальные не мешают разговору и корректно показывают актуальное состояние.                                                                                                                                                      |
| Перезагрузка / reconnect         | Сохраняются сессия, устройство и порядок пингов; выбранное устройство подтверждается сервером, сроки не продлеваются.                                                                                                                                    |
| Потеря аудио / сети              | Понятное восстановление; старые версии, ICE и подтверждения не возобновляют другую попытку или завершённый звонок.                                                                                                                                       |
| Отзыв / отключение аккаунта      | Доступ и локальное аудио прекращаются, собеседник получает серверное завершение.                                                                                                                                                                         |
| Доступность интерфейса           | Основные сценарии доступны с клавиатуры, на узком экране и при отказе разрешений микрофона/оповещений.                                                                                                                                                   |
| Веб ↔ веб / веб ↔ iOS            | Проверяется совместимость общего протокола. iOS-сценарий принимается после готовности нативного клиента и его инфраструктуры.                                                                                                                            |

Unit-тесты проверяют управление сессией и ресурсами, корреляцию ответов и применение версий. End-to-end тесты звонка используют настоящий backend, PostgreSQL/Redis и coturn; подмена WebSocket или PeerConnection не доказывает передачу аудио. Искусственный источник аудио допускается для автоматизации, но не заменяет ручную проверку микрофонов и слышимости в разных сетях.

Системные E2E принадлежат общему модулю над приложениями: project `web` проверяет настоящий веб-клиент, передачу WAV-микрофона и входящий PCM, mute/unmute и разговор через реальное истечение JWT и refresh, project `protocol` — общий механизм независимыми участниками, включая декодирование разных тестовых тонов, конкуренцию, сроки и восстановление. Оба набора запускаются и обслуживаются в одном модуле. Покрытие, границы и команды — в [README системных E2E](../../tests/e2e/README.md); iOS пока не подключён к автоматизации.

Точные команды и поддержанные версии браузеров фиксируются при реализации и проверке. В отчёте разделяются автоматические, ручные и непройденные сценарии. Диагностика помогает тестированию, но не подменяет пользовательскую приёмку приложения.

## Границы реализации и открытые вопросы

- API списков возвращает полные доступные группы/участников без пагинации; данные обновляются при фокусе и раз в минуту. Сортировка определяется контрактом Groups. Нагрузочная проверка больших списков не выполнена.
- Имена доступны из групп; получение профиля участника уже созданного звонка после потери общего членства отдельным API не реализовано. Пока используется последняя известная подпись или «Собеседник», без обхода прав доступа.
- Звук входящего вызова включается пользовательским действием через настройки звука; после перезагрузки браузер может снова потребовать такое действие. Remote audio имеет отдельное действие при блокировке autoplay.
- Автоматизация выполнена в Chromium с искусственным микрофоном и локальным coturn. Ручная слышимость между разными сетями, Safari, реальные мобильные браузеры и совместимость с ещё не готовым нативным клиентом остаются отдельными проверками.
- Web Push, PWA и кеширование фронта поручены, контракт находится в [разделе PWA](#pwa-web-push-и-кеширование). Фоновая доставка и целевые браузеры не прошли приёмку; постоянная сессия не является обещанием приёма вызова при закрытом браузере.
- Рабочий backend сохраняет обязательную APNs-конфигурацию. Локальный стенд генерирует синтетический тестовый ключ, не регистрирует VoIP-токены и не отправляет APNs; режим отключённого Push этим не вводится.

# Motion в Web/PWA: границы и порядок внедрения

Согласовано пользователем 2026-11-15: точечное применение Motion для жестов и локальных переходов Web/PWA по описанным ниже границам. Первый этап — свайп ответа; последующие области из карты применения рассматриваются отдельно. Зависимость Motion пока отсутствует в [манифесте Web](../../applications/web/package.json). Согласование решения не означает наличия реализации или завершённой приёмки. Готовность конкретных этапов описана в конце документа.

Motion используется точечно для жестов и локальных переходов интерфейса. Начать со свайпа сообщения, затем проверить ползунок защиты экрана звонка и меню сообщения. Навигация остаётся на React ViewTransition, простые и бесконечные анимации — на CSS. Более плавное ощущение и приемлемая стоимость загрузки подтверждаются измерениями и проверкой на iPhone.

## Основания и действующие ограничения

- Пользователь сообщил, что после исправления медленного свайпа ответ стал доступнее, но взаимодействие всё ещё ощущается хуже нативного. Оставшийся недостаток на устройстве не локализован: задержка распознавания, конкуренция с прокруткой и характер возврата требуют отдельной проверки. Наличие библиотеки само по себе не устанавливает причину.
- Уточнение пользователя 2026-11-16 о законченном интерфейсе с качеством нативного взаимодействия раскрыто в [контракте качества свайпа](../backend/modules/dialogs/message-replies.md#ожидаемое-качество-взаимодействия). Оно задаёт ожидаемый пользовательский результат и не является согласованием числовых параметров из чернового предложения.
- [Зимнее оформление](../design/winter-theme-task.md#анимации-только-средствами-css) сохраняет CSS как основной механизм и разрешает точечное исключение для Motion по этому документу. Первое применение — свайп ответа; другие области требуют готового профильного описания своего этапа.
- [Контракт ответа](../backend/modules/dialogs/message-replies.md#мобильный-свайп-для-ответа) задаёт распознавание жеста и переход на Motion для движения и пружинного возврата. Сохраняется жёсткий предел смещения; инерционный полёт отключён. Функциональные права, пороги, отмена и выбор ответа остаются у этого контракта.
- [Маршрутные переходы](../design/winter-theme-task.md#механизм-переходов--согласовано) уже используют постоянные границы React ViewTransition. Предложение не заменяет этот механизм и не добавляет параллельную анимацию того же перехода.
- Backend и Web/PWA входят в текущий объём. Нативный iOS-клиент временно deprecated по [приоритету платформ](../product/requirements.md#текущий-приоритет-платформ). Работа Motion в установленной iPhone PWA не означает внедрение нативных UIKit-жестов.

Документы-владельцы обновлены в части принятого первого этапа. Правила остальных взаимодействий продолжают действовать; их миграция не выполняется автоматически вслед за добавлением зависимости.

## Что даёт библиотека

[Motion drag](https://motion.dev/docs/react-drag) предоставляет перетаскивание, ограничения, выбор оси и настройку упругости. Это основа движения; выбор сообщения для ответа, права, долгий тап и отмена остаются логикой GChat.

[Motion values](https://motion.dev/docs/react-motion-value) позволяют обновлять визуальные значения без React-перерисовки на каждом изменении. Это полезно для жестов, однако текущий свайп уже меняет CSS-переменные напрямую: уменьшение числа React-рендеров не является доказанным выигрышем именно для него. У ползунка защиты экрана сейчас другая реализация — React state обновляется на каждом pointermove.

[AnimatePresence](https://motion.dev/docs/react-animate-presence) позволяет завершать анимацию выхода до удаления DOM. Это полезно для локальных панелей, но требует особенно внимательно отделять визуальное присутствие от доступности команд и срока жизни данных.

Сравнительного замера производительности библиотек и прототипа Motion в GChat пока нет. Утверждения о гарантированных 60/120 FPS, меньшем размере итоговой сборки или полном совпадении с нативным интерфейсом не делаются.

### Выявленное расхождение у ползунка

[Веб-контракт защиты](README.md#защита-от-нажатий-и-аудиовыход-в-окне-звонка) описывает движение «до конца». В текущем `CallScreenLock.tsx` условие использует 90% доступного хода (`start.distance * 0.9`). Перенос на Motion не должен молча закрепить одно из этих значений. Перед вторым этапом требуется согласовать точный критерий с владельцем контракта. До этого этап не готов к реализации.

## Предлагаемые технические правила

### Владение и размещение

- Добавить одну зависимость `motion` в Web после согласования. Версию, peer dependencies и совместимость с установленными React/TypeScript фиксировать по актуальному пакету и lock-файлу при внедрении. Motion+, react-spring, use-gesture и компоненты свайпа дополнительно не требуются для предложенного первого этапа.
- Поведение ответа остаётся в `features/dialogs`, защита экрана — в `features/calls`. Общие параметры и действительно переиспользуемая анимационная обвязка могут находиться в `shared/ui`, без импорта предметных разделов из shared. Не создавать универсальный менеджер жестов или второй UI runtime заранее.
- Координату жеста хранить в motion value. React state использовать для смысловых переходов: выбран ответ, открыто меню, жест завершён. Не перерисовывать ленту на каждом перемещении пальца.
- Один элемент имеет одного владельца transform. После миграции удалить конкурирующий CSS transition/inline transform только у переносимого элемента. Позиционирующую и анимируемую обёртки разделять; transform родителя не должен менять систему координат fixed-потомков или измерения popover.
- Motion не владеет Router, сессией, runtime, outbox, доступом или повтором команд. Нельзя ставить отправку, разблокировку, принятие/завершение звонка или запись черновика в callback окончания анимации.

### Загрузка

Предпочтительно загружать Motion в существующем ленивом модуле переписки. Для жестов допустима синхронная загрузка вместе с этим модулем: первое касание уже отображённого пузырька не должно ждать отдельного импорта движка. Не включать Motion в общий barrel UI kit так, чтобы он начал загружаться на экране входа и во всех настройках.

При расширении применения сравнить прямой импорт и `LazyMotion` с `m`. Согласно [руководству по размеру сборки](https://motion.dev/docs/react-reduce-bundle-size), набор `domAnimation` не включает drag/pan; для такого варианта необходим соответствующий набор возможностей, например `domMax`. Числа размера из сайта библиотеки не считаются размером добавки в GChat: измеряются реальные production-чанки, gzip и момент их загрузки в корневой и серверной сборках.

Для звонков важнее немедленная доступность управления: отказ импорта анимации не должен скрывать существующие базовые действия. Подключение Motion к общему Modal оценивается отдельно, поскольку Modal используется за пределами переписки и может расширить загрузку библиотеки на всё приложение.

### Жесты и состояние

Для свайпа сохраняются условия старта, пороги и исключения [контракта ответов](../backend/modules/dialogs/message-replies.md#мобильный-свайп-для-ответа). Нового ограничения скорости или длительности жеста не вводится. Плавный короткий шаг и небольшое диагональное отклонение должны оставаться пригодными для распознавания.

Палец непосредственно управляет положением без пружинного запаздывания во время удержания. Пружина применяется только к возврату. Инерционный полёт после отпускания отключён. Сохраняется жёсткий предел визуального хода; упругий выход за него не входит в первый этап.

Порог действия определяется координатами реального жеста, а не текущим кадром возврата, скоростью или выходом пружины за границу. Отмена указателя, потеря доступа, смена диалога/сессии и уход элемента из DOM прекращают жест и очищают визуальное состояние. Ни exit, ни отложенный callback не могут выбрать ответ после такой отмены.

Горизонтальный drag сосуществует с браузерным вертикальным pan и pinch zoom. `touch-action` задаётся до начала жеста. Способ разграничения направлений проверяется на Safari/iPhone; переключение `touch-action` после начала жеста не считается решением. Долгое нажатие и drag должны иметь единое согласованное распознавание без двух независимых обработчиков, которые могут открыть меню и ответить одновременно.

### Присутствие и закрытие

Первое применение к popover/dialog ограничить входом внутреннего содержимого. Внешний контейнер сохраняет top layer, позиционирование и семантику фокуса. Не превращать окно в обычный div ради анимации и не добавлять закрытие свайпом, которого нет в контракте.

Общий exit не включать автоматически. AnimatePresence удерживает уходящий DOM: это может продлить жизнь формы, подписки и обработчиков. Потеря доступа, смена сессии, завершение звонка и закрытие защитной панели удаляют соответствующее содержимое немедленно. Для будущего exit по обычной отмене отдельно описать момент блокировки взаимодействия, фокус и доступность уходящего представления; декоративная копия текста сообщения не создаётся.

### Токены, доступность и производительность

Параметры движения принадлежат общей системе [токенов UI kit](README.md#токены-ui-kit). Длительности и easing используют существующие значения. Параметры пружины stiffness/damping/mass задаются отдельными семантическими токенами после выбора профиля возврата: физические параметры нельзя автоматически вывести из одной CSS-длительности. Преобразование CSS-значений в настройки Motion централизуется, учитывает единицы и обновление конфигурации; компоненты не копируют числовые пресеты.

Предлагается анимировать только transform/opacity, без height, padding, top/left, фильтров и теней. Это соответствует [рекомендациям Motion по производительности](https://motion.dev/docs/performance) и сохраняемой части дизайн-контракта. Не включать глобальный layout, shared layout между маршрутами или анимацию каждого emoji сетки. Изменение доступной высоты при клавиатуре и скролле применяется позиционером сразу.

Использовать системный reduced motion. [MotionConfig и useReducedMotion](https://motion.dev/docs/react-accessibility) дают механизмы учёта настройки, но автоматическая политика не отменяет все виды движения: opacity может продолжить анимироваться. Для GChat предлагается явная политика: прямое следование пальцу сохраняется, автоматический возврат/вход/выход становятся мгновенными, никаких ожиданий callback отключённой анимации.

Сохраняются доступные команды с клавиатуры/экранного диктора, видимый фокус, роли и области нажатия из профильных контрактов. Motion не добавляет вибрацию или нативный haptic feedback; это отдельная платформенная возможность, не входящая в предложение.

## Порядок внедрения

1. Первый этап, исключение из CSS-правила, пружинный возврат без инерционного полёта и сохранение жёсткого предела смещения согласованы. Перед реализацией определить оставшиеся параметры возврата по разделу готовности. Дополнительные кандидаты остаются последующими этапами.
2. Снять исходное поведение свайпа на одном физическом iPhone: обычное и медленное движение, диагональ, прокрутка, клавиатура, работающий звонок. Зафиксировать модель, iOS, standalone/вкладку и версию сборки.
3. Реализовать один свайп ответа с Motion, сохранив существующую ленту и runtime. Проверить установленную PWA до расширения на другие элементы. Не менять библиотеку виртуализации и маршрутизацию в этой задаче.
4. Сравнить с исходной реализацией: плавность, отмены, задержка старта, React commits, длинные задачи и размер загрузки. Если остаточная проблема вызвана разграничением браузерной прокрутки, сначала исправить это взаимодействие; пружинная анимация его не маскирует.
5. При успешной приёмке отдельно согласовать ползунок защиты и меню. Затем рассмотреть панели Composer и общий Modal. Каждый этап проверяется и может быть отменён без миграции backend или пользовательских данных.

## Согласованные решения и готовность этапов

Пользователь принял 2026-11-15 рекомендацию начать со свайпа ответа, разрешить Motion как точечное исключение из CSS-правила, сохранить жёсткий предел смещения и использовать пружину только для возврата без инерционного полёта. Навигация остаётся на React ViewTransition. Карта остальных применений принята как направление развития; готовность каждого последующего этапа устанавливается отдельно. Для общих модальных окон принят рекомендуемый начальный объём — только вход содержимого; exit в него не входит.

Принятие направления не закрывает вопросы, для которых в проекте не было конкретного предложенного значения:

- Для первого этапа профиль пружины и измеримые границы приёмки ещё не определены. Вопрос и готовность переноса свайпа находятся у [контракта ответа](../backend/modules/dialogs/message-replies.md#открытые-решения). До уточнения этого пункта реализация переноса не начинается; исходные измерения существующего свайпа допустимы.
- Для ползунка защиты сохраняется расхождение полного хода и текущих 90%, описанное выше. Оно блокирует только этап ползунка; общее согласование Motion не выбирает за пользователя один из порогов.
- Exit модальных окон остаётся вне принятого объёма. Если он потребуется, момент закрытия, удержание DOM и возврат фокуса описываются отдельным уточнением.

`decision_status: accepted` фиксирует согласование границ и порядка внедрения, но не заявляет готовность этапов с перечисленными открытыми решениями. Значения `source: null`, `tests: []` и `implementation_status: absent` относятся к внедрению Motion, а не к отсутствию существующих жестов и браузерных тестов GChat.

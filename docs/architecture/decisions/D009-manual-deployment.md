# D009: ручной деплой на существующий сервер

Дата: 2026-11-05.

## Контекст

GChat требуется простой воспроизводимый выпуск. Уже есть сервер в Яндекс Cloud; пользователь согласовал использование GitHub Actions для сборки Docker-образа и nginx-конфига с последующей передачей на сервер и запуском приложения. Дополнительные платные сервисы не требуются.

## Решение

Сборка и выкладка используют отдельные workflow: сборка публикует релиз, а deploy-job скачивает выбранный опубликованный комплект без повторной сборки. Оператор запускает сборку через `workflow_dispatch` / Run workflow и выбирает, выполнять ли затем деплой; также сохраняется отдельный ручной запуск деплоя готового тега. Пуши, pull requests и теги не выкатывают приложение автоматически. GitHub Actions собирает артефакты и передаёт их на существующий сервер по SSH. В базовом варианте Docker Registry не используется. На сервере загружается готовый образ, отдельно применяются миграции, запускается приложение и проверяется готовность.

Существующие данные и секреты хранятся на сервере отдельно от релиза. Инфраструктура самостоятельного GChat изолирована от legacy Mattermost/Jitsi.

Для более сложных окружений предоставляются готовые Docker-образы всех собственных самостоятельно развёртываемых серверных компонентов GChat. Владелец окружения выбирает способ оркестрации и доставки. Готовые Helm charts и Kubernetes-манифесты в текущий объём не входят. Все Docker-образы собственных компонентов публикуются в GitHub Releases соответствующей версии приложения как скачиваемые архивы, вместе с manifest и контрольными суммами. Для базового деплоя используется та же сборка. Сама публикация релиза не является триггером выкладки; продолжение ручной сборки определяется выбранным оператором параметром деплоя. Состав образов и границы внешних зависимостей описаны в [основном документе](../../operations/deployment.md#поставка-для-сложных-окружений).

## Согласованное продолжение сборки деплоем

По запросу от 2026-11-07 согласовано изменение ручного процесса; этот раздел готов к реализации независимо от открытых вопросов подготовки сервера в основном документе.

- В форме **GChat build release** есть boolean-параметр `deploy` («Deploy after build»), включённый по умолчанию.
- При включённом параметре после успешных проверок, сборки и публикации отдельное задание вызывает существующий workflow деплоя с точным тегом, вычисленным в этой сборке. Выбор `latest` и повторная сборка исключены.
- При выключенном параметре выполняются только проверки, сборка и публикация; доступ к серверу не требуется. Ошибка или отмена сборки/публикации блокирует деплой.
- **GChat deploy release** сохраняет ручной запуск с параметром `version` и дополнительно поддерживает вызов из workflow сборки через `workflow_call`. Оба пути используют одни шаги доставки, настройки, SSH-секреты и блокировку `gchat-production-deploy`.
- Ошибка деплоя делает итог запуска сборки неуспешным, но опубликованный релиз сохраняется для повторной ручной выкладки.

Критерии приёмки: галочка изначально включена; успешная сборка передаёт собственный тег в deploy-job; снятая галочка, ошибка и отмена сборки не запускают доставку; ручной деплой продолжает принимать выбранный тег; оба пути исключают одновременную выкладку.

## Согласованный быстрый выпуск

По запросу от 2026-11-07 согласован boolean-параметр `fast` («Fast: skip checks») в форме **GChat build release**, выключенный по умолчанию. Этот раздел готов к реализации.

При `fast=false` сохраняется полный набор проверок. При `fast=true` пропускаются отдельные проверки backend, SDK, Web, документации и deploy-скриптов, Chromium PWA и smoke-тест образа через HTTPS. Установка зависимостей и отдельная сборка Web на runner, необходимые для этих проверок, также пропускаются. Docker-сборка продолжает устанавливать зависимости и компилировать backend и Web штатными командами; встроенные в сборку проверки и контроль целостности релизного комплекта сохраняются.

Вычисление версии, сборка образа, упаковка и публикация релиза выполняются в обоих режимах. Галочка `deploy` сохраняет прежнее значение по умолчанию и самостоятельно управляет последующим деплоем; серверные проверки установки сохраняются. Ошибка сборки или публикации блокирует деплой и в быстром режиме.

Критерии приёмки: `fast` изначально выключен; включение пропускает все отдельные шаги проверок и подготовку их окружения, но сохраняет Docker-сборку, публикацию и выбор деплоя; выключение сохраняет полный прогон.

## Последствия и границы согласования

Сборка не требует инструментов разработки на сервере и подписки на registry. Сохраняются существующие расходы Яндекс Cloud; бесплатность Actions ограничена включённой квотой. Обновление одного экземпляра приложения допускает обслуживающий перерыв.

Основной документ — [развёртывание GChat](../../operations/deployment.md): он содержит технический проект, критерии приёмки и открытые вопросы. Согласован способ доставки, а не каждая деталь проекта. Статус accepted этой записи не означает, что production-комплект реализован или что draft-детали основного документа приняты. Дополнительно согласованы nginx на хосте, TLS через Let’s Encrypt с автоматическим продлением и раздача Web из backend под `/apps/client` с перенаправлением `/`. Параметры сервера заполняются после подготовки GitHub Actions; эксплуатационные детали и границы проверки ведутся в основном документе.

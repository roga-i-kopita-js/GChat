# D008: Capacitor bridge для Web-клиента и нативных звонков

Публичный Web/native API, native HTTP-транспорт и управление router теперь определены в принятой [спецификации device](../../web/device-api.md). Эти границы обязательны для следующей интеграции; остальной статус draft и Gate 1/2 этого решения не меняются. Текущая реализация ещё использует прежние HTTP-вызовы из WebView до миграции.

Дата: 2026-11-05. Пользователь поручил подготовить документацию интеграции Capacitor, переиспользовать готовый Web-клиент и оставить весь звонок нативным, включая работу в фоне и при заблокированном экране.

Статус `draft`: это предложение для обсуждения, а не отчёт о реализации. Текущий объём решения — iOS-приложение с переиспользованием Web-клиента; минимальная версия первого релиза — iOS 16.0. По итогам обсуждения 2026-11-05 согласованы направления: Web работает в двух режимах: автономный сохраняет текущую браузерную авторизацию, встроенный получает от native только краткоживущий access token и сам запрашивает необходимые данные у backend. Во встроенном режиме native управляет жизненным циклом авторизации и даёт Web команды показа интерфейса. Web показывает форму и передаёт введённые логин и пароль native; native выполняет HTTP login, сохраняет сессию, выполняет refresh и logout; Web вызывает SDK через device; HTTP-запросы к backend выполняет нативный транспорт по контракту device. Стартовая форма сервера поставляется отдельным Web-приложением внутри нативной сборки; основной Web доступен на выбранном backend по `/apps/client`, а его статические файлы — по `/apps/static/:filename`. Механизм production-загрузки проверяется техническим spike; Web обновляется и откатывается через backend с сохранением совместимости bridge. Native call engine использует libwebrtc из официального WebRTC upstream, собранный в XCFramework на зафиксированном commit и подключённый как версионированный бинарный артефакт с checksum; приложение содержит тонкий собственный адаптер под DirectCalls. Нативный код пишется отдельно под платформы: Swift для iOS и Kotlin для Android, если Android вернётся в scope; Kotlin Multiplatform не вводится. iOS spike на реальном устройстве проверяет сборку, аудиомаршрутизацию, TURN-only и работу звонка в фоне. Точный commit и артефакт фиксируются после успешной проверки. По последующему поручению реализована [Web-сторона bridge](../../web/README.md#встроенный-web-и-capacitor-bridge) с `@capacitor/core`; Добавлена [iOS-оболочка](../../../applications/ios/README.md): Xcode-проект, Swift-плагин, нативная сессия и загрузка Web для spike. Общий нативный WSS и JSON-транспорт bridge реализованы с политикой запретов из Signaling. Call engine отсутствует; оболочка возвращает `nativeCalls: false`, Web отключает звонки. Порядок установки на Simulator и физический iPhone и текущие границы проверок ведутся в [README iOS](../../../applications/ios/README.md#проверки-и-ограничения). Это не закрывает технические spike и физическую приёмку.

## Контекст

GChat Web уже содержит пользовательский интерфейс входа, групп, контактов и администрирования, а также браузерный клиент звонков. Web использует `RTCPeerConnection`, `getUserMedia`, WebSocket и браузерные хранилища. Упаковка текущего звонкового клиента в WebView не обеспечивает требуемую независимость звонка от JavaScript и жизненного цикла WebView.

Нужно переиспользовать интерфейс Web, не создавая параллельные мобильные экраны для обычной работы, и при этом позволить звонку продолжаться при сворачивании приложения и блокировке экрана. На мобильной платформе системный входящий и активный звонок, сигнализация, WebRTC и управление аудио должны принадлежать нативному модулю. Серверное состояние и правила звонка остаются в [DirectCalls](../../backend/modules/direct-calls/README.md) и [Signaling](../../backend/modules/signaling.md).

## Предлагаемое решение

### Границы исполнения

- Capacitor загружает основной Web-клиент с выбранного backend по `/apps/client`; его статические файлы раздаются отдельно по `/apps/static/:filename`. Отдельное минимальное стартовое Web-приложение с формой адреса сервера включается в нативную сборку. Основной клиент переиспользует `applications/web`; отдельный форк его экранов, навигации и стилей не создаётся. Поддерживаемые мобильные сценарии Web остаются частью этого приложения.
- Web отвечает за группы, контакты, подтверждение исходящего звонка и остальные общие продуктовые экраны. Входной интерфейс Web используется в обоих режимах. Во встроенном режиме Web показывает форму по команде native и передаёт введённые данные native; HTTP login, refresh и logout выполняет native.
- Нажатие «позвонить» передаёт команду через Capacitor bridge. После неё звонком владеет нативный call engine; входящий звонок может быть принят из системного UI без запущенного WebView.
- Нативный модуль владеет WebSocket, командами и событиями DirectCalls, WebRTC через нативный API, микрофоном, аудиосессией, системным UI звонка и обработкой push. WebView не запускает параллельный Web-звонок.
- Native call engine использует libwebrtc из официального WebRTC upstream в виде XCFramework, собранного на зафиксированном commit и подключённого как версионированный бинарный артефакт с checksum. Собственный тонкий адаптер реализует интеграцию с общим Signaling/DirectCalls-контрактом; сторонние Swift-обёртки и неподдерживаемые бинарные пакеты не становятся дополнительной архитектурной зависимостью.
- Нативные call engine реализуются отдельно для каждой ОС: iOS — Swift, Android вне текущего scope — Kotlin. Kotlin Multiplatform и общий нативный runtime не вводятся; общими остаются backend-протокол, поведенческие требования и межплатформенные тестовые сценарии.
- При потере сети native поведенчески повторяет текущую recovery-логику Web: переподключается с той же retry/backoff-политикой, после регистрации запрашивает `call.current`, сохраняет монотонный sequence пингов и отправляет `call.ping` сразу и далее каждые 10 секунд с актуальными `audio_connected` и `recovery_id`; состояние применяет по версии и восстанавливает медиа через существующий Signaling/DirectCalls-протокол. Неизвестный результат `call.create` не приводит к автоматическому повтору. Browser-specific механизмы (`localStorage`, Web Locks) не портируются буквально; используется native-хранилище и нативное владение соединением. Поведенческий референс — [Web call client](../../../applications/web/src/features/calls/client.ts).
- Текущее браузерное исполнение сохраняется: в обычном браузере Web продолжает использовать существующий звонковый клиент. Capacitor и нативные модули выбираются через адаптер платформы.
- Backend остаётся авторитетным для состояний звонка, доступа, таймаутов и результата; локальные состояния Web и нативного UI не заменяют его.
- Входящий `ringing` одновременно доступен всем подключённым авторизованным клиентам через `call.updated`; VoIP push нативным устройствам работает независимо и не имеет приоритета. Web и native могут показать один и тот же вызов. Первое принятое сервером подтверждение атомарно выбирает устройство-победителя для разговора; остальные клиенты закрывают входящий UI по `call.updated`. Это соответствует правилу [DirectCalls «Несколько устройств получателя»](../../backend/modules/direct-calls/README.md#несколько-устройств-получателя--согласовано).
- VoIP payload передаёт `caller_display_name` для немедленного отображения в системном UI; остальные профильные данные не добавляются. Push остаётся недоверенным снимком: native подтверждает актуальность звонка через сервер. Подробный формат принадлежит [Push](../../backend/modules/push.md).
- Звонковый push не означает приоритет или эксклюзивное владение native-клиентом. APNs `200` не подтверждает доставку на устройство; если push задержан или не доставлен, любой другой подключённый клиент всё равно может принять уже доставленный ему `call.updated`. Отдельная логика per-call fallback не нужна.
- Звонки из обычного мобильного браузера поддерживаются в foreground. Работа после сворачивания браузера или блокировки экрана — best effort: приостановка страницы может остановить WSS/прикладные `call.ping`, после чего применяются штатные DirectCalls recovery/timeout и звонок может завершиться. Автоматический handoff в приложение не выполняется; Web предупреждает, что надёжная работа в фоне доступна в GChat app.
- После принудительного закрытия GChat пользователем (force quit/force stop) ОС может не разбудить native-приложение по push, поэтому доставка на это устройство не гарантируется. Если звонок доступен другому подключённому Web или native клиенту, тот может принять его по общему правилу первого ответа; если активных клиентов нет, вызов завершится по штатному `no_answer`. Это не fallback, а независимая доставка всем доступным клиентам.
- После перезагрузки устройства native target должен восстанавливаться и принимать push без обязательного ручного запуска GChat, используя сохранённую native-сессию и системную push-регистрацию. Это best effort: доставка зависит от готовности ОС, разблокирования устройства и сети. Другие подключённые клиенты могут принять вызов, не ожидая результата push.
- Если пользователь запретил необходимые системные уведомления/разрешения звонка, приложение явно показывает ограниченную доступность входящих и путь в настройки iOS. Доставка/системное оповещение на native-устройстве может быть ограничено; другие подключённые Web или native клиенты остаются равноправными получателями и могут ответить. Точные системные ограничения проверяются на поддерживаемых версиях iOS.
- Handoff уже созданного или активного звонка между браузерным и native call engine не входит в MVP. Один звонок остаётся закреплён за выбранным устройством/сессией; чтобы перейти с браузерного исходящего звонка на надёжную фоновую работу, пользователь завершает его и начинает новый звонок в приложении.

### Общий нативный WSS и доступ Web через bridge

Согласовано универсальное расширение bridge: встроенный Web отправляет и получает сообщения через общее нативное WSS-соединение. Мотивация — переиспользовать соединение для будущих Web-функций, включая переписку, без дополнительного сокета и обновления оболочки при появлении новых типов сообщений. Владение соединением остаётся у native, звонок — у нативного движка; встроенный Web не запускает параллельный браузерный call engine.

Контракт и границы безопасности ведутся в [Web: общий WebSocket через native](../../web/README.md#общий-websocket-через-native). Типы сообщений не зашиты в оболочку: ограничения отправки и получения конфигурируются в [БД Signaling](../../backend/modules/signaling.md#ограничения-web-сообщений-через-native-bridge), чтобы менять scope без выпуска приложения. Мотивация ограничений — исключить вмешательство Web в нативный звонок и передачу его служебной сигнализации. Маскирование payload и серверные пометки скрытия не вводятся; отдельные UI-события звонка по-прежнему не содержат SDP/ICE и транспортных секретов. WSS и универсальный транспорт bridge реализованы в NativeCore и адаптерах Swift/Web; сквозная интеграция общего WSS на iOS ещё не прошла приёмку. Это не меняет статус остальных частей D008 и не означает реализацию мессенджера.

### Два режима Web и единый интерфейс сессии

Web имеет два явно выбираемых при старте режима. Общие экраны и HTTP SDK используют единый интерфейс сессии; детали хранения и конкретный протокол refresh скрыты за адаптером.

- **Автономный режим (browser adapter)** сохраняет текущую реализацию: Web показывает вход, выполняет login, хранит сессию в `localStorage`, сериализует refresh через `navigator.locks` с сохранением `request_id`, выполняет logout и межвкладочную синхронизацию.
- **Встроенный режим (native adapter)** управляется native. Native проверяет сессию и командует Web показать форму входа или основной интерфейс. Web передаёт выбранный адрес сервера и введённые логин и пароль через `login({serverUrl, login, password})`; HTTP login выполняет native и надёжно сохраняет результат. Native с самого начала владеет сессией, выполняет refresh/logout и обслуживает звонки независимо от WebView. Web получает от native только access token, а данные пользователя, групп, контактов и администрирования запрашивает самостоятельно. HTTP login/refresh/logout из встроенного Web не выполняются. Refresh token не проходит через Web или bridge.

HTTP-запросы общих экранов в обоих режимах выполняет сам Web через существующий SDK. Во встроенном режиме HTTP-транспорт использует access token, переданный native в `route(...)` и сохранённый только в памяти Web; при необходимости получает актуальный токен через `getAccessToken`. После `ACCESS_TOKEN_EXPIRED` общий HTTP-слой однократно повторяет операцию, запросив токен через адаптер с признаком принудительного обновления; сам refresh выполняет владелец сессии. Долговременная копия мобильного токена в Web не создаётся.

Это позволяет разрабатывать общие экраны в автономном режиме и развивать Web-интерфейс независимо от реализации нативной авторизации при сохранении совместимости backend API и bridge. Web assets доставляются и обновляются через backend по правилам ниже; проверка production-загрузки в Capacitor остаётся обязательной.

Во встроенном режиме Web получает access token в аргументах `route(...)`, при необходимости обновляет его через `getAccessToken` и самостоятельно загружает необходимые ему данные. Native не передаёт отдельный DTO пользователя, роли или имени. Выбор между входом и основным интерфейсом принадлежит native: Web выполняет его команду `route(path, options?)` через существующий React Router. Отсутствие токена не переключает Web в самостоятельную авторизацию. Выход доступен как из Web, так и из native UI. Web вызывает `logout()` через bridge; оба инициатора используют одну native-операцию выхода. Смена пользователя выполняется через logout и последующий новый вход через Web-форму, обрабатываемую native, без отдельного события смены аккаунта. Права проверяет backend. Недоступный или несовместимый bridge приводит к явной ошибке, без переключения встроенного Web в автономную авторизацию или браузерный звонок.

### Предлагаемый bridge API

Bridge — внутренний версионируемый API между Web и нативным приложением, не новый публичный backend API. Формат аргументов и результатов — JSON; реализация должна валидировать данные на обеих границах. Ниже зафиксирован целевой минимум; реализованный внутренний формат Web-стороны описан в [контракте Web](../../web/README.md#внутренний-формат-gchat-bridge-v1). Наличие Web-адаптера не означает наличие совместимого native-плагина.

| Метод / событие                          | Направление            | Назначение                                                                                                                                                          |
| ---------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webReady({bridgeVersion})`              | Web → native           | Запросить актуальные указания native при инициализации/перезапуске WebView и каждом возвращении из фона.                                                            |
| `getCapabilities()`                      | Web → native           | Версия bridge, платформа и доступность функций; Web не делает выводов о готовности платформы только из наличия Capacitor.                                           |
| `selectServer({serverUrl})`              | Стартовый Web → native | Передать адрес сервера для загрузки основного Web из статики backend; не выполняет login и не получает токены.                                                      |
| `login({serverUrl, login, password})`    | Web → native           | Передать адрес сервера и данные формы; native выполняет HTTP login на выбранном сервере и сохраняет сессию. Пара токенов Web не возвращается.                       |
| `route(path, {accessToken?, replace?}?)` | native → Web           | Передать актуальный маршрут React Router и при необходимости access token для HTTP-транспорта Web. Токен обрабатывается отдельно от навигации.                      |
| `getAccessToken({forceRefresh?})`        | Web → native           | Получить актуальный краткоживущий access token для одного HTTP-запроса Web; native при необходимости или по запросу выполняет refresh.                              |
| `logout()`                               | Web → native           | Отозвать нативную сессию через Auth API и удалить секреты после подтверждённого результата.                                                                         |
| `loggedOut()`                            | native → Web           | Сообщить о завершённом выходе или подтверждённой инвалидации; без токенов, метаданных пользователя и нового аккаунта.                                               |
| `placeCall({peerId})`                    | Web → native           | Запустить один исходящий звонок после подтверждения пользователем. Ответ команды означает только принятый native запрос, не создание звонка или установление аудио. |
| `callSnapshot({call, runtime})`          | native → Web           | Передать полный актуальный снимок звонка и runtime при каждом `webReady`; отсутствие звонка — `call: null`.                                                         |
| `callStateChanged({call})`               | native → Web           | Передать актуальный безопасный DTO звонка, чтобы Web мог согласованно показать результат, если WebView доступен.                                                    |
| `callRuntimeChanged({status})`           | native → Web           | Передать состояние доступности/восстановления нативного call engine без транспортных секретов и SDP/ICE.                                                            |

Все методы bridge — асинхронные запросы с Promise-результатом. Ошибка имеет структурированный вид `{code, retryAfter?}`; строка сообщения не определяет поведение и не содержит секретов. Web сопоставляет стабильный код с пользовательским текстом и политикой повтора.

#### Управление маршрутом через React Router

Native управляет обязательными переходами командой `route(path, options?)`; Web выполняет её через существующий React Router. Например: `route('/login?serverUrl=<encoded-server-url>', {replace: true})` после выхода и `route('/calls', {accessToken, replace: true})` после входа. Обычная навигация внутри Web сохраняет `Link`/`NavLink`; допустимость маршрута и права проверяются по действующим Web/backend-контрактам. Bridge принимает только внутренние разрешённые пути, а не произвольные внешние URL.

`accessToken` — аргумент bridge-команды, а не параметр URL или React Router. Web извлекает его в память HTTP-транспорта до вызова `navigate`, передавая router только путь и параметры навигации. Токен не попадает в query, hash, `history.state`, браузерное хранилище, логи или диагностику. Обновление токена через `getAccessToken` не требует повторного перехода. `loggedOut()` очищает токен и пользовательские данные, после чего native вызывает `route('/login?serverUrl=<encoded-server-url>', {replace: true})`.

#### Восстановление WebView и актуальные указания native

При инициализации, перезапуске WebView и каждом возвращении из фона Web отменяет запросы предыдущего цикла, очищает пользовательские UI/кеши и временные токены, затем сообщает `webReady({bridgeVersion})`. До получения актуального указания native Web не показывает прежние пользовательские данные и не начинает их загрузку. Запоздавшие результаты bridge- и HTTP-запросов предыдущего цикла не применяются, даже если отмена запроса не остановила его выполнение.

Native определяет актуальное состояние самостоятельно и повторно даёт указание:

- Сессии и сохранённого адреса нет — native показывает отдельное стартовое Web-приложение с формой `/server`; загрузка основного Web ещё не выполняется.
- Сессии нет, адрес сохранён — `route('/login?serverUrl=<encoded-server-url>', {replace: true})`.
- Сессия готова — `route(...)` с актуальным access token и допустимым маршрутом; Web заново загружает данные экранов.
- Сессия восстанавливается — Web показывает ожидание в общей оболочке до получения актуального `route(...)` от native; отдельный маршрут восстановления не вводится.
- Временная ошибка восстановления — общая оболочка показывает структурированную ошибку операции синхронизации с возможностью повтора. Ошибка не маскируется под отсутствие сессии и не вызывает переход на вход.

Web не воспроизводит пропущенные события авторизации. Для первой версии пользовательские кеши сбрасываются при каждой такой синхронизации, даже если аккаунт не изменился. Обычный refresh без нового цикла синхронизации не вызывает очистку кешей. Сброс Web-состояния не останавливает native-звонок, WSS и аудио.

#### Синхронизация звонка без навигации

При каждом `webReady` native передаёт через `callSnapshot({call, runtime})` полный актуальный снимок доступного этой сессии звонка и локального runtime. Если звонка нет, `call` явно равен `null`, чтобы Web удалил прежнее отображение. Runtime включает необходимые для UI локальные состояния, в том числе mute и доступность/восстановление engine, без транспортных секретов.

Снимок начинает синхронизацию текущего цикла WebView; последующие изменения доставляются через `callStateChanged` и `callRuntimeChanged`. Native упорядочивает отправку снимка и последующих обновлений, чтобы запоздавший снимок не заменил более новое состояние. Web не применяет сообщения предыдущего цикла и устаревшие версии серверного DTO по правилам DirectCalls. Пропущенные события не воспроизводятся; при новой синхронизации Web получает новый полный снимок.

Снимок и обновления звонка не вызывают `route(...)` и не меняют открытую страницу. Web отображает состояние; native остаётся владельцем звонка, WSS и аудио. Синхронизация отображения не является условием продолжения звонка и не ожидает загрузки контактов или других Web-данных.

#### Экран 0: адрес сервера

Экран 0 реализуется отдельным минимальным Web-приложением с формой из одного поля — адреса сервера. Его assets включаются в нативную сборку, поэтому первый ввод адреса не требует загрузки основного Web с ещё неизвестного backend. Стартовое приложение содержит маршрут `/server`; этот маршрут не добавляется автоматически в существующий основной Web-клиент. Локальное стартовое приложение включено в ресурсы [iOS-оболочки](../../../applications/ios/README.md), native обслуживает его по `gchat-bootstrap://localhost/server` без доступа к сессии.

Если у native нет сохранённого адреса, он загружает стартовое приложение. Оно передаёт введённый адрес native через `selectServer({serverUrl})`. Native загружает основной Web-клиент с выбранного backend на `/apps/client/login?serverUrl=<encoded-server-url>`. Это загрузка другого Web-документа, а не переход React Router между двумя приложениями. После загрузки основной Web сообщает `webReady`; дальнейшие внутренние переходы выполняются через `route(...)` и его React Router. `serverUrl` кодируется стандартными средствами URL/URLSearchParams.

Форма входа получает адрес из query и передаёт его native вместе с логином и паролем в `login({serverUrl, login, password})`. Native использует выбранный адрес для HTTP login и сохраняет адрес для следующих запусков. `serverUrl` является аргументом bridge и конфигурацией назначения запроса, а не новым полем backend Auth login DTO. Формат и доверие к пользовательскому адресу должны проверяться на обеих границах; конкретные правила валидации остаются частью вопроса конфигурации и доверия.

Сохранённый адрес существует отдельно от удаляемой при logout сессии; сама сессия привязана к своему серверу. При подтверждённом выходе native удаляет токены/device binding сессии, сохраняет адрес и направляет Web на `/login` с этим адресом в query. Новый пользователь может войти на том же сервере без повторного ввода адреса. Пароль и токены в query не передаются.

#### Ограничение браузерных запросов по Origin

В production Web и backend работают на одном публичном origin. Разрешённый origin задаётся в env backend через существующую настройку `SIGNALING_BROWSER_ORIGINS` (JSON-массив точных origins); в production указывается публичный origin инстанса. HTTP CORS/Origin-проверка и браузерный WSS используют эту общую конфигурацию без второго независимого списка. Значение не выводится из `Host`, `Origin`, `X-Forwarded-Host` или query клиента. Для браузерного HTTP-доступа согласована строгая политика: разрешён только явно настроенный публичный origin инстанса с точным совпадением схемы, хоста и порта; wildcard, произвольное отражение Origin и допуск других доменов не используются. Запросы API с запрещённым или `null` Origin отклоняются сервером до выполнения бизнес-операции, а не только остаются без CORS-заголовков. Локальное development-окружение требует отдельной явной конфигурации разрешённых origins.

CORS регулирует браузерный доступ и не удостоверяет нативный клиент. Native HTTP login/refresh/logout и header-based WSS сохраняют работу без браузерного Origin по Auth/Signaling-контрактам; отсутствие Origin не даёт дополнительных прав, защищённые операции требуют действующей авторизации. Браузерный WSS отдельно проверяет Origin по [Signaling](../../backend/modules/signaling.md#браузерный-handshake--реализовано).

Серверная CORS/Origin-политика дополняется отдельным native-контролем навигации и доступа к bridge, описанным ниже. Описанные HTTP-ограничения — согласованное требование D008, а не утверждение о наличии глобальной CORS/Origin-проверки в текущем backend.

#### Запрет внешней навигации и доступ к bridge

Основной WebView закреплён за origin выбранного сервера: схемой, хостом и портом. Native запрещает переходы документа на другой origin, включая ссылки, программную навигацию и цепочки редиректов. Запросы открытия нового окна/WebView, в том числе `target="_blank"` и `window.open`, не должны обходить этот запрет; автоматического открытия внешнего браузера не выполняется. Внутренняя навигация React Router в основном приложении сохраняется.

Native разрешает основной bridge только доверенному основному документу выбранного origin; сторонние страницы и вложенные документы не получают доступ к методам и токенам. Отдельный серверный allowlist для native bridge не вводится: доверенный origin берётся из выбранной native-конфигурации, а не из query текущей страницы. Локальное стартовое приложение имеет отдельный минимальный доступ для выбора сервера и не получает сессионные токены или управление звонками.

Переход из локального стартового приложения к выбранному серверу выполняет сам native через согласованный `selectServer`-сценарий; это явная загрузка доверенного приложения, а не разрешение произвольной междоменной навигации Web. Сохранённая сессия и её токены привязаны к своему серверу: изменение `serverUrl` в query не перенаправляет login существующей сессии, refresh, logout или выдачу токена на другой backend. Попытка такого перенаправления отклоняется.

#### Конфигурация native и HTTP-транспорт Web

Синхронизация пользовательских Web-настроек с native не входит в MVP: текущие данные сессии, служебное состояние браузерного звонка и флаг диагностики не требуют общего settings-протокола. Методы `webBootstrapRequested`, `provideWebBootstrap` и `webSettingsChanged` не вводятся. Если появится конкретная общая настройка, её контракт обсуждается отдельно.

Адрес backend пользователь задаёт в отдельном стартовом Web-приложении; native получает его через `selectServer`, загружает серверный Web и при login получает адрес повторно вместе с данными формы. Основной Web доступен по `/apps/client`, а файлы сборки раздаются по `/apps/static/:filename`. React Router основного приложения использует `basename="/apps/client"`: логическому `/login` соответствует `/apps/client/login`, а `/calls` — `/apps/client/calls`. Native-команда `route(...)` принимает логический путь без префикса; React Router добавляет его при навигации. Backend обслуживает `/apps/client` и клиентские пути внутри `/apps/client/` входным HTML приложения, сохраняя path и query. Файловый маршрут `/apps/static/:filename` не использует SPA fallback: отсутствующий asset возвращает 404. Размещение вложенных assets и параметры сборки нужно детализировать при реализации. Это целевая схема D008; текущие корневые browser-маршруты не считаются уже перенесёнными. При следующих запусках с сохранённым адресом native загружает основной Web сразу с выбранного backend. Обновления и совместимость регулируются описанной ниже политикой. Native должен располагать конфигурацией для login, refresh, logout и WSS независимо от работающего WebView. Web использует same-origin `/api`; отдельная передача API-origin от native для HTTP-транспорта не требуется. Native строит HTTP-адреса из сохранённого адреса сервера, а `/ws` использует с заменой `https` на `wss`. Автономный browser build сохраняет текущие same-origin `/api` и `/ws`.

При сохранённом адресе native открывает `https://<server>/apps/client`; при новом входе использует `/apps/client/login` с адресом сервера в query. JS/CSS загружаются с того же origin по `/apps/static/:filename`. При ошибке загрузки native показывает ошибку и действие «Повторить», не удаляя адрес или сессию. Активный native-звонок продолжает работу независимо от загрузки Web; сетевые сбои самого звонка обрабатываются по DirectCalls. После успешной загрузки Web отправляет `webReady`, native передаёт актуальный маршрут, токен при готовой сессии и снимок звонка/runtime.

Native HTTP login создаёт отдельную мобильную Auth-сессию; browser-токены и browser `deviceId` не переносятся в приложение. После сохранения сессии native вызывает `device.register` для своей сессии и сохраняет полученный `deviceId` для reconnect. Web во встроенном режиме не открывает signaling-соединение и не регистрирует устройство в обход native.

Ошибка чтения secure storage или недоступность bridge возвращается как ошибка получения токена и не маскируется под отсутствие сессии.

`getAccessToken({forceRefresh?})` — асинхронная операция: Web ожидает ответ native и получает `{accessToken}`. Native возвращает текущий действующий access token либо сначала самостоятельно обновляет пару по Auth-контракту; Web не передаёт refresh token и не обновляет пару сам. Web использует токен, полученный через `route(...)` или этот метод, только в памяти HTTP-транспорта, не записывая в `localStorage`, Query cache или логи. Если backend возвращает `ACCESS_TOKEN_EXPIRED`, Web один раз повторяет исходную операцию с `getAccessToken({forceRefresh: true})`; native сериализует refresh, сохраняет `request_id` и повторяет тот же refresh-запрос при неизвестном результате. Параллельные запросы координируются native, чтобы не ротировать один refresh token конкурентно. Если Web нужен свежий токен, он вызывает `getAccessToken` заново. При подтверждённой инвалидации native возвращает `SESSION_INVALID` при получении токена; Web очищает UI и кеши. О завершённом выходе или подтверждённой инвалидации native сообщает Web событием `loggedOut()` без данных пользователя. Обычный refresh не вызывает это событие.

Общий набор стабильных bridge-кодов: `BRIDGE_UNAVAILABLE`, `UNSUPPORTED_VERSION`, `VALIDATION_ERROR`, `SECURE_STORAGE_ERROR`, `UNAUTHENTICATED`, `SESSION_INVALID`, `NETWORK_ERROR`, `RATE_LIMITED`. `retryAfter` задаётся для `RATE_LIMITED`, когда backend его возвращает. Ошибки Auth backend отображаются адаптером в эти коды, сохраняя исходный статус/код там, где он нужен для повтора; произвольные сообщения backend не используются как протокол.

Для WSS native использует тот же собственный session manager: сам получает актуальный access token, авторизует соединение и не запрашивает токен через Web bridge. `peerId` — UUID пользователя из списка Groups; отображаемое имя не является основанием для доступа.

Команды принятия, отклонения, завершения и mute принадлежат нативному интерфейсу звонка и его call engine, а не экрану React. Входящий push и системное действие «ответить» не должны требовать вызова bridge из Web.

Перед запуском приложения Web проверяет версию bridge. Неизвестная или несовместимая версия приводит к явному сообщению о недоступности мобильной интеграции, а не к незаметному переключению на браузерный звонок. Изменения несовместимого формата требуют повышения major-версии bridge и согласованной пары Web/native сборок.

### Обновление Web и совместимость

Для MVP backend раздаёт одну текущую Web-версию, обратно совместимую с поддерживаемыми установленными native-клиентами. Отдельные Web-сборки для каждой native-версии не вводятся, native не скачивает отдельные пакеты обновлений. Каждая Web-сборка объявляет поддерживаемые версии bridge; совместимость backend API также сохраняется. Несовместимые изменения bridge требуют согласованного выпуска Web/native и не должны попадать в обычный Web-деплой, отключающий поддерживаемые native-клиенты.

Деплой не перезагружает уже открытый WebView; новая Web-версия загружается при следующем открытии или явном повторе загрузки. Возвращение из фона с `webReady` синхронизирует существующий Web, но само по себе не требует перезагрузки документа. HTML проверяется на актуальность, JS/CSS имеют имена с хешем содержимого и сохраняются на период поддержки открытых клиентов. Публикация новой версии не удаляет файлы, нужные уже открытой предыдущей сборке.

Откат выполняется на backend: возвращается предыдущая Web-сборка вместе с её assets; отдельного native-обновления для этого не требуется при сохранении совместимости. При несовместимости bridge native показывает сообщение о необходимости обновить приложение, без переключения на браузерный call engine. Авторизованный native-звонковый контур продолжает работать независимо от доступности совместимого Web, пока backend поддерживает его протокол.

### Сессия и секреты

Во встроенном режиме вход выполняется в следующем порядке:

1. При запуске native восстанавливает сохранённую сессию из Keychain. Если она пригодна, самостоятельно выполняет refresh при необходимости, авторизует WSS и восстанавливает звонок без ожидания WebView. После готовности Web native командует открыть основной интерфейс через `route('/calls', {accessToken, replace: true})`.
2. Если нет ни сессии, ни сохранённого адреса, native загружает отдельное локальное стартовое Web-приложение с `/server`. Оно передаёт адрес native через `selectServer`, после чего native загружает основной Web на `/apps/client/login` с `serverUrl` в query. Если адрес уже сохранён и нужен вход, native командует Web показать общий экран авторизации через `route('/login?serverUrl=<encoded-server-url>', {replace: true})`.
3. Web получает адрес сервера из query, собирает логин и пароль и вызывает `login({serverUrl, login, password})` через bridge. Встроенный Web не отправляет HTTP login и не получает refresh token.
4. Native выполняет login на выбранном сервере по действующему Auth HTTP-контракту, сохраняет адрес и надёжно сохраняет полученную пару в Keychain с привязкой к этому серверу. До сохранения не сообщает об успешном входе. Ошибки операции возвращает форме через bridge; Web очищает временные данные формы после завершения операции и не сохраняет пароль.
5. После сохранения native запускает авторизованный звонковый контур и командует Web открыть основной интерфейс через `route('/calls', {accessToken, replace: true})`. Web принимает access token из bridge-команды в память HTTP-транспорта и самостоятельно загружает данные экранов.

Логин и пароль проходят через bridge только как аргументы команды входа. Пароль не сохраняется и не включается в события, логи или диагностику. Refresh token никогда не передаётся Web или через bridge. Native хранит его в iOS Keychain, сериализует refresh и соблюдает Auth-контракт повтора с тем же `request_id` при неизвестном результате. Access token для WSS native обновляет независимо от WebView, в том числе при reconnect и холодном старте по push. Access token передаётся в аргументах `route(...)` или ответе `getAccessToken`; остальные bridge-события его не содержат. Токены не включаются в URL, логи или диагностику.

Native сохраняет мобильную сессию как одну версионируемую запись: токены, `deviceId` и привязку к backend. До отправки refresh надёжно сохраняет незавершённую операцию с прежним refresh token и `request_id`; после успешного ответа атомарно заменяет пару и очищает операцию. При запуске восстанавливает контекст без WebView. Ошибка чтения хранилища означает временную недоступность с возможностью повтора, а невосстановимое повреждение записи требует нового входа. Адрес backend поступает из Web-формы входа после стартового экрана `/server`; сохранённый адрес сохраняется и после logout.

Для записи мобильной сессии в Keychain выбран `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: после первой разблокировки с момента перезагрузки она доступна native в фоне и при заблокированном экране, до первой разблокировки — недоступна. Запись не переносится на другое устройство; ограничения описаны в [документации Apple](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly). Недоступность до первой разблокировки не считается инвалидацией сессии и не приводит к её удалению. Фоновый refresh и авторизация для входящего звонка не требуют Face ID или другого интерактивного подтверждения. Приёмка включает пробуждение по push после истечения access token на lock screen и обработку недоступности контекста до первой разблокировки.

Для первой версии согласовано ограничение действующего Auth-контракта: если результат ротации потерян и повтор происходит после 30-секундного окна, допустим повторный ручной вход. Native повторяет незавершённый refresh с тем же `request_id`; при подтверждённом `SESSION_INVALID` закрывает авторизованный контур, отправляет `loggedOut()`, возвращает ошибку при запросе токена и при открытии приложения командует Web показать форму повторного входа. Сетевая ошибка или временный отказ не считаются потерей сессии. Расширение окна или новый протокол восстановления backend этим решением не вводятся.

Face ID предусмотрен как будущее направление для открытия интерфейса и чувствительных действий; конкретные сценарии пока не выбраны. Биометрическая проверка не должна блокировать фоновый доступ к сессии для звонков. Его наличие не считается механизмом восстановления утраченной серверной сессии и не отменяет согласованное ограничение refresh.

Web получает от native только access token, а необходимые данные запрашивает самостоятельно; для HTTP-запросов использует токен из `route(...)` в памяти и при необходимости запрашивает актуальный через `getAccessToken`, не сохраняя его в `localStorage`. Если сервер отверг токен как истёкший, Web запрашивает токен с `forceRefresh: true` и повторяет исходную HTTP-операцию один раз согласно действующему поведению Auth-клиента. После внутреннего refresh Web при необходимости получает актуальный токен повторным асинхронным вызовом. Browser build сохраняет действующие `localStorage` и browser refresh policy без изменений. Общий JS Auth-пакет может предоставлять общую HTTP-политику через разные адаптеры: browser adapter владеет браузерным refresh, Capacitor adapter получает токены через асинхронный native bridge; сам пакет не владеет хранилищем.

Logout в Capacitor-сборке координируется через native: серверный отзыв подтверждается по [Auth-контракту](../../backend/modules/auth.md), затем native удаляет сохранённую пару; при подтверждённой инвалидации native завершает авторизованную сигнализацию и прекращает выдавать access token. Неизвестный результат logout не очищает сессию как будто отзыв подтверждён; доступен повтор операции. Выход может инициировать пользователь в native UI или в Web через `logout()`; серверную операцию в обоих случаях выполняет native. После подтверждённого выхода native закрывает WSS и аудио, удаляет запись сессии и отправляет Web `loggedOut()` без payload. Web очищает UI и кеши, отменяет текущие запросы и не применяет запоздавшие результаты прежней сессии. Обработка события должна быть безопасна при повторе и при уже обработанном успехе `logout()`. Подтверждённая инвалидация сессии приводит к тому же событию. После выхода native командует Web показать форму входа через `route('/login?serverUrl=<encoded-server-url>', {replace: true})`; пользователь может ввести другой аккаунт, HTTP login снова выполняет native; событие не содержит данных следующего пользователя и не запускает автоматическую смену аккаунта. Refresh, logout и запись результатов координируются: запоздавший результат refresh не должен восстановить сессию после выхода. Локальное удаление сессии без подтверждённого серверного отзыва не согласовано.

### Жизненный цикл звонка

1. Web показывает доступных собеседников и выполняет пользовательское подтверждение исходящего вызова.
2. Web вызывает `placeCall` один раз. Native engine отправляет `call.create` в авторизованный WSS и связывает запрос с локальной операцией.
3. При таймауте или потере ответа engine сначала запрашивает актуальный серверный state через `call.current`/`call.get`; он не повторяет `call.create` автоматически, поскольку `request_id` не является ключом идемпотентности.
4. Входящий VoIP push будит iOS-приложение: native обрабатывает его системным API и сверяет `call_id` с серверным состоянием. Push — сигнал пробуждения, а не источник истины.
5. Native UI обрабатывает ответ, отклонение и завершение. Native engine регистрирует устройство, получает ICE-конфигурацию, обменивается SDP/ICE по WSS, использует TURN relay и подтверждает соединение только по правилам DirectCalls.
6. После переподключения native engine получает актуальное состояние звонка, а не воспроизводит локально накопленные события. Завершение, отзыв сессии или окончание звонка останавливают аудио и освобождают нативные ресурсы.
7. Если WebView остановлен, звонок, управление состоянием, аудио и push-обработка продолжаются на native стороне. События bridge — только синхронизация интерфейса при доступности Web, не механизм фоновой доставки или управления звонком.

В целевую iOS-интеграцию входят PushKit и CallKit. Backend [Devices](../../backend/modules/devices.md) и [Push](../../backend/modules/push.md) сейчас описывают APNs VoIP, но помечены `partial`; credentials и приёмка на настоящих устройствах ещё не выполнены.

## Рассмотренные варианты

- **Оставить звонок в WebView:** не соответствует требованию продолжения звонка независимо от WebView и не выбран.
- **Переписать весь интерфейс на Swift/Kotlin:** дублирует готовый Web-клиент и увеличивает стоимость сопровождения; не выбран.
- **Сохранить Web для контактов, нативный call engine и системный UI:** предлагаемый вариант; сохраняет общие продуктовые экраны и выносит фонозависимый звонок из WebView.
- **Передавать команды звонка через JS даже в фоне:** не выбран; исполнение JS не должно быть предпосылкой для обработки push, системного ответа и активного аудио.

## Последствия и границы

- Функциональность экранов Web не копируется, но мобильная Capacitor-сборка должна проверять её в WebView и на узких экранах.
- Появляется нативный код для каждой мобильной платформы и bridge-контракт, который нужно версионировать и тестировать совместно с Web.
- Browser call engine и native call engine будут разными адаптерами одного серверного контракта; поведение DirectCalls, ограничения и исходы должны оставаться совместимыми.
- Работа в фоне и на заблокированном экране является обязательным критерием приёмки. Она не доказывается запуском звонка только в foreground.
- Принудительное завершение пользователем, force stop, отсутствие сети, запрет push и системные режимы энергосбережения ограничены политиками ОС. Поддерживаемое поведение этих случаев нужно зафиксировать отдельно; нельзя обещать доставку при условиях, когда ОС её не гарантирует.
- Данный документ пока не фиксирует конкретный upstream commit и собранный XCFramework, конкретные модели тестовых устройств; необходимые изменения backend рассматриваются отдельно по профильным контрактам.

## Технический spike загрузки Web

Точный механизм production remote loading в Capacitor проверяется отдельным обязательным техническим spike. До успешной проверки эта часть не считается готовой к реализации. Назначение `server.url` для live reload и ограничение production-применения учитываются по [документации Capacitor](https://capacitorjs.com/docs/config); сам факт настройки URL не подтверждает работоспособность выбранной интеграции.

Проверить переход из локального стартового приложения к серверному Web, загрузку `/apps/client` и assets, доступность bridge после загрузки, повторную инициализацию после перезапуска WebView и цикл `webReady` → актуальный маршрут/токен/снимок звонка. Проверить ошибку загрузки с повтором без удаления сохранённой сессии и без остановки native-звонка. Проверить блокировку внешних ссылок, программных переходов, редиректов и новых окон, а также отсутствие bridge-доступа у стороннего документа. Зафиксировать проверенный механизм и ограничения; успешный foreground-показ страницы сам по себе не закрывает spike.

## iOS spike и критерии проверки

Конкретный первый этап без APNs согласован в [контракте нативных аудиозвонков iOS](../../ios/native-calls.md). Это не меняет статус остальных частей D008 и не отменяет Gate 2 или условия публичного релиза.

Spike ограничен пятью рабочими днями. Он состоит из двух независимых gate, чтобы выбор libwebrtc не зависел от готовности APNs credentials.

### Gate 1: native call engine и libwebrtc

Создать временный минимальный Swift harness с CallKit, без Capacitor и production UI. Активация/деактивация аудиосессии проверяется под управлением CallKit, а не только автономным запуском libwebrtc. Использовать backend test environment и существующий Web-клиент как peer. Проверки провести на двух физических iPhone: один на iOS 16.x, второй на актуальной iOS. UI/bridge, HTTP/WSS, авторизация и управляемые отказы автоматизируются, включая прогоны в Simulator; ручные проверки выполняются только на физических iPhone. Simulator физическую приёмку WebRTC, аудио, TURN, lock screen и background не заменяет. Автоматическое покрытие — в [плане автоматизации](../../../applications/ios/automated-tests.md); физические ручные сценарии, предусловия и формат отчёта — в [плане ручной приёмки iOS](../../../applications/ios/manual-tests.md).

Gate 1 считается пройденным, если:

- Официальный WebRTC upstream собирается в XCFramework на конкретном commit; записаны checksum артефакта и воспроизводимые шаги сборки.
- Native call engine устанавливает реальный WebRTC audio connection с Web-клиентом через TURN relay; оба участника подтверждают `call.connected` только после фактического WebRTC connected.
- Native реализует авторизованный WSS, `call.ping` с возрастающим `sequence`, корректными `audio_connected` и `recovery_id`, переподключение и согласованное с сервером recovery. Автоматический повтор `call.create` не выполняется.
- Двустороннее аудио, выбранная iOS аудиомаршрутизация и работа активного звонка при сворачивании приложения и блокировке экрана подтверждены на обоих устройствах.
- Проверены активация/деактивация CallKit-аудиосессии, прерывание обычным телефонным звонком, отключение Bluetooth, смена сети и исход при превышении серверного окна восстановления. Ручные сценарии Gate 1 — C01–C07 на физических iPhone, C10 выполняется автоматически по плану автоматизации; ручные проверки полного WebView с реальным аудио C08/C09 выполняются на этапе интеграции.

Итог Gate 1 — commit, checksum и инструкции сборки XCFramework, результаты сценариев на двух устройствах и явный список нерешённых блокеров. Если обязательный критерий не выполнен за timebox, Gate 1 не считается пройденным, а решение о подключении артефакта к приложению остаётся открытым.

### Gate 2: PushKit, CallKit и входящий cold start

Отдельно проверить получение VoIP push, системное отображение и обработку входящего звонка, включая cold start, фон и lock screen, на физических устройствах с APNs-конфигурацией. Отсутствие credentials или недоступность APNs не считается успешной проверкой и не блокирует сам вывод Gate 1 о сборке/работе libwebrtc; до прохождения Gate 2 публичный App Store релиз запрещён. Gate 2 остаётся обязательной частью приёмки iOS-приложения. Сценарии P01–P09 включают реальную доставку APNs, повторный/поздний push, ответ одновременно с отменой или ответом другого устройства. Инъекция payload проверяет обработчик, но не заменяет настоящую доставку. Финальная приёмка требует production APNs/TestFlight; Simulator используется для автоматических проверок обработчиков, а не для ручной приёмки или закрытия Gate 2.

### Общие критерии интеграции и приёмки

- Первое распространение — закрытая beta через TestFlight для команды и ограниченной группы пользователей. Публичный App Store релиз допускается после прохождения приёмки на обоих физических устройствах и проверки PushKit/CallKit с production-конфигурацией.
- Общие группы, контакты и административный интерфейс Web работают в обоих режимах без отдельного мобильного форка; встроенный режим выполняет команды native и использует его сессию.
- Web и native обмениваются типизированным запросом/событием bridge с проверкой версии; несовместимая версия обнаруживается явно.
- Во встроенном режиме native управляет авторизацией и командами показа UI; Web передаёт данные формы, а native выполняет HTTP login и надёжно сохраняет сессию до открытия основного интерфейса. Native выполняет refresh/logout и обслуживает звонки; Web получает только access token и сам загружает свои данные.
- Web вызывает защищённые методы SDK через device.session.run; native выполняет HTTP своим сетевым стеком. При `ACCESS_TOKEN_EXPIRED` владелец сессии один раз обновляет токен и повторяет допустимую операцию по контракту device. Автономный режим сохраняет текущее поведение авторизации.
- При отсутствии сохранённого адреса native загружает отдельное стартовое Web-приложение из нативной сборки. Введённый адрес передаётся через `selectServer`, native загружает основной Web по `/apps/client`; адрес передаётся в query `/apps/client/login`, затем в bridge login вместе с данными формы. Logout удаляет сессию, сохраняет адрес сервера и возвращает на `/login` с этим адресом; проверяется новый вход другим пользователем.
- Недоступность bridge во встроенном режиме не запускает автономную авторизацию или браузерный call engine.
- Инициализация/перезапуск WebView и возвращение из фона вызывают `webReady`, отмену прежних запросов и очистку пользовательских кешей; Web выполняет актуальное указание native, не воспроизводит пропущенные события и не применяет запоздавшие результаты предыдущего цикла. Проверяются выход и повторный вход под другим аккаунтом, пока WebView недоступен, а также временная ошибка восстановления сессии.
- Native самостоятельно сериализует refresh по Auth-контракту и авторизует WSS при reconnect после истечения access token и при cold start от входящего push, без работающего WebView.
- При каждом `webReady` Web получает полный снимок звонка/runtime, включая `call: null`, затем текущие обновления. Проверяются восстановление активного звонка, завершение во время недоступности WebView, отсутствие смены страницы и отбрасывание устаревших сообщений.
- Выполняются Web ↔ iOS и iOS ↔ iOS сценарии ответа, отклонения, завершения, занятости, reconnect и истечения сроков; аудио идёт через TURN relay.
- Неопределённый результат `call.create` не порождает дублирующий звонок; Web/native не запускают одновременно два клиента сигнализации или аудио.
- Уже созданный браузерный звонок не перехватывается native; новый звонок из приложения имеет отдельный `call_id` и обычную серверную проверку занятости.
- Пароль допускается только в аргументах `login({serverUrl, login, password})` Web → native, не сохраняется и не попадает в события, логи или диагностику. Refresh token и push token не проходят через bridge. Передача TURN credentials, SDP и ICE в универсальном потоке WS-сообщений регулируется политикой БД по [контракту Web](../../web/README.md#общий-websocket-через-native); отдельные UI-события звонка этих данных не содержат. Access token допускается в аргументах `route(...)` и ответе `getAccessToken`; перед вызовом React Router токен извлекается в память HTTP-транспорта, не попадает в URL, `history.state`, хранилища, логи или диагностику. Остальные bridge-события токены не содержат.

## Открытые решения

Модель авторизации согласована: автономный Web сохраняет текущее поведение, встроенный получает от native только access token и сам загружает необходимые данные HTTP-запросами. Native управляет авторизацией и даёт Web команды навигации. При отсутствии адреса используется `/server`, после ввода — `/login` с адресом в query. Web передаёт адрес сервера и данные формы, native выполняет HTTP login, хранит сессию, выполняет refresh/logout и обслуживает звонки. Передача пары токенов Web → native и `transferId` не используются.

Перечисленные по итогам ревью архитектурные вопросы разобраны; проверки без обязательной физической оценки описаны в [плане автоматизации](../../../applications/ios/automated-tests.md), ручная оценка только на физических iPhone — в [ручной приёмке iOS](../../../applications/ios/manual-tests.md). D008 сохраняет статус draft: это не подтверждение реализации или результатов испытаний. Следующая работа — технический spike production-загрузки Web, iOS Gate 1/2 и детализация реализации в профильных контрактах; новые публичные контракты согласуются до реализации.

Выполнение Gate 1/2 — последующая работа по [описанному плану spike](#ios-spike-и-критерии-проверки), а не отдельные архитектурные вопросы. После проверок зафиксировать результат, commit и checksum XCFramework; до успешного Gate 2 публичный App Store релиз остаётся заблокирован.

# D008: Capacitor bridge для Web-клиента и нативных звонков

Дата: 2026-11-05. Пользователь поручил подготовить документацию интеграции Capacitor, переиспользовать готовый Web-клиент и оставить весь звонок нативным, включая работу в фоне и при заблокированном экране.

Статус `draft`: это предложение для обсуждения, а не отчёт о реализации. Текущий объём решения — iOS-приложение с переиспользованием Web-клиента; минимальная версия первого релиза — iOS 16.0. По итогам обсуждения 2026-11-05 согласованы направления: Web UI выполняет login, после чего передаёт мобильную сессию native; native владеет долговременным хранилищем и refresh. Native call engine использует libwebrtc из официального WebRTC upstream, собранный в XCFramework на зафиксированном commit и подключённый как версионированный бинарный артефакт с checksum; приложение содержит тонкий собственный адаптер под DirectCalls. Нативный код пишется отдельно под платформы: Swift для iOS и Kotlin для Android, если Android вернётся в scope; Kotlin Multiplatform не вводится. iOS spike на реальном устройстве проверяет сборку, аудиомаршрутизацию, TURN-only и работу звонка в фоне. Точный commit и артефакт фиксируются после успешной проверки. Capacitor не добавлен в зависимости; Xcode-проект отсутствует.

## Контекст

GChat Web уже содержит пользовательский интерфейс входа, групп, контактов и администрирования, а также браузерный клиент звонков. Web использует `RTCPeerConnection`, `getUserMedia`, WebSocket и браузерные хранилища. Упаковка текущего звонкового клиента в WebView не обеспечивает требуемую независимость звонка от JavaScript и жизненного цикла WebView.

Нужно переиспользовать интерфейс Web, не создавая параллельные мобильные экраны для обычной работы, и при этом позволить звонку продолжаться при сворачивании приложения и блокировке экрана. На мобильной платформе системный входящий и активный звонок, сигнализация, WebRTC и управление аудио должны принадлежать нативному модулю. Серверное состояние и правила звонка остаются в [DirectCalls](../../backend/modules/direct-calls/README.md) и [Signaling](../../backend/modules/signaling.md).

## Предлагаемое решение

### Границы исполнения

- Capacitor показывает существующее приложение из `applications/web`; отдельный форк экранов, навигации и стилей не создаётся. Поддерживаемые мобильные сценарии Web остаются частью этого приложения.
- Web отвечает за входной интерфейс, группы, контакты, подтверждение исходящего звонка и остальные существующие экраны.
- Нажатие «позвонить» передаёт команду через узкий Capacitor bridge. После неё звонком владеет нативный call engine; входящий звонок может быть принят из системного UI без запущенного WebView.
- Нативный модуль владеет WebSocket, командами и событиями DirectCalls, WebRTC через нативный API, микрофоном, аудиосессией, системным UI звонка и обработкой push. WebView не запускает параллельный Web-звонок.
- Native call engine использует libwebrtc из официального WebRTC upstream в виде XCFramework, собранного на зафиксированном commit и подключённого как версионированный бинарный артефакт с checksum. Собственный тонкий адаптер реализует интеграцию с общим Signaling/DirectCalls-контрактом; сторонние Swift-обёртки и неподдерживаемые бинарные пакеты не становятся дополнительной архитектурной зависимостью.
- Нативные call engine реализуются отдельно для каждой ОС: iOS — Swift, Android вне текущего scope — Kotlin. Kotlin Multiplatform и общий нативный runtime не вводятся; общими остаются backend-протокол, поведенческие требования и межплатформенные тестовые сценарии.
- При потере сети native поведенчески повторяет текущую recovery-логику Web: переподключается с той же retry/backoff-политикой, после регистрации запрашивает `call.current`, сохраняет монотонный sequence пингов и отправляет `call.ping` сразу и далее каждые 10 секунд с актуальными `audio_connected` и `recovery_id`; состояние применяет по версии и восстанавливает медиа через существующий Signaling/DirectCalls-протокол. Неизвестный результат `call.create` не приводит к автоматическому повтору. Browser-specific механизмы (`localStorage`, Web Locks) не портируются буквально; используется native-хранилище и нативное владение соединением. Поведенческий референс — [Web call client](../../../applications/web/src/features/calls/client.ts).
- Текущее браузерное исполнение сохраняется: в обычном браузере Web продолжает использовать существующий звонковый клиент. Capacitor и нативные модули выбираются через адаптер платформы.
- Backend остаётся авторитетным для состояний звонка, доступа, таймаутов и результата; локальные состояния Web и нативного UI не заменяют его.
- Входящий `ringing` одновременно доступен всем подключённым авторизованным клиентам через `call.updated`; VoIP push нативным устройствам работает независимо и не имеет приоритета. Web и native могут показать один и тот же вызов. Первое принятое сервером подтверждение атомарно выбирает устройство-победителя для разговора; остальные клиенты закрывают входящий UI по `call.updated`. Это соответствует правилу [DirectCalls «Несколько устройств получателя»](../../backend/modules/direct-calls/README.md#несколько-устройств-получателя--согласовано).
- VoIP payload передаёт `caller_display_name` для немедленного отображения в системном UI; остальные профильные данные не добавляются. Push остаётся недоверенным снимком: native подтверждает актуальность звонка через сервер. Подробный формат принадлежит [Push](../../backend/modules/push.md).
- Звонковый push не означает приоритет или эксклюзивное владение native-клиентом. APNs `200` не подтверждает доставку на устройство; если push задержан или не доставлен, любой другой подключённый клиент всё равно может принять уже доставленный ему `call.updated`. Отдельная логика per-call fallback не нужна.
- Звонки из обычного мобильного браузера поддерживаются в foreground. Работа после сворачивания браузера или блокировки экрана — best effort: приостановка страницы может остановить WSS/прикладные `call.ping`, после чего применяются штатные DirectCalls recovery/timeout и звонок может завершиться. Автоматический handoff в приложение не выполняется; Web предупреждает, что надёжная работа в фоне доступна в GChat app.
- После принудительного закрытия GChat пользователем (force quit/force stop) ОС может не разбудить native-приложение по push, поэтому доставка на это устройство не гарантируется. Если звонок доступен другому подключённому Web или native клиенту, тот может принять его по общему правилу первого ответа; если активных клиентов нет, вызов завершится по штатному `no_answer`. Это не fallback, а независимая доставка всем доступным клиентам.
- После перезагрузки устройства native target должен восстанавливаться и принимать push без обязательного ручного запуска GChat, используя сохранённую native-сессию и системную push-регистрацию. Это best effort: доставка зависит от готовности ОС, разблокирования устройства и сети. Другие подключённые клиенты могут принять вызов, не ожидая результата push.
- Если пользователь запретил необходимые системные уведомления/разрешения звонка, приложение явно показывает ограниченную доступность входящих и путь в настройки iOS. Доставка/системное оповещение на native-устройстве может быть ограничено; другие подключённые Web или native клиенты остаются равноправными получателями и могут ответить. Точные системные ограничения проверяются на поддерживаемых версиях iOS.
- Handoff уже созданного или активного звонка между браузерным и native call engine не входит в MVP. Один звонок остаётся закреплён за выбранным устройством/сессией; чтобы перейти с браузерного исходящего звонка на надёжную фоновую работу, пользователь завершает его и начинает новый звонок в приложении.

### Выделенный модуль авторизации Web

В Web выделяется единый модуль управления клиентской сессией. Auth UI, HTTP SDK и остальные features используют его публичный интерфейс и не обращаются напрямую к `localStorage`, Capacitor bridge или конкретной реализации refresh. Модуль выбирает адаптер один раз при старте приложения:

- **Browser adapter** сохраняет существующее поведение браузерного клиента: `localStorage`, `navigator.locks`, сериализацию refresh с сохранением `request_id`, повтор HTTP-операции после `ACCESS_TOKEN_EXPIRED`, logout и межвкладочную синхронизацию.
- **Capacitor adapter** делегирует владельцу сессии native login handoff, получение состояния, асинхронный запрос access token, принудительный refresh и logout через bridge. Refresh token не сохраняется и не ротируется Web-кодом.

Общий интерфейс модуля предоставляет AuthProvider состояние пользователя и методы входа/выхода, а HTTP-транспорту — способ получить access token для запроса. Для browser adapter токен поступает из текущего web session store; для Capacitor adapter каждый запрос получает токен асинхронно от native. После `ACCESS_TOKEN_EXPIRED` общий HTTP-слой однократно повторяет операцию, запросив токен через соответствующий adapter с признаком принудительного обновления. Платформенный выбор, хранение и протокол refresh инкапсулированы в модуле; React-компоненты и бизнес-функции не ветвятся по платформе.

В браузере сохраняется прежнее поведение без обязательного наличия Capacitor. В Capacitor-сборке тот же пользовательский интерфейс входа используется с native adapter; после успешного login тот передаёт пару токенов native через `adoptSession`, ожидает подтверждение и не сохраняет долгоживущую копию в браузерном хранилище. Отказ или неизвестный результат handoff обрабатывается модулем явно и не считается успешным входом.

### Предлагаемый bridge API

Bridge — внутренний версионируемый API между Web и нативным приложением, не новый публичный backend API. Формат аргументов и результатов — JSON; реализация должна валидировать данные на обеих границах. Ниже зафиксирован целевой минимум для проектирования, не существующие методы.

| Метод / событие                                                                  | Направление  | Назначение                                                                                                                                                          |
| -------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `webReady({bridgeVersion})`                                                      | Web → native | Сообщить, что Web инициализировал bridge и готов ответить на стартовый запрос конфигурации.                                                                         |
| `webBootstrapRequested({requestId})`                                             | native → Web | Запросить у готового Web стартовый снимок конфигурации и разрешённых пользовательских настроек.                                                                     |
| `provideWebBootstrap({requestId, schemaVersion, serverUrl, revision, settings})` | Web → native | Вернуть снимок по корреляционному `requestId`; `serverUrl` — origin публичного хоста, с которого загружен Web.                                                      |
| `webSettingsChanged({revision, settings})`                                       | Web → native | Передать новую ревизию разрешённых Web-настроек; Web остаётся их источником истины. Native повторно запрашивает bootstrap после потери событий/перезапуска WebView. |
| `getCapabilities()`                                                              | Web → native | Версия bridge, платформа и доступность функций; Web не делает выводов о готовности платформы только из наличия Capacitor.                                           |
| `adoptSession({transferId, accessToken, refreshToken})`                          | Web → native | Принять результат login и надёжно сохранить сессию нативно; успех возвращается только после подтверждённой записи. Повтор с тем же `transferId` идемпотентен.       |
| `getAuthState()`                                                                 | Web → native | Первичная синхронизация после старта WebView: авторизован ли пользователь и его безопасные claims, без секретов.                                                    |
| `getAccessToken({forceRefresh?})`                                                | Web → native | Получить актуальный краткоживущий access token для одного HTTP-запроса Web; native при необходимости или по запросу выполняет refresh.                              |
| `logout()`                                                                       | Web → native | Отозвать нативную сессию через Auth API и удалить секреты после подтверждённого результата.                                                                         |
| `authStateChanged({status, user})`                                               | native → Web | Уведомить Web о входе, выходе или инвалидации сессии; refresh token и access token в событии не передаются.                                                         |
| `placeCall({peerId})`                                                            | Web → native | Запустить один исходящий звонок после подтверждения пользователем. Ответ команды означает только принятый native запрос, не создание звонка или установление аудио. |
| `callStateChanged({call})`                                                       | native → Web | Передать актуальный безопасный DTO звонка, чтобы Web мог согласованно показать результат, если WebView доступен.                                                    |
| `callRuntimeChanged({status})`                                                   | native → Web | Передать состояние доступности/восстановления нативного call engine без транспортных секретов и SDP/ICE.                                                            |

Все методы bridge — асинхронные запросы с Promise-результатом. Ошибка имеет структурированный вид `{code, retryAfter?}`; строка сообщения не определяет поведение и не содержит секретов. Web сопоставляет стабильный код с пользовательским текстом и политикой повтора.

#### Стартовая конфигурация и синхронизация настроек

После `webReady` native запрашивает `webBootstrapRequested` и принимает только ответ с совпадающим `requestId` и поддерживаемой `schemaVersion`. Повторный или запоздавший ответ не перезаписывает более новую ревизию. Web загружается в Capacitor с публичного HTTPS-хоста инстанса; он вычисляет `serverUrl` из origin загруженной страницы и передаёт его в bootstrap. `serverUrl` не вводится в форме авторизации и не хранится как отдельная настройка:

- HTTP API использует `<serverUrl>/api`.
- Signaling использует `<serverUrl>/ws`, заменяя схему `https` на `wss`; в локальной разработке `http` преобразуется в `ws`.

Docker-развёртывание публикует Web, REST API и WSS на одном внешнем host; proxy направляет `/api` и `/ws` в backend, а остальные Web-маршруты — в SPA. Внутреннее число контейнеров/процессов не меняет этот публичный контракт. Browser-сборка сохраняет текущие same-origin `/api` и `/ws`; Capacitor загружает Web с того же публичного origin, поэтому он может вычислить адреса до передачи native. Для release обязателен HTTPS origin; HTTP разрешён только для localhost в development. Native валидирует `serverUrl` и не использует fallback на локальный `capacitor://localhost` origin. Web runtime инициализация из `location.origin` согласуется с текущей моделью приложения, однако remote loading Web assets и подключение конфигурации Capacitor ещё предстоит реализовать.

Поле `settings` содержит только явный allowlist несекретных Web-настроек; Web остаётся источником истины, а `revision` монотонно растёт при их изменении. Вместо периодического polling Web отправляет `webSettingsChanged`; при повторной инициализации или пропуске обновлений native запрашивает свежий snapshot. Секреты, access/refresh tokens и произвольное содержимое `localStorage` в этот контракт не входят. Список настроек и их схема определяются после инвентаризации Web. `serverUrl` задаётся origin загруженного Web и не синхронизируется как изменяемая пользовательская настройка.

`adoptSession` — этап handoff после существующего Auth login, а не новый endpoint backend. Web создаёт `transferId` один раз для полученной пары и повторно использует его только при повторе передачи той же пары. Native валидирует формат и атомарно сохраняет пару вместе с `transferId` как одну запись защищённого хранилища; подтверждение возвращается после успешной записи. Повтор того же `transferId` и той же сессии подтверждается идемпотентно; несовпадающая уже установленная сессия не перезаписывается молча и возвращает `SESSION_CONFLICT`. В Capacitor-режиме Web держит пару только в памяти до подтверждения и не записывает её в `localStorage`; после подтверждения очищает временное состояние. Если ответ потерян, Web вызывает `getAuthState`: при уже сохранённой сессии продолжает работу, иначе предлагает повторить handoff, пока пара ещё доступна в памяти, или войти снова после перезапуска. Повтор handoff не создаёт новую серверную сессию. Refresh token не выдаётся обратно Web ни при `getAuthState`, ни при `getAccessToken`.

Мобильный login создаёт отдельную Auth-сессию; browser-токены и browser `deviceId` не переносятся в приложение. После подтверждённого handoff native вызывает `device.register` для своей сессии и сохраняет полученный `deviceId` для reconnect. Web в Capacitor-режиме не открывает signaling-соединение и не регистрирует устройство в обход native. Это исключает конкурирующих владельцев WSS и перенос браузерной привязки на другую установку.

`getAuthState` нужен Web только для восстановления UI при старте Capacitor WebView; он возвращает `signedIn` с безопасными claims либо `signedOut`. Native не принимает от Web claims как основание доступа и при каждом защищённом запросе использует серверный Auth. Ошибка чтения secure storage или недоступность bridge возвращается как ошибка и не маскируется под `signedOut`.

`getAccessToken({forceRefresh?})` — асинхронная операция: Web ожидает ответ native и получает `{accessToken, expiresAt}`. Native возвращает текущий действующий access token либо сначала самостоятельно обновляет пару по Auth-контракту; Web не передаёт refresh token и не обновляет пару сам. Перед каждым защищённым HTTP-запросом Web запрашивает токен через этот метод и держит его только в памяти на время запроса, не записывая в `localStorage`, Query cache или логи. Если backend возвращает `ACCESS_TOKEN_EXPIRED`, Web один раз повторяет исходную операцию с `getAccessToken({forceRefresh: true})`; native сериализует refresh, сохраняет `request_id` и повторяет тот же refresh-запрос при неизвестном результате. Параллельные запросы координируются native, чтобы не ротировать один refresh token конкурентно. Native уведомляет Web только об изменении состояния авторизации или claims, не передаёт access token событием; если Web нужен свежий токен, он вызывает `getAccessToken` заново. После `SESSION_INVALID`/`ACCESS_TOKEN_INVALID` native публикует `authStateChanged` со статусом выхода/инвалидации; Web очищает только UI и кеши.

Общий набор стабильных bridge-кодов: `BRIDGE_UNAVAILABLE`, `UNSUPPORTED_VERSION`, `VALIDATION_ERROR`, `SECURE_STORAGE_ERROR`, `UNAUTHENTICATED`, `SESSION_INVALID`, `SESSION_CONFLICT`, `NETWORK_ERROR`, `RATE_LIMITED`. `retryAfter` задаётся для `RATE_LIMITED`, когда backend его возвращает. Ошибки Auth backend отображаются адаптером в эти коды, сохраняя исходный статус/код там, где он нужен для повтора; произвольные сообщения backend не используются как протокол.

Для WSS native использует тот же собственный session manager: сам получает актуальный access token, авторизует соединение и не запрашивает токен через Web bridge. `authStateChanged` не содержит токенов. `peerId` — UUID пользователя из списка Groups; отображаемое имя не является основанием для доступа.

Команды принятия, отклонения, завершения и mute принадлежат нативному интерфейсу звонка и его call engine, а не экрану React. Входящий push и системное действие «ответить» не должны требовать вызова bridge из Web.

Перед запуском приложения Web проверяет версию bridge. Неизвестная или несовместимая версия приводит к явному сообщению о недоступности мобильной интеграции, а не к незаметному переключению на браузерный звонок. Изменения несовместимого формата требуют повышения major-версии bridge и согласованной пары Web/native сборок.

### Сессия и секреты

Для Capacitor-сборки Web сохраняет существующий экран входа и может использовать общий JS Auth-пакет для выполнения login по текущему HTTP-контракту. Полученная пара токенов передаётся нативной стороне для явной передачи владения сессией. Native подтверждает сохранение в защищённом хранилище; только после подтверждения Web удаляет токены из своего session store. Если передача или запись не подтверждена, Web не очищает локальную сессию, не запускает звонковый engine и показывает ошибку вместо неподтверждённого успеха.

После передачи native становится единственным долговременным владельцем мобильной сессии. Он хранит refresh token в iOS Keychain, access token — в памяти или защищённом хранилище по результатам реализации, сериализует refresh и соблюдает Auth-контракт повтора с тем же `request_id` при неизвестном результате. Native обновляет access token для собственного WSS независимо от WebView, в том числе при reconnect после истечения его 120-секундного срока и при холодном старте по push. Refresh token никогда не возвращается Web и не включается в bridge-события, URL, логи или диагностику.

Web получает от native только состояние входа и безопасные claims пользователя; для каждого своего HTTP-запроса он асинхронно запрашивает актуальный access token у native через bridge, не сохраняя его в `localStorage`. Если сервер отверг токен как истёкший, Web запрашивает токен с `forceRefresh: true` и повторяет исходную HTTP-операцию один раз согласно действующему поведению Auth-клиента. После внутреннего refresh native может уведомить Web о смене токена без передачи самого токена; Web при необходимости получает его повторным асинхронным вызовом. Browser build сохраняет действующие `localStorage` и browser refresh policy без изменений. Общий JS Auth-пакет может предоставлять общую HTTP-политику через разные адаптеры: browser adapter владеет браузерным refresh, Capacitor adapter получает токены через асинхронный native bridge; сам пакет не владеет хранилищем.

Logout в Capacitor-сборке координируется через native: серверный отзыв подтверждается по [Auth-контракту](../../backend/modules/auth.md), затем native удаляет сохранённую пару; при подтверждённой инвалидации native завершает авторизованную сигнализацию и публикует событие Web. Неизвестный результат logout не очищает сессию как будто отзыв подтверждён.

### Жизненный цикл звонка

1. Web показывает доступных собеседников и выполняет пользовательское подтверждение исходящего вызова.
2. Web вызывает `placeCall` один раз. Native engine отправляет `call.create` в авторизованный WSS и связывает запрос с локальной операцией.
3. При таймауте или потере ответа engine сначала запрашивает актуальный серверный state через `call.current`/`call.get`; он не повторяет `call.create` автоматически, поскольку `request_id` не является ключом идемпотентности.
4. Входящий VoIP push будит iOS-приложение: native обрабатывает его системным API и сверяет `call_id` с серверным состоянием. Push — сигнал пробуждения, а не источник истины.
5. Native UI обрабатывает ответ, отклонение и завершение. Native engine регистрирует устройство, получает ICE-конфигурацию, обменивается SDP/ICE по WSS, использует TURN relay и подтверждает соединение только по правилам DirectCalls.
6. После переподключения native engine получает актуальное состояние звонка, а не воспроизводит локально накопленные события. Завершение, отзыв сессии или окончание звонка останавливают аудио и освобождают нативные ресурсы.
7. Если WebView остановлен, звонок, управление состоянием, аудио и push-обработка продолжаются на native стороне. События bridge — только синхронизация интерфейса при доступности Web, не механизм фоновой доставки или управления звонком.

В целевую iOS-интеграцию входят PushKit и CallKit. Backend [Devices](../../backend/modules/devices.md) и [Push](../../backend/modules/push.md) сейчас описывают APNs VoIP, но помечены `partial`; credentials и приёмка на настоящих устройствах ещё не выполнены.

## Рассмотренные варианты

- **Оставить звонок в WebView:** не соответствует требованию продолжения звонка независимо от WebView и не выбран.
- **Переписать весь интерфейс на Swift/Kotlin:** дублирует готовый Web-клиент и увеличивает стоимость сопровождения; не выбран.
- **Сохранить Web для контактов, нативный call engine и системный UI:** предлагаемый вариант; сохраняет общие продуктовые экраны и выносит фонозависимый звонок из WebView.
- **Передавать команды звонка через JS даже в фоне:** не выбран; исполнение JS не должно быть предпосылкой для обработки push, системного ответа и активного аудио.

## Последствия и границы

- Функциональность экранов Web не копируется, но мобильная Capacitor-сборка должна проверять её в WebView и на узких экранах.
- Появляется нативный код для каждой мобильной платформы и bridge-контракт, который нужно версионировать и тестировать совместно с Web.
- Browser call engine и native call engine будут разными адаптерами одного серверного контракта; поведение DirectCalls, ограничения и исходы должны оставаться совместимыми.
- Работа в фоне и на заблокированном экране является обязательным критерием приёмки. Она не доказывается запуском звонка только в foreground.
- Принудительное завершение пользователем, force stop, отсутствие сети, запрет push и системные режимы энергосбережения ограничены политиками ОС. Поддерживаемое поведение этих случаев нужно зафиксировать отдельно; нельзя обещать доставку при условиях, когда ОС её не гарантирует.
- Данный документ пока не фиксирует конкретный upstream commit и собранный XCFramework, матрицу тестовых устройств или схему распространения приложения; необходимые изменения backend рассматриваются отдельно по профильным контрактам.

## iOS spike и критерии проверки

Spike ограничен пятью рабочими днями. Он состоит из двух независимых gate, чтобы выбор libwebrtc не зависел от готовности APNs credentials.

### Gate 1: native call engine и libwebrtc

Создать временный минимальный Swift harness без Capacitor и production UI. Использовать backend test environment и существующий Web-клиент как peer. Проверки провести на двух физических iPhone: один на iOS 16.x, второй на актуальной iOS. Симулятор допустим для UI/bridge smoke tests, но не подтверждает WebRTC, аудио, TURN, lock screen или background.

Gate 1 считается пройденным, если:

- Официальный WebRTC upstream собирается в XCFramework на конкретном commit; записаны checksum артефакта и воспроизводимые шаги сборки.
- Native call engine устанавливает реальный WebRTC audio connection с Web-клиентом через TURN relay; оба участника подтверждают `call.connected` только после фактического WebRTC connected.
- Native реализует авторизованный WSS, `call.ping` с возрастающим `sequence`, корректными `audio_connected` и `recovery_id`, переподключение и согласованное с сервером recovery. Автоматический повтор `call.create` не выполняется.
- Двустороннее аудио, выбранная iOS аудиомаршрутизация и работа активного звонка при сворачивании приложения и блокировке экрана подтверждены на обоих устройствах.

Итог Gate 1 — commit, checksum и инструкции сборки XCFramework, результаты сценариев на двух устройствах и явный список нерешённых блокеров. Если обязательный критерий не выполнен за timebox, Gate 1 не считается пройденным, а решение о подключении артефакта к приложению остаётся открытым.

### Gate 2: PushKit, CallKit и входящий cold start

Отдельно проверить получение VoIP push, системное отображение и обработку входящего звонка, включая cold start, фон и lock screen, на физических устройствах с APNs-конфигурацией. Отсутствие credentials или недоступность APNs не считается успешной проверкой и не блокирует сам вывод Gate 1 о сборке/работе libwebrtc; до прохождения Gate 2 публичный App Store релиз запрещён. Gate 2 остаётся обязательной частью приёмки iOS-приложения.

### Общие критерии интеграции и приёмки

- Первое распространение — закрытая beta через TestFlight для команды и ограниченной группы пользователей. Публичный App Store релиз допускается после прохождения приёмки на обоих физических устройствах и проверки PushKit/CallKit с production-конфигурацией.
- Capacitor загружает текущий Web-клиент; вход, группы, контакты и административный интерфейс не требуют отдельного мобильного форка.
- Web и native обмениваются типизированным запросом/событием bridge с проверкой версии; несовместимая версия обнаруживается явно.
- Мобильная сессия передаётся native после login; Web удаляет свою копию только после подтверждения безопасного сохранения нативной стороной.
- Native самостоятельно сериализует refresh по Auth-контракту и авторизует WSS при reconnect после истечения access token и при cold start от входящего push, без работающего WebView.
- Выполняются Web ↔ iOS и iOS ↔ iOS сценарии ответа, отклонения, завершения, занятости, reconnect и истечения сроков; аудио идёт через TURN relay.
- Неопределённый результат `call.create` не порождает дублирующий звонок; Web/native не запускают одновременно два клиента сигнализации или аудио.
- Уже созданный браузерный звонок не перехватывается native; новый звонок из приложения имеет отдельный `call_id` и обычную серверную проверку занятости.
- В bridge, логах и диагностике отсутствуют пароли, refresh token, push token, TURN credentials, SDP и ICE.

## Открытые решения

1. Определить, как Capacitor-приложение получает публичный HTTPS-origin инстанса до первой загрузки удалённого Web-клиента; поле авторизации `serverUrl` не вводится.
2. Инвентаризировать Web-настройки и зафиксировать allowlist/схему `settings`.
3. Реализовать загрузку remote Web assets и bootstrap `serverUrl` в Capacitor.
4. Выполнить Gate 1 в согласованный timebox; зафиксировать результат, commit и checksum XCFramework.
5. Выполнить Gate 2 после настройки APNs credentials; до его успешного завершения публичный App Store релиз заблокирован.

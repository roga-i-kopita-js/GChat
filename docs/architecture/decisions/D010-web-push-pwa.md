# D010: PWA, Web Push и кеширование фронта

Дата: 2026-11-05.

Пользователь согласовал реализацию PWA по документации: Web Push, manifest и кеширование фронта без системного нативного звонка. Согласованы регистрация через WSS, повторная привязка подписки, постоянная VAPID-пара с восстановлением после замены и кнопка обновления с защитой разговора во всех вкладках. Дополнительно согласован механизм координации через общий и исключительный Web Lock. Целевые браузеры включают Safari; включение в список не означает выполненную приёмку.

## Контекст

GChat Web уже содержит браузерный звонковый клиент, manifest и иконки. Manifest требуется адаптировать к двум размещениям: корневому и серверному `/apps/client`. Открытая страница получает звонки по WSS; для уведомления при закрытой странице нужен отдельный Web Push. Существующий APNs VoIP предназначен для нативного iOS-клиента и не используется как браузерный транспорт.

Нужны установка приложения, загрузка фронта из кеша и видимое уведомление о входящем вызове. Уведомление открывает клиент; принятие звонка остаётся действием пользователя в Web с проверкой текущего состояния на backend.

## Решение

- Использовать стандартные Service Worker, Push API и Notifications API. Backend отправляет Web Push с VAPID через библиотеку `web-push`; отдельный брокер не вводится.
- Регистрировать подписку через существующий авторизованный WSS после `device.register`. Адрес принадлежит одной актуальной паре device/session и переносится при повторной регистрации endpoint. Формат, хранение и ограничения принадлежат [Devices](../../backend/modules/devices.md#web-push).
- Сохранять задания Web Push в существующем транзакционном outbox DirectCalls независимо от VoIP и WSS. Изменения схемы и жизненного цикла принадлежат [DirectCalls](../../backend/modules/direct-calls/README.md#web-push-в-outbox); отправка и VAPID — [Push](../../backend/modules/push.md#web-push).
- При сборке формировать service worker с версией фронта и полным набором статических ресурсов. Использовать согласованный HTML и assets одной сборки; для готовой новой версии показывать кнопку «Обновить», откладывая обновление на время звонка во всех окнах этого профиля. Правила кеша, установки и UI принадлежат [Web](../../web/README.md#pwa-web-push-и-кеширование).
- Разделить установку PWA и разрешение уведомлений: установка сама по себе не означает согласия на Web Push.

## Рассмотренные варианты

- Только manifest: даёт метаданные установки, но не доставку Web Push и не кеширование фронта.
- Только WSS: не обеспечивает уведомление при закрытой странице.
- Push из обработчика создания звонка без outbox: сетевой сбой связывает создание звонка с провайдером, рестарт может потерять доставку.
- Автоматический `skipWaiting` и перезагрузка страницы: могут сменить работающий клиент во время разговора. Согласована явная кнопка обновления с защитой звонка во всех окнах; без действия пользователя сохраняется штатное ожидание завершения старых клиентов.
- Network-first HTML при cache-first assets старой версии: усложняет согласованность сборки. Предлагается кешировать HTML и ресурсы как единое целое.

## Границы и последствия

Кеш делает доступной оболочку, но не авторизует пользователя офлайн и не позволяет звонить без backend. Уже открытые окна могут оставаться на предыдущей версии до явного обновления либо закрытия. Откат frontend также является новой установкой service worker и подчиняется тому же жизненному циклу.

Web Push не обеспечивает CallKit, автоматический ответ, непрерывный звонковый рингтон или гарантированное пробуждение браузера. На iPhone требуется установка на экран «Домой» и поддержка Web Push ОС; доставка и работа при блокировке проверяются на физических устройствах. [WebKit о Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

## Согласованные уточнения

- При готовности новой сборки показывать кнопку «Обновить». Во время звонка обновление откладывается; действие в другой вкладке не должно прервать разговор.
- После повторного входа автоматически привязывать существующую разрешённую браузерную подписку к текущей сессии. Выход исключает доставку старой сессии.
- Для регистрации использовать существующий авторизованный WSS после `device.register`.
- В целевую проверку включить Chrome, Edge, Firefox, Safari на macOS и установленную PWA на iOS/iPadOS. Включение в список не означает выполненную приёмку.

- Для VAPID использовать стабильную пару на окружение, сохранять её между деплоями и резервировать приватный ключ. После вынужденной замены подписка автоматически перевыпускается при следующем открытии GChat; до этого доставка на неё недоступна. Правила принадлежат [Push](../../backend/modules/push.md#контекст-и-вопрос-смены-vapid-ключей).

## Координация обновления

Вкладка-владелец WSS удерживает shared Web Lock `gchat-frontend-update` с момента до подключения и до закрытия транспорта. Кнопка обновления ставит exclusive-запрос в очередь и сообщает вкладкам о подготовке через BroadcastChannel. Владелец прекращает новые исходящие вызовы, завершает уже начатые команды и получает актуальное состояние после подключения. При отсутствии незавершённого звонка закрывает WSS и освобождает shared lock; при разговоре ждёт его окончания. Новые владельцы не подключаются, пока exclusive-запрос ожидает или выполняется. Это закрывает гонку между проверкой локального состояния и входящим событием WSS.

Исключительный lock удерживается при активации worker и до уничтожения документа перезагрузкой. `clients.claim()` вызывает смену controller; вкладки перезагружаются при замене worker, первая установка не перезагружает клиент. Без нажатия сохраняется штатное ожидание. Активация через `skipWaiting` и совместимость блокировок описаны в [Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting) и [Web Locks API](https://developer.mozilla.org/en-US/docs/Web/API/LockManager/request).

## Открытые вопросы

- Предложенный список разрешённых push-провайдеров требует проверки на целевых браузерах; точные минимальные версии фиксируются после проверки.
- Минимальные версии и настоящая доставка Web Push требуют ручной приёмки; автоматические проверки Chromium не заменяют её.

## Статус реализации

Реализованы backend Web Push, схема БД, manifest обеих сборок, кеш оболочки, управление уведомлениями, восстановление VAPID-подписки и согласованное обновление вкладок. Автоматические проверки и ограничения описаны в контрактах владельцев. Миграция к рабочему окружению не применялась; реальные Web Push, Safari и мобильные устройства требуют отдельной приёмки.

# D005: полноценный веб-клиент GChat

Дата: 2026-11-03. Пользователь задал направление: полноценный клиент GChat для веба. После документации пользователь поручил реализацию. Веб-приложение, WS-билеты и API групп реализованы; ограничения и непроверенные платформенные сценарии ведутся в контрактах владельцев. Уточнение реализации: 2026-11-04.

## Контекст

GChat получает браузерный клиент, через который пользователь входит, видит доступных людей и совершает голосовые звонки. Он использует общий backend и участвует в тех же звонках, что нативный iOS-клиент. На нём также можно проверять DirectCalls и передачу аудио через coturn, но назначение приложения шире диагностического стенда.

У backend пока не определены публичные HTTP-маршруты выдачи групп и участников. Для полноценного интерфейса их нужно спроектировать и реализовать; ввод UUID не заменяет пользовательский сценарий выбора собеседника. Отдельных решений требуют браузерная сессия, несколько вкладок и ограничения приёма вызова вне открытой страницы.

Браузерный WebSocket не принимает произвольные HTTP-заголовки, а действующий контракт требует Authorization до upgrade. Браузерный способ подключения требует согласованного расширения Auth/Signaling. См. [WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket).

## Решение

Использовать workspace-приложение React / TypeScript / Vite с пользовательскими экранами групп, участников и звонка. Сохранить общий Auth, Devices, DirectCalls и Signaling. Для типовых задач использовать готовые библиотеки, не создавать альтернативный сервер сигнализации или отдельную модель звонка.

Для браузерного WSS используется короткоживущий одноразовый билет, выдаваемый авторизованным HTTP-запросом и проверяемый до upgrade. Сессия и device binding сохраняются на browser profile; Web Locks сериализует refresh и выбирает владельца WSS/медиа, BroadcastChannel синхронизирует остальные вкладки. Точные правила и ограничения localStorage находятся в веб-контракте.

Используется один origin для веб-приложения, HTTP API и WSS с маршрутизацией через proxy. Конкретное размещение и параметры развёртывания определяются при реализации. Браузерные ограничения, способы оповещения и поддерживаемые версии требуют отдельной проверки.

## Рассмотренные варианты

- Страница для звонка по UUID: не соответствует выбранному назначению полноценного клиента. UUID остаётся внутренним идентификатором и элементом диагностики.
- WS-билет: сохраняет проверку доступа до upgrade; требует нового HTTP API, атомарного погашения и правил Origin. Выбран для реализованного браузерного пути.
- Авторизация первым WS-сообщением: требует неавторизованного состояния после upgrade и отдельного протокола ограничений.
- Cookie-авторизация: требует контракта cookie, CSRF, Origin, refresh и выхода. В текущей реализации cookie-путь не вводится; возможное изменение хранения сессии потребует нового согласования.
- Передача access token в URL: противоречит действующему контракту; не предлагается.
- Отдельный сервер-посредник с пользовательскими секретами: добавляет серверный контур и владельца сессий; для него потребуется самостоятельное обоснование.

## Последствия и границы

Реализация включает пользовательский UI и необходимые API-зависимости: группы, участники, браузерный доступ и восстановление сессии. Недостающие backend-контракты не являются основанием сокращать клиент до формы диагностики. Маршруты и DTO определяются в профильных контрактах; их состав не дублируется в этой записи.

Веб-платформа не предоставляет автоматически гарантии APNs/CallKit. Поведение в фоне, при закрытой странице, Web Push и PWA остаётся продуктовым вопросом; открытая вкладка не доказывает готовность этих сценариев. История, видео и другие новые функции также не выводятся из слова «полноценный» без отдельного решения.

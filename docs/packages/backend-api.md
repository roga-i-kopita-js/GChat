# Внутренний клиент HTTP API backend

Это проект для обсуждения. Согласовано направление: отдельный внутренний пакет с генерацией JavaScript-клиента по OpenAPI backend без привязки к UI-фреймворку. Также согласованы явные стабильные `operationId` в backend, автономный экспорт OpenAPI из сборки и хранение схемы и сгенерированных исходников в Git. Runtime-валидация DTO в пакете исключена. Генератор — Hey API (`@hey-api/openapi-ts`). Целевые среды — браузер и Node.js; поддерживаются ESM и CommonJS. Публичный API — класс `BackendApi` с методами по `operationId`. Название пакета и оставшиеся детали процесса генерации ниже предложены к согласованию. Пакет, команды генерации и подключение к приложениям пока не реализованы.

## Назначение и границы

Предлагаемое имя — `@gchat/backend-api`, каталог — `packages/backend-api/`. Пакет предоставляет исполняемый JavaScript-клиент HTTP API и TypeScript-декларации для приложений монорепозитория. Первый потребитель — веб-клиент, включая административные маршруты. Клиент можно использовать и из Node.js без зависимости от браузерного хранилища или React.

Задача пакета — убрать ручное дублирование маршрутов, параметров и DTO в JS/TS-потребителях. HTTP-операции и модели генерируются из спецификации; небольшой общий слой настройки транспорта и обработки ошибок может поддерживаться вручную. Сгенерированные файлы вручную не исправляются.

В объём первой версии предлагается включить все HTTP-операции экспортированной спецификации, в том числе Auth, Groups, Devices, DirectCalls, Backoffice и healthcheck, если они присутствуют в документе. Наличие административного метода в клиенте не даёт прав на его выполнение: доступ проверяет backend.

Публичная точка входа — `@gchat/backend-api`: сгенерированные HTTP-операции и DTO без зависимости от React и TanStack Query. Генерация React hooks, query/mutation options и отдельная точка `/react-query` в текущий объём не входят. Приложение самостоятельно подключает HTTP-операции к используемому UI и менеджеру запросов. Управление сессией и refresh остаётся в приложении.

WebSocket-события, WebRTC, управление звонком, UI и нативный Swift-клиент в этот пакет не входят. Генерация метода получения WS-билета не означает генерацию WebSocket-протокола. Пакет не импортирует backend DTO, NestJS или сервисы backend во время выполнения.

## Исходное состояние

- [OpenAPI backend](../backend/openapi.md) строится из контроллеров и DTO через `@nestjs/swagger`; JSON доступен на `/docs-json`.
- [Настройка Swagger](../../applications/backend/src/swagger/setup-swagger.ts) пока использует стандартную генерацию документа без реализации согласованной политики явных `operationId` и указывает версию `0.0.0`.
- Swagger-плагин Nest CLI дополняет схемы при сборке. Проверка только исходных TypeScript-классов не доказывает полноту схем скомпилированного приложения.
- [Веб-клиент](../web/README.md) сейчас содержит ручной HTTP-слой в [auth.ts](../../applications/web/src/auth.ts), включая хранение сессии и refresh. Готового общего SDK нет.
- Корневой [workspace](../../pnpm-workspace.yaml) пока перечисляет приложения и E2E-пакет; каталог `packages/backend-api/` ещё не подключён.

## Источник контракта и генерация

Источником для генерации служит OpenAPI-документ конкретной ревизии backend. Требуемое поведение маршрутов по-прежнему описывают профильные backend-контракты; пакет не создаёт альтернативный HTTP-контракт. Если схема расходится с кодом или согласованным контрактом, расхождение фиксируется и исправляется у владельца. Ручная правка SDK не должна скрывать ошибку схемы.

Предлагаемый процесс:

1. Собрать backend через его штатную конфигурацию, чтобы отработал Swagger-плагин.
2. Экспортировать OpenAPI JSON автономной командой из этой сборки и сохранить входной артефакт для генерации. Зафиксировать ревизию backend и контрольную сумму схемы; секреты и реальные пользовательские данные в артефакт не включать.
3. Проверить корректность схемы: разрешимость ссылок, уникальность `operationId`, наличие схем тел, параметров и ответов для генерируемых операций. Пробелы не заменять произвольными ручными типами.
4. Запустить выбранный генератор с зафиксированными версией и конфигурацией, затем собрать JavaScript и декларации.
5. Проверить результат и совместимость с потребителями в том же изменении.

Генерация должна воспроизводиться из локального файла схемы без обращения к произвольному развёрнутому серверу. Обычная сборка потребителя использует подготовленный пакет и не требует работающего backend, PostgreSQL или Redis. Получение актуального входного артефакта — отдельный шаг.

Согласован [автономный экспорт OpenAPI из сборки](../backend/openapi.md#автономный-экспорт-для-генерации-клиента). Генератор читает локальный `openapi.json`, полученный без запуска HTTP-сервера и внешних сервисов. Сейчас документ создаётся при старте HTTP-приложения; автономный экспортёр ещё не реализован. Имя команды и способ изоляции определяются при реализации.

Согласованный генератор — Hey API (`@hey-api/openapi-ts`). Используется генерация HTTP-клиента и типов без React/TanStack Query-интеграции и runtime-валидаторов. Точная версия, конфигурация и команды закрепляются при реализации после проверки реальной схемы backend; выбранный инструмент не означает, что такая проверка уже выполнена. Результат — TypeScript-исходники с последующей сборкой в JavaScript ESM и CommonJS с TypeScript-декларациями для обоих форматов. Возможность пользоваться пакетом из обычного JavaScript обязательна; потребитель не должен компилировать исходники пакета.

Имена операций определяются явными стабильными `operationId` по [согласованным правилам OpenAPI](../backend/openapi.md#имена-операций-operationid). Политика принята, но ещё не внедрена в контроллеры. Генератор должен использовать эти идентификаторы как основу имён функций.

## Публичный API

Согласовано: публичная точка входа экспортирует именованный класс `BackendApi`, типы операций и DTO, тип результата `ApiResult<T>` и класс HTTP-ошибки `ApiError`. Все HTTP-операции доступны методами одного экземпляра без группировки по контроллерам. Название каждого метода совпадает с явным `operationId` соответствующей операции контроллера; одинаковые внутренние имена методов разных контроллеров не создают коллизий в SDK.

Конструктор принимает объект настроек:

| Настройка | Поведение |
| --- | --- |
| `baseUrl` | Обязательный базовый адрес без зашитого production host. Для веба допускается `/api`, для Node.js — абсолютный URL. Базовый путь сохраняется при добавлении маршрута. |
| `fetch` | Необязательная подмена транспорта с контрактом Fetch API; по умолчанию используется транспорт среды. |
| `getAccessToken` | Необязательный синхронный или асинхронный поставщик текущего access token. Вызывается для защищённой операции перед запросом и возвращает строку токена либо `null`/`undefined` при его отсутствии. Публичные операции не получают Bearer автоматически. |

Экземпляры изолированы: адрес сервера, транспорт и токен одного клиента не влияют на другой. Глобальный изменяемый singleton не используется.

Пример согласованного интерфейса (реализации пока нет):

```ts
import { BackendApi } from '@gchat/backend-api';

const api = new BackendApi({
  baseUrl: '/api',
  getAccessToken: () => sessionStore.accessToken,
});

const result = await api.adminListUsers({
  query: { search: 'ivan' },
});

console.log(result.data, result.status, result.headers);
```

Каждый метод принимает один объект аргументов. В нём присутствуют только применимые к операции секции `path`, `query` и `body`, сгенерированные по OpenAPI, и необязательный `signal: AbortSignal`. Секции с обязательными параметрами обязательны в TypeScript-сигнатуре. Если все аргументы необязательны, метод допускает вызов без объекта. URL и HTTP-метод задаются сгенерированной операцией и не передаются вызывающим кодом.

Имена JSON-полей сохраняются, включая `snake_case`. Необязательное поле отличается от `null`; даты остаются строками, если схема описывает строки. Кодирование path/query и сериализация тела выполняются по схеме. Пустой ответ `204` не разбирается как JSON, его `data` — `undefined`.

Успешный вызов возвращает `Promise<ApiResult<T>>`:

```ts
export type ApiResult<T> = {
  data: T;
  status: number;
  headers: Headers;
};
```

`T` генерируется из успешных ответов операции; для ответа без тела используется `undefined`. Любой HTTP-ответ вне диапазона 200–299 приводит к исключению `ApiError`, а не к успешному результату с полем `error`. Сетевой отказ и отмена сохраняют исходную транспортную ошибку, не преобразуясь в `ApiError`.

Класс и методы операций генерируются на основе OpenAPI с Hey API; ручные обёртки для каждого endpoint не поддерживаются. Общий слой транспорта и обработки ошибок может быть написан вручную. Конкретная конфигурация Hey API и при необходимости расширение генерации должны обеспечить этот публичный контракт; наличие готовой реализации класса в инструменте пока не проверено.

Согласовано: runtime-валидации DTO в пакете нет. Генерируются только HTTP-клиент и статические TypeScript-типы; валидаторы, схемы для проверки данных во время выполнения и зависимости для такой проверки не добавляются. Клиент сериализует запросы и разбирает ответы, но не проверяет их поля, обязательность, enum или ограничения по OpenAPI. Статические типы отражают спецификацию и не гарантируют соответствия фактического ответа сервера. Проверка OpenAPI при экспорте и генерации выполняется инструментами разработки и не входит в исполняемый клиент.

## Авторизация и повторы

Пакет передаёт Bearer для операций с соответствующим `security` в OpenAPI. Отсутствие или неверное описание `security` исправляется в backend, а не списком защищённых маршрутов внутри SDK. Клиент не проверяет административные права локально и не заменяет guards backend.

Хранение токенов, вход и выход из пользовательского интерфейса, декодирование JWT, refresh, координация вкладок и device binding остаются ответственностью приложения по [Auth](../backend/modules/auth.md) и [веб-контракту](../web/README.md). Сгенерированные методы login/refresh/logout выполняют только соответствующий HTTP-запрос.

Автоматические повторы, refresh на `401` и повтор исходного запроса в пакет не входят. Приложение решает, допустим ли повтор конкретной операции. В частности, `request_id` для refresh формирует и сохраняет владелец сессии; SDK не заменяет его новым значением. Ошибка сети, отмена или `503` не гарантируют, что сервер не выполнил действие.

## Ошибки

Формат backend-ошибок принадлежит [ErrorModule](../backend/modules/errors.md). Класс `ApiError` наследует `Error` и сохраняет HTTP-статус, заголовки, машинный код, безопасное сообщение и `fields`, если ответ содержит стандартную оболочку `error`. Неизвестный код остаётся доступным строковым значением, чтобы новый серверный код не ломал разбор ответа.

Для `429` вызывающему коду доступен `Retry-After`; клиент сам не ждёт и не повторяет запрос. HTTP-ошибка без стандартной оболочки, включая `503` readiness, сохраняет статус и разобранное тело как неизвестное значение. Синтаксически некорректный JSON приводит к ошибке разбора ответа. После успешного разбора соответствие структуры JSON схеме DTO не проверяется.

Сетевой отказ и отмена отличаются от HTTP-ответа и не получают выдуманный backend-код. Правила обработки не должны терять полученный статус из-за ошибки разбора тела. Сетевой отказ и отмена пробрасываются без обёртки. Ошибка разбора JSON успешного ответа сохраняет исходную причину разбора и доступные HTTP-метаданные; она не является backend-ошибкой.

Пакет не пишет в логи тела запросов, пароли, заголовки авторизации, refresh-токены или WS-билеты. Транспортные ошибки не должны автоматически включать конфигурацию запроса с секретами в текст ошибки.

## Подключение и обновление

Предлагается внутренний workspace-пакет с `private: true`, подключаемый через `workspace:*`. Публикация в npm registry для первого этапа не требуется. Приложения используют публичную точку входа собранного пакета, не импортируют внутренние файлы генератора. Поддерживаются оба формата: ESM и CommonJS, по правилам раздела ниже.

При реализации потребуется добавить пакет в workspace, определить его build/typecheck/generate/check-команды и порядок сборки перед потребителями. Версии инструментов и команды фиксируются в манифестах и lock-файле; сейчас таких команд нет.

Изменение HTTP-контракта должно сопровождаться обновлением входной схемы, перегенерацией и проверкой потребителей. Текущая строка `info.version: 0.0.0` не доказывает совместимость; для связи результата с backend используются ревизия и контрольная сумма. Перед удалением операции или изменением её сигнатуры проверяются потребители.

Перевод веб-клиента на пакет — отдельный этап после согласования проекта и реализации. Он должен сохранить действующие правила refresh, синхронизации вкладок и обработки ошибок. Текущая задача не меняет `auth.ts` и не вводит новые backend-маршруты.

## Среды выполнения и форматы модулей

Согласованные среды выполнения — браузер и Node.js. Пакет поставляет JavaScript в форматах ESM и CommonJS и TypeScript-декларации, совместимые с обоими форматами. ESM-потребитель использует `import`, CommonJS-потребитель — `require`; обе формы предоставляют одинаковые HTTP-операции и настройки клиента. Потребителям не требуется компилировать TypeScript пакета или загружать ESM через динамический импорт из CommonJS.

Публичные экспорты пакета направляют `import` и `require` на соответствующие сборки и декларации. Браузер использует ESM-сборку через сборщик приложения; отдельная глобальная переменная или script-tag сборка не требуется. Основной HTTP-клиент не зависит от DOM, браузерного хранилища или Node.js-модулей, недоступных в браузере.

По умолчанию используется Fetch API среды выполнения, с возможностью передать собственный совместимый транспорт. CommonJS-сборка не меняет контракт HTTP-клиента и не вводит отдельный транспорт. Точные минимальные версии браузеров и Node.js фиксируются при реализации в конфигурации и манифесте с учётом потребителей и выбранной версии Hey API; поддержка произвольных устаревших сред не подразумевается.

## Хранение артефактов и проверка актуальности

Согласовано хранить в Git снимок `openapi.json` и сгенерированные TypeScript-исходники пакета. Изменения HTTP-контракта, входной схемы и соответствующего SDK рассматриваются вместе на ревью. Сгенерированные исходники обновляются генератором; ручные исправления в них не допускаются.

`dist` в Git не хранится: JavaScript ESM и CommonJS с соответствующими TypeScript-декларациями собираются из исходников пакета перед сборкой потребителей. Обычная сборка потребителя не запускает экспорт схемы и не требует сборки backend.

CI собирает backend, автономно экспортирует схему и повторяет генерацию с зафиксированными инструментами и конфигурацией. Полученные схема и исходники сравниваются с сохранёнными в Git; различия, включая новые или удалённые файлы, означают ошибку проверки. Проверка не обновляет артефакты автоматически в репозитории. Точные пути снимка и генерируемых исходников определяются при реализации.

Результат экспорта и генерации не должен содержать меняющиеся timestamps или другие случайные значения, вызывающие различия при неизменном контракте. Ревизия backend и контрольная сумма служат для отслеживания происхождения схемы; изменение посторонних файлов не должно менять снимок или SDK только из-за нового commit SHA.

## Критерии приёмки будущей реализации

- Одинаковые схема, конфигурация и версии инструментов дают одинаковый результат генерации; проверка обнаруживает устаревшие артефакты.
- В Git хранятся снимок OpenAPI и сгенерированные TypeScript-исходники; `dist` собирается отдельно. CI обнаруживает изменения, добавления и удаления файлов при повторном экспорте и генерации.
- Пакет работает в браузере и Node.js. Проверены ESM `import` и CommonJS `require` собранного пакета, одинаковый состав операций и разрешение TypeScript-деклараций для обоих форматов. Потребитель не компилирует исходники пакета и не импортирует исходники backend.
- Пакет работает без React и TanStack Query и не генерирует специфичные для них экспорты.
- Runtime-валидация DTO отсутствует: не генерируются валидаторы и не подключаются зависимости для проверки данных по схемам. Сериализация запросов, разбор JSON и обработка HTTP-ошибок сохраняются.
- `BackendApi` требует `baseUrl` при создании; все операции вызываются методами одного экземпляра с единым объектом аргументов. Успех возвращает `{ data, status, headers }`, HTTP-отказ выбрасывает `ApiError`, транспортные ошибки сохраняются.
- Операции имеют уникальные явные `operationId`; переименование контроллера или его метода при сохранении `operationId` не меняет имена генерируемых функций.
- Проверены path/query, JSON-тела, необязательные и nullable-поля, успешный JSON и `204`, базовый путь `/api` и абсолютный URL.
- Проверены Bearer для защищённых операций, отсутствие автоматического Bearer на публичных, смена токена между вызовами и изоляция экземпляров.
- Сохраняются HTTP-статус, заголовки и ошибки валидации; проверены `401`, `403`, `429`, `503`, неизвестный код, ответ без стандартной оболочки и некорректный JSON.
- Отмена и сетевой отказ различимы; ни один из этих сценариев не запускает скрытый повтор или refresh.
- Автономный экспорт из сборки не запускает HTTP-сервер, не требует подключений к PostgreSQL, Redis и APNs или production-секретов; результат соответствует документу HTTP-приложения той же сборки.
- Обычная сборка потребителя не обращается к серверу за OpenAPI и не требует инфраструктуры backend.
- Схема проверяется из сборки со Swagger-плагином; выбранный генератор успешно обрабатывает реальные DTO backend, включая административные методы и исключение healthcheck.
- Перед переводом веб-клиента проверено сохранение его сценариев сессии; наличие SDK само по себе не означает завершения миграции.

Это требования к будущим проверкам. Код пакета и тесты в рамках текущего документа не создаются.

## Открытые решения

Подтвердить название `@gchat/backend-api` и каталог `packages/backend-api/`. Публичный API класса согласован; конфигурация генерации, точные пути артефактов, версии инструментов и минимальные версии сред фиксируются при реализации в соответствии с этим контрактом.

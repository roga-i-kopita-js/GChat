# Разработка и workspace

Монорепозиторий использует pnpm, приложения размещаются в applications. Точные ограничения Node.js и pnpm определены в [package.json](../package.json), версия для nvm — в [.nvmrc](../.nvmrc); разрешённые версии зависимостей — в [lock-файле](../pnpm-lock.yaml). Для backend используется [собственный манифест](../applications/backend/package.json).

## Подготовка

Если используется nvm, выполните nvm install и nvm use из корня. Установите версию pnpm из packageManager подходящим способом: актуальный Corepack либо глобальная установка указанной версии при отсутствии конфликтующего shim. Два способа одновременно не требуются.

```sh
pnpm install
pnpm projects
```

Workspace включает `@gchat/backend`, `@gchat/ios`, `@gchat/web` и отдельный пакет системных E2E `@gchat/e2e` в `tests/e2e/`. Запуск и границы E2E описаны в [README пакета](../tests/e2e/README.md); веб-клиент — в [README приложения](../applications/web/README.md). Инструкции запуска backend и локальных зависимостей — только в [README backend](../applications/backend/README.md). Нативный клиент собирается Xcode, не pnpm; выбор мобильного стека описывается в [iOS](../applications/ios/README.md).

## Зависимости

Используется единый корневой lock-файл; отдельные package-lock.json, yarn.lock и вложенные pnpm lock-файлы не создаются. Для воспроизводимой установки применяется pnpm install --frozen-lockfile. Это правило процесса; наличие CI-пайплайна проверяйте по конфигурации репозитория.

Зависимости приложения добавляйте адресно через pnpm --filter @gchat/backend add или add -D. Общие инструменты при необходимости добавляются через pnpm add -Dw. Пакеты остаются private.

## Git и окружение

Храним исходники, манифесты, lock-файл, миграции и конфигурацию. Исключения заданы [.gitignore](../.gitignore). Секреты и локальные env не коммитятся. Примеры параметров — в .env.example без действующих секретов; локальные настройки новых приложений хранятся в каталоге приложения.

Корневой Compose и setup.sh относятся к [legacy](legacy/mattermost.md). Команды локального backend обслуживают отдельный Compose и не запускают старый мессенджер.

## Стиль JavaScript и TypeScript

Статус раздела: **accepted**, согласовано пользователем 2026-11-08.

Область — поддерживаемые вручную JS/JSX/TS/TSX/MJS/CJS/MTS/CTS во всём workspace: приложения, пакеты, scripts и тесты. Swift, зависимости, результаты сборки и генерируемый SDK не переводятся вручную на этот стиль. Существующие исключения генерации и форматирования сохраняются; изменение генератора требует отдельной оценки.

Обязательные правила:

- Фигурные скобки обязательны у всех ветвей if/else и тел for/for-in/for-of/while/do-while, включая однострочные return/throw. Проверяет Oxlint `curly: ["error", "all"]`.
- Одна переменная на объявление const/let/var; объявления не объединяются запятыми. Проверяет Oxlint `one-var: ["error", "never"]`.
- Вложенные тернарные выражения запрещены, включая цепочки `a ? b : c ? d : e`. Используйте if/else или отдельную функцию с понятным именем; одиночный тернарный оператор допустим. Проверяет общее правило Oxlint `no-nested-ternary: "error"`, в том числе в JSX и тестах.
- При создании объектного литерала `await` в выражениях его полей запрещён: сначала получите результат в отдельной переменной, затем используйте её в объекте. Запрет охватывает вложенные выражения значений, spread и вычисляемые ключи, включая объекты в return, аргументах и присваиваниях. Тела методов и callback имеют собственную границу выполнения и допускают await; объектный литерал внутри такой функции проверяется самостоятельно. Например, вместо `const value = { user: await loadUser() };` используйте `const user = await loadUser();` и затем `const value = { user };`. Порядок вычислений и побочные эффекты при выносе сохраняются; автоматического исправления нет. Проверяет локальное правило `gchat/no-await-in-object: "error"` из `scripts/oxlint-plugin.mjs` без дополнительных зависимостей. Проверка правила: `node --test scripts/oxlint-plugin.test.mjs`.
- Promise-цепочки `.then()`, `.catch()` и `.finally()` запрещены, в том числе внутри `await`, `return` и `void`, с optional chaining и статическими вычисляемыми именами методов. Используйте async/await и блоки try/catch/finally для обработки ошибок и освобождения ресурсов. Ошибку можно передать вызывающему коду через await без локального catch; пустой catch не добавляется ради стиля. Promise.all/race/allSettled/any и создание Promise остаются допустимы. Проверяет локальное правило `gchat/no-promise-chains: "error"` из `scripts/oxlint-plugin.mjs`. Проверяются также ссылки на эти методы без вызова; имя должно быть статически определено. Штатное prefer-await-to-then не используется, поскольку даже strict-режим разрешает цепочки в return. Проверка синтаксическая: у одноимённого метода другого API, например Zod `.catch()`, допустимо узкое отключение только этого правила с пояснением и немедленным включением после выражения. Автоматической переписи цепочек нет: сохраняются порядок, распространение ошибок и cleanup. Проверка настройки: `node --test scripts/async-style.test.mjs`.
- Свойства результата await получайте только деструктуризацией: `const { property } = await asyncFn();` (включая переименование, значения по умолчанию и вложенный pattern). Формы `await asyncFn().property`, `(await asyncFn()).property`, индексный/optional доступ и `const result = await asyncFn(); result.property` запрещены. Локальное правило `gchat/no-await-call-member: "error"` проверяет непосредственный аргумент await, прямой доступ к разрешённому результату и доступ через const-переменные/их const-алиасы с учётом лексической области. Переменные, полученные деструктуризацией, не ограничиваются: `const { user } = await asyncFn(); user.name` допустимо. Обычный `await service.load()`, ожидание скаляра, Promise.all и возвращение всего результата не требуют искусственной деструктуризации. Проверка синтаксическая, без определения Promise-типа и анализа последующих присваиваний let/var: для синхронной фабрики с Promise-полем используйте `const object = factory(); await object.ready`. Синхронные fluent-вызовы (`await page.getByRole(...).click()`) остаются допустимы. Типы и непрослеживаемые потоки данных проверяются отдельно TypeScript. Автоматического исправления нет: перенос await и деструктуризация методов могут менять поведение и this. Проверка: `node --test scripts/await-call-member.test.mjs`.
- Prettier явно фиксирует точки с запятой (`semi: true`), круглые скобки параметров стрелок (`arrowParens: "always"`), два пробела (`tabWidth: 2`, `useTabs: false`) и LF (`endOfLine: "lf"`).
- Сохраняются одинарные кавычки в JS/TS (`singleQuote: true`), двойные в JSX (`jsxSingleQuote: false`), завершающие запятые (`trailingComma: "all"`), пробелы внутри объектных скобок (`bracketSpacing: true`), отдельная строка закрывающей скобки многострочного JSX-тега (`bracketSameLine: false`) и ориентир переноса 100 символов (`printWidth: 100`). PrintWidth не является жёстким ограничением длины строки.
- Расстановка пробелов, переносы, отступы, вид блоков и несколько инструкций на одной строке нормализуются Prettier. Дублирующие его правила в Oxlint не вводятся.
- Краткие стрелки с выражением сохраняются: `(item) => item.id` допустимо. Принудительный `{ return ...; }` для всех map/filter/JSX-callbacks не вводится. Требования к сортировке импортов и пустым строкам сохраняются.
- Inline-callback, включая callback React hooks, обработчики JSX, map/filter и возвращаемую из эффекта функцию очистки, используют вывод типов TypeScript. Избыточные аннотации параметров и результата не добавляются, если контекст или тело функции уже определяют нужный тип. Функциональное выражение с заданным типом переменной/свойства также не дублирует тип результата. Для самостоятельных объявлений функций и функций в переменных без заданного функционального типа явный возвращаемый тип сохраняется. Явная аннотация допустима, когда она намеренно задаёт или ограничивает контракт, например тип предиката; `any` и приведения типов не заменяют вывод. В Oxlint это отражают `allowExpressions: true` и `allowTypedFunctionExpressions: true` у `typescript/explicit-function-return-type`.

Порядок применения: включить правила в общей корневой конфигурации, применить исправления ко всем поддерживаемым исходникам в указанной области, проверить diff на изменения поведения. Не откатывать накопленные пользовательские правки и не создавать коммит без запроса.

Критерии приёмки: `pnpm lint` и `pnpm docs:check` проходят; повторное автоисправление не меняет файлы; для затронутых пакетов проходят профильные проверки типов и относящиеся проверки поведения. Наличие скобок проверяется линтером даже для уже отформатированного однострочного if, отсутствие точки с запятой — проверкой Prettier.

Инструменты: [Prettier options](https://prettier.io/docs/options), [Oxlint curly](https://oxc.rs/docs/guide/usage/linter/rules/eslint/curly). Версии и фактические значения — в корневых манифестах и конфигурации.

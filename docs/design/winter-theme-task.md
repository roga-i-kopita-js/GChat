# Задание: зимнее оформление GChat «Северное сияние»

Обновить оформление Web/PWA и общего веб-интерфейса внутри iOS: светлая голубая палитра, круглые аватарки, редкие снежинки и плавная смена основных разделов. Интерфейс остаётся компактным, современным и привычным для пользователя iOS.

Визуальный ориентир — [последний эскиз](winter-theme-preview.png) и просмотренный пользователем HTML `ignore/design-previews/gchat-winter-preview.html`, вариант `aurora`. Точные цвета и градиенты из HTML согласованы как значения токенов по умолчанию и зафиксированы ниже, чтобы не зависеть от локального файла в ignore. Снимок показывает оформление; движение определяется требованиями ниже. Все анимации в реализации выполняются только средствами CSS.

## Статус и границы

Задание согласовано пользователем: оформление сверяется с готовой HTML-вёрсткой без повторного согласования заданных в ней деталей. Уточнения пользователя по охвату, токенам, точной палитре и React ViewTransition имеют приоритет над макетом. Документ готов к реализации; открытых проектных решений нет.

По уточнению пользователя дизайн-система с конфигурируемыми токенами применяется ко всему приложению Web/PWA и общему веб-интерфейсу iOS: входу, звонкам, диалогам и переписке, контактам, настройкам, администрированию, общей оболочке, карточкам, модальным окнам и состояниям загрузки, ошибки и отсутствия данных. Экран разговора, входящий вызов и подтверждения также входят в область применения дизайн-системы. Оформление задаётся общей системой токенов по [контракту UI kit](../web/README.md#токены-ui-kit), а не отдельной темой только для трёх основных разделов. Размеры и оформление берутся из готовой HTML-вёрстки с адаптацией по правилам ниже.

Состав меню, доступ к контактам и административному разделу сохраняются по [контракту Web](../web/README.md#экраны-и-навигация). На desktop сохраняются действующие панели и ограничения ширины; рамка мобильного устройства и тень внешнего контейнера из эскиза в приложение не переносятся.

Правила истории, переписки, доступа и звонков остаются у владельцев: [история](calls-history.md), [диалоги](../web/dialogs.md), [настройки](../web/settings.md), [экран звонка](call-screen.md). Внешний вид системного CallKit и системных панелей задаёт ОС по контракту общего экрана звонка. Прежнее исключение экрана разговора и модальных подтверждений из оформления больше не действует.

### Конфигурирование — согласовано

По уточнению пользователя дизайн-систему конфигурирует только разработчик через общие токены. Пользовательские настройки оформления и переключатель тем в приложении не требуются. Состав настраиваемых параметров определён ниже.

### Область применения декора — согласовано

Снег отображается общим фоном на всех экранах приложения, включая экран разговора. Модальные окна, в том числе входящий вызов и подтверждения, отображаются поверх декора. Декор не перекрывает текст и действия, не перехватывает нажатия и не мешает чтению. Рисунок, количество и параметры движения снежинок согласованы. По последнему указанию пользователя линии ветра удалены. Движение декора выполняется только средствами CSS, параметры задаются токенами; при системном уменьшении движения декор неподвижен.

### Состав токенов — согласовано

Существующая система базовых и семантических токенов UI kit распространяется на всё приложение. Разработчик конфигурирует через токены:

- цвета и градиенты поверхностей, текста, акцентов, состояний и аватаров;
- типографику, отступы, размеры, скругления, границы и тени;
- размеры, количество, прозрачность и параметры движения снежинок;
- длительности и easing переходов и анимаций.

Компоненты используют общие токены; одинаковые параметры не дублируются локальными значениями в стилях экранов. Значения по умолчанию берутся из согласованного HTML и разделов ниже. Для отсутствующих в макете экранов используются те же семантические токены и действующая функциональная компоновка, без добавления демонстрационных действий.

## Готовность

Открытых решений нет. HTML задаёт геометрию и оформление; интерфейс применяется ко всему приложению. Внешний вид системных экранов остаётся у ОС. Приёмка ниже определяет обязательные проверки, а не сообщает о выполненных результатах.

## Оформление

### Палитра — согласовано

Использовать голубой вариант «Северного сияния». По подтверждению пользователя точные цвета и градиенты варианта `aurora` из HTML задают значения токенов по умолчанию. Фиолетовые акценты и подложки заменены голубыми; общий фон приложения имеет мягкий голубовато-мятный градиент прежней шапки. По последнему указанию пользователя шапки прозрачны и не имеют отдельной заливки или нижней рамки; градиент один на весь viewport и не начинается заново на каждом блоке.

| Назначение                                    | Значение из эскиза                          |
| --------------------------------------------- | ------------------------------------------- |
| Основной акцент                               | `#2477ad`                                   |
| Светлая поверхность                           | `#f4f9fc`                                   |
| Фон основного экрана                          | Общий голубовато-мятный градиент из прежней шапки  |
| Мягкая акцентная подложка                     | `#e0eff8`                                   |

| Основной текст                                | `#263e4e`                                   |
| Вторичный текст                               | `#617785`                                   |
| Снежинки                              | `#80a4bc` с прозрачностью по разделу декора |
| Дополнительная поверхность (`canvas`)         | `#e7f0f7`                                   |
| Базовая заливка аватара (`avatar`)            | `#ddecf7`                                   |

Системная панель PWA использует светлый тон верхней границы приложения: токен `--ui-system-bar-color`, по умолчанию `#ddeaeb` (цвет в центре верхнего края контрольного снимка). Системная панель принимает один цвет, градиент страницы сохраняется. Сборка и Vite dev подставляют этот токен в HTML `theme-color` и `msapplication-TileColor`; production manifest получает тот же цвет в `theme_color` и `background_color`. Токен задаётся шестизначным HEX, поскольку manifest не поддерживает CSS custom properties. Цвет задаётся до выполнения приложения; параметры устанавливаются одинаково в корневой и серверной сборках.

Общий градиент приложения (прежний фон шапки) состоит из двух слоёв в указанном порядке:

1. `radial-gradient(ellipse at 100% 0, color-mix(in srgb, #e2f1e8 97%, #000 3%), transparent 65%)`.
2. `linear-gradient(120deg, color-mix(in srgb, #deedf9 97%, #000 3%), color-mix(in srgb, #f4f9fc 97%, #000 3%))`.

Палитра градиентов аватара из HTML; направление каждого — `145deg`:

| Вариант            | Начальный цвет | Конечный цвет | Цвет инициалов |
| ------------------ | -------------- | ------------- | -------------- |
| Голубой            | `#e6f2fa`      | `#cee1ef`     | `#416780`      |
| Ледяной (`ice`)    | `#e3f1f3`      | `#cde2e7`     | `#426c75`      |
| Туманный (`mist`)  | `#e8eff6`      | `#d2e0ec`     | `#536a7d`      |
| Стальной (`steel`) | `#e0ebf4`      | `#c5d9e9`     | `#446780`      |

Затемнение 3% применяется к фону и цветам градиента относительно исходной палитры, а не фильтром ко всему интерфейсу. Текст, аватары, кнопки и иконки не затемняются общим слоем. Контраст обычного текста — не менее 4,5:1, кроме согласованного ниже значения вторичного текста из макета.

По явному решению пользователя вторичный текст сохраняет точное значение `#617785` из HTML без затемнения ради контраста. Его расчётный контраст на основном фоне с затемнением 3% — около 4,14:1, на поверхности `#f4f9fc` — 4,42:1. Для этих сочетаний принято исключение из требования 4,5:1; реализация сохраняет цвет макета. Вопрос закрыт.

Оформление светлое независимо от темы окружения; отдельная тёмная тема этим заданием не проектируется. Значения оформляются общими токенами по [правилам UI kit](../web/README.md#общая-оболочка-и-ui-kit).

### Списки и аватары — согласовано

- Сохранить двухстрочную иерархию: имя, затем результат звонка или превью переписки. Время и отдельное действие звонка остаются справа. Пропущенные вызовы сохраняют красный акцент, подпись и иконку.
- Аватары в списках круглые, 44 × 44 CSS px, с мягким градиентом из согласованной палитры. Инициалы — 13 px, вес 500; без тяжёлых обводок, блеска и декоративных колец. Это значение размера относится к спискам, а не к крупным аватарам в карточках и на экране разговора.
- Цвет одного пользователя одинаков во всех списках и карточках. Сохранить стабильное назначение по идентификатору пользователя из [контракта UserCard](../web/user-card.md), а не по имени или позиции строки. Геометрия и оформление принадлежат общему компоненту.
- Системный шрифт, перенос длинных имён и увеличение текста до 200% сохраняются. Декор не ухудшает чтение и не занимает место полезного содержимого.

### Шапки, фильтры и нижнее меню — согласовано

Оформление берётся из варианта `aurora` HTML:

- Шапка раздела: заголовок 28 px, вес 600, межстрочный интервал 1,2, межбуквенное расстояние −0,8 px; внутренние отступы 28 px сверху, 24 px по бокам и снизу. Справа декоративная снежинка 24 px; фон — прозрачный, виден общий градиент приложения. Отдельная заливка и разделитель снизу отсутствуют. Это шапка содержимого раздела, а не дополнительная общая верхняя панель приложения.
- Фильтр: линейные текстовые пункты с промежутком 12 px, активный выделен акцентным цветом и подчёркиванием 2 px. Фон фильтра прозрачный, без заливки активного пункта. Область нажатия — не меньше 44 × 44 CSS px.
- Нижнее меню: поверхность со скруглением 20 px, рамкой 1 px, внешним отступом 12 px по бокам и снизу и внутренним отступом 6 px. Активный пункт имеет мягкую акцентную подложку, скругление 12 px; иконки 22 px, подписи 11 px. Сохраняются действующие пункты, права доступа и безопасная область устройства; меню не перекрывает содержимое. Смена цвета и подложки активного пункта — 180 мс, при уменьшенном движении сразу.

Все значения выражаются токенами с поддержкой пользовательского масштаба текста; они не задают фиксированную ширину или высоту приложения из макета. На desktop сохраняется действующая адаптивная раскладка.

## Анимации только средствами CSS

Временные параметры, промежуточные кадры и движение задаются через `@keyframes`, `animation`, `transition`, CSS custom properties и псевдоэлементы View Transitions. JavaScript/React разрешён для навигации, выбора направления, переключения классов или атрибутов состояния, интеграции React ViewTransition и её очистки. Для обычных CSS-анимаций разрешена обработка `animationend`/`animationcancel`.

В коде приложения не использовать Web Animations API (`Element.animate`, `Animation`), `requestAnimationFrame`, таймеры для управления ходом анимации, покадровое изменение inline-стилей, Canvas/WebGL и сторонние библиотеки анимации. Нативные снимки и жизненный цикл перехода делегированы React ViewTransition; это согласованная интеграция, а не собственное управление кадрами. Декор — DOM или SVG; SVG задаёт рисунок, движение выполняется CSS.

Локальный HTML-эскиз использует Web Animations API и горизонтальное скольжение для смены разделов. По последующему решению пользователя навигационные переходы берутся из базового примера React Router, описанного ниже; HTML остаётся ориентиром оформления и декора.

### Механизм переходов — согласовано

По прямому указанию пользователя использовать [руководство React Router по View Transitions](https://reactrouter.com/how-to/view-transitions). Для установленных React/React DOM 19.3 и React Router 8.5 применяется текущий рекомендуемый подход: постоянная граница React `<ViewTransition>` вокруг области с `Outlet` в общей раскладке. React Transitions роутера остаются включёнными. Граница не получает новый key при смене URL и не пересоздаёт дерево маршрутов ради анимации.

Устаревшие `viewTransition` props/options React Router и `useViewTransitionState` не используются одновременно с React ViewTransition. Приложение не вызывает `document.startViewTransition()` вручную. По уточнению пользователя «в примере анимация была свайпом в сторону» визуальное движение берётся из готового HTML-макета: горизонтальный сдвиг старого и нового экранов. Руководство React Router определяет интеграцию, а HTML — рисунок и параметры движения.

Старый экран представлен нативным снимком браузера. Приложение не клонирует DOM и не монтирует вторую копию страницы/Outlet. Нижнее меню, декор и глобальные окна находятся вне движущейся области; общий снимок документа не должен замораживать декор, блокировать меню или закрывать глобальные окна.

При отсутствии поддержки View Transitions навигация выполняется без анимации. По [ограничениям интеграции React Router](https://reactrouter.com/how-to/view-transitions#migrating-from-react-routers-view-transitions) Back/Forward могут выполняться без анимации; корректность URL, данных и прокрутки обязательна независимо от наличия движения.

### Визуальное поведение переходов — согласовано

1. На телефоне (до 800 CSS px включительно) содержимое `Outlet`, включая заголовок и фильтр при наличии, сдвигается по горизонтали, как в HTML-макете: 210 мс, `cubic-bezier(.32,0,.2,1)`, без растворения. При выборе вкладки правее текущей новый экран въезжает справа от `translateX(100%)` к нулю, старый уходит от нуля к `translateX(-100%)`. При выборе вкладки левее направления зеркальные. Порядок берётся из существующего нижнего меню, включая административный раздел. Внутри одного раздела открытие вложенного маршрута выполняется въездом справа, возврат к родительскому — въездом слева. Проверяется граница сегмента пути: похожий префикс не означает родительский маршрут. Для Back/Forward между соседними маршрутами направление определяется порядком ранее посещённых записей истории по публичным location.key и типу навигации Router; Back движется вправо, Forward — влево. При недоступном порядке записей и отсутствии отношения родитель/потомок POP не получает анимацию с угаданным направлением. Это локальное состояние оформления, без управления историей или очереди навигаций. Токены длительности и easing позволяют разработчику переопределить параметры; easing по умолчанию совпадает с макетом, длительность по запросу пользователя от 2026-11-14 ускорена вдвое для переходов экранов и локального фильтра истории.
2. Постоянная граница охватывает содержимое маршрутов общей раскладки, включая доступный пользователю административный раздел. Общая анимация включается при изменении pathname, то есть при смене экрана. Изменение только query или hash в пределах текущего пути не запускает переход: в частности, «Все / Пропущенные» не двигает весь экран. По уточнению пользователя этот фильтр на всех ширинах использует fade только области списка истории под контролами по [контракту истории](calls-history.md#визуальное-соответствие-gchat). Шапка, фильтр, нижнее меню и сведения о звонке неподвижны. Список получает одну постоянную вложенную границу React ViewTransition; длительность и easing задаются теми же общими токенами, что и переходы экранов. Повтор выбранного фильтра, пагинация и фоновые обновления не запускают анимацию списка. Сохраняются URL фильтра, loaders, прокрутка и Back/Forward. Обновления fetcher/runtime также не включают переход. Не добавляются отдельные анимации для каждого вложенного элемента или дополнительный роутер. Нижнее меню остаётся на месте; фоновый снег не перезапускается при навигации.
3. Повтор активного раздела не создаёт отдельной анимации. При быстрых переходах React ViewTransition координирует и объединяет обновления по своим [правилам](https://react.dev/reference/react/ViewTransition#how-does-viewtransition-work); итоговый экран соответствует последней актуальной навигации. Собственная очередь анимаций не вводится. Нижнее меню остаётся доступным.
4. Уходящий снимок — только визуальное представление: без интерактивных действий, дублирования DOM-идентификаторов и элементов в accessibility tree. Снимки создаёт браузер; в приложении смонтирован один текущий экран. Доступность нового содержимого и завершение перехода координируются штатной интеграцией; отдельной блокировки на таймере нет.
5. Завершение, пропуск и отмена перехода не оставляют заблокированный интерфейс или переходные состояния. При уменьшенном движении или отсутствии API интерфейс не ждёт события отключённой анимации. Анимация не создаёт второй router, runtime, подписки или дополнительные сетевые запросы сверх действующих loaders/runtime и не прерывает звонок. Сохраняются URL, Back/Forward, прокрутка и данные по действующим контрактам.

По запросу пользователя от 2026-11-14 на desktop (от 801 CSS px) переходы маршрутов общей раскладки используют fade вместо горизонтального сдвига: прозрачность старого экрана меняется от 1 к 0, нового — от 0 к 1, без transform и изменения геометрии. Это относится и к переключению переписок: список диалогов остаётся на месте. Длительность и easing берутся из общих токенов переходов. Локальное переключение фильтра истории использует fade списка на всех ширинах по контракту истории. Правила уменьшенного движения и отсутствия API действуют для fade так же, как для мобильного перехода.

### Снежинки — согласовано

- Использовать узнаваемые шестилучевые снежинки с ответвлениями, включая декоративный знак в шапке. Звёздочки и символы искр не подходят.
- Одновременно — не больше 10 падающих декоративных снежинок размером 13–17 CSS px. Основное размещение — по краям и в свободных областях.
- Медленное падение: цикл 24–34 секунды, `linear`, разные отрицательные задержки. Лёгкое боковое покачивание: цикл 8 секунд, `ease-in-out`, смещение от −5 до +8 px. Прозрачность — 0,22–0,48.
- Снежинки не накапливаются внизу и не создают прокрутку. Траектория адаптируется к высоте контейнера; фиксированная высота эскиза не переносится в приложение.

### Доступность и производительность

При `prefers-reduced-motion: reduce` переходы разделов и бесконечное движение декора отключены. Раздел меняется сразу; допускаются статические снежинки и линии. Интерфейс не должен ждать события окончания отключённой анимации.

Для движения экранов и декора анимировать только `transform` и `opacity`; не анимировать размеры, отступы, `top`/`left`, размытие и тени. Для небольших контролов разрешены CSS-переходы цвета текста и фоновой заливки. Невидимый декор ставится на паузу через CSS-состояние. Глобальные входящие и подтверждения отображаются выше декора и переходных слоёв и остаются доступны.

## Критерии приёмки

1. Все экраны приложения используют общую конфигурируемую дизайн-систему с токенами. Цвета и градиенты по умолчанию соответствуют согласованной палитре HTML, включая вторичный текст `#617785` с принятым исключением по контрасту. Аватары в списках круглые, 44 × 44 CSS px, инициалы — 13 px с весом 500; цвет стабилен по ID пользователя во всём приложении. Шапки, фильтры и меню соответствуют готовому HTML по указанным выше правилам.
2. Встречаются снежинки с шестью разветвлёнными лучами; они не мешают чтению, нажатию и прокрутке. Линий ветра нет. Шапки и содержимое располагаются на едином голубовато-мятном фоне без отдельной заливки шапки и без повторного начала градиента на границах блоков.
3. При навигации на телефоне содержимое `Outlet` сдвигается по горизонтали, как в HTML-макете. Реальные псевдоэлементы старого и нового экранов имеют длительность 210 мс и зеркальные перемещения на полную ширину при переходах вправо и влево; одного вызова API недостаточно для проверки анимации. На desktop от 801 px, включая переключение диалогов, старый и новый экраны меняют только прозрачность от 1 к 0 и от 0 к 1; горизонтального перемещения страницы и списка диалогов нет. Локальная смена фильтра истории использует fade списка на всех ширинах. Переопределение токенов меняет длительность и easing. Нет скачков раскладки, пустого кадра, мерцания или изменения положения нижнего меню; декор продолжает движение. При уменьшенном движении или отсутствии API содержимое меняется без анимации.
4. Прямое и обратное переключение, повтор активного пункта и серия быстрых нажатий приводят к последнему выбранному разделу. Возврат по ссылке «Назад» из вложенного маршрута использует противоположное открытию направление, включая последовательный возврат с двух уровней настроек. Back/Forward сохраняют корректный маршрут и направление при наличии анимации. После завершения, пропуска или отмены перехода нет временных слоёв, заблокированного фокуса и дублирования элементов для скринридера. Без поддержки View Transitions и при Back/Forward без анимации сохраняется корректная навигация.
5. При уменьшенном движении разделы доступны сразу, снег неподвижен. Смена настройки во время перехода также оставляет интерфейс рабочим.
6. Движение реализовано CSS, переходами маршрутов управляет React ViewTransition согласно руководству React Router; в коде приложения отсутствуют запрещённые механизмы управления анимацией, ручные DOM-копии экранов и параллельная legacy-интеграция `viewTransition`.
7. Проверены 360 × 640, 390 × 844, 430 × 932 CSS px, desktop от 801 px, длинные имена, увеличение текста до 200%, клавиатура и безопасные области. У интерфейса нет горизонтальной прокрутки и перекрытых действий.
8. Входящий и текущий звонок, диалоги, фильтры, состояния загрузки/ошибок, навигация и ограничения доступа сохраняют действующее поведение. Выполнена отдельная визуальная проверка на iPhone/WebView; браузерный снимок её не заменяет.
9. После реализации выполнены `pnpm docs:check`, typecheck, build и относящиеся проверки по [инструкциям Web](../../applications/web/AGENTS.md). Это требования к будущей приёмке, а не результаты проверки реализации.

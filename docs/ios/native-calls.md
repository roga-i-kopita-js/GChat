# Нативные аудиозвонки iOS: этап без APNs

## Статус и назначение

Первый этап согласован пользователем 2026-11-07: нативный WebRTC без APNs/PushKit, сборка официального SDK и отдельный Swift harness с CallKit до интеграции основной оболочки. Движок сначала реализован в отдельном harness, затем по отдельному поручению [подключён к основной оболочке](native-app.md), которая сообщает `nativeCalls: true`. Статус accepted разрешает реализацию этого этапа, но не подтверждает прохождение Gate 1.

Добавлены [pin и сборочный скрипт SDK](../../applications/ios/WebRTC/README.md), модель DTO/проекции/пингов и оркестратор DirectCalls в NativeCore, отдельный [CallKit harness](../../applications/ios/CallHarness/README.md). Официальный XCFramework собран для device/simulator arm64 и упакован с лицензиями; checksum находится в build-lock.json. Harness собирается для Simulator arm64 и физического iPhone; двусторонний звук Web → iOS подтверждён пользователем на одном устройстве, [результат проверки](../../applications/ios/CallHarness/README.md#текущая-проверка). Полная физическая приёмка не завершена. Основное приложение подключает движок по отдельному принятому контракту интеграции.

Основа — [D008](../architecture/decisions/D008-capacitor-bridge.md#ios-spike-и-критерии-проверки): Swift, официальный upstream libwebrtc, собственный тонкий адаптер, существующие DirectCalls и Signaling. Выбор стороннего готового SDK или неофициального бинарного пакета не входит в этот проект.

## Первый этап

Сначала выполнить Gate 1: отдельный минимальный Swift harness с CallKit и настоящим аудио, без зависимости звонка от Capacitor/WebView. Harness — инструмент разработки, а не второй продуктовый интерфейс. Он использует общий NativeCore для HTTPS-авторизации и WSS; собственный backend или отдельный протокол звонков не вводятся.

Два последовательных результата:

1. **SDK:** воспроизводимая сборка libwebrtc из официального upstream в XCFramework для iPhone arm64 и Simulator arm64. До начала сборки фиксируются точный upstream commit, версия Xcode и аргументы. Результат — локальный артефакт, SHA-256, лицензии и инструкция повторной сборки. Прохождение проверки определяет пригодность выбранного commit; неудача фиксируется как блокер, а не повод подключить другую зависимость без обсуждения.
2. **Аудиозвонок:** исходящий и входящий при открытом harness, ответ/отклонение/отмена/завершение, mute и аудиомаршрутизация. Peer — существующий Web-клиент на изолированном стенде. Проверяются двусторонний звук, TURN relay, восстановление сети и продолжение уже начатого разговора при сворачивании/блокировке.

Первоначальная проверка SDK выполнена в отдельном harness. По последующему явному поручению пользователя SDK и движок подключены к основной оболочке по принятому контракту интеграции; это исключение порядка работ не превращает частичные результаты в полный Gate 1 из D008.

## APNs, CallKit и входящий вызов

- APNs credentials, регистрация VoIP-токенов, PushKit, автоматическое пробуждение native-приложения и Gate 2 исключены из текущего этапа. Существующий backend и его APNs-код не удаляются; на тестовом стенде APNs выключен настройкой `APNS_ENABLED=false`.
- CallKit остаётся в первом этапе: системные действия ответа/завершения и активация/деактивация аудиосессии проверяются совместно с libwebrtc. Исключение APNs не означает исключения локальной системной интеграции iOS.
- При открытом harness входящий отображается его собственными кнопками ответа/отклонения. Нельзя требовать системный экран поверх foreground: [Apple DTS описывает это ограничение CallKit](https://developer.apple.com/forums/thread/844750). Успешный completion `reportNewIncomingCall` и наличие вызова в `CXCallObserver` проверяются отдельно от пользовательского подтверждения интерфейса и слышимости.
- Новое входящее доступно через WSS, пока harness исполняется и подключён. Сохранение фонового WSS в ожидании нового звонка не обещается. Фоновый режим audio используется для настоящего активного разговора.
- В Info.plist harness объявляются режимы `audio` и `voip` для нативного VoIP/CallKit. Запись `voip` не регистрирует PushKit, не требует APNs credentials и не даёт гарантии пробуждения или сохранения фонового WSS. Режимы описаны в [документации Xcode](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes).
- После открытия native приложение регистрирует устройство и запрашивает `call.current`. Только серверный актуальный ringing позволяет показать входящий; ответ требует действия пользователя. Завершённый вызов не возобновляется, сроки не продлеваются локально.
- [Эксперимент Web Push → native](../../applications/ios/web-push-launch-spike.md) подтверждает отдельные участки перехода. Перенос тестовой URL-схемы, гарантированное открытие одним нажатием, автоматический ответ и перенос браузерной сессии не входят в Gate 1. Продуктовая интеграция ссылки согласуется отдельно после готовности движка.
- Требования [BR-05/BR-06](../product/requirements.md#3-обязательные-требования-первой-версии) и условия публичного релиза в D008 сохраняются. Этап без APNs — ограниченный этап разработки, а не полная приёмка приложения.

## Владение и границы

- NativeCore остаётся владельцем сессии и единственного WSS. Будущий call controller получает сообщения через существующий нативный канал; Web не получает SDP/ICE или TURN credentials через UI bridge.
- Оркестрация протокола отделена от платформенного WebRTC-адаптера. Код состояния можно проверять без UIKit/libwebrtc; медиатесты используют настоящий SDK. Внедрение адаптеров не создаёт второго транспорта.
- WebRTC-адаптер владеет PeerConnection, аудиотреком и обработкой ICE. CallKit-адаптер владеет системными действиями звонка и жизненным циклом аудиосессии. UIKit, AVAudioSession и CallKit не добавляются в переносимый пакет NativeCore.
- Общая аудиоконфигурация CallKit/WebRTC подготавливается до создания первого CXProvider и до регистрации входящего или запроса исходящего системного звонка, без активации сессии приложением. Ошибка подготовки не создаёт provider и не регистрирует системный звонок; активный звонок другого выбранного устройства также не создаёт локальный provider. После активации CallKit приложение не повторяет настройку category/mode при ответе или смене динамика. Адаптер передаёт активацию/деактивацию WebRTC; состояние UI следует фактическому маршруту. Этот порядок соответствует [рекомендации Apple DTS по ранней подготовке аудио](https://developer.apple.com/forums/thread/810385); [отдельное пояснение](https://developer.apple.com/forums/thread/837211) описывает связь инициализации provider с идентификатором аудиосессии. Соблюдение порядка само по себе не подтверждает исправление системного UI или громкости.
- Backend остаётся источником истины. [DirectCalls](../backend/modules/direct-calls/README.md) владеет состоянием, выбором устройства и сроками; [Signaling](../backend/modules/signaling.md) — доставкой и адресным обменом. Новый backend API не требуется.
- Используются штатные криптографические механизмы WebRTC/runtime. Собственные алгоритмы и дополнительные криптографические зависимости не вводятся.

## Протокольное поведение

Реализация следует действующим контрактам, не копирует браузерные механизмы хранения и блокировок буквально:

- После регистрации устройства и переподключения выполняется `call.current`; применяется только актуальная версия DTO. Терминальное состояние не воскрешается запоздалыми событиями.
- Используются существующие команды создания, принятия, отклонения, отмены и завершения. Неизвестный результат `call.create` не повторяется автоматически; приложение сверяет состояние.
- SDP и ICE привязаны к текущим call/negotiation/device/session по Signaling. Поздние результаты предыдущей сессии или переговоров не применяются.
- `call.connected` отправляется только после фактического WebRTC connected и для действующей negotiation. Команда UI или успешная установка SDP не считаются подключением аудио.
- Native отправляет `call.ping` сразу и затем каждые 10 секунд с монотонным sequence, фактическим `audio_connected` и текущим `recovery_id`. Состояние recovery берётся с сервера; превышение срока завершает локальные ресурсы согласно серверному исходу.
- Отзыв сессии/отключение аккаунта прекращает авторизованный звонковый контур. При обычном завершении освобождаются PeerConnection, микрофон, аудиосессия, таймеры и системный UI.
- SDP/ICE, TURN credentials, токены и полные сообщения сигнализации не записываются в UI-диагностику и артефакты проверки.
- Harness предоставляет кнопку копирования диагностического снимка, доступную и до входа. Снимок содержит время, версию приложения/iOS, проверенный origin сервера, UUID текущего аккаунта/звонка, состояние авторизации/WSS/звонка/медиа, последнее имя события и безопасное сообщение ошибки. Пароль, токены, SDP/ICE, TURN credentials и полные сетевые сообщения в снимок не включаются. После копирования показывается подтверждение.
- Тот же безопасный снимок, дополненный состоянием foreground и счётчиком/временем полученных WSS-сообщений, хранится одним перезаписываемым файлом в контейнере harness для чтения с подключённого устройства средствами разработки. Это не история сигнализации и не отправка телеметрии на сервер.
- Для диагностики аудиомаршрутизации снимок включает до 32 последних локальных аудиособытий с монотонным временем: подготовку, активацию CallKit/WebRTC, начало/остановку аудио и системную смену маршрута. Записываются только типы выходов, системная причина и параметры category/mode/options/sample rate/buffer; названия и идентификаторы аксессуаров исключены. Буфер ограничен в памяти текущего процесса, отдельные файлы истории не создаются.

## Проверки и приёмка

### Отложенные дефекты текущего этапа

По явному решению пользователя от 2026-11-10 ползунок громкости (AUDIO-002) и мигание/откат системной кнопки динамика CallKit (AUDIO-001) исключены из текущего скоупа работ. Текущие элементы управления сохраняются; их исправление, удаление или замена не входят в этот этап. [Запись решения](call-volume-ui.md) объясняет границу, [реестр](audio-bugs.md) сохраняет результаты воспроизведения и статус deferred.

Эти дефекты не блокируют оставшиеся проверки движка и подготовку последующих задач. Они не считаются исправленными или пройденными; полный Gate 1 по D008 не объявляется закрытым на основании частичного прогона. Требования будущей полной приёмки из [контракта громкости](call-volume.md) и [маршрутизации](audio-devices.md) сохраняются. Возврат к отложенным дефектам выполняется отдельной задачей.

### Остальные проверки

Порядок сборки SDK опирается на [официальную инструкцию WebRTC](https://webrtc.googlesource.com/src/+/main/docs/native-code/ios/README.md). Перед загрузкой проверяются свободное место и возможность сборки зависимостей. Агент не удаляет пользовательские данные ради сборки. Точные pin и checksum фиксируются по результату SDK-проверки; без них SDK не подключается к основной оболочке.

Автоматически проверяются состояние и гонки протокола: неверный порядок/дубликаты версий, неизвестный результат создания, конкуренция устройств, устаревший negotiation, монотонность пингов, recovery и инвалидирование сессии. Сборка Simulator проверяет подключение SDK и системных адаптеров, но не заменяет физическое аудио.

Физическая приёмка — сценарии C01–C07 из [ручного плана](../../applications/ios/manual-tests.md), автоматический C10 — из [плана автоматизации](../../applications/ios/automated-tests.md). Для полного Gate 1 сохраняется матрица D008: физический iPhone с iOS 16.x и физический iPhone с актуальной iOS. Проверка только на доступном iPhone 14 является частичным результатом; неподтверждённые сценарии остаются not_run/blocked с причиной.

Локальным стендом владеет E2E-пакет: отдельный TURN-контейнер с портами, опубликованными только на явно выбранном LAN IPv4 Mac; тестовые PostgreSQL/Redis и аккаунты остаются в выделенном `gchat-web-test`. Backend слушает loopback, native получает HTTPS/WSS через отдельный LAN proxy с доверенным сертификатом, Web peer — через отдельный localhost-порт. APNs выключен. Секреты берутся только из игнорируемых E2E fixtures; рабочие env, аккаунты и `gcall.online` не используются. Стенд не объявляется автоматическим iOS E2E runner.

Успех этапа: зафиксированы SDK/артефакт и реальные результаты Gate 1, включая двусторонний звук через TURN, системную аудиосессию и продолжение разговора в фоне. Готовность SDK или passing unit tests не обозначает готовности всего Gate 1.

## Следующий этап: интеграция основного приложения

По поручению пользователя ручные прогоны Audio Test завершены; следующий объём подготовлен в [контракте основного приложения](native-app.md). Контракт интеграции отдельно подтверждён пользователем; переход к реализации не означает успешного выполнения пропущенной физической матрицы.

Управление системной громкостью harness описано в отдельном [принятом контракте](call-volume.md).

Выбор доступного аудиоустройства harness описан в [принятом контракте маршрутизации UI](audio-devices.md).

В согласованном текущем объёме основное приложение использует существующий [bridge v1](../web/README.md#внутренний-формат-gchat-bridge-v1): `placeCall`, безопасные события и нативный UI ответа/отклонения/завершения/mute. Полный набор команд управления из Web в этот объём не входит; его последующее добавление требует отдельного согласования.

Интеграция должна сохранить нативное владение звонком и текущую модель cycleId, восстановление полного снимка после foreground/WebView restart и независимость аудио от JavaScript. Продуктовый переход из Web Push должен восстанавливать native-сессию и актуальный звонок, не принимать его автоматически. Эти требования не означают, что такой код уже существует.

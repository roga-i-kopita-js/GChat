# Бизнес-требования к бэк-офису GChat

Статус: согласовано направление — раздел администрирования в веб-клиенте, две роли, возможности существующего контракта CLI и административный API для веба. CLI оставляется только для создания администраторов. Документ описывает требования к будущей реализации; основные вопросы согласованы, статус технического проекта указан по ссылке ниже. Реализация серверной части описана в [Backoffice](../backend/modules/backoffice.md); веб-интерфейс реализован в [веб-клиенте](../web/README.md#администрирование).

Технический проект backend — [Backoffice](../backend/modules/backoffice.md) (accepted; серверная реализация описана в контракте).

Общие требования продукта — в [requirements.md](requirements.md). Визуальная основа — [интерактивный макет](../design/backoffice.html) и [превью](../design/backoffice-preview.png). Макет показывает основные сценарии, но не заменяет требования и не определяет правила управления ролями.

## Цель и границы

Администратор управляет аккаунтами GChat через браузер: создаёт доступ для пользователей, меняет пароли, отключает и повторно включает аккаунты. Для повседневных административных действий не требуется прямой доступ к базе данных или серверной консоли.

Бэк-офис — раздел «Администрирование» существующего веб-клиента с общей авторизацией и аккаунтами GChat. Его функции доступны через административный API. CLI backend только создаёт новые аккаунты администраторов, включая первого. Остальные операции CLI не предоставляет. Администратор может отключить другого администратора через бэк-офис. При потере административного доступа оператор может создать нового администратора через CLI. Параметры команды определены в Auth: обязательные имя и логин, скрытый ввод пароля и необязательная группа. Доступ к собеседникам определяется [Groups](../backend/modules/groups.md#выдача-клиенту--реализовано), исходящие звонки — [DirectCalls](../backend/modules/direct-calls/README.md#доступ-администратора--согласовано).

Администрирование в iOS-клиенте в этот объём не входит. В разделе «Звонки» администратор видит все группы и активных пользователей и может инициировать звонок без общей группы по указанным контрактам. Расширение доступа реализовано.

## Роли и доступ

| ID | Требование | Ожидаемое поведение |
| ----- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BO-01 | Две роли | Аккаунт имеет одну из двух ролей: пользователь или администратор. Через БО создаётся пользователь, через CLI — администратор; роль существующего аккаунта не меняется. Администратор сохраняет обычные пользовательские возможности. |
| BO-02 | Раздел администрирования | После входа администратору доступен раздел «Администрирование». Обычный пользователь этого раздела не видит. |
| BO-03 | Проверка прав | Backend разрешает административное чтение и изменение только авторизованному администратору с действующим доступом. Прямой переход по адресу раздела или самостоятельный запрос к API не обходят проверку прав. |
| BO-04 | Роль в сессии | Роль включается в access JWT при входе и обновлении токенов. Клиент использует её для отображения доступных разделов; backend проверяет право на операцию по актуальной роли аккаунта из БД при каждом запросе, а не по роли в JWT. Значение роли не выбирается клиентом. Владелец видит роль в собственном JWT, администратор — в БО; в обычные списки собеседников роль не включается. |

## Возможности администратора

### Список и карточка аккаунта

| ID | Требование | Ожидаемое поведение |
| ----- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BO-05 | Обзор аккаунтов | Администратор видит аккаунты независимо от собственного членства в группах, включая отключённые. Список содержит имя, логин, роль, группы и состояние доступа. |
| BO-06 | Поиск и фильтрация | Доступны поиск по части имени или логина без учёта регистра (например, `андр` находит `Андрей`) и фильтр: все, активные, отключённые. Поиск и фильтрация выполняются backend. Список загружается страницами по 25 аккаунтов по умолчанию с общим числом совпадений; следующие страницы запрашиваются отдельно. Аккаунты сортируются по имени по возрастанию, при одинаковом имени — по ID. Группы сортируются по названию по возрастанию, при совпадении — по ID. Отсутствие совпадений отображается как пустой результат. |
| BO-07 | Карточка аккаунта | Администратор открывает аккаунт из списка, видит его данные и доступные действия. Для выбора аккаунта не требуется вручную вводить UUID. Пароли, хеши и токены действующих сессий не отображаются. |

API возвращает статус аккаунта вместе с временем отключения. Статус не хранится отдельно: backend вычисляет его как `active` при отсутствии времени отключения (`disabled_at = null`) и `disabled` при его наличии. Это правило едино для списка, карточки и результата изменения аккаунта.

Состояние «Активен» означает, что аккаунт включён и может входить в GChat. Оно не означает, что пользователь сейчас онлайн или доступен для звонка. Пользователь может состоять в нескольких группах; единственная группа в демонстрационных строках макета не вводит такого ограничения. Счётчики в макете — сводка аккаунтов, а не статистика присутствия или звонков.

### Операции с аккаунтами

Правила создания и изменения аккаунтов определены в [Auth](../backend/modules/auth.md#cli); CLI ограничен созданием администраторов. Правила валидации данных и безопасного изменения аккаунта принадлежат Auth, нормализации групп и членства — [Groups](../backend/modules/groups.md#создание-через-cli--реализовано).

| ID | Операция | Ожидаемый результат |
| ----- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BO-08 | Создать аккаунт | Администратор задаёт имя и группу. Логин по умолчанию генерируется backend, пароль — браузером; допускаются явно заданный логин и скрытый ввод пароля по правилам Auth. После успеха администратор получает данные для передачи пользователю. Самостоятельной регистрации нет. |
| BO-09 | Назначить группу при создании | При вводе названия форма показывает подсказки существующих групп. Пользователь включается в группу с указанным названием. Если группы нет, форма предупреждает о её создании вместе с аккаунтом; backend создаёт её по правилам Groups. Получение подсказок само по себе группу не создаёт. |
| BO-10 | Сменить пароль | Администратор может сменить пароль обычному пользователю, другому администратору или себе. Пароль заменяется, все сессии аккаунта отзываются. Новый вход требует нового пароля. Отключённый до операции аккаунт остаётся отключённым. |
| BO-11 | Отключить аккаунт | Вход и использование существующих сессий запрещаются. Аккаунт, логин и членство в группах сохраняются. Администратор может отключить другого администратора, но не собственный аккаунт; backend запрещает самоотключение, включая прямой запрос к API. Повторное отключение уже отключённого аккаунта успешно, сохраняет исходное время отключения и удаляет оставшиеся сессии. |
| BO-12 | Включить аккаунт | Администратор может включить обычного пользователя или другого отключённого администратора. Пользователь снова может войти с текущим паролем; роль и членство сохраняются. Старые сессии не восстанавливаются. Если необходимый отзыв старых сессий не подтверждён, аккаунт остаётся отключённым согласно Auth. Повторное включение уже активного аккаунта успешно и не завершает его новые сессии. |

Логин и новый пароль показываются после подтверждённого успешного создания или смены пароля. Браузер генерирует пароль криптографически стойким генератором либо принимает ручной ввод и отправляет готовое значение в backend. Пароль обязателен в запросе; backend сохраняет только хеш и не возвращает пароль в ответе. Для окна результата браузер использует отправленное значение, сохранённое только в памяти. Новый пароль доступен однократно в окне результата, его можно скопировать для передачи пользователю. После закрытия окна браузер очищает сохранённое значение; повторно просмотреть пароль нельзя. Существующий пароль не восстанавливается и не раскрывается. Пароли и токены не попадают в логи и диагностику.

Макет показывает автоматическую генерацию пароля; согласованная возможность задать пароль явно потребует дополнения формы при детализации дизайна.

### Подтверждения и результаты

| ID | Требование | Ожидаемое поведение |
| ----- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| BO-13 | Подтверждение изменений доступа | Перед сменой пароля, отключением или включением показаны выбранный аккаунт и последствия. Отмена закрывает подтверждение без выполнения операции. |
| BO-14 | Понятный результат | После операции интерфейс показывает подтверждённый успех или ошибку. При успехе API возвращает `{user}` с данными аккаунта после операции, без пароля; интерфейс обновляет карточку по этим данным. Список и карточка отражают фактическое состояние. При потере ответа нельзя показывать подтверждённый отказ или успех без основания: результат обозначается как неизвестный и требует проверки состояния. |
| BO-15 | Границы веба и CLI | Перечисленные операции с обычными аккаунтами предоставляются через административный API бэк-офиса. CLI только создаёт администраторов по правилам Auth. Отключение другого администратора доступно через бэк-офис; команды управления существующими аккаунтами в CLI отсутствуют. |

Загрузка, отправка операции, пустой список, отсутствие совпадений, отказ в доступе и недоступность сервера должны различаться в интерфейсе. Во время отправки повторное нажатие не создаёт дополнительную операцию. Неизвестный результат изменяющей операции не является основанием для её автоматического повтора.

Согласно согласованным [правилам Auth](../backend/modules/auth.md#последовательности-административных-операций), сессии и результаты ротации переносятся в PostgreSQL: изменение доступа и отзыв сессий выполняются одной транзакцией. Подтверждённый откат не оставляет изменений, потеря подтверждения COMMIT может оставить результат неизвестным. Интерфейс не сообщает подтверждённый успех или отказ без основания. Устойчивый журнал и автоматическое восстановление не требуются. Текущее состояние серверной реализации указано в техническом контракте Backoffice.

## Основные сценарии

### Выдать доступ новому пользователю

1. Администратор входит в GChat и открывает «Администрирование».
2. Выбирает «Создать аккаунт», указывает имя и группу, при необходимости задаёт логин и пароль.
3. При ошибке данных интерфейс объясняет, что исправить; успех не показывается до подтверждения результата.
4. После успешного создания администратор получает данные входа и передаёт их пользователю.
5. Пользователь входит в обычный клиент и получает доступ к собеседникам по правилам групп.

### Восстановить доступ при потере пароля

1. Администратор находит нужный аккаунт и открывает карточку.
2. Выбирает смену пароля и подтверждает завершение всех сессий.
3. После успеха получает новые данные входа для передачи пользователю.
4. Если аккаунт ранее был отключён, включение выполняется отдельным действием.

### Временно закрыть и вернуть доступ

1. Администратор выбирает аккаунт и подтверждает отключение.
2. Аккаунт теряет доступ, но остаётся в списке с сохранёнными данными и группами.
3. Позже администратор подтверждает включение.
4. После успешного включения пользователь входит заново; старые сессии не возобновляются.

## Вне текущего объёма

- Удаление аккаунтов и освобождение логинов.
- Изменение логина и отображаемого имени существующего аккаунта.
- Отдельное управление группами: создание вне операции создания пользователя, переименование, удаление, изменение состава существующих групп.
- Самостоятельная регистрация, самостоятельное восстановление пароля и автоматическая рассылка данных входа.
- Дополнительные роли, индивидуальные разрешения и разграничение администраторов по группам.
- Управление звонками других пользователей, статистика звонков и просмотр их содержимого.
- Журнал административных действий, автоматическое восстановление прерванных операций и массовые операции.

Создание администраторов делегировано CLI; отключение другого администратора доступно через бэк-офис. Веб-операции назначения и смены ролей в текущий объём не входят.

## Критерии приёмки

Это условия будущей приёмки, а не отчёт о выполненной реализации.

- Администратор после обычного входа открывает раздел; пользователь не видит раздел и не получает административные данные или возможности через прямой запрос к API.
- Администратор видит активные и отключённые аккаунты вне собственных групп, находит их по имени/логину и фильтрует по состоянию.
- Карточка показывает роль, состояние и все группы аккаунта; существующий пароль и сессионные секреты недоступны.
- Создание с существующей группой включает пользователя в неё; создание с новым названием создаёт группу по правилам Groups. Невалидные данные и занятый логин дают понятный отказ.
- После успешного создания новые данные можно скопировать. После закрытия окна пароль повторно не раскрывается.
- Подтверждённая смена пароля отзывает все сессии; старый пароль больше не подходит; ранее отключённый аккаунт не включается автоматически.
- Отключённый аккаунт не может войти или использовать старые сессии. Включение разрешает новый вход без восстановления старых сессий.
- При встречных одновременных отключениях администраторов побеждает первая успешно выполненная операция; вторая отклоняется после повторной проверки доступа исполнителя.
- Попытка отключить собственный аккаунт отклоняется backend без изменения аккаунта и сессий, в том числе при прямом запросе к API.
- Отмена подтверждения не изменяет аккаунт. Потеря ответа или частичный сбой не отображаются как подтверждённый успех.
- Раздел пригоден для настольного и узкого мобильного экрана и доступен с клавиатуры.
- CLI ограничен созданием администраторов; повседневные операции с обычными пользователями доступны через бэк-офис.

## Открытые вопросы

Открытых продуктовых вопросов в текущем объёме нет. Роли, доступ, первый администратор, собственный аккаунт и встречные отключения определены в требованиях выше. Назначение роли существующему аккаунту, перенос production-данных и расширение CLI в объём не входят.

Технические правила находятся в [Backoffice](../backend/modules/backoffice.md), Auth и Groups. Состояние серверной реализации указано в техническом контракте; веб-интерфейс пока отсутствует, макет должен быть приведён в соответствие с согласованными правилами при работе над веб-интерфейсом.

# Диалоги: требования и модель безопасности

Документ расширяет [требования продукта](requirements.md) чатами 1х1. Серверный контракт — [DialogsModule](../backend/modules/dialogs/README.md), запуск клиента — [frontend bootstrap](../web/bootstrap.md), экраны и поведение — [диалоги Web](../web/dialogs.md). Согласовано серверное шифрование вместо E2EE: backend может расшифровать историю и выдаёт её через sync после проверки доступа. Это заменяет предыдущую модель приватных ключей на устройствах. Backend-контракт согласован (accepted), серверный модуль реализован; клиентский проект остаётся отдельным этапом. Этот продуктовый документ остаётся draft из-за незавершённого клиентского проекта и визуальной приёмки.

## Согласованные границы

- Только два участника, один постоянный диалог на неупорядоченную пару аккаунтов, независимо от групп и устройств. Повторное/конкурентное создание открывает тот же диалог.
- Специальная кнопка у контакта открывает диалог и не начинает звонок.
- Раздел «Диалоги» в нижнем меню объединяет серверные диалоги и локально сохранённые переписки без дубликатов.
- Текст и базовый готовый набор стикеров с открытой лицензией. Нет загрузки файлов, голосовых сообщений, реакций или отдельного emoji picker. Обычные Unicode emoji в тексте разрешены и учитываются по code points; сервер не нормализует текст.
- Весь UI — Web. Согласовано: WS передаёт сигналы о новых сообщениях и прочтении, диалог и история запрашиваются, а прочтение подтверждается через REST. В native авторизация и WSS остаются за существующим bridge; REST использует общий HTTP SDK/Auth-адаптер. Второе WSS-соединение и browser call engine в native не создаются.
- Визуальный эталон — Telegram для iOS, светлая тема; название и знак остаются GChat.
- Сервер хранит диалоги и зашифрованную историю бессрочно. TTL, автоматического удаления и пользовательского удаления в текущем объёме нет. Потеря доступа, отключение аккаунта и смена устройства не удаляют историю; согласованная политика отдельных резервных копий описана в серверном контракте.
- Сервер принимает содержимое по защищённому HTTPS REST API, шифрует для БД и расшифровывает при разрешённой выдаче. Клиентские ключи истории, публикация публичных ключей и их обмен не нужны.
- Клиент синхронизирует сообщения с сервером и хранит локальную позицию. Новое устройство после авторизации получает доступную историю; потеря локального кеша не уничтожает серверную переписку.
- Отправка не зависит от первого входа получателя. После первого входа он читает историю даже с отправителем офлайн. Согласованы системные push с текстом сообщения в body, для стикера — «Стикер», с учётом разрешений и возможностей платформы. Длинный текст может сокращаться; системное push до первой регистрации устройства не гарантируется. Правила — в [серверном контракте](../backend/modules/dialogs/README.md#уведомления).
- Коды восстановления, backup клиентских ключей, подтверждение устройств и cross-signing в объём не входят. Серверные ключи шифрования — отдельные инфраструктурные секреты, их хранение и резервирование определяются в серверном контракте.

## Доступ к диалогу и истории

Auth владеет аккаунтами/сессиями, Devices — привязкой устройства, Groups — членством. Правило инициатора-администратора следует [DirectCalls](../backend/modules/direct-calls/README.md#доступ-администратора--согласовано).

| Операция                                        | Правило                                                                                            |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Создание/отправка обычным пользователем         | Действующие сессия/устройство, оба аккаунта активны, есть общая группа                             |
| Создание/отправка администратором               | Те же проверки, общая группа не обязательна                                                        |
| Ответ обычного пользователя администратору      | Требуется общая группа                                                                             |
| Чтение истории с сервера                        | Активный участник, действующие сессия/устройство; общая группа либо один участник — активный admin |
| Утрата последней общей группы                   | Обычный диалог нельзя читать/продолжать с сервера; исключение активного администратора сохраняется |
| Другой пользователь, включая постороннего admin | Переписка недоступна                                                                               |
| Отключённый actor или отозванная сессия         | История/отправка недоступны, в том числе через старый сокет                                        |

Каждая операция проверяет актуальные права. Наличие диалога, знание ID или роль администратора вне диалога не заменяют участие и серверное разрешение. Согласовано: активный участник может читать прежнюю историю с отключённым собеседником при сохранении остальных условий доступа; отправлять ему новые сообщения нельзя. Отключённый аккаунт не получает доступ и не даёт исключения активного администратора. Точная проверка описана в [серверном контракте](../backend/modules/dialogs/README.md#доступ).

Permissions конкретного диалога для UI возвращаются ресурсным GET /dialogs/:dialog_id/permissions в DialogsModule, с объектом dialogs в ответе, а не полями DTO диалога. Общие permissions в Auth не получают dialog_id и проектируются отдельно. Контекстный расчёт и повторная проверка на каждой операции описаны в [серверном проекте](../backend/modules/dialogs/README.md#permissions); получение permissions не резервирует право отправки или чтения.

Согласован вариант В: недоступный для чтения диалог остаётся в списке с актуальными метаданными активности, включая время последнего сообщения. Эти сведения доступны активному участнику и на новом зарегистрированном устройстве. Они не открывают содержимое при запрете чтения истории, но позволяют наблюдать активность диалога.

Согласована сортировка по последнему сохранённому сервером сообщению, для пустого диалога — по созданию. Открытие, черновик, повторная отправка уже сохранённого сообщения и reconnect не поднимают строку. Точные правила — в [серверном контракте](../backend/modules/dialogs/README.md#операции-rest).

Утрата права доступа не удаляет скачанные сообщения с устройства. Восстановление группы возвращает серверное разрешение по текущим правилам; локальный ключ истории для чтения не нужен.

## Серверное шифрование и безопасность

Backend получает содержимое сообщения в памяти, шифрует его до записи в PostgreSQL и расшифровывает только в рамках разрешённой операции. Участники получают сообщения через HTTPS REST API; по общему WSS передаются серверные сигналы о новых сообщениях и изменении прочтения без содержимого сообщений. В БД находятся шифротекст и метаданные: участники, устройства, время, объём и активность. Согласован AES-256-GCM; размеры параметров, поля хранения и управление серверными ключами закреплены в [серверном контракте](../backend/modules/dialogs/README.md#серверное-шифрование-и-ключи), включая точный формат AAD, бюджет попыток и учёт ключей.

Администратор приложения вне диалога не получает API-доступа к переписке. Оператор с одним dump БД без ключей видит шифротекст и метаданные; оператор с доступом к backend и ключевому материалу технически может читать содержимое. Защиты E2EE от оператора инфраструктуры нет — это согласованная граница.

Вход под аккаунтом участника даёт доступ к разрешённой этому аккаунту истории. Поэтому после сброса пароля обладатель новых credentials, включая администратора, может технически войти и прочитать такую историю. Прежнее обещание, что сброс пароля не даёт ключей старой переписки, больше не действует; отдельного клиентского секрета истории нет. Это не добавляет административный маршрут чтения и не обходит актуальные группы/роли/состояние аккаунта.

Серверные ключи хранятся отдельно от сообщений, не передаются клиентам, не переиспользуют JWT/TURN secrets и не попадают в репозиторий или диагностику. Для восстановления БД нужны отдельно сохранённые подходящие серверные ключи. Потеря ключей — инфраструктурная авария, не клиентский сценарий recovery.

Текст сообщения включается в системное уведомление и может быть виден на экране блокировки по настройкам устройства. Для обычного APNs текст передаётся службе Apple; особенности Web Push и повторная проверка доступа описаны в серверном контракте. Это согласованная выдача содержимого и не разрешает сохранять его в логах.

Локальные сообщения и позиции sync изолируются по серверу, аккаунту и устройству. Смена аккаунта не подхватывает чужую историю; поздние события bridge не меняют новую сессию. Подготовка и выбор платформенного хранилища выполняются через frontend bootstrap. Защита от XSS, безопасный вывод текста и отсутствие содержимого в логах обязательны.

## Хранение и синхронизация

PostgreSQL хранит диалоги и упорядоченные зашифрованные сообщения. Клиент через REST sync получает новые сообщения после локальной позиции либо предыдущие страницы истории. После сохранения страницы обновляет локальную позицию; после reconnect продолжает с неё. Повторно полученное объединяется по ID.

Успешная отправка означает серверное сохранение. Повтор определяется только клиентским ID в пределах диалога и отправителя: после потери ответа тот же ID возвращает исходное сообщение без создания дубликата и сравнения содержимого. Разные ID позволяют отправить одинаковый текст отдельными сообщениями. Точное правило — в [серверном контракте](../backend/modules/dialogs/README.md#создание-и-идемпотентность). Это не означает доставки другому устройству или прочтения человеком. Транспортные ACK и гарантированное воспроизведение WS-событий не входят в минимальную синхронизацию. Согласованы галочки исходящих сообщений: одна — «Отправлено» после сохранения сервером, две — «Прочитано» по подтверждению клиента. Клиент сам определяет момент прочтения и передаёт позицию через REST; backend проверяет позицию и права. Отдельного статуса доставки на устройство нет; загрузка истории, push и WS-сигнал не означают прочтение. Согласована общая для устройств аккаунта монотонная позиция прочтения на участника; изменение передаётся WS-событием, статус возвращается при получении сообщений. Технический контракт подтверждений — в [DialogsModule](../backend/modules/dialogs/README.md#статусы-сообщений). WS-сигнал запускает REST-запрос; после reconnect REST sync выполняется и без события. Системные push с содержимым остаются отдельным каналом. Согласована одна best-effort попытка после commit без устойчивых заданий, очереди и автоматических повторов; риск потери уведомления принят. Ошибка push не отменяет сохранение сообщения, получатель загружает его через REST при следующей синхронизации.

Сервер не хранит открытые дубли текста/ID стикера или plaintext preview в БД; list/get не выдают содержимое недоступного диалога. Полные сообщения, серверные ключи, токены и payload не попадают в диагностику. Backup БД содержит шифротекст/метаданные; backup ключевого материала хранится отдельно. Бессрочное хранение рабочей истории согласовано; сроки отдельных backup-снимков остаются эксплуатационным вопросом.

## Интерфейс и библиотека

Для виртуализации ленты согласована `virtua`; собственные компоненты GChat задают внешний вид Telegram iOS. Зависимости проекта пока не изменены. Это виртуализация ленты, не готовый UI чата, backend или криптопротокол.

У библиотеки [независимое ядро на TypeScript](https://github.com/inokawa/virtua/tree/main/src/core) и отдельные адаптеры. Для текущего клиента используется поддерживаемый React-адаптер из `virtua`; пакет публикует JS и декларации типов. Публичный `virtua/unstable_core` помечен нестабильным; использовать его вместо поддерживаемого адаптера в этом проекте не предлагается. Согласованный выбор библиотеки сохраняет обязательную проверку плавности на iPhone, описанную ниже.

Сравнение размера выполнено 2026-11-07 по опубликованным npm-пакетам. Все варианты собраны одинаково: esbuild 0.28.2, ESM/browser, target es2022, minify и tree shaking; React, React DOM и их subpath-импорты исключены как уже существующий runtime приложения. Измеряется сборка реэкспорта компонентов для динамической ленты, gzip level 9; собственные компоненты/адаптер GChat в измерение не входят. Это измерение размера, не FPS или потребления памяти.

| Пакет и измеренная версия         | Экспорты                      | Minified, байт | Gzip, байт |
| --------------------------------- | ----------------------------- | -------------- | ---------- |
| `virtua@0.54.2`                   | `Virtualizer`                 | 7788           | 4142       |
| `virtua@0.54.2`                   | `VList`                       | 8234           | 4230       |
| `react-window@2.5.3`              | `List`, `useDynamicRowHeight` | 18868          | 6886       |
| `@tanstack/react-virtual@3.14.26` | `useVirtualizer`              | 34705          | 10481      |
| `react-virtuoso@4.18.20`          | `Virtuoso`                    | 61633          | 20627      |

Версии получены из манифестов опубликованных пакетов; у TanStack включена его runtime-зависимость `@tanstack/virtual-core@3.19.11`. У остальных измеренных пакетов дополнительных runtime-зависимостей нет; React/React DOM — peer dependencies. Все четыре имеют MIT и диапазоны peer dependencies, включающие используемый React 19. Измеренные версии не являются добавленными или зафиксированными зависимостями GChat.

`virtua` — самая маленькая из четырёх в этом измерении. В [документации](https://github.com/inokawa/virtua) описаны автоматическое измерение высоты, обратная прокрутка и оптимизация рендеринга; [пример чата](https://github.com/inokawa/virtua/blob/main/stories/react/advanced/Chat.stories.tsx) показывает подгрузку сверху и удержание конца ленты. Это обосновывает выбор для GChat, но не доказывает, что она быстрее всех на наших сообщениях. Для стикеров нужно резервировать геометрию до загрузки изображения, чтобы изменение размера не сдвигало ленту.

Альтернативы: [TanStack Virtual](https://tanstack.com/virtual/latest/docs/chat) предлагает end anchoring и условное следование новым сообщениям; [react-window](https://github.com/bvaughn/react-window) поддерживает динамическую высоту, но требует отдельной оценки поведения чата; [react-virtuoso](https://github.com/petyosi/react-virtuoso) имеет готовые механизмы для изменяемой ленты при большем размере в этом измерении. Коммерческий `@virtuoso.dev/message-list` не входит в сравнение.

Ограничение для iOS: автор virtua отмечает особенности reverse scroll в Safari во время непрерывного жеста; [issue 473](https://github.com/inokawa/virtua/issues/473) описывает отложенную корректировку до отпускания прокрутки. Это не результат проверки текущего GChat/WKWebView. До окончательной приёмки выбранной реализации нужно проверить на целевом iPhone длинную ленту с переменной высотой, prepend, инерционную прокрутку, появление клавиатуры и новые сообщения при чтении старых. Сравнительные замеры FPS, длинных кадров и памяти на GChat ещё не выполнялись; абсолютный лидер по скорости не установлен.

Согласован начальный набор из пяти Animal Pals с фиксированными IDs, локальным распространением и CC0 1.0. Единственный источник состава, IDs, правил подготовки ресурсов и валидации — [каталог в контракте Dialogs](../backend/modules/dialogs/README.md#каталог-стикеров-и-unicode). Файлы, provenance, контрольные суммы и лицензия подготовлены в `packages/dialog-assets/`; клиентская визуальная приёмка ещё не выполнена. Пользовательская загрузка и удалённый каталог не входят в объём.

Для строгой визуальной приёмки нужны зафиксированные экраны Telegram iOS и согласованный макет GChat: список диалогов, пустое состояние, диалог, ввод, выбор стикера, загрузка истории, запрет доступа, ошибка синхронизации и запрет доступа. В спецификации фиксируются размеры, цвета, типографика, пузырьки, интервалы, время и состояния отправки. Применяются существующие [контрольные размеры Web](../design/README.md#мобильный-приоритет-веб-интерфейса), safe area и проверка экранной клавиатуры. Само словесное требование «как Telegram» не заменяет эти референсы.

## Критерии приёмки

Это требования к будущей реализации, не отчёт о выполненных проверках.

- Кнопка у контакта открывает единственный диалог пары; повторное создание не дублирует его и не начинает звонок.
- Раздел в нижнем меню показывает серверные/локальные диалоги без дублей; сортировка соответствует согласованному правилу.
- Сервер проверяет участие, роль, группу и сессию на каждой операции. Посторонний admin, чужой ID и отозванная сессия не открывают историю.
- При потере права чтения сообщения с сервера недоступны, разрешённые актуальные метаданные остаются видимыми.
- Отправка и sync работают после обрыва/перезапуска без дубликатов; локальная позиция сохраняется вместе с полученными записями.
- Сообщение отправляется до первого входа получателя и читается им после входа с отправителем офлайн. Новое устройство/переустановка не требуют ключей прежнего устройства.
- В БД нет открытых сообщений/ключей, а в логах и диагностике — содержимого и секретов. Серверные ключи не передаются клиентам. Границы технического доступа операторов и входа после сброса пароля соответствуют выбранному серверному шифрованию.
- В native Auth/WSS используют существующий bridge, REST — общий SDK с Auth-обёрткой. WS не передаёт текст/объект сообщения, потерянные сигналы восстанавливаются REST sync; смена сервера/аккаунта не смешивает данные.
- UI соответствует согласованным референсам Telegram iOS, работает на узком экране с клавиатурой и safe area.

## Открытые решения перед реализацией

Backend-контракт [DialogsModule](../backend/modules/dialogs/README.md) принят и готов к реализации, серверных открытых решений в его объёме нет. Это не означает наличия кода или завершённой эксплуатационной подготовки. Удаление/TTL рабочей истории не требуются; чтение при отключённом собеседнике согласовано.

Для Web остаются точные интерфейсы локального кеша/позиций sync и общего bootstrap/bridge, детали правила видимости для прочтения и визуальные референсы. Платформенные хранилища, сверка видимого раздела раз в 30 секунд, черновики, повторы отправок, компоновка экранов и выбор virtua согласованы в профильных документах. Выдача имени собеседника согласована как ещё не реализованное расширение backend. Физическая очистка локального кеша и позиций при обычном logout согласована пользователем; механизм и барьер очистки ещё проектируются в bootstrap. Файлы стикеров подготовлены, их клиентская визуальная приёмка остаётся открытой. Оставшиеся решения и критерии приёмки ведутся в [клиентском проекте](../web/dialogs.md#решения-для-согласования). Клиентская криптография, recovery, подтверждение устройств и cross-signing не требуются.

Этот продуктовый документ и frontend bootstrap остаются draft до завершения клиентских границ. Реализация backend разрешена по принятому профильному контракту; реализация незавершённых клиентских частей требует готовности их собственных документов.

# Системные E2E GChat

`@gchat/e2e` — общий модуль сквозного тестирования системы, расположенный над приложениями в `tests/e2e/`. Он владеет системными сценариями, тестовыми участниками, запуском приложений, общим стендом, подготовкой данных и артефактами. Backend, веб-клиент и будущие нативные клиенты выступают участниками проверяемой системы.

Цель — проверять пользовательские цепочки и взаимодействие приложений через реальные HTTP/WS и медиатранспорт. Звонки — первый покрытый функциональный блок; пакет не ограничен ими. Добавление других сценариев не требует нового E2E-модуля в каждом приложении. Unit- и модульные интеграционные тесты остаются в своих приложениях.

Источники требуемого поведения: [требования продукта](../../docs/product/requirements.md) и профильные контракты, для текущих звонков — [DirectCalls](../../docs/backend/modules/direct-calls/README.md), [Signaling](../../docs/backend/modules/signaling.md), [Auth](../../docs/backend/modules/auth.md) и [Devices](../../docs/backend/modules/devices.md).

## Наборы и границы

Один Playwright-конфиг управляет двумя реализованными projects:

| Project    | Участники                                                                               | Назначение                                                                                                                       |
| ---------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `protocol` | Эталонные браузерные участники + backend + PostgreSQL/Redis + coturn                    | Жизненный цикл и согласованность звонка, конкуренция, дедлайны, восстановление и декодируемое аудио независимо от реализации UI. |
| `web`      | Настоящий веб-клиент в независимых браузерных контекстах + тот же backend и зависимости | Пользовательский путь через интерфейс: вход, контакты, звонок, микрофон, вкладки, перезагрузка и завершение.                     |

Оба набора находятся в общем модуле, запускаются одной командой и используют один тестовый контур. Они дополняют друг друга: protocol-набор не доказывает корректность production-клиента, UI-набор не заменяет проверку серверных гонок и декодирования аудио.

iOS пока не подключён к автоматизации. Сквозные веб ↔ iOS и iOS ↔ iOS сценарии должны добавляться сюда вместе с готовым нативным клиентом и инструментами запуска. Наличие общего модуля не означает уже реализованного покрытия всех приложений.

## Текущее покрытие звонков

В `protocol` два независимых участника входят через реальный HTTP API, регистрируют устройства через WS и согласуют нативные RTCPeerConnection через backend. Аудио идёт через настоящий coturn. React-приложение, его signaling-клиент и модель состояния здесь не импортируются. Backend, WebSocket, PeerConnection, часы и фоновые обработчики не подменяются.

Источник каждого участника — Web Audio с отдельным тоном 440/880 Гц. На принимающей стороне анализируется декодированный PCM: частота должна соответствовать собеседнику, энергия превышать порог. Выключение источника должно дать тишину у собеседника, включение — вернуть тон. Дополнительно проверяются оба relay-кандидата выбранной пары и рост RTP-счётчиков в обе стороны.

| Сценарий                           | Что должно выполняться                                                                                                                                                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Полный разговор и повторный звонок | `ringing → connecting → active → ended`; одного `call.connected` недостаточно; оба подтверждения относятся к одной попытке; повторный `accept` не меняет состояние и сроки; после завершения те же пользователи могут позвонить снова. |
| Аудио и освобождение ресурсов      | Тоны декодируются в обе стороны; выключение источника даёт тишину; после завершения закрыты PeerConnection, дорожки и AudioContext тестовых участников, освобождены участники PostgreSQL и busy-ключи Redis.                           |
| Отмена и отклонение                | Оба участника получают одинаковый конечный DTO с правильной причиной; `call.current` возвращает `null`.                                                                                                                                |
| Встречные вызовы и занятость       | Конкурентные создания оставляют один звонок; проигравший получает `CALLER_BUSY`, третий пользователь — `RECIPIENT_BUSY`.                                                                                                               |
| Конкурентное принятие              | Из двух сессий получателя выбирается одна; другая получает `FORBIDDEN`, не получает ICE-конфигурацию и не может завершить разговор.                                                                                                    |
| Серверные дедлайны                 | Без ответа — `no_answer`; при недоступном TURN — `connection_timeout`, без обхода через P2P. Завершение происходит не раньше серверного срока.                                                                                         |
| Переподключение и восстановление   | Краткий обрыв WS не прекращает аудио; reconnect сохраняет session/device. Новая медиапопытка восстанавливает тот же звонок без сброса `started_at`; старые подтверждение и ICE отклоняются.                                            |
| Неизвестный результат              | Потерянный ответ на реальный `call.create` разрешается через `call.current`, без второго создания. Повтор `call.end` возвращает неизменённый конечный результат.                                                                       |
| Потеря аудио без восстановления    | Истечение окна восстановления даёт `connection_lost` и освобождает участников.                                                                                                                                                         |
| Отзыв сессии                       | Logout выбранной сессии завершает активный звонок с `session_revoked`, закрывает её WS и освобождает медиа тестовых участников.                                                                                                        |

В `web` сценарии проверяют вход, исходящий/входящий вызов, принятие, отмену подтверждения, отклонение, кнопку микрофона, дополнительную вкладку, сохранение сессии и восстановление после перезагрузки. Проверяются relay-маршрут и RTP-счётчики с искусственным микрофоном Chromium; отдельный viewport проверяет узкий экран.

В `tests/web/media.e2e.ts` настоящий веб-клиент звонит эталонному участнику в обеих ролях: инициатора и получателя. Chromium получает сгенерированный `microphone.wav` через штатный `--use-file-for-fake-audio-capture`; файл циклически передаёт амплитудно-модулированные 440/660 Гц. Штатные `getUserMedia`, PeerConnection, обработка микрофона веб-клиентом и backend не заменяются. Собеседник передаёт отдельный тон 880 Гц.

Наблюдатель веб-клиента вызывает исходный `HTMLMediaElement.play()` с тем же результатом и после готовности подключает измеритель к фактическому `srcObject`. Проверяются PCM потока, переданного реальному аудиоэлементу, и его состояния `paused`, `muted`, `volume`. Дополнительный измеритель использует silent sink; он не меняет дорожки, источник или воспроизведение клиента. Это не измерение физического выхода динамиков.

Дополнительные системные критерии:

| Сценарий                           | Проверка                                                                                                                                                                                                                                               |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Веб ↔ эталон, входящий и исходящий | WAV-микрофон веб-клиента декодируется на другой стороне; поток 880 Гц поступает в играющий аудиоэлемент веб-клиента; выбран relay-маршрут.                                                                                                             |
| Настоящий mute/unmute              | После UI-действия у собеседника тишина при продолжающемся RTP и состоянии `active`; входящий звук не выключается; unmute возвращает частоту микрофона. Завершение отсоединяет аудиоэлемент и завершает дорожки.                                        |
| Разговор дольше срока JWT          | Аудио, состояние и версия звонка проверяются с интервалом, рассчитанным из срока JWT (не больше трёх секунд); исходный access token действительно истекает и получает `401 ACCESS_TOKEN_EXPIRED`. После реальной ротации контакты доступны с HTTP 200. |
| Общая сессия вкладок после refresh | Одна успешная операция refresh, неизменные session/device и `started_at`; две дополнительные вкладки используют обновлённую сессию и остаются наблюдателями. У профиля сохраняется один исходный WS без переподключений.                               |

Длительный сценарий ждёт реального `exp` подписанного JWT без подмены часов или ответов Auth. Его собственный timeout — 210 секунд. В E2E-сервере по умолчанию `AUTH_ACCESS_TOKEN_TTL_SECONDS=15`, поэтому реальное истечение проверяется примерно за 15 секунд; настройка рабочего backend по умолчанию остаётся 120 секунд. Наблюдение длительности использует периодические измерения без ожидания восстановления сигнала внутри каждого измерения. Подготовка fixtures генерирует WAV заново; после обновления пакета перед прогоном снова выполните `fixtures`.

Не покрыты реальные микрофоны и слышимость человеком, другие сети, Safari, мобильные ОС, iOS/CallKit/APNs, закрытый браузер, TLS-терминация, перезапуск backend, аварии PostgreSQL/Redis, отключение аккаунта, потерянный ответ refresh и потерянный HTTP-ответ logout. Наличие сценария в документации не является отчётом об успешном прогоне. Проверки ресурсов эталонного участника не заменяют проверку ресурсов конкретного production-клиента.

Тестовый `AudioContext` работает с частотой 48 кГц и `sinkId: { type: "none" }`: граф обрабатывает настоящий звук без зависимости от физического аудиовыхода компьютера. Это штатный [silent output Chromium](https://developer.chrome.com/blog/audiocontext-setsinkid), а не подмена PCM. Проверка явно требует silent sink, чтобы случайный возврат к устройству по умолчанию не прошёл незаметно.

Для удалённого WebRTC-потока сохраняется muted `<audio>` как медиа-рендерер Chromium. `MediaStreamAudioSourceNode` подключается к анализатору только после успешного `audio.play()`. Позднее завершение `play()` после закрытия или замены PeerConnection игнорируется. `MediaElementAudioSourceNode` для этого `srcObject` не используется: в проверенном Chromium он возвращал нули при ненулевой энергии входящего RTP.

Сценарий задержанного рендерера откладывает вызов настоящего `play()` до поступления RTP и затем проверяет реальные декодированные тоны. Источник, PeerConnection и PCM не подменяются. Дополнительно проверяется сохранение аудио после принудительной сборки мусора и выключения/включения источника.

Ранее наблюдался плавающий нулевой PCM; его точная исходная причина не подтверждена детерминированным воспроизведением на прежнем приёмнике. Изменения устраняют зависимость измерителя от физического устройства и упорядочивают запуск рендерера и анализатора. Успех повторов подтверждает проверенные сценарии, но не является доказательством причины исходного сбоя. Проверки relay, энергии и частоты разделены, при сбое сохраняются безопасные аудиометрики. Пороги не снижены, автоматические retries не включены.

## Структура

- `tests/protocol/direct-calls.e2e.ts` — системные проверки протокола звонков.
- `tests/web/direct-calls.e2e.ts` — сквозные пользовательские сценарии через веб-клиент.
- `tests/web/media.e2e.ts` — настоящее веб-аудио, mute/unmute и длительный разговор с ротацией сессии.
- `fixtures/web/actions.ts`, `audio-observer.ts` — UI-действия и наблюдатель фактического входящего аудиопотока.
- `fixtures/protocol/participant.ts` и `participant.html` — независимый участник протокола и его страница.
- `playwright.config.ts` — projects, порядок выполнения, автоматический запуск и остановка приложений.
- `vite.config.ts` — страница эталонных участников на loopback:5174 с отключённым HMR.
- `compose.yml` — отдельные PostgreSQL, Redis и coturn.
- `scripts/fixtures.mjs` — миграции, тестовые пользователи, синтетические ключи и WAV-микрофон.
- `scripts/backend.mjs` — запуск собранного backend с конфигурацией стенда.
- `scripts/reset.mjs` — очистка звонков и их Redis-проекций перед каждым сценарием.
- `scripts/inspect.mjs` — read-only проверка звонков, привязок участников и busy-ключей.

У пакета свои зависимости и команды; версии берутся из `package.json` и workspace lock-файла. Правила Prettier/Oxlint общие с приложениями. Тестовый контур не входит в production-сборки. В веб-пакете нет собственного Playwright-конфига или зависимости от E2E-модуля.

## Запуск

Команды выполняются из корня репозитория с Node/pnpm из `.nvmrc` и `package.json`. Нужен работающий Docker. Стенд рассчитан на Chromium на этом же компьютере. Порты 3300, 5173, 5174, 55439, 56389, 53479 и UDP 55000–55039 должны быть свободны.

```sh
pnpm install
pnpm --filter @gchat/backend build
pnpm --filter @gchat/e2e exec playwright install chromium
pnpm --filter @gchat/e2e stack:up
pnpm --filter @gchat/e2e fixtures
pnpm test:e2e
```

`pnpm test:e2e` запускает все projects из общего пакета. Playwright сам поднимает backend, дожидается `/ready`, запускает Vite веб-приложения на 5173 и страницу участников на 5174, затем останавливает принадлежащие прогону процессы. Заранее запускать эти серверы не требуется; существующие процессы на тех же портах не переиспользуются. PostgreSQL/Redis и coturn управляются отдельными `stack:up` / `stack:down`.

Для выбора набора или сценария:

```sh
pnpm --filter @gchat/e2e test --project protocol
pnpm --filter @gchat/e2e test --project web
pnpm --filter @gchat/e2e test --project protocol --grep 'two complete'
```

Общий конфиг поднимает весь набор серверов даже при выборе одного project. Все сценарии выполняются одним worker последовательно, поскольку используют одну БД. Не запускайте несколько независимых E2E-прогонов одновременно: reset очищает звонки общего стенда.

Конфиг задаёт срок access JWT 15 секунд и короткие тестовые дедлайны: ожидание ответа 7 секунд, соединение 18, восстановление 15. Часы и worker настоящие. Для проверки со штатными сроками передайте значения окружения:

```sh
AUTH_ACCESS_TOKEN_TTL_SECONDS=120 \
DIRECT_CALLS_RINGING_TIMEOUT_SECONDS=60 \
DIRECT_CALLS_CONNECTING_TIMEOUT_SECONDS=30 \
DIRECT_CALLS_RECONNECT_TIMEOUT_SECONDS=30 \
pnpm test:e2e
```

Переменные передаются только процессу E2E-backend. Для другого срока JWT можно запустить, например, `AUTH_ACCESS_TOKEN_TTL_SECONDS=10 pnpm test:e2e`. Веб-клиент рассчитывает запас refresh как четверть срока JWT, но не больше 15 секунд; короткий JWT не вызывает ротацию при каждом HTTP-запросе. Окружение рабочего backend не меняется. Тестовые пользователи: `anna`, `maxim`, `elena`, пароль каждого — `gchat-web-test-password`; общая группа — «Близкие». Повторный запуск fixtures меняет тестовые ключи. Для ручной проверки можно отдельно запустить `pnpm --filter @gchat/e2e backend` и [веб-клиент](../../applications/web/README.md#изолированный-стенд-и-проверки); перед автоматическим прогоном остановите их.

## Изоляция и очистка

Compose-проект сохраняет имя `gchat-web-test`, БД — `gchat_web_test`, Redis-префикс — `gchat:web-test:`. Это выделенный контур; инфраструктура приложений и legacy Mattermost/Jitsi не используются. Скрипты fixtures/reset/inspect имеют фиксированные loopback-адреса и не читают рабочие `DATABASE_URL` или `.env`. Reset очищает звонки с зависимыми строками и их Redis-проекции; пользователи и сессии сохраняются до удаления стенда.

Ключи и настройки генерируются в игнорируемом `tests/e2e/.local/` с правами 0600. APNs-ключ синтетический, VoIP-токены не регистрируются, запросов в Apple нет. Разрешение loopback-реле в coturn предназначено только для этого стенда.

Wire traces отключены у обоих projects: токены, TURN credentials, SDP и ICE-адреса не включаются в диагностику. Результаты, снимки интерфейса и безопасные артефакты всех наборов сохраняются в игнорируемом `tests/e2e/test-results/`.

После прогона удалите только тестовую инфраструктуру и её данные:

```sh
pnpm --filter @gchat/e2e stack:down
```

Сгенерированная конфигурация `.local/` остаётся на диске; после нового создания стенда снова выполните `fixtures`.

## Добавление сценариев

Системные E2E всех приложений размещаются здесь. Добавляйте сценарий в соответствующий project и группируйте файлы по функциональности. Общая подготовка данных и ресурсов принадлежит этому пакету. Приложения не должны импортировать E2E-код.

Новый сценарий должен проверять наблюдаемый результат взаимодействия системы, опираться на принятый контракт, иметь изолированные тестовые данные и освобождать свои ресурсы. Для проверки возможностей конкретного клиента используйте сам клиент; эталонный участник служит проверке общего протокола. При добавлении подсистем обновляйте подготовку/очистку и эту документацию. Новые инструменты для нативных платформ подключаются после согласования подхода; текущий Playwright-набор не объявляется нативным E2E.

Unit- и модульные интеграционные тесты продолжайте хранить рядом с соответствующими приложениями. Они проверяют отдельные компоненты и не заменяют этот системный контур.

## Проверки пакета

```sh
pnpm --filter @gchat/e2e typecheck
pnpm --filter @gchat/e2e lint
pnpm docs:check
```

Для исправления форматирования и линтинга: `pnpm --filter @gchat/e2e lint:fix`. Изменения сценариев и инфраструктуры проверяются общим `pnpm test:e2e` на выделенном стенде.
